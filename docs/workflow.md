## Claude implements; the dev reviews

**Claude implements; the dev reviews.** Contract changed **2026-08-05**, replacing the hand-typed-walkthrough model that ran from project start. Claude edits every file directly — `Classes/`, `Scenes/` and `game.gd` included. The dev is practicing an agentic workflow for a role that requires it; **he will say so explicitly if he ever switches back**, so until those words are said, this is the contract. He is still here to learn: explain the *why*, not just the *what*.

## Plan before touching ANY file

**Plan before touching ANY file — tightened 2026-08-06, no size exception.** The trigger used to be blast radius (feature / invasive change / bugfix); it no longer is. The dev's words, after `Stats.Stat.COH` vs. a bespoke field (#142) got decided and coded before he ever saw the fork stated: *"I'd like to see a plan from you about what code changes you are going to make... before you edit something, no matter how minor."* Every file — `Classes/`, `Scenes/`, `game.gd`, `docs/`, `tests/`, scaffolding, all of it — gets a plan first, him included on things he'd otherwise never be asked about (a `.gitignore` fix made and only narrated afterward, same session, is the shape to avoid). Reading/searching to build the plan needs no announcement — only `Edit`/`Write`/anything that mutates a tracked file does.

## Depth scales with the change

**Depth scales with the change; the plan step itself never gets skipped.** Hitting more than one of — a new capability, more than one valid approach, an architectural choice, more than a couple of files, unclear scope — means **formal Plan Mode** (`EnterPlanMode`/`ExitPlanMode`): explore, write the plan, nothing gets edited until he approves it. That is a lock, not a promise. A genuinely fork-free edit (an obvious typo, a one-liner he already dictated verbatim) still gets stated before it happens — one line, then wait a beat — but doesn't need the formal mode-switch.

## A plan that stops working gets re-planned

**A plan that stops working gets RE-PLANNED, not patched around and narrated after.** Discovering mid-implementation that the approach is wrong, or silently switching to a different one, means STOP before finishing the edit — lay out the revised plan and wait, exactly like the first one. Explaining a pivot in the wrap-up is the failure this replaces, not a lighter version of compliance.

## What a plan must contain

**What a plan must contain** (the full version — a fork-free one-liner just needs the one-line statement of intent above):

- **The question** the change answers, and **what already answers it**, naming what was actually grepped. *Grep the question, not the name* (Law #4).
- **Every caller/reader of anything being changed, counted from the code.** Relaxing a predicate for one caller without checking its other three is exactly how the Group Move hole shipped (2026-08-04).
- **Files touched** and what each change is.
- **How it will be verified** — decided before building, not after.
- **The riskiest assumption**: what would make this plan wrong.

## Review surface = the plan + the diff

**Review surface = the plan + the diff.** A summary of a change is not evidence of the change. Keep the unit of work to **one reviewable diff**; never chain several tasks' worth of edits before he has seen any of them. Commit points are review points.

## Report verification honestly

**Report verification honestly** — what ran, what passed, and what was *not* checked. **The suite is not the gate:** 6 of 7 cases passed against the build that bricked the pause menu (#131), and 955 green cases sat on top of a `clear_board` that had stopped clearing the board (#132). Anything touching UI, input, or ordering needs the game actually launched. **Falsification — reintroducing a bug to prove its regression test goes red — answers whether the TEST has teeth, not whether the fix works;** that second question is his, by playing. So falsify only where the test could plausibly be blind: **ordering/timing**, a **missing wire**, an assertion leaning on a Godot quirk (freed refs, `visible`, orphan counts, queue state), or a test that reaches its precondition by *setting state directly* rather than driving the real path. Skip it when the assertion sits one hop from the change. Run the **one suite file**, never the tree.

## Retired with the old contract

**Retired with the old contract (2026-08-05).** These existed *solely* because a human retyped Claude's output, and that whole failure class is now gone — do not re-derive them from this file's git history: the whole-function code-block law (#128/#132), file+function prose anchoring, one-heading-one-file (#141), and "verify by reading the real file after a walkthrough — transcription drift is the top failure mode." Likewise the standing exceptions that carved narrow write permission out of the old rule (2026-06-12 scaffolding, 2026-07-16 header comments / `.tscn` / comments, 2026-08-05 bug-reporting) are **absorbed, not revoked** — everything they permitted is now simply permitted.

## Still live, unchanged by the switch

**Still live, unchanged by the switch:**

- **Content is disposable; cleanliness is not.** `.tscn` scenes and saved `Scenarios/*.tres` are placeholder — fix them to match the code rather than carrying a legacy-compat branch for their sake.
- **File header comments.** Any `Classes/`/`Scenes/`/`game.gd` file touched that lacks a top-of-file description comment (what the file/class IS and its place in the architecture) gets one added.

## A dirty working tree is a ticket defect at both ends

**A dirty working tree is a ticket defect at BOTH ends (dev rule, 2026-08-26).** His words: *"no issue is acceptable if it causes the workspace to be continuously dirty… and no issue is complete if it can still leave the tree dirty."* Two gates, at opposite ends of a ticket. **Acceptance:** refuse a design whose ordinary operation — running the game, opening the editor, a routine tool pass — produces tracked modifications; say so before building rather than shipping it. **Completion:** green tests and a clean `git status` at commit time are NOT the test; the question is whether anything he normally does re-dirties it afterwards. A permanently-modified file trains him to ignore `git status`, and a real uncommitted change then hides in the noise — it also destroys the staleness tell for whose work a tree is holding. **How:** for any file the project writes back (a `.tres`, a generated artifact, a settings file), ask what the real writer emits when it saves and make the committed bytes BE that — round-trip through that writer and diff, never hand-author a serialized format and reason that it is equivalent. There is already ONE answer to putting uids back after a save that drops them, `DevWidgets.restore_uids` ([#481](https://github.com/Phaazoid/Godoiosis/issues/481)) — it handles the `[gd_resource` header line as well as the `ext_resource` ones; do not write a second. The two cases, and note that in BOTH the code was correct and the only symptom was a `git status` line: **acceptance = [#540](https://github.com/Phaazoid/Godoiosis/issues/540)** — `lookdev_meshlib.tres` embedded the ground atlas as an `Image` sub-resource, and `ImageTexture::set_image()` keeps **no reference** to the Image it is handed, so the parsed sub-resource id was gone the moment the file was read and the next editor save minted a fresh one; fixed by moving the atlas to a PNG on disk, since only an `ext_resource` survives a save. That ticket is also a standing warning about naming a cause you have not measured — the *generator* was the obvious suspect and was measured **innocent** (`gen_lookdev_assets.gd --meshlib` is byte-stable over a clean tree), and the missing `uid=` attributes were a separate, already-closed matter.

**Completion = [#111](https://github.com/Phaazoid/Godoiosis/issues/111)** — `display_name` hand-inserted into `MainAttacks/*.tres` at a position Godot does not use (a `WeaponAttackData` field serializes *before* the inherited `AttackData` ones), so the first editor save handed him a modified `ChainSword.tres` he never edited; fixed in #546, proven by the committed file becoming byte-identical to his editor's own output. Two traps found there: a headless `ResourceSaver.save()` **strips every `uid=`** where the editor preserves them; and **an `@export` whose default is a CALL has no default ANY saver can see**, so every save writes it out — the runtime writer the value, the editor `null` — which is how `WeaponData.mod_spaces` (then `SPACE_CAPACITIES.duplicate()`) pinned every template saved to that day's const. This line first called it a headless quirk; it is not, and [#1185](https://github.com/Phaazoid/Godoiosis/issues/1185) fixed it with a default the parser can FOLD. A collection default is folded, never called for.

**The writer's own ids = [#1343](https://github.com/Phaazoid/Godoiosis/issues/1343)** (2026-10-21). Every `[sub_resource]` id an Update wrote was a fresh draw from a generator seeded by the save path, so the first Update of every committed mission renumbered it, and any edit that added a reference renumbered everything after it. `save_over` now carries the prior file's ids across the save (`DevWidgets.carry_sub_ids`), the same shape as `restore_uids`. The 8 missions were re-saved once through the fixed writer, so an unchanged Update on any of them is a byte no-op. → `docs/sharp-edges.md` → *The writer keeps a file's sub_resource ids*

## Aesthetic tuning values get a knob, not a guess

**Aesthetic tuning values get a knob, not a guess (dev rule, 2026-08-12).** When a shader/lighting/post/animation value is a matter of taste, don't burn rounds picking numbers — expose it and hand it to the dev: *"I can find the values that work, and we can save a lot of time."* **The surface exists as of #212 (2026-08-15): the dev-tools window's Moods tab (`Classes/dev/MoodsTool.gd`)**, so the usual answer is one line in a knob table, not a new panel. **Since #272/#373/#380 there are THREE tabs and the fork is "who may disagree about this value": one board vs another → a Look knob (it joins presets, and since #373 every Look knob does — the table is scene mood entire); nobody, ever → a `GameKnobs` row (board markup, the unit readout, camera handling, world construction, fire — the game constants, entire since #380), written back into the declaration that authors it; one tile vs another → an `ObjectKnobs.FIELDS` row (a TileSet custom-data column), authored on the dev-tools **Tiles** page — which since [#902](https://github.com/Phaazoid/Godoiosis/issues/902) (2026-09-12) also DRAWS the seven world-construction globals those rows fall back to, and the per-KIND burn rules the tile's ground obeys. Three stores, three files, three Saves; what the page buys is finding a value where you would look for it, with each section naming what it moves. **A FIFTH home since [#900](https://github.com/Phaazoid/Godoiosis/issues/900) (2026-09-10), and the first whose owner is CONTENT: one authored ATTACK vs another, for an effect that attack PLAYS** — a shared `EffectLook` the attack names per element, PARTIAL, falling through to the `GameKnobs` row for every value it does not author, with presence as the override so the shape needs no sentinel. What decides eligibility is an effect's RULE vs its LOOK (how far a current arcs is a property of electricity; how bright its bolt is is not), and an effect that OUTLIVES the attack — a burning tile's — belongs to the ground instead. Its rows are a PROJECTION of `GameKnobs.CLASS_KNOBS` and shipping code reads only the look's dictionary, which is what keeps `GameKnobs` dev-only. Putting a game-wide value in Look is the mistake that shape exists to prevent — see `docs/design/presentation-effects.md` → *Where a presentation value is authored*.** **[#394](https://github.com/Phaazoid/Godoiosis/issues/394) (2026-09-01) added a FOURTH answer to that fork, and it is the one to reach for when the honest answer is "anyone may disagree": the player SCALES it.** A `PlayerSettings.Scale` row multiplies what the dev authored, so the knob stays exactly where it is, Save-to-source is untouched, and **no slider is ever inert** — where MOVING the value to `PlayerSettings` (the #422 ruling, correct when the two set it on the same axis) takes the knob away, and a PALETTE (#422's own shape) leaves the knob tuning a set nobody is looking at — **though that last cost is RE-AUTHORING's, not the palette's ([#685](https://github.com/Phaazoid/Godoiosis/issues/685) round 5, 2026-09-04): a value that is SEMANTIC (an element's HUE) can be ADAPTED out of the authored static under every palette and strands no knob, while a value that is a ROLE (near-white text that has to become near-black on a light ground) is an inversion with nothing to derive from and must be authored per palette. Ask which a colour is before paying for a second set of them.** Ask which of the three the value wants: *anyone, by degree* → a Scale row; *anyone, same axis* → it moves; *anyone, between authored sets* → a palette. *(Corrected 2026-10-20: the Weather page (#1260) is a live knob page too. One weather vs another is that weather's `WeatherLook`/`WeatherRules` file.)* A knob there may only name a property that is **authored and READ** — anything the game writes back per frame gives a slider that moves and silently reverts, which is the one failure that makes a tuning panel worthless, and `tests/dev/test_moods_tool.gd` pins it by writing, waiting two frames and reading back. An `@export` or an inspector-reachable resource is still right for a value the dev tunes in the editor rather than in play.

## Probes run on Sonnet 5.5

**Probes run on Sonnet 5.5 (dev rule, 2026-10-22).** His words: *"when sessions send out probes, basically non-full session contexts, to do things like research, etc, they use sonnet 5.5. It is a very robust model, and a lot cheaper, so it'll help us save on tokens while using these swarm tactics."* And on exceptions: *"If sessions really think they need a probe stronger than sonnet, they can feel free to ask permission. I'm happy to review that kind of thing."*

**Why it exists.** On 2026-10-21 one session coordinated about 20 parallel sessions through the audit bugs #1349–#1377. Every session, and every subagent it sent out, ran on the main model, and the whole batch hit the usage limit partway through, leaving most branches half-built. The work was resumed in waves. The fix is not fewer sessions but cheaper probes.

**What counts as a probe.** Anything without the full session context:
- an Agent-tool subagent of any type: general-purpose, Explore, Plan, claude-code-guide, or a custom agent;
- agent-team teammates;
- workflow agents.

**What does not count:**
- a **fork**, which inherits the whole conversation and always runs on the main model, whatever the setting says;
- a **full session** started with `start_session`, which keeps the main model and is the place for work that needs it.

**How it is enforced.** The dev's user settings (`~/.claude/settings.json`, untracked, every project on his machine) carry `"env": { "CLAUDE_CODE_SUBAGENT_MODEL": "claude-sonnet-5-5" }`.
- The full id pins exactly the model he named. The Agent tool's `sonnet` alias resolves to the same model as of Claude Code 2.1.284.
- The setting is a **default**, not an override (documentation checked 2026-10-22, against Claude Code 2.1.308). Precedence is: a per-call `model`, then an agent's frontmatter `model`, then the variable, then the main model.
- The built-in **Explore** and **Plan** agents are not moved by the variable alone, which is why the rule asks for an explicit `model: "sonnet"` on them.

**Why not FORCE.** `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` was considered and rejected the same day. It ignores the per-call `model`, so a stronger probe the dev approved could never actually run.

**Asking for a stronger probe.**
- When he is present, ask before passing `model: "opus"` (or anything above Sonnet), with the reason: what the probe has to do that Sonnet cannot.
- In an unattended run such as `/agent-queue` there is nobody to ask. Stay on Sonnet, and say in the writeup if a stronger probe would have helped.

**Other machines.** Codev's setup has no such setting, so this rule is the only enforcement there: pass `model: "sonnet"` on every probe.

## Whose turn it is is derived from the thread

Open work lives in [GitHub Issues](https://github.com/Phaazoid/Godoiosis/issues).

**Whose turn it is is DERIVED FROM THE THREAD, never labelled (dev ruling, 2026-08-25).** The last thing said on an issue is the answer: if the newest comment leads with `🤖 Claude says:`, Claude spoke last and it is waiting on the dev; otherwise it is Claude's. An issue with no comments is judged by its **body** the same way. Run **`/agent-queue`** to walk everything that is Claude's turn (`priority/P1-soon` first) and advance each one step.

## Claim an issue by assigning it before starting work

**CLAIM AN ISSUE BY ASSIGNING IT BEFORE STARTING WORK (dev rule, 2026-09-06).** His words: *"when we start working on an issue/series of issues, we use the assignees feature in github to mark it… now that codev is starting to more actively use the github, we don't want to accidentally overlap work."* `c3potheds` writes here too — [#766](https://github.com/Phaazoid/Godoiosis/pull/766), [#765](https://github.com/Phaazoid/Godoiosis/pull/765), [#667](https://github.com/Phaazoid/Godoiosis/pull/667), [#657](https://github.com/Phaazoid/Godoiosis/pull/657), [#636](https://github.com/Phaazoid/Godoiosis/pull/636), the Play API / headless-playtest arc — and until this rule nothing on the tracker said who was inside a ticket: **0 of 137 open issues carried an assignee** the day it went in. So `gh issue edit <n> --add-assignee @me` before advancing an issue, and **an issue already assigned to someone else is theirs** — leave it, take another, and say which ones you skipped rather than skipping them silently. Two dev rulings set the shape, both 2026-09-06: **(1) an assignment means "this side OWNS this thread", not "hands on it right now"** — held through plan → build → review → merge and left on the closed issue as the record of which side did it, released only when we walk away (re-scoped, deferred, or blocked on something we are not chasing); **(2) claim only what is ACTUALLY being worked** — an umbrella is claimed when the whole arc is genuinely in flight, never as a reservation over children you are not building yet, which is the same over-claiming that made the old `agent/*` labels carry no information. Ruling 1 is what makes the field worth having, and the state it exists to survive is *plan posted, awaiting his answer*: under a "hands on it now" reading that issue reads as free, and codev takes it mid-arc — which is most of the collision the rule is for.

## Assignment is not turn

**Assignment is NOT turn, and this is not the `agent/*` labels coming back.** Turn stays derived from the thread (above); assignment is claimed, and the two are independent — an issue assigned to us *while waiting on the dev* is the normal mid-arc state. The labels died for copying an answer **the thread already held** (Law #4 — one question, one answer). This answers a question **no thread holds**: codev's work leaves no trace on the issue until they push, so there is nothing cheaper to derive from and a claimed field is the only answer available. A hand-maintained field violates Law #4 only when something cheaper already answers it. An issue assigned to us **and** someone else is not ours either — `/agent-queue`'s selector drops it deliberately, because a second name means somebody joined, and that is a conversation rather than a race.

**Two limits, both real and neither engineered around:** an unassigned issue is **NOT** proof codev is not on it — only one side of this convention is Claude's to enforce, and telling `c3potheds` it exists is the dev's; and `gh` here is authed as **Phaazoid**, so a Claude claim and a dev claim are the same string — the line this draws is *this side vs codev*, never *Claude vs the dev*.

## The comment convention

**This makes the comment convention load-bearing rather than decorative.** Every comment Claude posts under the user's account **leads with `🤖 Claude says:`** and **ends with** `— Claude (<model>) · <date>` (name the model actually running, e.g. Fable 5 / Opus 5 — the signature is provenance), authored via the Write tool → `gh issue comment --body-file` (never an inline non-ASCII arg — Windows PowerShell 5.1 mojibakes it before upload; see the encoding note in `tests/README.md`). *(Corrected 2026-10-20: `tests/README.md` has no such note, and git shows it never had one. The fact is the parenthetical itself: PowerShell 5.1 mojibakes a non-ASCII inline argument, so always use `--body-file`.)* **Drop the lead-in and the queue will hand that issue back to Claude forever.**

## Every PR body carries a How to check this section

**Every PR body carries a `## How to check this` section (dev rule, 2026-09-02).** What to do, what you should see, what a failure looks like, and what the tests already cover — his words: *"a question I've been asking you a lot lately is 'What can I do to test this'… it's fine if the answer is just 'this is a docs-only change, nothing to see', but I'd still like an easy place to see and know."* The fourth line is the load-bearing one, because it is where **the suite's blind spots get stated out loud** rather than left for a play-check round to find: a green run is not evidence a thing works (see the collaboration contract's *the suite is not the gate*), and this is the section that says which half was measured and which half is his to play.

## Every merge bumps the version

**Every merge bumps the version — each build must be distinguishable (dev rule 2026-08-11; the MECHANISM moved to merge time 2026-08-14).** The one store is `project.godot`'s `application/config/version` (`Build.version()` is the one reader, #134). Semver-shaped: a **feature** bumps the middle digit (`0.1.0` → `0.2.0`), a **bugfix or docs-only** change bumps the last (`0.2.0` → `0.2.1`; docs ruled equivalent to a bugfix 2026-08-12, PR #206). **A build that goes OUT is made by `tools/archive-build.ps1`** ([#1027](https://github.com/Phaazoid/Godoiosis/issues/1027), extended by [#1060](https://github.com/Phaazoid/Godoiosis/issues/1060)) — it refuses on a dirty tree, exports with the one `Windows Desktop` preset, zips the result beside the export, **pushes it to itch with `butler`**, **tags `v<version>` at the commit it was built from**, and last **announces that version into the intake Worker's `release` row**, which is what the in-game update nag reads on every launch.

**That order is load-bearing and #1060 changed what it means**: once a build going out means one that is *on itch*, a tag written before the upload would make its claim early — so the push precedes the tag, the announce follows everything, and each prefix fails safe (a failed push leaves nothing tagged and nobody nagged; a failed tag or announce leaves a build up that nobody has been pointed at yet). `-NoUpload` skips both new steps; `-NoPush` still means only the git tag. **It also refuses a version `CHANGELOG.md` has no `## v<version>` heading for ([#1075](https://github.com/Phaazoid/Godoiosis/issues/1075))** -- the release ledger, which the game SHIPS (the one non-resource file in `include_filter`) and reads for the title screen's what's-new card through `ReleaseNotes`. An entry arrives by a RELEASE PR, unlabelled and merged last, headed with the version main will be at once it merges; the procedure is at the top of that file, and its player lines are the dev's prose. That tag is the only thing that maps a version back to a commit *and* to a kept binary: `version-bump.yml` writes the number and stops, an export is taken from the WORKING TREE rather than from HEAD (so one taken mid-authoring matches no commit at all), and a player build's report carries the version string alone — `Checkout.describe()` answers `""` where `DevTools.enabled()` is false. Exporting by hand instead overwrites the last build and leaves no record that the version ever shipped.

## Do not bump the version in a PR's diff

**Do NOT bump it in a PR's diff.** `.github/workflows/version-bump.yml` does it on main after a merge, reading the merged PR's **labels** for the semver call (`type/feature` → middle digit, anything else → last). The old rule put the bump inside each PR, and the cost turned out to be structural rather than occasional: **any two PRs branched off one base edit the same line, so every concurrent pair conflicts on `project.godot`** — four collisions in one day (2026-08-14) before the dev called it. Consequence to remember: the label is now load-bearing, so a feature PR that ships unlabelled silently gets a patch bump; and the version on your branch is always *behind* main by design — never "fix" it by hand.

**Merges that land seconds apart ([#1398](https://github.com/Phaazoid/Godoiosis/issues/1398), 2026-10-21).** The bump's number is main's own *at push time* plus one, never the PR's, so `tools/version-bump/bump.sh` re-reads main and recomputes on every attempt (up to eight), and an unforced push is the compare-and-swap that keeps two runs off one number. Before this, the run did one `git pull --rebase` and one push, and a merge landing between the two turned the `bump` check red and lost that merge's bump: five times, #1341's feature bump among them. The workflow deliberately has **no `concurrency` group**. GitHub keeps one running and one *pending* run per group and cancels the pending one when a third arrives, which lost #1138's bump on 2026-09-28 with only a grey mark, and the loop already makes bump runs safe against each other. A push refused while main has *not* moved is not a race and is not retried. **A red `bump` run is repaired by re-running that job**: it keeps the PR's labels, re-reads main and applies exactly one bump of the right kind. `bash tools/version-bump/race-test.sh` reproduces the race locally against a throwaway remote; run it after any change to the script.

## Leave the working tree on the branch he has to test

**LEAVE THE WORKING TREE ON THE BRANCH HE HAS TO TEST, and say which branch that is (dev rule, 2026-08-14).** His words: *"I don't like having to merge to see the changes you made. That makes it so I have to merge before testing things."* Merging is what a review EARNS; it must never be the way he obtains the code to review. So the last act of any PR that needs his eyes is to check that branch out and say plainly *"you are on `<branch>` — launch it."* Corollaries, each of which has already cost something:

## Never move his working tree silently

- **Never move his working tree silently.** His Godot session is open on `C:\Iosis\Godoiosis` and renders whatever is checked out. Switching to a branch off main without saying so is what produced the false bug report *"the camera doesn't follow enemies anymore"* — he was playing a build that predated the camera work. **Since #295 the running build says which checkout it came from** — `branch @ shortsha` under the Battle3D help line, and a `Checkout:` line in every `report.md` — so a wrong build is a glance rather than a diagnostic round trip. `Checkout.describe()` (`Classes/core/Checkout.gd`) is the one reader, dev-only, and it answers a *different* question from `Build.version()`: a branch's version is deliberately behind main, so it names a release and can never identify a working tree. The rule above is unchanged by it — a readout catches the mistake, it does not prevent it.

## Only switch his tree when it is on main — HARD RULE

**ONLY switch his tree when it is on `main` — HARD RULE (dev, 2026-08-25).** His words: *"you're only allowed to switch my work tree if I'm on main. Otherwise, it means I'm looking at another agent's session, and don't want to be moved."* `main` is the idle state and the only one that is safe to take. **Any other branch means someone else's work is checked out and being looked at**, and the rest of this section does not authorize moving it — check `git branch --show-current` BEFORE `git switch`, and if it is not `main`, leave it and say which branch your work is on so he can check it out himself. This bit on 2026-08-25: #497 followed the leave-him-on-the-branch rule below and moved him off `fix/427-corner-cap-zfight`, which he had switched to mid-session. Nothing was lost — the switch was clean and his work was pushed — but he was looking at it.

**ONE CARVE-OUT (dev, 2026-08-28): a branch YOU put him on, that you are about to work on, may be taken back to `main` first — his proposal, on being shown the bind.** The hard rule's reason is *another agent's session is checked out*, and that does not apply to a branch this session owns and handed him. It exists because **git refuses a second worktree on a branch already checked out**, so him sitting on your branch is exactly what forces you into his tree — which the worktree convention forbids; #418's settings-lock fix was done in his tree for want of this. **THE TELL IS OWNERSHIP, NOT THE BRANCH NAME**: if you did not put him there this session, nothing changes — leave it and say which branch your work is on. Two preconditions, both required: `git status --short` must be **CLEAN** (dirt may be his own content edits, so stop and ask rather than carry it across), and the move is **announced**, never silent. Put him back on the branch at hand-off as usual. Practical companion: keep ONE long-lived agent worktree and `git switch` inside it, so Godot's cold import (~1 min, `.godot/` being gitignored) is paid once rather than per ticket.

## Never leave him on main or an unrelated branch; one open PR at a time

- **Never leave him on `main` or an unrelated branch after doing work.** That is the state that forces a merge-to-test — *subject to the hard rule above, which outranks it: an occupied tree stays put.*
- **Prefer ONE open PR at a time** when the work needs feel-checks, so "the branch you're on" is unambiguous. Four concurrent PRs is also what produced the `project.godot` collisions.
- Getting back: `git switch main && git pull`. Testing a different open PR: `gh pr checkout <n>`.

## Delete a branch when its PR merges

**DELETE A BRANCH WHEN ITS PR MERGES — remote AND local (dev rule, 2026-08-14).** GitHub auto-deletes the head branch on merge here, so the copy that actually rots is the **local** one: `git switch main && git pull && git branch -d <branch>` is the last step of landing work, not a chore for later. Left alone it compounds — the first sweep deleted **101** stale branches (93 local, 96 remote, overlapping), leaving exactly `main` on both sides.

## Branch sweep discipline

**Sweep discipline, because a branch cleanup is the one tidy-up that can destroy work.** Delete with `git branch -d` / `git push origin --delete` only what is **merged into main**; `-d`'s refusal to drop an unmerged branch IS the safety net, so never reach for `-D` just to get past it. For anything git calls unmerged, check the CONTENT before deciding: `git diff main...<branch> --name-only` coming back **empty** means the branch introduces nothing main lacks. **Unmerged by SHA is not unlanded by content** — all five survivors of the first sweep were either content-identical to main or strictly *behind* it, including one that looked exactly like lost design canon (*"Record three dev rulings"*) whose every line had already landed via a different commit. Check, then delete; do not bulk-force and do not leave them forever out of caution.

## Canon-sweep discipline

**Canon-sweep discipline before calling a doc update done (added 2026-07-16, after a full-corpus staleness sweep found 9/22 `docs/design/` files drifted):** a "canon swept" claim means a grep-verified pass over the *whole* `docs/design/` tree (+ this file) for the issue's own number and any renamed/removed code symbol or term it touched — not just an edit to the one file that's obviously the topic's home. Staleness hides in three places a narrow, feature-specific edit misses: (1) a status banner elsewhere in the *same* file that a detail-section-only edit didn't reach; (2) a sibling file stating the same fact from a different angle (weapons.md and elemental-system.md both independently described issue #7 as open after it closed); (3) a "living list" tracker (`docs/design/grill-queue.md`) that can go stale from a *different* ticket's work than the one closing. For multi-session issues, sweep against the issue's *final* state at close — re-read its own comment history, not just what the current session built.

## Embedded-content sweep

**Embedded-content sweep when a diff adds fields to EMBEDDED content (dev rule, 2026-08-20, from #258's fireball):** `.tres` files omit properties at their default value, so every committed resource that EMBEDS a copy of a content type — snapshot scenarios under `Scenarios/` and `tests/fixtures/` above all — silently predates any field added later and loads the default, however the canonical file was authored. *(Corrected 2026-10-20: there is no `tests/fixtures/` folder, and git has no history of one. The embedded fixture scenarios live in `Scenarios/fixtures/`, loaded by `tests/ui/test_game_scene_smoke.gd`.)* That is how the Fireball lob shipped flat: the snapshot's embedded carving predated `arc_clearance`/`up_tolerance`, so the authored arc never reached the board the dev tested on, while every test stayed green against the canonical resource. So a diff that adds an authored field to an embeddable content type (`AttackData`, `WeaponData`, anything a scenario snapshot copies) must, in the SAME diff: (1) sweep the committed `.tres` fixtures that embed that type and re-author the ones whose defaults are now wrong, and (2) say in the PR which fixtures were swept — or state explicitly that nothing embeds the type, so the dev knows the staleness class was checked rather than missed. His words: *"if something like this fireball issue ever happens in the future, I'd like it called out, so that I know not to rely on stale tests."* A field whose default is correct for old content needs no rewrite — but the sweep statement is still owed.

## A deleted or renamed content file sweeps its referrers

**The mirror — a DELETED or RENAMED content file sweeps its `ext_resource` REFERRERS in the SAME diff (#596, 2026-08-27):** the rule above is a field *added* to embedded content; this is the same law pointed the other way, and it bites harder because **the tree that authors the rename is the one place structurally unable to see it.** `356a2e7` renamed `WeaponMods/Super Scope.tres` → `Line Sniper.tres` and `WeaponVariants/brrr.tres` → (gone) without touching the four files still naming the old paths, so `Noemie.tres` stopped loading, `Scenarios/missions/Level_1.tres` went with it, and five cases reddened across four suites two steps from the cause — while the editor stayed happy, since it holds the old resource in memory and the deleted file may still sit untracked beside it.

**A green local run is not evidence here; it is the one environment that cannot detect the fault.** So: grep the repo for the OLD basename before committing any content deletion or rename, and repoint every referrer in the same diff. `tests/law/test_resource_uid_references.gd` grades this automatically since #596 — it now holds BOTH halves of *a reference that resolves to nothing*, the `uid=` half (#240) and the `path=` half (#596), and one failure names referrer and target together. **Which file a referrer should point at afterwards is a CONTENT call, not a code one:** the rename pairing makes a guess look obvious, and a wrong guess is silent — `Super Scoper.tres` reads like `brrr.tres`'s heir and is actually `Super Gun.tres`'s, so it would have re-armed three boards with a mod they never carried. Ask.

## Content that lost a reference loads degraded

**...and content that lost one loads DEGRADED rather than refusing ([#608](https://github.com/Phaazoid/Godoiosis/issues/608), 2026-08-27).** The rule above makes a dangling reference loud; this makes it survivable. **The dev tools live INSIDE the running game**, so content that refuses to load takes the Unit and Item Editors down with it — the only surfaces that could repair it. His words: *"I can't go in and author the fix myself in dev mode."* **Measured before designing, and it decides the mechanism: a dangling `ext_resource` is a hard PARSE error** — `load()` returns null for the WHOLE file and then for everything referencing it, so there is no "let that property come back null" to reach for and the text must be repaired *before* Godot parses it. That fact is pinned by `tests/core/test_content_repair.gd`'s first case, so if Godot ever starts returning a partial resource the mechanism gets revisited instead of quietly rotting. `ContentRepair.load_tolerant` is the ONE answer: strip the dangling reference, load the repaired text, `take_over_path` back to the real file (without which every dev tool writes its edits into `user://__repaired/` and the real content is never fixed).

**The CHAIN is the hard half and was #596's actual shape** — `Level_1` → `Noemie` → a weapon that was gone, where the middle file EXISTS so the top file's own references all look fine while it still will not load; children are repaired first, each claiming its real path, which caches it so the parent's retry resolves from memory. **A repaired child must be HELD across that retry** — it is refcounted, and dropping the reference frees it *and* its cache entry, a false negative that reads exactly like the feature not working. It **refuses rather than guesses** twice: a missing SCRIPT is a code fault, not content, and a file broken some other way gets no repaired copy. Wired at `ScenarioManager.load_scenario`, `ResourceCatalog` (the catalogs every editor reads) and `ReplayRun.load_run` ([#871](https://github.com/Phaazoid/Godoiosis/issues/871)) — ordinary runtime `load()` stays strict. *(Corrected 2026-10-20: it is also wired at `RosterCatalog.resolve` and `SubstanceCatalog`.)*

**A caller that only wants the DIAGNOSIS asks `ContentRepair.missing_references(path)`**, which is the same walk with the Script refusal removed and with `ResourceLoader.exists` as the existence question, so it answers in an exported pack too. **One edge it is worded around, measured: an `ext_resource` NOTHING USES does not fail the file** — Godot prints the load error and carries on — so a missing reference is not always a missing property, and a caller says a file *references* what it cannot load rather than that it lost it. **The save refusal is what stops the repair BECOMING the loss:** `DevWidgets.save_over` rejects a degraded resource while the gap is still open, naming the missing file, and lifts the moment the property is filled — which is how a repair is meant to end, with the dev replacing the reference rather than anything quietly dropping it. `BoardLint` reports it as DEGRADES.

## Staleness marker

**Staleness marker (added 2026-07-16):** every living design doc (all of `docs/design/` except the three deliberately-frozen historical records — the coherence audit, the co-dev agenda, the wiki triage ledger) carries a `**Canon checked through #NN (date).**` line in its opening banner. When a sweep re-verifies a doc, bump its marker to the current highest issue number + that day's date. A marker sitting far behind the current issue count is the at-a-glance signal a doc is due for a re-check — don't let it go stale by forgetting the bump once you've actually re-verified the doc.
