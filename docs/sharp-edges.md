## Missions talk now: a fixture that boots one must hang up

**Missions talk now (#182) — a test fixture that boots one through `begin_mission` must hang up.** Dialogic's layout lands on the TREE ROOT, outside every suite fixture: it eats synthesized clicks (the #370 CI red — "the press never armed the drag"), survives `_scene.free()`, and bleeds into later suites through the persistent autoload. **#687 did not change this for tests, and the reason is worth knowing before anyone deletes the dance**: the parent is now `game.get_viewport()`, which is `GameView` in the shipped tree but IS the root in a suite whose board sits directly under it. `DialogFixtures.end_all_dialog(self)` (`tests/support/`) is the one teardown dance (end, await `timeline_ended`, two frames); a suite that synthesizes clicks also calls `scenario_director.disarm()` in `before_test`.

## Grant or copy a carried item via copy_for_grant()

**Grant/copy a carried item via `copy_for_grant()`, never a bare `duplicate(true)`** (revised #59 — this used to say the opposite; the door lived on `EquippableData` as `copy_equippable()` until #697 widened the authoring doors to `Item`, and it moved down with them). `RuneData` and a `VialData` still want a full deep copy (`Item`'s base implementation, which leaves a rune's library carvings shared because they are path'd, #1313), but `WeaponInstance` overrides it to keep `template` a SHARED reference while each of its own `spaces` copies shallowly — a generic `duplicate(true)` would deep-copy the template too and silently fork a weapon off its family.

**`WeaponData` overrides it too since [#835](https://github.com/Phaazoid/Godoiosis/issues/835) (2026-09-08), and answers with an INSTANCE** -- `WeaponInstance.make(self)`, because a unit cannot hold a shared family template and the default deep copy handed one over FORKED, which is the fault #80 closed by taking templates out of the pickers. That is what lets a template be AUTHORED into any of the three Item-typed kit doors and arrive as the plain weapon it names. It answers NULL for an unmapped `weapon_type`, and every granting door guards that now, because `Unit.add_item(null)` puts the null in the first free slot and reports SUCCESS.

## Never run the full test suite locally

**NEVER run the full test suite locally. CI owns it (dev rule, 2026-08-15).** `.github/workflows/tests.yml` runs the whole tree on every push and every PR against `main`, carrying the *same* two guards as `run_tests.ps1` (#93's verdict parsing and #146's zero-cases check) — **on GitHub's image since the repo went public (2026-09-27)**. From 2026-09-14 until then it ran on three self-hosted runners in WSL2 on the dev's own machine; those runners now take Tests only when `tools/ci-failover/` re-runs a stalled run on them during a GitHub outage (the comment above `runs-on` in that workflow is the record), so **a job queued past six minutes is GitHub's outage, and the watcher's to handle**. A local full run duplicates the gate, and during a failover it also competes with it for the same cores. The full tree's job has always been *"don't merge a regression"*, and CI is already that gate; a local full run duplicates it exactly and buys nothing.

**Locally: area folders only** (`run_tests.ps1 rules`, `presentation`, …), and a bare `run_tests.ps1` now defaults to the `fast` tier rather than the whole tree so the expensive thing takes deliberate typing. If something cross-cutting needs checking before pushing, run the narrowest area that loads the surface you touched — a change that breaks `game.gd` parsing shows up in `ai`/`flow`/`ui`, not in `rules`. **This rule is unconditional on purpose.** It replaces a conditional one ("one full run, after his feel-check") that got misapplied three times, twice on #254 and once on #257 — and the #257 miss happened because the rule was *paraphrased into an approved plan* with the timing inverted, which gave the paraphrase more authority than the rule. Cite this line; do not restate it.

## Never pin authored content in a test

**NEVER pin AUTHORED CONTENT in a test (dev rule, 2026-08-15; full rule + the seams to use = `tests/README.md` #9, *the content razor*).** A test may **load** a real mission to exercise a real path; it may not **assert** anything about what that mission contains — not a cell coordinate, an elevation, a cell *count*, a footprint size, or a roster size. Sibling of #8's tuning razor, for the other thing the dev edits without touching code: *"authored content shouldn't be pinned, and level geometry, not to mention contents, units, objectives, all of it is authored."* **`b057f6e` "quick level update" painted eight tiles onto `Level_1` and reddened a case about the board-swap funnel** — a content commit breaking a test about input wiring. Measured while fixing it (PR #290): three raised cells added to Prolog took `tests/presentation` from **165 executed / 1 failure to 116 / 7**, four suites reddening at their first content-dependent case — and since a failure aborts the rest of its own suite, three painted tiles cost **49 test cases**. Derive every expectation from the seam under test (`BoardPicker.column_tops_from` = the footprint, `BoardSpace.surface_point` = where a sprite sits, **`BoardSpace.surface_transform` = how flat markup LIES on a cell, tilt included (#281)**, `board_heights.elevation_at` = an overlay's level, `game.get_move_range` = where a unit may be ordered), and make a content precondition a non-vacuity **message**, never a threshold. `tests/presentation/` is the DECLARED exception to `tests/README.md` #4's "never load a `.tres`": it loads real missions on purpose, because the wire bugs it hunts (#103, #222) only appear on the real load path. Two hazards that exist only on a non-flat board, both found by falsification rather than reasoning: a taller column **shadows** the cell behind it so a click lands on the blocker (ask the real picker, not a UI-overlap check), and a unit on a terrace with no ramp off it **genuinely cannot move** (find one that can, don't assume the first).

## gdUnit4's Total execution time is not wall clock

**gdUnit4's `Total execution time` line is not wall clock** — it read `1min 55s` for a 573-case run right after a cache clear, then `12s` for the identical run warm. It is not a usable number in either direction; trust `run_tests.ps1`'s own stopwatched `Elapsed` line instead. **Measured on `Elapsed`: full run 153–157s** (eleven consecutive runs 2026-07-26, 605 cases; independently 158s at 610 cases on 2026-07-27), **`fast` 42s** (156 cases), **51s for three areas together** (2026-07-27). That is **~0.26s/case across every tier** — a flat per-case cost, not a startup overhead you can amortize, and ~7x the "~0.035s/case warm" this note used to claim. The same suite passes **Linux CI in a 34s total job** while the case count only grew 573 → 610, so it is a Windows/environment factor, not suite size — **cause unconfirmed** (antivirus scanning the repo tree and `.godot` cache state are the untested suspects). The old "~20s full / ~7s fast / ~3-5s per area" figures came from trusting gdUnit4's warm number; all corrected 2026-07-27. Practical consequence: **no tier is a fast inner loop right now** — pick the narrowest area you can. Re-measure before ever acting on "the tests are getting slow".

**Observation, same day (2026-07-27, Unit.gd review session): three consecutive full runs came in at 19.5s / 19.9s / 20.9s at 610–612 cases — ~8x faster than the measurements above, on the same machine, hours apart.** The session had just run `godot --headless --import` (needed to register a new `class_name`), and the speed persisted across later runs that did not re-import. That is a data point for the `.godot`-cache suspect, **not** a correction: **this entry stands as written**, because the slow behaviour has recurred repeatedly and the fast state has not been shown to last. If you find yourself waiting 2.5 minutes again, an import pass is worth trying before anything else.

**Third data point (2026-07-29, #103): 49.3s at 803 cases = 0.061s/case, again after an `--import` pass earlier in the session** (run to generate a new test file's `.uid`). Note the direction: the case count grew 610 → 803 while wall clock fell 155s → 49s, which is more evidence that suite size is not the variable. Two of two fast runs followed an import; the hypothesis is holding but still uncontrolled — nobody has yet run the same suite slow-then-import-then-fast in one sitting, which is the measurement that would settle it. **Fourth data point (2026-08-02, #128): 53.9s at 937 cases = 0.058s/case, again after two `--import` passes earlier in the session** (run to check for script errors and to verify a UID fix). Three of three fast runs have now followed an import, and the per-case cost has sat within 0.058–0.061 across the last two while the suite grew 803 → 937. Still uncontrolled in the same way — nobody has deliberately reproduced the SLOW state to import out of it — but the import-first advice above has yet to be contradicted.

## game.clear_selection() runs on every terminal menu pick

**`game.clear_selection()` runs on every TERMINAL menu pick, not just on cancel** — `ActionMenuController` emits `cancelled` *before* `action_selected`, so `MainActionMenu._on_menu_cancelled` fires it on the way **into** whatever mode you just chose. **Since #467 a CATEGORY pick deliberately does neither** (no `cancelled`, no teardown): the ring survives so a wrong turn costs a right-click, and clearing the selection while the player is still choosing an action for that unit is this trap by definition. `tests/ui/test_radial_menu.gd` counts the signal rather than a side effect, because `clear_selection` does not null `selected_unit` — a case asserting on the unit passed against a mutant that emitted here. Anything that must survive into a mode therefore cannot be cleared there: `exit_current_mode()` is the mode-ending path, and that is why `last_clicked_cell` (and, since #107, `selected_unit`) are nulled there instead. **Bitten twice** — #105 (clearing the knockback/terrain previews there wiped the shove ghost the instant you opened Attack, making its landing tile unaimable) and #107 (clearing `selected_unit` there crashed Move/Group Move and silently no-op'd Attack).

**Both are now pinned by `tests/ui/test_game_scene_smoke.gd` (#114, 2026-07-29)** — the claim that the game scene segfaults inside gdUnit4 was **false**, and that layer is ordinary-suite testable; see `tests/README.md` → *Testing the game scene*. The one trap to respect when adding cases there: a test that sets `game.game_state` directly instead of firing a real menu pick **cannot see either bug**, because `clear_selection()` only runs on the `cancelled`-before-`action_selected` ordering. **The other half of that asymmetry is a lifecycle rule (#149, 2026-08-07): a stored selection must be RELEASED whenever its unit is freed, and the thing that catches a dangling one is a TYPED read, not a null check.** Measured 2026-08-07, because the reverse is the intuitive guess and it is wrong: a freed reference reports `typeof` 24 (OBJECT) and `is_instance_valid` false, yet it compares **`== null` as TRUE**. So `if selected != null` would have caught it — the guard is simply never reached, because the *typed assignment on the line above* (`var u: Unit = game.selected_unit`) has to resolve the ObjectID to type-check it and dies with *"Trying to assign invalid previously freed instance"* first. The practical consequence is for **tests**: `assert_object(game.selected_unit).is_null()` **cannot see this bug** and passes against it (verified) — a regression case here must do the typed read to have any teeth. Both places that free units now do it: `game._on_unit_died` nulls the field, and `ScenarioManager.clear_board` calls `exit_current_mode()` rather than `clear_selection()` — the same swap `MissionController.abandon_mission` already made for the same reason. `_on_unit_died` deliberately does **not** call `exit_current_mode`: that would reset `game_state` to IDLE and unlock the board mid-AI-turn. Reported as *"F3 during an AI turn crashes"*, but the AI is only the stretch where units die while the board is locked and nothing overwrites the stale value; `end_turn()` leaves it set, since `clear_selection` does not touch it.

## get_tree().paused breaks every click

**`get_tree().paused` breaks every click in this project, because the game lives in a SubViewport.** `GameContainer` (a `SubViewportContainer`) forwards mouse input into `GameView` only while it can process, so a paused tree severs the click path *above* anything inside — `PROCESS_MODE_ALWAYS` on a Control in there makes it processable and still unclickable. Freeze `game.process_mode = PROCESS_MODE_DISABLED` instead: it stops every loop under Game while leaving the forwarding chain alive. Measured both ways 2026-08-05 (#131); the tree-pause version shipped and made the pause menu unusable. `ModalLock` is the worked example.

## A HUD surface must catch its own clicks

**A HUD SURFACE MUST CATCH ITS OWN CLICKS, or the click lands on the board ([#929](https://github.com/Phaazoid/Godoiosis/issues/929) follow-up, 2026-10-09).** `battle3d._unhandled_input` picks the cell under any click the HUD lets through, so a see-through box aims, moves or selects whatever lies beneath it: the aim strip shipped `IGNORE` throughout and a click on its arrow queued an attack at empty ground. A box (or an ancestor up to its full-rect host) is `MOUSE_FILTER_STOP`; the full-rect host stays `IGNORE` so the board is clickable around it; `PASS` falls through exactly like `IGNORE`. **`tests/law/test_hud_catches_its_clicks.gd` walks every CanvasLayer in the game's viewport** and names each offender, and a surface see-through on purpose goes in its `SEE_THROUGH` table with the reason. It cannot see a surface its fixture never builds (cards, the update banner, the dialogue box). Canon: `docs/design/visual-clarity.md` principle 7.

## await_millis hangs the whole run if the tree is paused

**gdUnit4's `await_millis` HANGS THE WHOLE RUN if the tree is paused.** It is implemented with a `Timer` **node** parented under `root` (`GdUnitAwaiter.await_millis`), and a Timer is pausable — so once anything sets `get_tree().paused` it never fires, the test awaits forever, and the run dies with no failure message and no timeout (measured 2026-08-05, #131). `SceneTree.process_frame` is emitted regardless of pause, so **frame counting is the only wait that survives a paused tree**; `tests/ui/test_report_flow.gd` carries a local `_frames(n)` helper for exactly this. Related, and the reason it bites: a *failing* case aborts the remaining cases in its own suite, so a hang or a failure early in a file hides everything below it — falsifying a late case means temporarily disabling the earlier one.

## frame_post_draw never resumes in a headless run

**`await RenderingServer.frame_post_draw` never resumes in a headless run.** It is the standard way to wait for a valid viewport texture (a screenshot needs it), but `--headless` never draws, so the await is not slow — it is permanent, and it takes the whole calling coroutine with it. The suite runs headless, so any code awaiting it needs a `DisplayServer.get_name() == "headless"` escape or it hangs the test that reaches it (measured 2026-08-05, #131 — the symptom was a suite reporting *one* case, not a timeout message). `BugReporter.capture_frame` is the worked example.

## A terrain height number is half a level

**A TERRAIN HEIGHT NUMBER IS HALF A LEVEL ([#427](https://github.com/Phaazoid/Godoiosis/issues/427) slice 1, 2026-08-23).** `Terrain.UNITS_PER_LEVEL` is 2, so a 45° ramp climbs 2 and a cell at "height 4" is two levels up. Every height in the codebase speaks this unit — `BoardHeights`, `RulesService.height_step_ok`, `FallRules.damage_for`, `Reach.EYE_HEIGHT` and the authored `up_tolerance`/`down_tolerance`/`arc_clearance` on `AttackData` — which is what keeps `Reach` free of conversions. **A ramp's CLIMB is authored too since slice 2** — 1 unit (the 26.6° RCT slope) or `UNITS_PER_LEVEL` (45°) — so `height_step_ok` and `PlanResolver`'s two landing rules ask `ramp_climb_at` rather than comparing against the constant; the old `abs(delta) != UNITS_PER_LEVEL` clause is GONE, and the half-level refusal survives because flat ground climbs 0.

**The 3D mirror counts ONE ROW PER UNIT** (`BoardSpace.ROW_HEIGHT` = `CELL_SIZE / UNITS_PER_LEVEL`), so a mirror cell is NOT a cube and `BoardSpace.top_row_of` is the one height-to-row conversion — it replaced `Terrain.level_of` at every site that places geometry, leaving `level_of` to the one rule that genuinely counts whole levels, fall damage. A ground slab is still one LEVEL deep, which is why every world position survived. **The store is FOUR CORNER HEIGHTS per cell** (`Vector4i(NW,NE,SE,SW)`, one sparse `corner_heights` field); `elevation_at` (the lowest corner) and `ramp_rise_at` (which pair is high) are DERIVED views, which is the only reason the rules layer and the 3D stack needed no structural edit.

**A CELL'S SHAPE IS A MASK OF RAISED CORNERS since slice 3** — flat, four outer corners, the four cardinal ramps (the adjacent pairs), four inner corners, and two refused saddles; `RampRise` survives as the AUTHORING vocabulary only, `is_on_rise_axis` is deleted, and `rise_of_corners` answers NONE for a corner form instead of erroring (that `push_error` was the migration checklist and it has been walked). **The rules ask the shared EDGE**: `height_step_ok` compares `Terrain.edge_of_corners` from either side, which replaced both height clauses, both sideways guards and the climb arithmetic in one comparison — so walking ACROSS a continuous slope is now legal (dev call, provisional) and a ramp is enterable strictly from its LOW side.

**`Terrain.height_at_uv` is the one surface**, splitting each cell on the diagonal joining its two EQUAL corners, and `gen_lookdev_assets` CALLS it rather than reimplementing the rule — pinned by `tests/law/test_cap_mesh_matches_the_surface.gd`, because both triangulations meet all four corners and only an interior point can tell them apart. **A corner is AUTHORABLE since slice 4** — the Tile Brush's fourth `PaintMode`, `CORNER`, which drags the grid VERTEX four cells share rather than painting a tile, and does not replace the cell brush (dev: *"different tools for different situations"*). Three things carry it. `Terrain.VERTEX_CORNERS` is the one cell-offset→corner-bit table (`CORNER_COMPONENTS` is its bit→`Vector4i`-component twin, the write direction of `corner_mask`'s read); `BoardHeights.set_vertex` is the WELD, taking the ground predicate as a parameter on `prune_groundless`'s justification; and **`Terrain.corner_toward` is the CLAMP, which ASKS `is_legal_corners` rather than restating any of its three refusals** — so the tool is structurally unable to author a saddle, a third height or a climb past 45°, and a corner simply stops rising once its own tile would break instead of cascading into its neighbours. The gesture is ABSOLUTE (`_paint()` re-fires per motion event, so a relative step runs away down a drag) and right-click pulls a point down to the board floor. Two traps it paid: `battle3d._update_pointer` computes the vertex ABOVE its cell early-out, because the answer changes halfway across a cell (#471's law); and `BrushGhost` gained a declared `Kind`, because a renderer inferring the mode from an unset `source` reads `null == null` against a ghost layer nothing has built yet and paints a tile at the origin.

**MARKUP ON A CORNER CELL IS THE FOLLOW-UP the tool surfaced (found in play, same day): `Terrain.height_at_uv` is the ONE surface, and slice 3 had shipped a second answer beside it.** `BoardSpace.lie_on` described a cell with one `Transform3D` — a PLANE — taking its height from the corners' MEAN, so `surface_point` (units, flames, props) and `surface_height_at` disagreed by a quarter of the climb on a corner form; the mean (`centre_height_of_corners`) is DELETED and `lie_on` reads the surface. And no transform can describe a corner cell at all — four non-coplanar points, and an affine transform maps a plane to a plane — so the best-fit plane crossed the ground by a quarter of the climb at every corner, six times `fill_lift` — which is what the arrows and move tiles cutting through the ground were.

**It was NOT the z-fighting, and this line claimed it was until the report came back unchanged on a build carrying the fix**; see the cap entry below, and take the correction as the lesson: confirming a mechanism proves the mechanism, never that it is the one being reported (#490's law, milder). `lie_on` returns an IDENTITY basis on a non-planar form (`Terrain.is_planar_form`) rather than a tilt it cannot honour, and the FOLD lives in `BoardOverlays._surface_mesh` — four vertices at their true heights, split on the diagonal `height_at_uv` splits on, cached by the cell's shape; planar cells keep the one shared `PlaneMesh` and are bit-identical. A SPRITE's shape travels in its marker entry ALONGSIDE the basis, never instead of it, because the knockback drop pointer carries an orientation of its own and lies on nothing. The lesson that generalizes: **the renderer's END of that key was pinned and its SOURCE was not**, so a mutant deleting it passed the whole mirror suite — #103's shape, caught only by falsifying.

**THE Z-FIGHT ITSELF WAS THE CAP MESH (2026-08-25): A CAP DRAWS NOTHING IN ITS OWN FLOOR PLANE.** `_form_mesh` puts each top-face corner at `lo + height * ROW_HEIGHT`, so an OUTER corner — three corners at the low height — had a whole top triangle lying on `lo`, its own floor; `_write_column` places that cap on a column whose top block reaches exactly the cell's surface, i.e. the same plane, so two upward-facing identically-textured faces were coplanar to the float. **THREE cap faces live in that plane and all three had to go** — the side wall of an edge whose corners are both low (always skipped: `if height[i] == 0 and height[next] == 0: continue`, the rule the others were derived from), the flat top triangle, and the BOTTOM QUAD. Removing only the triangle is what proved it: the quad then had the area to itself, and being back-facing it rasterises to no pixels, so the shimmer became **holes straight through the board** (measured at the background colour).

**Which way a duplicated face points decides only what the artefact LOOKS like** — a coplanarity check must count UP and DOWN alike, read every surface not just the ground one, and **skip DEGENERATE triangles or it reds on correct geometry** (every cap has one: a wall whose first corner is at the floor gets `floor_here == top[i]`, so the quad's first triangle has two identical vertices). The cap is an open shell now; its opening is exactly the footprint the block's top face covers, and meshlib items carry no collision shape or navmesh, so nothing but the rasteriser reads it. Which form suffers is the whole tell and it matched the report exactly: a WEDGE's low side is an EDGE with no area so wedges never fought, and an INNER corner's flat triangle is at its HIGH plane where nothing else is drawn, so it must SURVIVE — a guard widened to "skip every horizontal triangle" holes three quarters of every inner corner. The block beneath a cap is therefore LOAD-BEARING, not filler, and now says so. An epsilon lift was rejected: it would make the drawn cap disagree with `height_at_uv`, and the flame taught this project twice (#243/#298) that coplanarity is fixed by geometry, never by a number. Canon: `docs/design/verticality.md`.

## A buried face is still a drawn face

**A BURIED FACE IS STILL A DRAWN FACE, AND BACK-FACE CULLING IS LOAD-BEARING NOW ([#559](https://github.com/Phaazoid/Godoiosis/issues/559), 2026-08-26).** The cap entry above is two surfaces meeting in a PLANE; this is two meeting along an EDGE. `_block_mesh` emits all six faces of every ground block with no knowledge of its neighbours and `_write_column` fills columns solid, so a side quad's top edge sat exactly in the top face's plane — which is also where the NEIGHBOUR's top face ends. Four surfaces on one line, and a pixel centre landing on it could be won by the dirt. **The camera is what turned that into a bug:** off-axis the wins scatter across scanlines and read as texture, but at yaw 0/90/180/270 a whole row of cell borders projects to ONE screen row and the scatter becomes a brown hairline across the board — and `CameraRig3D.align_to_detent` snaps to exactly those yaws on the enemy phase, so the game reaches the pose by itself. Fixed by geometry, not a number: sides start `BoardSpace.SIDE_RIM` below the surface and a RIM wearing the **top** material closes the gap, so the surface still meeting the neighbour there is ground-coloured.

**A ground block's TOP face keeps its FULL extent** — `BoardSpace.CELL_SIZE` must go on matching the authored `GridMap.cell_size`, and the cap's open shell is safe only while the block below covers the whole footprint. `_mat()` also went back to `CULL_BACK`, which had been DISABLED since the Stage 0 bootstrap (#203) and was **silently insuring every open shell in the meshlib**: an exposed opening used to show its own inside surface, and now shows the sky through the board — so `_form_mesh`'s deliberate opening is pinned by `test_a_cap_opening_lies_on_the_block_top` rather than merely argued in a comment.

**Diagnosis rule worth carrying: a CONSTANT artefact colour, unchanged by whatever is behind it, rules out every shading cause at once** (cascade banding, AO, depth haze all MODULATE what is underneath) and proves something is being DRAWN; tracing a terrain edge THROUGH the artefact then separates an overlay from a seam between two renders. Canon: `docs/design/presentation-effects.md`, `docs/design/verticality.md`.

## load() serves the resource cache

**`load()` serves the resource CACHE, so overwriting a `.tres` at runtime needs `take_over_path(path)` first** (measured 2026-07-29, #99). Save a *fresh or duplicated* resource over a path that has been `load()`ed this session and the file on disk is written correctly — but every later `load()` of that path keeps handing back the **stale pre-edit object**, so the tool shows old content until a restart. `CACHE_MODE_IGNORE` reads the new file but forks a second object and leaves the cache stale for everyone else; `take_over_path` is the only call that repairs the entry, and it is a **safe no-op when the resource already owns the path** (verified), so it can go on every save site unconditionally. The rule: *whoever writes a path must claim it.* This silently affected `ScenarioManager.save_scenario` (re-saving a loaded scenario made Load **and the F2 reset** replay the pre-save board) and both dev editors; all three now route through it. Editing a resource **in place** — the Attack Editor's FAMILY mode (*Weapon Families*, renamed by #473), which mutates the live cached `main_attack` — was already correct, because the object being saved *is* the cache entry.

**Claiming the path is NECESSARY BUT NOT SUFFICIENT, and that observation about in-place editing is the whole of why ([#589](https://github.com/Phaazoid/Godoiosis/issues/589), 2026-08-27).** `set_path(path, true)` clears the OLD owner's `resource_path` and evicts it, so a pool editor saving its `duplicate(true)` fixed the *cache* while orphaning the *object* — and the orphan is what every board unit, every mod's `granted_attacks` and every template's `main_attack` is still holding. The board never saw an edit, **and neither did a respawn** (a catalog scan is a cache hit still holding the orphan, so only a relaunch cleared it) — which is why tweaking an attack meant rebuilding the mod/weapon/unit chain by hand. Worse, an orphan's `resource_path` is now **empty**, so any holder re-saved afterwards writes it INLINE as a `sub_resource` rather than an `ext_resource`, forking the content silently; nothing in `Resources/` had hit that yet. `save_over` now adopts the edited values onto the object that already owns the path and saves THAT — **one path, one object** — through a `duplicate(true)` snapshot, so path'd sub-resources stay shared while the live object gets its own inline ones (assigning the editor's own objects across would leave later keystrokes reaching the board on nested fields but not on scalars). The three tools that already hand out the live object land on `live == edited` and are untouched. Pinned by `tests/dev/test_dev_tool_live_sync.gd`, whose cases hold the ORIGINAL reference and assert on **that** — asserting through `load(path)` is the blind version and passes against the bug.

## The writer preserves a resource's uid= attributes

**The same writer preserves a resource's uid= attributes since #481 (2026-08-24).** `ResourceSaver.save()` at runtime writes no `uid=` — the running game's `ResourceUID` holds no registration for the path — and mints a NEW uid for a *fresh* resource, while `take_over_path` preserves none of it. That drops the file's OWN header uid AND the `uid=` on its `ext_resource` reference lines (script/texture/other-resource refs): the Carbine main attack lost `uid://dbboy21d8bwwo` on an ordinary Update, and the same Update stripped `uid=` from the family template's script references — each harmless until the target moves and the `path=` fallback breaks. So `DevWidgets.save_over` captures `uid_map_in_file(path)` *before* saving and `restore_uids()` puts them all back *after* (header text + `ResourceUID`; the ext_resource uids belong to their targets and are already registered).

**A new save route must do ALL THREE — write through to the object that owns the path (#589, above), claim the path, AND preserve its uids — not just one.** **A reference the PRIOR file never had is filled from `ResourceUID` instead (#540):** replaying the old text cannot answer for a line this save is the first to write, and the editor would stamp it on its next save, which is churn — the same registry `test_resource_uid_references.gd` grades the line against, so the two cannot disagree. **An ext_resource uid follows the `path=`, never the line's `id=` ([#996](https://github.com/Phaazoid/Godoiosis/issues/996), 2026-09-16):** an id is a SLOT, and Godot's saver hands a repointed slot the same id, so replaying by id stamped terraces_intro's uid on the line that now named terraces_start — and Godot resolves a known uid BEFORE the path, so the beat kept playing the old file, then deleting it made the whole mission a parse error. The restore asks the target's own registry first and replays the prior uid for the SAME PATH only when the target cannot answer. Pinned by `tests/dev/test_dev_tool_save_uid.gd`; the repo-law guard is `tests/law/test_resource_uid_references.gd`.

## DirAccess.get_files() returns packed names in an export

**`DirAccess.get_files()` on `res://` returns PACKED names in an exported build, not source names** (found by the first export, 2026-08-04, #130 → [#141](https://github.com/Phaazoid/Godoiosis/issues/141)). A text resource comes back as `Foo.tres.remap` and an imported asset as `Mage.png.import` — the source `.png` is never in the pack at all, only `.godot/imported/*.ctex`. So **every scan that filters on a source extension matches nothing once exported**, and eleven of them do: the ten `.tres` catalogs (weapons, armor, jobs, runes, transmutations, elemental + terrain reactions, mods, attacks, scenarios) and `SpawnTool._build_sprite_catalog`'s `.png`. The symptom is not a crash, it is an **empty game** — Mission Select lists nothing and every catalog is silently empty; `SpawnTool` is the only one that turns it into a visible error (`keys()[-1]` off its empty dropdown).

**The suite is structurally blind to this** — it runs in the editor context, where every scan is correct, so nothing here is caught by a green run. **FIXED 2026-08-04 by `Classes/core/ResourceDir.gd`**, the one answer to "which resource files of this extension live in this folder?": it strips the packed suffix, de-duplicates (the editor holds *both* `Mage.png` and `Mage.png.import`) and sorts, so discovery is deterministic in every context. All eleven scans call it; **never re-derive a folder listing beside it.** `project.godot` briefly carried `export/convert_text_resources_to_binary=false` as a stopgap — that is **reverted, deliberately**: with the strip in place the default (binary, `.remap`) is both faster and the *harder* path, and leaving it off meant the `.remap` branch never executed in any real build, i.e. coverage that only looked like coverage. Note `project.godot` cannot carry an explanatory comment — Godot rewrites the file and strips them — which is why this note lives here. What the suite CAN pin is the normalization itself: `tests/core/test_resource_dir.gd` uses the real `.png`/`.png.import` pairing (54 of each) and is falsified against its own bug — a no-de-dup mutant returns 108.

**AND THE ARTIFACT ITSELF IS PINNED NOW ([#868](https://github.com/Phaazoid/Godoiosis/issues/868), 2026-09-09), because two more of this family shipped anyway:** `tests/export/test_export_smoke.gd` exports a real pack and RUNS it — once as its own main scene (a clean log catches an excluded runtime addon) and once through `Scenes/Smoke/smoke.tscn`, which loads every authored mission inside that pack. **The second shape is not redundant: measured, a boot that stops at the title screen exits 0 with a two-line log while the same broken pack reports 0 units**, because nothing on the title screen loads a mission. Needs no export templates (`--export-pack` writes resources, never an executable) and it MUST run standing outside this project — a Godot that finds `project.godot` in its working directory mounts the source tree as `res://` even with `--main-pack` given, which silently turns the whole suite into a source run.

**Two standing rules it does not replace: when a new ADDON lands, decide whether the RUNNING GAME needs it** (`exclude_filter` was correct on 2026-08-05 and silently wrong from 2026-08-18, when Dialogic became the project's one runtime autoload and the main scene stopped compiling in every export), **and never ask `FileAccess.file_exists` about a packed resource** — a pack holds `Foo.tres.remap` and no `Foo.tres`, so the file-level question answers NO for everything shipped; `ResourceLoader.exists` is the one that resolves it.

## A headless --import used to empty Dialogic's registries

**A headless `--import` used to EMPTY Dialogic's registries in `project.godot`, and the fix is a LOCAL PATCH to a VENDORED addon** ([#447](https://github.com/Phaazoid/Godoiosis/issues/447), 2026-08-21). `directories/dch_directory` and `dtl_directory` map a name to a `.dch`/`.dtl` file, and they are the one thing that turns the `torv:` starting a timeline line into Torv: wipe them and `event_text.get_or_create_character` fabricates a throwaway `DialogicCharacter`, so the prolog's speaker loses its display name (`"Torv"` → `"torv"`), its authored colour and its portrait, while every other test stays green.

**Measured 5 of 5 on fresh worktrees**, and one `git add -A` from shipping, since it is an ordinary tracked-file modification like any other. **The cause is ALIASING, and it took three wrong fixes to find — a Dictionary is a REFERENCE type, so `ProjectSettings.get_setting()` hands out the settings' OWN stored object.** `DialogicResourceUtil.get_directory` passed it straight to `update_directory`, whose prune (`ResourceLoader.exists()`, false for every `.dch`/`.dtl` mid-import because the format loaders arrive with the editor plugin) erased entries *inside ProjectSettings itself*; from there nobody had to save deliberately — the next `ProjectSettings.save()` by anyone wrote the emptied registries out. So **the patch is two clauses and each is useless alone** (measured, both ways): `get_directory` `.duplicate()`s what it reads, and `set_directory` skips its own explicit write when `DisplayServer.get_name() == "headless"`. Deliberately NOT a fix to the prune predicate, which is the obvious one and was tried first: it leaves the registry populated mid-import and **segfaults the cold import, 2 of 2**, which would red CI outright since the workflow imports exactly once. A real editor session is not headless and is untouched by any of it. A **Dialogic upgrade will silently drop this** — `.github/workflows/tests.yml`'s *Guard committed project settings* step is the canary, which warns, prints the diff and restores rather than failing, because a lost patch has nothing to do with whichever PR happens to hit it. Pinned by `tests/law/test_dialogic_registries.gd`, and the shape of that suite is the other finding worth carrying: it reads `project.godot` through `ConfigFile`, **never the live registry**, because the running process REPAIRS the registry as a side effect of using it — parsing a timeline re-registers the characters it names — so every case passed against a totally wiped file while it read `DialogicResourceUtil.get_directory()`. Its speaker case reads the event's own regex against its own raw line for the same reason: `character_identifier`'s getter answers from the resolved character, which derives its own name by finding its path in the live registry.

**A law that reads a store something else keeps repairing is checking the repair, not the store.**

## A legacy device id on an input binding is rewritten at load

**A LEGACY `device` ON AN INPUT BINDING IS REWRITTEN AT EVERY LOAD, so the committed bytes drift from what the engine actually runs (2026-08-27, found in passing while adding `[shader_globals]` for #552).** `device` is not decoration — it **GATES matching**: a binding at device 5 fires only for device-5 events, and `-1` (`DEVICE_ID_EMULATION`) is the wildcard that matches every device. Godot 4.6 had no dedicated ids for the keyboard or the mouse, so `InputEventKey.new().device` was literally **0**; 4.7 added **`DEVICE_ID_KEYBOARD = 16`** and **`DEVICE_ID_MOUSE = 32`** — they sit just above the joypad range, which is 0..15 — and ships a compat migration that rewrites a legacy 0 on load: **key 0 → 16, mouse 0 → 32, joypad 0 stays 0**, that being a real device. Measured across the whole value matrix, every other value passes through untouched, so it is a targeted shim rather than a coercion. This project carried six 4.6-era zeroes across the 4.7.1 upgrade (`91fc091`) — F1, F2 and the four arrow-key `cam_*` alternates — so **`ProjectSettings.save()` re-emitted them as 16 and every pass that touched settings re-dirtied `project.godot` with 12 lines of churn unrelated to whatever was being changed**, which is the acceptance half of the dirty-tree rule. Normalized by round-tripping through the writer itself, never by hand-editing a number, and verified idempotent (a second `save()` is byte-identical).

**Three things worth carrying.** (1) **It was never an export trap** — the migration runs on the exported `project.binary` path too, proved by authoring a real `ECFG`-magic binary holding raw `device:0` and loading it back as 16; do not file this beside `DirAccess.get_files()`. (2) **The suite was structurally blind to it** — every synthesized event under `tests/` is an `InputEventAction` or an `Input.action_press`, both device-agnostic, and `InputEventKey.new()` now defaults to 16 anyway, so no existing case could have gone red however the bindings drifted. (3) **`ConfigFile` is the only reader that sees the committed truth**, the migration being downstream of parsing: `ProjectSettings.get_setting` reported 16 while the bytes on disk said 0. `tests/law/test_input_device_ids.gd` therefore reads through `ConfigFile` for precisely the reason the Dialogic law above does, and its second case compares **committed against loaded** rather than blacklisting the one bad number, so the NEXT engine's migration reds and names itself instead of waiting to be noticed as save churn. Merely opening the editor does **not** rewrite the file (measured) — only an explicit `save()` does, which is why the tree stayed clean day to day and why a tooling pass is what finally surfaced it.

## OptionButton.add_item auto-selects the first entry

**`OptionButton.add_item` auto-selects the first entry** (`selected` goes -1 → 0 on the first add; `clear()` resets to -1). So a dropdown rebuild that re-selects by name **must `select(-1)` before its match loop**, or a name that no longer exists leaves the control silently pointing at whatever sorts first. Load-bearing wherever a dropdown selection is a write target rather than a filter — the dev tabs' Update button overwrites the file the dropdown names (#99; since 2026-08-11 Update is load-gated to the LOADED file and Delete confirms via `DevWidgets.confirm_delete`, capping that blast radius).

**A code-built full-screen Control needs `set_anchors_and_offsets_preset`, never `set_anchors_preset`** (measured 2026-08-04, #132). Anchors alone leave a freshly-`new()`ed Control added under the `ui_layer` CanvasLayer at **0x0**, so its dim never covers anything and its `CenterContainer` centres on the origin — the modal renders in the top-left corner. Measured: `PauseMenu`, `MissionEndBanner` and `CrisisPrompt` were all root=(0,0) with their panel at (0,0), against a 1152x640 viewport; `MissionSelectScreen` was the only one correct. It is **not** limited to Controls built during `_ready()` before the SubViewport has a size, which is what that file's own SIZING note claimed until this was measured. `ActionMenuController`'s root **is** full-rect since #467 and eats every click on purpose: angular selection has no "miss", so the surface that used to catch outside clicks is now the menu itself. ## Never put a ColorPicker in the dev-tools window

**NEVER put a `ColorPicker` or `ColorPickerButton` in the dev-tools window — it froze the whole window solid the first time one was opened** (found in play 2026-08-14, #212). It was the project's first ColorPicker anywhere, and sharp edge (4) below already warned that new subwindow UI inherits this window's quirks: `DevOverlay` is a real OS window that embeds its own subwindows while the project does not. **The exact mechanism is UNPROVEN** — the fix removes the widget rather than theorising — but note this is a ban on the **ColorPicker family, not on popups**: `OptionButton` popups are used heavily by every dev tab and are fine, so "popup = freeze" was the wrong first diagnosis. An inline `ColorPicker` Control is not the escape either; it carries its own menus for colour mode and picker shape. Pinned by a law in `tests/dev/test_moods_tool.gd` that walks the built panel for ColorPicker descendants.

## An instance override in a parent scene shadows the value

**AN INSTANCE OVERRIDE IN A PARENT SCENE SHADOWS THE VALUE EVERYONE EDITS, silently and forever ([#403](https://github.com/Phaazoid/Godoiosis/issues/403), 2026-08-21).** `Scenes/Main.tscn` instances `DevOverlay.tscn` and carried `size = Vector2i(900, 720)` on that instance, so [#382](https://github.com/Phaazoid/Godoiosis/issues/382)'s widening of the declared size (900x360 → 1160x520), made in the very commit that added the tool tree, **never reached a running build** — the dev-tools window stayed 900 wide while the file said otherwise, which is why the dev's own suggested fix ("open a little wider") had already been applied and changed nothing. Nothing is wrong at either end: the declaration is right, an override is a legal edit, and the only symptom is that editing the declaration does nothing.

**The general shape is Law #4 in a `.tscn`: an instance override is a second answer that WINS, and it is invisible from the file it overrides** — so a value with a scene default is worth asking *which* file the running game reads. The cheap general form of the guard is `tests/dev/test_dev_window_fit.gd`'s seam law, which instantiates the overlay by BOTH paths and requires them to agree. Its sibling law measures each page's widest ROW against the width the window leaves it, and deliberately **not** the page's ScrollContainer — the knob panels scroll horizontally since #403, so that container's minimum is near zero by design and an assertion pointed there could never fire. Two measured facts from the same ticket, each the opposite of the obvious guess: an `HSplitContainer` does **not** squeeze its first child to fit its second (the tree was never displaced; the overflow goes off the RIGHT edge), and **`clampi(v, lo, hi)` answers with the bound it tests LAST** — so with `hi < lo`, `show_beside`'s position clamp returned a NEGATIVE x and parked a too-wide window off the left of the screen, taking the tree with it. `DevOverlay.clamp_to_screen` is static and pure so a screen this machine does not have can still be asked about.

## A typed array's element arrives as a type id

**A TYPED ARRAY'S ELEMENT ARRIVES AS A TYPE ID, NOT A CLASS NAME — and a row that never draws has no symptom at all ([#804](https://github.com/Phaazoid/Godoiosis/issues/804), 2026-09-06).** `get_property_list()` reports an `Array[Vector2i]` with `hint_string` **`"6:"`** — `TYPE_VECTOR2I`'s enum value, then a colon, then the element's own hint — never `"Vector2i"`. #803's coordinate row compared against the class name, matched nothing, and **the attack stamp was unauthorable in the running Attack Editor for the whole of that ticket's life**, reachable only through Godot's own inspector. Nothing caught it: the tips law reads the property TABLE rather than the built controls, and the live-sync suite drives a scalar — so no case ever asked *did this row appear*. `DevWidgets._is_cell_array` parses the leading id now, and #804's grid cases are what ask the question.

**The general shape is the "test the wire" law pointed at a UI builder: a `match` arm that silently draws nothing looks identical to a field nobody edits**, so any new arm needs a case that finds its control, not just one that checks the data behind it.

## A keybinding lives in one OS window

**A KEYBINDING LIVES IN ONE OS WINDOW AND IS DEAD IN THE OTHER — the project has two (dev rule, 2026-08-16, after this bit for the fifth time).** `embed_subwindows` is off, so the game and `DevOverlay` are two real OS windows, and a key event reaches only the **focused** one. Every dev key was handled in `DevController._input`, which lives in the game subtree — so F1/F2/F3 (Shift+F3 since [#1050](https://github.com/Phaazoid/Godoiosis/issues/1050)) **and** Z/C did nothing whenever the dev-tools window had focus, which is exactly where authoring leaves you: pick a tile from the palette, press Z to turn the ramp rise, and nothing happens until you click the game window back. The dev found it in play, again: *"this is maybe the 5th time this issue has bit us."* **The fix is a FORWARD, never a second handler** — `DevController.handle_dev_key(event)` is the one public entry and `DevOverlay._input` calls it, so two windows are two input SOURCES for one set of bindings; it is idempotent by construction because only one window has focus, so exactly one caller fires per event.

**Cost of forwarding, and it is not optional:** a focused `LineEdit`/`TextEdit` in the dev window has to be excluded first, or typing a scenario name toggles the overlay and resets the board (a `SpinBox` edits through a `LineEdit`, so that covers the level and map-size fields too). The generalizable shape: **"which window is this handler in?" is a question every binding in a multi-window project must answer, and nothing in the code says it out loud** — a handler compiles, runs, and is simply never reached. Pinned by `test_the_rise_keys_work_from_the_dev_tools_window_too` (drives `DevOverlay._input`, so the forward is asserted rather than assumed) plus its typing-guard twin.

**Its sibling rule: a dev PAGE owns its own input (dev, 2026-08-23).** `DevOverlay.showing(page)` is the one answer to which page is up -- a FUNCTION, because Spawn and Character Editor share the Unit Authoring container, so either shows only when that container is the current top-level tab AND the current authoring one. `DevController.brush_armed()` / `spawn_armed()` combine it with the game state, and BOTH halves are load-bearing: Spawn is the overlay's BOOT page, so the page test alone made SPACE spawn during ordinary play. Both SPACE handlers (game.gd's and battle3d's) plus the 3D help line read the one predicate -- a readout that names a key must ask the same question the gate does, and it must join the help line's DIFF KEY too or the label goes stale (#308's shape).

## A tooltip on a code-built row goes on every control in it

**A tooltip on a code-built row must be set on EVERY control in it, not the row** (#212, 2026-08-15). A slider and a SpinBox have `mouse_filter` STOP, so Godot asks *them* for the tooltip and never walks up to the row's label — set it on the row alone and hovering the handle you are dragging shows nothing, which is exactly when the text is wanted. `DevWidgets.apply_tooltip` walks and sets all of them. **The GAME-SIDE half of that same rule has a second clause, and it fails the other way (2026-09-02, the settings page's descriptions moving to hover):** a plain **`Label` defaults to `MOUSE_FILTER_IGNORE`**, so the Viewport never PICKS it and its tooltip is dead however correct the text is — which on a page of mixed rows means half of them work and half do not, indistinguishably in a screenshot. `info_panel._badge` and its stat pair already set `mouse_filter = STOP` beside their own `tooltip_text` for exactly this; `SettingsScreen._tooltip_subtree` does it across a whole row's span.

**And `Control.get_tooltip(point)` CANNOT see that failure** — it answers with the control's own text (walking up to a parent only when its own is empty) and does no picking at all, so it returns the right string for a control Godot would never ask; a suite asserting through it passed with the `mouse_filter` line deleted, and the reachability had to be pinned as its own case on the filter itself. Picking is the Viewport's and has no public entry to drive. Related: a tooltip is a plain `Label` with no autowrap, so long text runs off the screen — `DevWidgets.wrap_tooltip` wraps in code rather than by hand-typed newlines, so the width cannot drift the next time the wording is edited. And the tooltip PANEL is opaque by project theme (#384): the engine default draws it at half-alpha black, unreadable over other text, so `Resources/UiTheme.tres` (wired as `gui/theme/custom`) overrides exactly `TooltipPanel/panel` -- that resource is the ONE seam for game-wide control chrome, so a future global style override is a line in it, not a per-control hunt.

**The REFLECTIVE editor had no tooltips at all until [#473](https://github.com/Phaazoid/Godoiosis/issues/473) (2026-08-22)** — `apply_tooltip`/`wrap_tooltip` existed and `build_resource_editor` simply never called them, so every field in the Attack and Item editors drew bare and `Max Range`/`Min Range` were two adjacent lookalike spinboxes with nothing to tell them apart (the dev typed into the wrong one and silently emptied the Carbine's reach). Text lives in an overridable **static `property_tips()`** beside the `@export` it describes, each class merging its parent's. **A function rather than a const table, and not by preference: GDScript refuses to let a subclass declare a member its parent already has**, so a `const PROPERTY_TIPS` on `AttackData` makes one on `WeaponAttackData` a *parse error* — a data table meant to be extended down an inheritance chain cannot be a const. The object row is tipped BEFORE its nested block is built, since `apply_tooltip` recurses and the other order paints the parent's text over every field inside.

**`property_tips()` GREW A FAMILY in [#825](https://github.com/Phaazoid/Godoiosis/issues/825) (2026-09-07), and the shape is the point rather than the tips**: a resource now also declares WHICH SECTION each field is drawn in (static `property_sections()`, merged down the chain the same way) and WHICH FIELDS DO NOT APPLY to it right now (instance `hidden_fields()`, since that answer is about its own values) -- so the Attack Editor's form is a walk over the resource's own declaration and `DevWidgets` stays generic, asking with `has_method` exactly as it does for `grid_fields()`. **That retired the two SKIP LISTS**, which is the reusable half: a field was drawn because nobody had excluded it, and is now drawn because something declares a home for it, so `tests/dev/test_attack_editor_layout.gd` can refuse a field in NO section -- the state #803 shipped and nothing noticed for a ticket. Relevance is applied by toggling `visible` off `changed`, never by rebuilding (#741), and the hide list is derived from what each rule READS rather than from what looks irrelevant -- `arc_clearance` survives the MELEE hide because the lane trace reads it whatever the vertical rule says.

**A SECTION hides with its rows since [#900](https://github.com/Phaazoid/Godoiosis/issues/900)** -- the per-attack look section is the first that can be empty, and a heading drawn over nothing is worse than an absent section. It is DERIVED in `_draw_sections` (a heading hides when every row that section drew is registered with the binder and hidden) rather than declared on the resource, so relevance is still stated once; a section holding a bespoke row that owns its own visibility -- the range block, which registers nothing -- keeps its title by construction.

## Scene for static, code for dynamic

UI rule: **scene for static, code for dynamic.** Fixed controls live in `.tscn`; data-shaped UI (editor fields, stat rows) is generated.

## A plain Panel lays out nothing

Plain `Panel`s report 0×0 minimum size for absolutely-positioned children inside containers. **A `Panel` with children is almost always this bug: it lays out nothing, so the child sits at its top-left at its own minimum size.** [#966](https://github.com/Phaazoid/Godoiosis/issues/966) was the second instance (the inspect panel's item slots: every label above centre and `(E)` past the border), and the #685 entry below, which describes the behaviour, did not stop it, so the rule is the call site: give a plate with children a `PanelContainer`, and keep `Panel.new()` for childless rectangles (`ModFittingCard`'s swatch, `ShapePlate`'s cells, `RuneDetailCard`'s cost bars).

## An HFlowContainer's minimum width is its widest child

**AN `HFlowContainer`'S MINIMUM WIDTH IS ITS WIDEST CHILD, AND A `Panel` IMPOSES NO CEILING — so one over-wide chip walks the whole column out of the dock (bug report, 2026-09-04, #685 follow-up).** Wrapping happens only *between* children, never inside one, so a flow container demands its widest child's full width from whatever line it sits in; and nothing between that line and an anchored `Panel` clips or constrains it, because minimum sizes propagate UPWARD and a plain `Panel` neither clips nor sizes its children. Measured: the action-queue dock is 216 design-px with a 46px slack on its row line, `"Into the void!"` is 72px, and the row's right edge landed **4px outside the panel** while `OuterScroll` and `SectionsBox` silently grew 200 → 232 to carry it.

**Two consequences for tests, and the second is the general one.** (1) **Pinning "several of these fit" says nothing about "one big one fits"** — a case that crowds a container by COUNT with short items is structurally blind to the widest-child rule. (2) **A BUDGET THAT EXPANDS TO FIT WHATEVER IT IS MEASURING IS NOT A BUDGET**: two guards here compared the row against its own section's live width — one of the things that grows — so neither could ever fail, and one passed at 224-in-230 while the row hung outside a 216px dock. Assert against a reference the `.tscn` ANCHORS (`BackgroundPanel`'s rect), never a sibling in the same layout pass. The same error produced a bad *measurement* first: "the row needs 209 and its section leaves 215" was the symptom read as the budget. `tests/ui/test_queue_badge_widths.gd` is the law that resulted — it prices every authored badge against the anchored dock with the line's widest hp readout present, because character counts lie in a proportional font (`Thermal` overflows where `Chilled` fits).

## A clip_text Label declares a minimum width of one

**...AND ITS SIBLING, POINTING THE OTHER WAY: A `clip_text` LABEL DECLARES A MINIMUM WIDTH OF **ONE**, so in a row-laying container it draws as a sliver of its first glyph unless something asks on its behalf (four bites: #788, #944, #989, [#1024](https://github.com/Phaazoid/Godoiosis/issues/1024)).** That is what the flag MEANS, and an `HBoxContainer`/`HFlowContainer` gives a child exactly its minimum unless the child's flags carry `SIZE_EXPAND` — so the fix is `SIZE_EXPAND`, or `UiText.fit_width(label, floor, ceiling)`, which measures the label's own text off the font it will actually draw with and clamps.

**The bounds stay at the caller**: what a surface can spare is that surface's fact, and a shared helper's constant is a fact about whichever caller it was measured at. A VBox / MarginContainer / PanelContainer stretches a child to its own width instead, so clipping THERE is the design, not this bug. The symptom is silent and looks like missing text rather than a layout fault. Sweep it with `tests/support/label_fit.gd` — `unasked_labels` is the structural half (fixture-free) and `draws_in_full` the content half. Full rule + all four bites: `docs/design/missions.md`.

## Unit.has_squad() means has squadmates

`Unit.has_squad()` means "has squad*mates*" (members > 1). Every unit always belongs to exactly one managed squad, even solo.

## A Packed*Array is a value type

**A `Packed*Array` IS A VALUE TYPE, AND THE ASSERTION YOU WOULD CATCH IT WITH CANNOT SEE IT (2026-08-28, #629 — bit twice in one session).** `Array` and `Dictionary` are reference types; `PackedStringArray`/`PackedInt32Array` are **values**. So `(store["errors"] as PackedStringArray).append(x)` appends to a **copy** and the store never changes — silently, with no error and no warning. It cost a generator that read every duration correctly and reported none of them, and then, after the same trap was fixed once, an error channel that recorded nothing. **The second half is what makes it dangerous: `assert_array()` on a Packed*Array reached through a Dictionary reports it EMPTY whatever it holds**, so `is_empty()` on one passes *vacuously and can never fail* — which is exactly the assertion anyone writes to check the channel. That is how a case that deliberately corrupts input went GREEN against code that was correctly refusing it.

**Use `Array[String]` for anything a Dictionary hands out for appending** (the reference semantics are the point, not the typing), and **assert on `.size()` of a TYPED local**, never `assert_array()` on the Variant chain. Indexing that chain (`store["errors"][0]`) fails at runtime too, for the same reason `game.*` reads need explicit locals.

## get_theme_stylebox() answers for a control that overrides nothing

**`get_theme_stylebox()` ANSWERS FOR A CONTROL THAT OVERRIDES NOTHING, so "does it have a box?" is an assertion that cannot fail (2026-09-18, #1022).** The lookup is override -> theme -> engine default, and the engine's own Button `normal` IS a real `StyleBoxFlat` -- which is *precisely* the chrome that disappears on this project's panels (EXECUTE_BG's note). A case pinning that the detail chip "paints its own box" read the theme's and passed against a mutant that deleted the override outright. **Ask `has_theme_stylebox_override(name)` when the point is that the control brings its OWN**, and keep the value read for what it looks like; the same applies to `get_theme_color`, which is why `test_pre_mission_contrast` can see a label with no override at all. Sibling of the `Packed*Array` entry above: both are assertions whose shape guarantees a pass.

## Sprite3D.offset's two axes do not share a sign

**`Sprite3D.offset`'s TWO AXES DO NOT SHARE A SIGN, `flip_h` MOVES NO GEOMETRY, AND THE PROBE YOU WOULD CHECK THAT WITH ANSWERS ZERO (2026-08-28, #634).** The origin sits at column `w/2 - offset.x` from the texture's left but row `h/2 + offset.y` from its top — guess one sign from the other and the art lands mirrored about its own pivot. `flip_h` leaves the QUAD exactly where it is and mirrors only the UVs, so any horizontal offset correction must invert with it by hand; an engine that mirrored the quad instead would make that line double-negate. **And the trap that nearly hid both: `get_aabb()` on a Sprite3D returns `(0,0,0)` until the node is IN THE TREE** — headless included, which is where you would probe it. A first pass compared flip on to flip off, got zero from each, and reported "unchanged" as if that were the answer.

**A probe that returns the same value for both branches of a fork has answered neither** — print the raw numbers and check they are not all zero before reading a verdict off them.

## set_process(false) in _init does not survive entering the tree

**`set_process(false)` IN `_init` DOES NOT SURVIVE ENTERING THE TREE, and a Sprite3D's AABB LIES ABOUT WHETHER IT DRAWS ([#747](https://github.com/Phaazoid/Godoiosis/issues/747), 2026-09-05).** A node built with `.new()` and added to a live tree ticks `_process` **exactly once** whatever `_init` said, then the flag takes. `UnitSprite3D._process`'s "the animation ran off the end" branch therefore fired on a node that had never animated, calling `_apply_state_texture()` — which for a POOLED planning ghost (built by `.new()`, so its sprite triple is empty) answers **null**. The ghost went blank on the frame `UnitMirror.set_ghosts` built it, in the diorama only, and `OverlayMirror._ghost_sync`'s whole-array cache meant nothing ever pushed again — so it stayed blank until the move was cancelled and requeued, which is why the FIRST move of a launch was 100% reproducible and a later one needed the pool to grow past its high-water mark. Two rules: **`_process` hands `texture` back only if it BORROWED it** (#629's gate, on the release side), and the pool writes through `show_still()` rather than around the one door, so the other five `_apply_state_texture` callers are harmless on a ghost too.

**The diagnostic lesson is which OBSERVABLE to trust**: `visible` stays true (so `ghost_count()` and all three existing ghost cases pass with the bug present), and `get_aabb()` fills in from the texture's own size a frame later even on a sprite with **no render base at all** — it reported `(1,1,1)` on a ghost drawing nothing, which sent one round of diagnosis at the wrong mechanism. `VisualInstance3D.get_base()` is the read that actually answers *is this drawn*; `RenderingServer.instance_get_base()` does not exist in 4.7.

## The midpoint of two adjacent cell centres sits on their boundary

**THE MIDPOINT OF TWO ADJACENT CELL CENTRES SITS EXACTLY ON THEIR SHARED BOUNDARY, AND `floori` RESOLVES A BOUNDARY TO THE `+` SIDE — so a symmetric-looking operation is DIRECTION-DEPENDENT (2026-08-29, #602 round 2).** `map_to_local(a).lerp(map_to_local(b), 0.5)` for adjacent `a`,`b` is not "between two cells", it is *on the line*, and `floori(v / TILE_SIZE)` then names cell `b` for a step north/east and cell `a` for one south/west. `MovementComponent` parked a falling body there and `UnitMirror` asked which cell it was over: the sprite popped back to the LAUNCH surface for a shove north or west and behaved correctly for one south or east — wrong half the time, invisible the other half, and it survived a suite that only ever shoved one way.

**Never resolve a cell from a point you deliberately placed on a cell edge**; either finish the step into the destination (what #602 did) or carry the cell you already know — `MovementComponent.cell` is assigned to the destination before the legs run. The general form: a *tie* in a floor/round is a decision, and an operation that lands on ties by construction has made it for you.

## A version-gated poll: a continuous animation announces itself on discrete events

**A VERSION-GATED POLL MEANS A CONTINUOUS ANIMATION MUST ANNOUNCE ITSELF ON DISCRETE EVENTS, NEVER PER FRAME (2026-08-28, #521 slice B).** `OverlayMirror` rebuilds every standing prop, flame and marker whenever `BoardSpace.staging_version` moves — that gate is what makes a tear-out re-seat what stands on it (#308's shape). So an animation that moves those cells CONTINUOUSLY cannot bump the version to be drawn: it would rebuild the whole board every frame. The answer is to find the discrete events inside the motion — a tile LANDING, not a tile moving — and bump only there. **Generalizable: when a new animation crosses a diff-keyed store, the question is not "how do I invalidate" but "what are the discrete moments inside this motion".** **AMENDED by [#893](https://github.com/Phaazoid/Godoiosis/issues/893) (2026-09-18), and the amendment is the more reusable half: this entry used to end "letting the thing fly undressed in between", which shipped a burning tile's flame and a cell's tall grass hanging in mid-air while their ground climbed — reported twice.** The version rule is right and unchanged; what was wrong is that it answered a question nobody had asked, because **REBUILDING and PLACING are different prices and the gate only ever forbade the expensive one.** `BoardSpace.staged_offset` was live on every frame of the flight all along; `BoardMirror.reseat_cell` is a `position` write that asks it, touches no version and drops nothing, called from the same `_sync_flight_maps` loop that already moves the ground — so one line answers *where is this column right now* for the column and its contents together. So the question above has a second half: **once you know the discrete moments, ask what still has to be RE-READ between them.** (One line was enough only because #992 had already made every standing node's parts local deltas under a root carrying the whole of `surface_point`.)

## A channel polled below a gate needs a door on every path that ends the gate

**A CHANNEL POLLED BELOW A GATE NEEDS A DOOR ON EVERY PATH THAT ENDS THE GATE — AND THE OBVIOUS DOOR CAN EARLY-RETURN (2026-08-29, #602).** The cliff follow publishes its depth inside `battle3d._mirror_camera`'s playback-locked block, and closes it on `CameraRig3D.restore_view` — correct for an ordinary pass. A BOARD SWAP releases the same lock and never reaches it: `frame()` calls `drop_stashed_view()` first, so `restore_view` early-returns on `_view_borrowed`, and with nothing left polling, the rig sat under the *new* board for ever. Two doors for two meanings — a release CLIMBS out (the player was watching), a swap CUTS (the pit does not exist any more).

**Enumerate the paths that clear the gate, not the ones that clear the channel**; and note the guard door was not silent-broken but *conditional*, which no grep for the reset call would have shown. Found by `SharedBoard`'s leak fingerprint, which reds when the reset door cannot reach something — a diff it cannot undo IS a channel with no door.

## A latch makes every choice behind it unobservable

**A LATCH MAKES EVERY CHOICE BEHIND IT UNOBSERVABLE — so a case claiming to pin one of those choices is vacuous, and only a mutant will say so (2026-08-29, #602 round 3; TWO survived in a row).** The tear-out solves the diorama's camera height ONCE and holds it. Two design decisions sit behind that latch — reading the ground under each unit rather than their stand height, and the latch itself — and the comment claimed each was what kept a fall from being counted twice. Deleting the latch: **green**, because the height is read off the ground and a falling body's ground does not move. Swapping the ground read for a stand-height read: **also green**, because the latch settles the height before anything is falling, so at the only moment either is evaluated the two agree exactly.

**The generalizable form: ask what STATE EXISTS at the instant the latched value is computed — anything that only differs later is invisible to every test, however carefully the case is written.** Both survivors were fixed the same way: name the property the latch really has (a body THROWN onto lower ground must not walk the shot down after it), test that, and say in the comment that the other choice is kept for what it MEANS rather than for a behaviour it protects. **Do not delete an unobservable-but-correct choice to make the mutants tidy** — declare it.

## One spelling can still be two bases

**ONE SPELLING CAN STILL BE TWO BASES (2026-08-29, #602 round 4).** Round 2 anchored the void death's brick burst by re-deriving the camera's stop from the body's own fall through the SAME function the shot read (`Pacing.followed_fall`) — one spelling, per #472's law, so it could not drift. It was wrong anyway: the shot hangs off the STAGE's height and the body off the VOID's lip, so a shared formula fed from two different bases put the cubes five units under the frame on any fight staged above a pit, while agreeing with itself perfectly — and being base-relative, NO slider setting could close it, which is what the dev's fruitless tuning session was. Sharing the arithmetic is necessary, not sufficient: **check what each reader measures FROM, and when the bases can differ, pass the composed FACT (a callable answering "where is the frame's bottom") rather than the recipe.** Its two companions from the same round: a knob whose store is re-pushed per frame is only tunable at the store (`HealthBlockDebris.lifetime` is overwritten from `block_lifetime` every frame — the born-dead-slider guard read from the other side), and a repealed ruling's arithmetic may stand on a reason the ruling never named (the dolly floor's contribution-cap survived the wheel carve-out it was written for; deleting them together went red inside the round).

## A post-phase assertion is worthless when a later phase tidies up

**A POST-PHASE ASSERTION IS WORTHLESS WHEN A LATER PHASE TIDIES UP REGARDLESS (2026-08-28, #521 slice B — found by a mutant, after the identical trap had just been fixed one case over).** A case asserting "nothing is left in the air after the pass" passed with the code that guaranteed it DELETED, because the exit's `clear_staging()` puts the board down either way. The property actually at risk was one phase earlier — the board the ENTRY hands the fight. **Ask which phase owns the property, and drive that phase alone**; slice A already wrote this down as "test the decision, not the aftermath" and it still cost two cases in one session.

## Godot ternary and typed dictionaries

Godot ternary exists (`x if cond else y`); typed dictionaries (`Dictionary[String, int]`) are used throughout — keep chains typed end-to-end.

## Retyping a persisted @export field is a data migration

**Retyping a persisted `@export` field from String to an enum is a *data* migration, not just a code change.** Godot silently *drops* type-mismatched values when loading a `.tres` (a saved `Dictionary[String, int]` won't populate a `Dictionary[Stats.Stat, int]` — it loads empty) and *strips* them on the next resave. After retyping such a field (stat-dict keys, `weapon_type`, `scaling_stat`), rewrite every saved `.tres` to the enum form — enums serialize as plain ints (`base_stats = Dictionary[int, int]({0: 20, …})`, `weapon_type = 1`). Bit 2026-06-19 (#7 fallout): every unit loaded with 0 stats → LDR 0 → nobody could move; the only intact copy of the string data was git HEAD, since the migration commit never touched the `.tres`. Migrate from HEAD, not the working tree (Godot may have already stripped it).

## Dev tools are a separate OS window; the game is in a SubViewport

**Dev tools = separate OS window; the game is wrapped in a SubViewport (June 2026 refactor).** Scene tree (**`Battle3D.tscn` is the main scene as of 2026-08-14 — the game boots into the 3D view, and `Main.tscn` is *hosted* by it rather than launched directly**; dev ruling: *"Always boot into 3D, allow the swap into 2D using the button we already have"* — F4. Everything below is unchanged, it is just mounted one level deeper, at `/root/Battle3D/Main`. **Consequence already paid once: `game.gd` resolved the dev overlay by the ABSOLUTE path `/root/Main/DevOverlay`, which silently returned null under the new mount and made F1 dead in the 3D build. It is relative now (`../../../DevOverlay`) — do not put an absolute `/root/...` path anywhere in the game subtree.**): `Main` (Node) → `GameContainer` (SubViewportContainer, Stretch on, texture_filter Nearest) → `GameView` (SubViewport, embed ON) → `Game` (game.tscn instance); `DevOverlay` (a `Window`, embed ON) is a sibling of `GameContainer` under `Main`. Project `embed_subwindows` = **OFF** → `DevOverlay` is a real OS window (second-monitor capable); `GameView` embeds so the game's own popups (action menu) stay in-game. Cross-boundary refs: `game.gd` → `get_node("/root/Main/DevOverlay")`; `dev_overlay.gd` → `get_node("../GameContainer/GameView/Game")` (+ `…/Game/ScenarioManager`). Gotchas this created — all already handled, **do not undo**: (1) SubViewports default to LINEAR filtering; `game._ready` sets the viewport default to Nearest via `RenderingServer.viewport_set_default_canvas_item_texture_filter(get_viewport().get_viewport_rid(), RenderingServer.CANVAS_ITEM_TEXTURE_FILTER_NEAREST)` — per-node `texture_filter` only patches part of the tree (the chain breaks at any `CanvasLayer` / non-CanvasItem ancestor). (2) Embedded popups don't auto-dismiss on outside-click (input is forwarded through the container), which is why the action menu has been Control-based since #26 and must not go back to a `Popup`. (3) **The UI lays out in a fixed 1280x720 DESIGN SPACE, stretched to the window (#659, 2026-09-02)** — `Classes/ui/GameSurface.gd`, a script on `GameContainer`, gives `GameView` a `size_2d_override` + `size_2d_override_stretch` each time the container resizes. So an authored pixel size is a design-space unit, not a screen pixel: it is the same fraction of the window at every resolution, and the factor is never below 1 (the container's `custom_minimum_size` floors it, so a smaller window clips as it always did rather than shrinking the UI). The design resolution has ONE source, that same `custom_minimum_size`, which `battle3d.gd` also reads for the PiP. Consequences: `get_viewport_rect()` inside the game is the DESIGN space while `GameView.size` is still physical (do not compare them); `Control.get_screen_transform()` does NOT compose the content scale for a Control under a `CanvasLayer` — use `get_final_transform() * get_global_transform_with_canvas()`, the chain a click traverses; and `battle3d.gd` needs no part of this, since all three of its views work by setting the container's anchors or size.

**The no-hardcoded-pixel-POSITIONS rule stands unchanged** (use viewport-relative; the hover panel's old `BOTTOM_LEFT_POS=410` broke on a viewport-height change). **Dialogic's dialog box scales too since #687** — `ScenarioDirector._start` hands `game.get_viewport()` to `Dialogic.Styles.load_style` before every timeline, because `end_timeline` FREES the layout and the next start rebuilds it, so there is no one-time place to declare a parent (its own default is `dialogic.get_parent()`, the tree root). It lands as a SIBLING of `Game` inside `GameView`, so the freeze that disables the *`Game` node* cannot reach it, and the layout is a `CanvasLayer` — `UiLayers.LAYER_DIALOGUE`, over the HUD and under the wheel and every card since [#1034](https://github.com/Phaazoid/Godoiosis/issues/1034), which also gave the freeze its reach by having `ModalLock` pause Dialogic (see the `ModalLock` and `UiLayers` bullets). Do not "simplify" it to `game.ui_layer` — a z_index there would not order it against anything on another layer. (4) Any new subwindow UI (PopupMenu/dialogs) inherits these quirks — prefer Control-based menus.
