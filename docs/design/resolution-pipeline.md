> **Amendment 2026-07-30 — healing is a short-circuit, not a sixth stage.** An attack authored with `AttackData.heals` reinterprets the SAME base-damage number (E1) as HP restored instead of removed, and `_resolve_one` returns right after computing it — before elemental (stage 3), Will/death (stage 4), or knockback ever run. Mutual exclusivity (an attack is EITHER damage OR heal) is authored, not runtime-guarded — the resolver just never has a code path where both branches run for one action. Scope, deliberately: no overheal, no lifecycle interaction (a downed unit's HP can move but its `lifecycle_state` doesn't — reviving is `Unit.revive()`'s separate, declared door), no AI scoring yet (`AITactics`' candidate scorer reads `resolved.damage`, so it cannot see a heal as good — the standing AI-catchup gap, #117). Tests: `tests/law/test_healing.gd`.

## Why this doc exists

Three systems are the **same operation** wearing different hats:

| system | status | derives… |
|---|---|---|
| **Reactions** (counters, and reactive heals since #148) | built (`SquadManager.calculate_reactions_for_squad`) | who reacts to whom, and with which kind, from the plan |
| **Elemental reactions** | built, Phase 2 ([elemental-system.md](elemental-system.md), E1–E8) | reacted damage + state changes, from the plan |
| **Will / death outcomes** | built, Phase 3 (#33, #56, #57 — [will-and-death.md](will-and-death.md)) | downed / maim / overkill / Crisis, from the plan |

All three: a consequence **derived from the ordered plan at queue time → surfaced in the preview → replayed at execution.** Counters already work exactly this way; the other two are specified to. They are not merely *similar* — they are **coupled and ordered** (see "The forced ordering"). If each is built as a private subsystem, you get the plan walked three times, three preview paths that drift apart, and elemental-damage and Will-lethality that disagree about ordering. **One pipeline prevents all of that.** Decide its shape now; Phase 2 builds it, Phase 3 slots into it.

## The pattern is already in the codebase

The counter implementation is the working prototype of the whole idea:

- `SquadManager.calculate_reactions_for_squad()` walks `action_queue`, derives `CounterAttackAction`s, and **returns** them — never stores them in the queue.
- `SquadManager.get_display_entries_for_squad()` calls it so the **preview** shows the derived counters.
- Execution instantiates counters fresh from the plan.

That's *derive → show → replay*. The pipeline generalizes this one proven move so elemental and Will reuse it instead of reinventing it.

## The pipeline

**One pure pass over the ordered plan**, in the execution order squad-system.md already promises (**moves → attacks → counters**), producing a **`ResolvedPlan`**: for every action, its resolved damage, its state-deltas, and its lifecycle outcome. **Preview and execution both consume the `ResolvedPlan`** — execution stops computing and just plays it back.

Conceptual stages, applied per attack in queued order while a **hypothetical copy of unit state** is threaded forward:

1. **Position** — projected via `Unit.get_projected_destination()` (the leader's planned cell, etc.), which since #105 is one call of the shared `Unit.projected_cell(unit, actions, require_valid, use_knockback)` — the same derivation plan validation uses, with the two axes it needs answered differently stated as arguments. Its inverse, `Unit.projected_unit_at(units, cell)`, is what `BoardContext.projected_unit_at_cell` (and therefore victim gathering) asks.
2. **Base damage** — originally the math inside `AttackAction.create()` (`weapon.power + scaling_stat`, or `STR` unarmed); per R8 this moved into the pipeline (elemental E1) and has moved again since — `PlanResolver._source_base_damage` now reads whichever `AttackData` the order stamped (`AttackAction.fired_attack`: a carving, a specific `WeaponAttackData`, or null = the weapon's main), scaled by `scaling_blend` + active mods (#59, #72), or bare `STR` unarmed.
3. **Elemental** — read the target's hypothetical states, match an `ElementalReaction`, modify damage, write state add/remove. (Phase 2.)
4. **Will / death** — read the *now-final* damage, pick the rung: downed / maim / overkill-kill / Crisis. (Phase 3.)
5. **Counters** — counter *existence* is derived from the attack plan as `calculate_reactions_for_squad` does today, **but read from the threaded hypothetical** (projected positions + liveness), not live state; each counter is itself an attack and **re-enters stages 2–4** (so a counter can complete a combo — elemental E7 — and can down/kill). A counter-er killed earlier in the pass is not derived (liveness is always-true until Phase 3's Will stage).

## The forced ordering (the insight neither downstream doc states)

Elemental resolution **produces the final damage number**, and the Will ladder **judges "fatal?" against that number.** Therefore, per attack, the order is mandatory:

```
base damage  →  elemental modifies it  →  Will reads the result
```

A `SHOCK × WET` combo that boosts damage can push a hit from *"this downs them"* to *"this overkills — dead."* That coupling is real game behavior and it can only be correct if both live in **one ordered pass**. This is the single most important reason the pipeline is one thing, not three.

## Contract — R-invariants

Numbered for test coverage, like the squad spec's I/C and elemental's E. Violating any is a bug.

- **R1. One pass, one `ResolvedPlan`.** No system privately re-walks the plan to derive its own consequences.
- **R2. Pure & deterministic (Law #1).** Reads a snapshot of board/unit state, returns results, mutates **no** live state, contains **no RNG**.
- **R3. Preview and execution consume the *same* `ResolvedPlan` (Law #2).** Execution applies resolved damage / state-deltas / lifecycle outcomes and derives nothing new mid-combat.
- **R4. Hypothetical state is threaded forward — and it carries HP, not just element states.** The threaded hypothetical models, per unit, `{projected position, element states, HP, (Will — Phase 3)}`. An earlier action's deltas (HP from damage, state add/remove) are visible to later actions *within the same pass*; live unit state changes only at execution, action by action. **The carrier is built Will-ready from day one:** Phase 2 reads/writes only element states + HP-from-damage, but the Will field exists so Phase 3 slots in without re-threading. This is the keystone's whole point — a `SHOCK×WET` hit and the Will ladder read the *same* evolving HP.
- **R5. Derived, never stored.** Like counters: recomputed from the plan on every change, never persisted as player orders. The player authors *orders only*; damage, reactions, and Will-outcomes fall out of resolution.
- **R6. Order is the player's lever.** Attacks resolve sequentially in queued order; reordering the combo changes the outcome. That *is* the skill expression — protect it. **Extended to MOVES 2026-08-20 ([#412](https://github.com/Phaazoid/Godoiosis/issues/412), standing-reactions grill):** move orders resolve in queued order too, with drag-reorder as the lever — the queue is the clock for mid-move events (an overwatch trigger is the first customer, [standing-reactions.md](standing-reactions.md)). Simultaneity survives as presentation and as validation: destination conflicts and formation rotations stay whole-plan, order-independent questions.
- **R7. Stage order is fixed:** position → base damage → elemental → Will/death → (counters re-enter base→elemental→Will). **Damage is final before the Will stage reads it.** **Counter *derivation* consumes the threaded hypothetical** (projected positions + liveness), not live state: a counter-er downed/killed earlier in the pass cannot counter. Phase 2 builds the counter stage reading the hypothetical with a liveness flag that is **always-true until the Will stage exists**; Phase 3 only flips it on.
- **R8. One outcome model.** Every stage annotates the *same* `ResolvedOutcome` per action (damage delta, state changes, lifecycle result); one preview widget renders it ("−12", "Electrocuted!", "Downs them", "No Will → lethal"). No per-system preview path. **The `ResolvedOutcome` is the single source of truth for an action's damage** — `AttackAction` stops *computing* damage (E1), and `execute()` consumes the `ResolvedPlan` rather than a frozen `AttackAction.damage`. (Remove the old field or keep it as a populated mirror — a build-time call; that it no longer *originates* the number is locked.)
- **R9. Plans do NOT break. (Added 2026-07-05 as the BREAK doctrine; REPEALED AND INVERTED 2026-08-09, dev + co-dev, out of [#124](https://github.com/Phaazoid/Godoiosis/issues/124)/[#155](https://github.com/Phaazoid/Godoiosis/issues/155).)** The `ResolvedPlan` is a **guarantee, not a prediction**: execution replays it exactly, R3 stands unamended (execution derives nothing new, ever), and any mechanism that would make execution diverge from the preview is **redesigned until the resolver can predict it, or it doesn't ship**. Where the old doctrine's three divergence classes went: **choice** — eliminated at the source (player Crisis, the only live instance, becomes a deterministic equipped ability, [#158](https://github.com/Phaazoid/Godoiosis/issues/158); reaction/guard abilities were already standing policies, jobs.md chassis rule 3 — now exception-free); **cascade** — was never a divergence (full-information self-sabotage is predicted and previewed at plan time, Law #2 — R1–R8 already deliver it); **knowledge** — deliberately unresolved (hidden information does not exist yet; when fog arrives it must be designed against this rule, not the rule bent to fit it).

### The BREAK doctrine — REPEALED 2026-08-09 (was: R9 expanded, 2026-07-05)

The dev's line repealing it, with the co-dev, out of the [#124](https://github.com/Phaazoid/Godoiosis/issues/124)/[#155](https://github.com/Phaazoid/Godoiosis/issues/155) discussion: *commit harder to the commitment that the action queue never lies.* The 2026-07-14 ratification had adopted BREAK **try-it-and-see** — "whether it stays is decided at the table, not on paper" — and it did not survive to the table: [#155](https://github.com/Phaazoid/Godoiosis/issues/155) put the three answers the project held for "a precondition died mid-pass" side by side, and the resolution was that **the situation itself must not exist**. Nothing of the doctrine was ever built (no banner, no BREAK markers, no re-entry), so the repeal is docs-and-doctrine only, with zero code to unwind. Where each piece went:

- **Known cascades were never BREAKs.** Full-information self-sabotage (attack triggers a reaction → leader shoved → later orders orphan) is predicted and previewed at plan time — that half was always just Law #2 riding R1–R8, and it survives untouched. Planning your own ruin stays legal; doing it *unknowingly* stays forbidden.
- **Choice-points are eliminated at the source.** Player Crisis — the only live instance — becomes a deterministic **equipped ability** ([#158](https://github.com/Phaazoid/Godoiosis/issues/158)): equipped + will gate passed → always fires, previewed like any other rung, no mid-execution question. Future reaction/guard abilities were already bound to "standing policies, never prompts" ([jobs.md](jobs.md) chassis rule 3); that rule now has **no exception**.
- **Fog is the one edge left open, on purpose.** Hidden information does not exist in the game yet; when it arrives it must be designed to honor the absolute rule rather than the rule bending to it. The old NB stays worth keeping for that future design: a resolver facing hidden state must distinguish *planner-visible* state from *true* state — but what execution does with the difference is that design's question, and it may not answer "silently diverge."
- **The banner, the queue's BREAK markers, and the Play API's `answer(choice_id, accept)` verb are dead** — none were built ([visual-clarity.md](visual-clarity.md) / [play-api.md](../play-api.md) annotated). The headless bridge never needs mid-execution input.
- **[#124](https://github.com/Phaazoid/Godoiosis/issues/124) (same-pass rescue) is the strengthened rule's first positive customer**: instead of an order whose precondition might die, the resolver predicts the down *and* the pickup and propagates both — the queue previews the whole sequence as fact.

R1–R8 **subsume the elemental E-invariants** (E1–E8 are this contract scoped to the elemental stage) and give Will a defined plug-in point rather than a parallel mechanism.

**Deferred (not locked — revisit when relevant):** volley / simultaneous-hit ordering *within* one AoE. v1 volleys hit distinct targets with separate state stores, so sibling pass-order is moot now; revisit when tile states or multi-hit-same-target arrive (do volley siblings resolve sequentially against threaded state, or all against one pre-volley snapshot?). **Narrowed 2026-08-20: Guard's substitution ([#414](https://github.com/Phaazoid/Godoiosis/issues/414)) is the first multi-hit-same-target, and its ruling is scoped to standing-reaction LIVENESS only — within a single attack's volley, a reaction's liveness (a Guard's range/lifecycle check) reads at the volley's START, then the damage packets thread HP as usual ([standing-reactions.md](standing-reactions.md) → *One blast, one moment*). Chosen so an outcome can never hinge on volley gather order — an order the player neither authors nor sees, against R6's own doctrine. Tile-state threading within a volley stays deferred.**

**A reaction stage AFTER counters — HALF BUILT, half still deferred (captured 2026-07-31; the derived half shipped as [#148](https://github.com/Phaazoid/Godoiosis/issues/148), 2026-08-07).** Two ideas wanted the same thing: a healer who can act *after* the counter phase (so the heal covers the damage the counter just did), and a defending squad's healer who reacts to being attacked at all. Today a queued heal is an ordinary `AttackAction` carrying `AttackData.heals`, so it resolves in the **attack** stage — structurally always too early for either. Nothing about R7 forbids a stage past counters: the stage order it fixes is *within a hit* (position → base damage → elemental → Will/death), and counters "re-entering stages 2–4" is precedent for a later phase re-entering them too.

> **The DERIVED half needed no new stage, and that is the finding worth keeping.** A defending squad's reactive heal is emitted *after* the damaging reactions into the same `plan.counters` list, and `resolve_counters` walks that list in order — so it already lands after the only damage the defending squad can take in that phase (a counter's own `hits_allies` splash). Everything the stage would have owed was owed anyway and is met where it stands: derived and previewed like any counter (**R3/R5**), deterministic (no prompt — [jobs.md](jobs.md) chassis rule 3, R9), and threaded through the **shared hypothetical** (**R4**) — the last one twice over, because #148's target *choice* also reads the hypo (`PlanResolver.projected_hp`/`projected_lifecycle`) rather than the live board, or the healer would patch whoever was hurt before this pass's swing. Rules: [squad-system.md](squad-system.md) → *Reactive healing*, C8–C10.
>
> **The PLAYER-AUTHORED half still owes the real stage**, and is the whole reason it stays on the books: it is a *stored order that defers past counters*, and `plan.counters` is derived-only (Law #2 / R5), so it cannot ride the list above. Building the stage costs the same then as it would have now — which is exactly why #148 did not pay for it early (dev, 2026-08-07).
>
> **It has TWO more prospective customers as of 2026-08-19, and they push past what "a stage" means** (scratchpad: **Defend** and **Overwatch**, [weapons.md](weapons.md)). Both are stored player orders that defer — but where the healer's case defers *within one pass* (past the counter stage, still inside the plan that authored it), these two defer **across the phase boundary into the enemy's turn**: Defend's grant lapses at the end of the enemy phase, and Overwatch fires when an enemy moves, which happens in a pass the authoring player does not own. **That is a different thing from a late stage and should not be filed as the same work.** A late stage is one more step in a pass; these are *standing effects that outlive the pass that created them* and are consumed — or expire — inside somebody else's. Nothing in R1–R9 forbids it (R5's "derived, never stored" governs *consequences*, and a Defend grant is an authored order, not a derived one), but three questions land the moment either is designed and none are answered today: **where does a standing effect live** between passes (it is battle-scoped `Unit` state by the persistence seam's own test, so it saves like the Crisis flags do); **how does the enemy phase's own `ResolvedPlan` see it** without the resolver privately re-walking anything (R1); and **what previews it to the player**, given that the promise is a triggered shot showing in the queue *before* the enemy has planned anything. The third is the sharp one and is a Law #2 question, not a plumbing question. **The design pass happened 2026-08-20 ([standing-reactions.md](standing-reactions.md), [#413](https://github.com/Phaazoid/Godoiosis/issues/413)/[#414](https://github.com/Phaazoid/Godoiosis/issues/414)), and the sharp question is answered: the triggered shot annotates the crossing MOVE's own queue row the moment such a move is queued — the player's while planning, the AI's in its drawn plan — and the standing footprint is always drawn on the board, so nothing previews before a crossing move exists to hang it on. The first question keeps the answer this note already gave (battle-scoped `Unit` state by the seam's own test, saving like the Crisis flags); the second is now a #413 build question.**

## Movement order — queue order is REAL (decided 2026-08-20; captured un-picked earlier the same day)

**R6 says order is the player's lever — and it now says it about moves too.** The fork this section held open was picked hours later in the standing-reactions grill ([standing-reactions.md](standing-reactions.md), [#412](https://github.com/Phaazoid/Godoiosis/issues/412)): **cut (b)** — move orders resolve in queued order, the player may **drag-reorder queued moves**, and units are still *shown* moving together (simultaneity survives as presentation). The queue is the clock for every mid-move event; an overwatch trigger ([#413](https://github.com/Phaazoid/Godoiosis/issues/413)) is the first customer, and future on-entry mechanics (traps, fire-on-entry) inherit the same clock. The rejected cut **(a)** — keep moves parallel, the spatially-front crosser eats the shot — died for being a proxy for time that can contradict the watched story and for not generalizing to tile watches; a third cut (lockstep walk-time: earliest path-step entering the footprint eats the shot) was offered in the grill and **declined** — the dev wants explicit order as the mechanic, the bigger design space. If this is ever revisited, whatever replaces the queue clock must *replace* it, never sit beside it as an override (Law #4).

**The sizing recorded at capture time stands — it is #412's scope:** `GroupMoveSolver`'s member-order emission becomes the *default* row order rather than display cosmetics (rows inside a batch are individually reorderable; the batch stays one authoring gesture and one gate pass); drag-to-reorder is a new queue-panel affordance either way (the #49 lane never shipped it); and nothing breaks in validation — parallel moves were an *absence* of an ordering rule, not a guarantee, so `SquadPlanValidator`'s whole-plan questions (destination conflicts, formation rotations) stay order-independent, and transient ally co-occupancy during ordered playback is the rotation fiction, already legal. A reorder is a plan edit riding the synchronous resolve→repaint chain (Law #2 machinery unchanged).

## Where it lives

A dedicated resolver invoked by `SquadManager` (already the derived-action home and overweight, so a separate class is the clean seam). The base-damage math from `AttackAction.create()` becomes a value the resolver writes (E1). **Class layout is a build-time call**; what's locked here is the contract and the stage order. Naming is open — `PlanResolver` with pluggable stages, or a thin `ElementResolver` that Phase 3 extends — decide when building Phase 2.

## Migration is incremental — you do *not* build all stages at once

1. **Phase 2 (elemental v1)** introduces the pipeline with only **base-damage + elemental** stages, plus the `ResolvedPlan` / `ResolvedOutcome` types and the single preview model (R8). The threaded hypothetical carries **HP + a Will slot** from the start (R4), and the counter stage reads it with an **always-true liveness flag** (R7) — both so Phase 3 adds the Will stage without re-threading or re-deriving counters. Counters keep working as they do; just make sure they flow through the same resolved result (R3). *The deliverable is the general seam, not a private elemental box.*
2. **Phase 3 (Will/death) — DONE.** Added the **Will stage** reading the resolved damage (R7), no re-architecture needed — it slotted in behind elemental exactly as planned, across #33 (scaffold + Will resource), #56 (limb-slot/MOV), and #57 (Crisis stance + lethality preview).
3. **Counters** already fit (they're attacks); the work is ensuring they **re-enter** the stages so E7 holds.

Building Phase 2 against this contract costs almost nothing extra now and saves rebuilding the resolver/preview in Phase 3.

## The persistence seam — FORMALIZED (#8, decided 2026-06-21)

The code splits **transient vs persistent**, and that split is now the **locked boundary** — no feature invents its own persistence. The `Unit` *node* ("these only exist during combat") holds a `UnitInstance` *resource* (the canonical persistent-identity store; HP already lives there). The rule, decided once so elemental and Will don't each grow a private store:

- **Transient `Unit` node = battle-scoped.** Everything that resets at mission start: v1 boolean element states (`Unit.element_states`, live in code), projected position, the resolver's per-pass hypothetical copy. Re-created per spawn.
- **Persistent `UnitInstance` resource = identity across missions.** The *only* persistent store **of unit state**: fixed stats, HP, limb loss, weapon proficiency, **and Will**. Anything needing cross-mission memory lands here. *(The cross-mission save/load wiring is the future campaign layer — today `UnitInstance` is `.new()`'d per spawn, so nothing survives a mission through the campaign flow yet; what's locked is **where** persistent state belongs, so each feature rides along once that layer exists rather than being stranded on the transient node. Scenario saves, though, now round-trip this store — see the #83 note below.)*
- **Campaign store (named 2026-07-05, audit A8) = what the *player/party* knows and owns.** The "no third store" rule is **unit-scoped** — it forbids a second home for *unit* state, not party state. Party/player-scoped persistence — the transmutation **codex**, squad **familiarity/connections**, the authored **economy**, unlockables / recipes / achievements — is the pattern every game carries, and its designated home is a single **campaign-store** resource in the future save-file layer. Named now, #8-style, so features land on the right side: new persistent state picks by one test — *is it about a unit, or about the party?* Unit → `UnitInstance`; party → campaign store. Nothing builds it yet; the codex is likely its first customer.

**Scenario saves carry the instance side ([#83](https://github.com/Phaazoid/Godoiosis/issues/83), 2026-07-22):** `ScenarioUnitEntry.capture_unit_state`/`apply_unit_state` snapshot the whole persistent store per unit — edited stats, current HP/Will, the full inventory (`copy_equippable` both directions; `equipped_index` replaced the old standalone equipped-weapon copy), limb states (an installed prosthetic re-links against the carried *instance*, by index — matching by template collapses two prosthetics built on one family onto the same item), weapon proficiency, aura, and affinity — applied *after* `initialize()`'s reset on load. This is the dev-scenario layer exercising the seam (it unblocks the #9 fixture library), not the campaign layer itself.

**...and since [#177](https://github.com/Phaazoid/Godoiosis/issues/177) (2026-08-10) that layer has TWO declared save kinds, forked per unit.** An **authored** save (`capture_scenario(name, authored = true)` — the Scenario tab's checkbox, default on) writes a **cast** unit — one spawned from a standalone character file under `Resources/Units/` (provenance = `Unit.unit_data_source`, stamped by `UnitFactory` only for a `::`-free real `resource_path`, so a scenario-embedded sub-resource never counts) — as a **reference**: `entry.unit_data` is the file itself and `entry.state_saved = false` means *nothing was captured; the spawn's own `initialize()` + starting kit are the whole answer*. Every load re-reads the character as authored **then**, so editing `Torv.tres` updates every mission he appears in. Ad-hoc units keep the full #83 snapshot in both modes, and every non-authoring caller (`BugReporter` above all) keeps the default — a bug report stays a byte-exact mid-battle capture. The dev call behind the fork (2026-08-10): *references for the cast; snapshots return when mission-to-mission carryover arrives.* To make a character file able to express a whole loadout, `UnitData` grew the **starting-kit block** (`starting_jobs` / `starting_inventory` / equip + wear picks / `starting_proficiency` / `starting_prosthetics`), seeded by `Unit._seed_starting_kit()` right after `initialize()` through the gated equip doors; a snapshot's `apply_unit_state` **clears the seeded kit before restoring** so a save stays authoritative rather than doubling inventory. Pinned by `tests/flow/test_cast_references.gd` + `tests/unit/test_starting_kit.gd`, each falsified against its own bug. **A DEV EDIT breaks the reference (dev-ratified 2026-08-20, out of the verticality fixture):** a unit the Unit Editor has saved (or a cast spawn the Spawn tab put on the other team) sets transient `Unit.dev_edited`, and an authored capture writes it as an ordinary **snapshot** instead of re-referencing — the edit made it board-local, and a reference would silently discard it, which is exactly how inventory/team edits to the fixture could never be saved. Sticky by construction: the snapshot entry respawns with no `unit_data_source`, so later authored Updates keep it a snapshot. Untouched cast units keep reference semantics exactly.

**...and since [#87](https://github.com/Phaazoid/Godoiosis/issues/87) (2026-07-30) the BATTLE-scoped side too — a save is a true mid-battle snapshot.** This **reverses**, for the save-resume axis only, the line that used to sit here saying battle state stays out of saves. That line was right for a *mission boundary* and wrong for *pause/resume*, which is a different axis the seam had not separated; weapon-state-only was explicitly rejected as a lopsided snapshot (charge kept, but downed units standing up and fires going out). What round-trips: per-carried-weapon battle state (spring readiness, carbine magazine, mace charge, chainsword rev — by **inventory index**, so two of a family track independently), element states, lifecycle + the downed clock, the two Crisis flags (`in_crisis` + `crisis_surge_pending` — the third, `crisis_offered_pending`, died with the offer, #158), `rally_count`, live `StatEffect`s **with their remaining countdowns**, squad `has_acted` (on the leader's entry), and `MissionController`'s captured zones + `contested` latch (on `ScenarioData`).

The seam itself is **unweakened**, and that is the point of the mechanism: none of those fields became `@export` where they live. Weapon readiness/charge/rev/ammo are still plain vars on `WeaponInstance` subclasses so `make()`/`copy_equippable()` re-arm every weapon; lifecycle, element states, Crisis and rally are still plain vars on the transient `Unit`. The snapshot captures them **explicitly**, exactly the way limb fittings have always been captured rather than serialized — so a mission boundary still resets battle state for free, while a save can put it back. Two structural rules hold it together, both pinned by falsified tests:

- **A restore replays the RESULT, never the EVENT.** `Unit.restore_lifecycle`/`restore_stat_effects` exist because the normal entry points have consequences the save already recorded — `_go_downed()` emits `went_downed` (ejecting the unit from a squad the loader has not rebuilt yet) and re-spends Will, `apply_stat_effect()` reseeds a countdown from its `duration`.
- **Effects settle before gear and before HP.** Settling enforces the wear gates, so a restored debuff applied after the armour would strip gear the save says is worn (the same *a save is authoritative* rule `worn_armor_index` follows); and a `+CON` effect moves max HP, which the saved `current_hp` was measured against.

`WeaponInstance.capture_battle_state()`/`apply_battle_state()` are a `Dictionary` rather than one int even though every family currently tracks exactly one number — #108's lesson is that a seam which cannot say what content needs grows a second one, and the first family wanting two counters would be that seam. Keys are family-private strings, not a shared enum: they name one class's fields, not a game vocabulary.

Still deliberately NOT saved: the queued action plan (player intent, re-authorable after a load, and serializing `BaseAction` graphs with live `Unit` refs is its own feature), the live `active_attack` aiming cursor, and projected-knockback cells (derived from a resolve pass each time).

**Save-format forward-compat ([#11](https://github.com/Phaazoid/Godoiosis/issues/11), closed 2026-07-22):** the future campaign save file carries a `save_version` + migration path **from day one** — real player saves can't be hand-repaired. Dev-phase scenario `.tres` deliberately do NOT: additive `@export` defaults cover schema growth for free, and structural breaks are caught by the scenario load-integrity suite (#9) and repaired by scripted text-level migration (clean-over-legacy, 2026-07-16). A load-time version hook couldn't do that job anyway — Godot drops moved/unknown properties during `load()`, before any migration code could see them (proven twice: #80 and the missing-`weapon_type` wave).

Both features that hung on this seam are now resolved:

- **Element states** (elemental fork 3): boolean + chain-scoped → **transient `Unit`** (built; threaded as a copy through the resolver pass). The deferred over-time layer can revisit.
- **Will** (will-and-death fork 1, persist-vs-reset): **PERSISTS → `UnitInstance`** (decided #8, 2026-06-21). Max Will (innate identity) and current Will both live on the persistent store, beside the limb-loss it already advertises. Fork 2 (individual vs squad-*pooled* Will) stays open but is compatible: per-unit Will sits on `UnitInstance` regardless; a squad pool, if added, is **additive**, not a relocation.

> **Paired reconcile (#12) — DONE 2026-06-21:** the benched `level` / `level_up()` / `randi_range` leveling path (predating and contradicting no-leveling, [progression.md](progression.md)) was stripped from `UnitInstance`, along with the now-dead `growth_ranges` on `UnitData`. The store is now clean — *fixed stats, no growth; home for HP / limb-loss / proficiency / Will.* ([#12](https://github.com/Phaazoid/Godoiosis/issues/12))
