## Purpose

Squads are Iosis's distinctive mechanic. Units group under a leader, plan together, execute together, and defend each other. Squad-vs-squad combat is the intended heart of the game; lone units are vulnerable by design.

## Entities

- **Unit** — a board piece. Holds a reference to its current squad. Never manages squad membership itself.
- **Squad** — a leader + members + an `action_queue` of player-authored orders. Manages only its own lists.
- **SquadManager** — the sole authority for squad lifecycle and the home of derived-action (counter) resolution.

## Invariants

Numbered for test coverage. Violating any of these is a bug, full stop.

- **I1.** Every unit on the board belongs to exactly one managed squad at all times. A solo unit is a 1-member squad, not squadless.
- **I2.** Only `SquadManager` creates or destroys squads. All member removal funnels through `Squad._erase_member()` — the sole caller of `members.erase()` (mirrors the sole adder `_add_member`). Its callers: `_detach_from_current_squad()` (single-unit — join/leave/death) and `disband_squad()` (bulk teardown). (Chokepoint added 2026-06-21, [#23](https://github.com/Phaazoid/Godoiosis/issues/23).)
- **I3.** Every live squad appears in `SquadManager.squads`; destroyed squads are removed from it and freed. No "ghost squads" holding units.
- **I4.** `Unit.has_squad()` answers "does this unit have squadmates" (`members.size() > 1`) — not "does a squad object exist" (that's always true, per I1).
- **I5.** The leader is always a member of their own squad. When the leader leaves/dies, leadership reassigns to the member with the highest **effective** LDR (base + PER band; first-in-member-order breaks ties) — "biggest capacity commands" (banner). If the new leader's capacity is smaller than the outgoing membership, the newest-joined members beyond capacity are detached into solo squads (same pass, `check_reassign_leader`).
- **I6.** Members must stand within the **leader's cohesion radius** (`Stats.Stat.COH` — per-unit since [#142](https://github.com/Phaazoid/Godoiosis/issues/142), still decoupled from LDR; banner), measured in **PATH distance over terrain the member can traverse** since [#151](https://github.com/Phaazoid/Godoiosis/issues/151) (2026-08-06) — **walls block cohesion**: you cannot order someone through solid rock you can't see or hear through, so a Manhattan-close member on the far side of a wall is *not* in the squad. Per-member because traversal is per-unit (#115 — a Waterwalker's bubble crosses water; a future flyer's crosses cliffs), occupancy-blind always (an enemy body never severs a squad). One seam answers it: `SquadCohesion` (`field`/`in_range`/`cells`), a bounded `path_hops` walk from the leader's cell, consulted by the validator, the solver, the squad-up gates, the overlays and the range clamp alike — the metric swap was one edit there because the 2026-08-06 consolidation had already routed all eleven asking sites through it. Read only via `Squad.get_max_squad_range()` — never a member's own COH; default COH went 3 → 4 with the swap, since path ≥ Manhattan makes the same number a strictly tighter leash. After leader reassignment, out-of-range members are detached into solo squads (`check_reassign_leader`), and since the successor's COH may be shorter, a swap can detach members the old leader held. **New with #151, the loss-of-contact backstop:** movement can no longer *author* a split (the validator refuses it), but displacement nobody chose still can — a shove around a corner, ice melting under a formation — so `SquadManager.enforce_contact()` ejects an out-of-contact member into a solo squad at the settle points, mirroring downed ejection and equally un-previewed. There were two -- end of a resolution pass, turn start after the ticks -- and #772 (2026-09-05) added a THIRD: a pre-mission REPOSITION settles immediately. That one is different in kind, and deliberately so: the other two answer a displacement nobody chose, while this answers the player placing a member out of reach on purpose, so the ejection is shown at the moment of the decision rather than a turn after it (dev: it "ejects them there and then in the battle preview"). This is also the migration path for pre-#151 saves: a loaded squad that was Manhattan-legal but path-split self-heals at its first settle point.
- **I7.** Spawning a unit creates its solo squad (`spawn_unit` → `create_squad`).

## Action queue rules

- The queue contains **player-authored orders only**. Derived actions (counters) are never stored in it (see Counter rules).
- **One order per action-type per unit.** Queuing a new move/attack for a unit replaces its previous one — *except* volley siblings (one AoE order = several `AttackAction`s sharing a `volley` array; `_is_volley_sibling` exempts them from replacement; a *new* attack order still sweeps the entire old volley). **That exemption is vestigial on the player path since #15**: the queue stores one AIM per attack (`AttackAction.declare` leaves `volley` empty) and the volley is re-derived into `ResolvedPlan.attacks` each resolve, so no volley member is ever in `action_queue` outside `tests/squad/test_volley.gd`. The code still handles one correctly — `remove_action` routes it through `_remove_volley` — it simply no longer arises. Worth knowing before designing against it: #228 was filed believing a queue cancel had to propagate across a volley, and the live version of that problem turned out to be the **group move** instead (see the LIFO rule below).
- Members without an explicit move get a **hold move** (`init_hold_position`) when the squad becomes active, so every member has a stance in the plan.
- Cancelling all of a unit's actions must leave no residue: if only hold moves remain in the squad's queue afterward, the queue clears entirely and the squad deactivates. **This binds every path that cancels, including a refused batch** — `queue_group_move`'s all-or-nothing rollback missed it until 2026-08-04, and the squad it stranded read as a stuck game: the queue panel open on nothing but hold rows, no cancel Xs, an Execute that moved nobody.
- **A batch is queued whole or not at all, and REFUSED counts as failure ([#443](https://github.com/Phaazoid/Godoiosis/issues/443), 2026-08-21).** `queue_group_move` asks the Law #3 chokepoint for every move the solver authored; the all-or-nothing rollback above used to ask only whether any move in the queue came back **invalid**, which is structurally blind to an order `queue_action` never accepted — that move is not invalid in the queue, it is **absent** from it. So the rollback also fires when fewer orders landed than were authored, and `queue_group_move` returns false when it authored nothing at all. The refusal that actually reaches this is **move-before-main**: a leader holding a main action has its own move refused while every follower's is queued, at offsets solved for a destination the leader never reaches, and the squad marches off and abandons it. The menu half is the *convenience*, not the rule: `MainActionMenu._can_move` is now the single gate **both** movement rows read (Group Move used to carry a hand-copy of it that had drifted, which is how the row survived a queued main action), but the menu is one door among several — the Play API and the AI reach `queue_group_move` directly, so the batch contract has to hold without it. **[#461](https://github.com/Phaazoid/Godoiosis/issues/461) (2026-08-21) closed the half #443 could not see: `_can_move` only ever answers about the unit whose MENU is open, and the refusal above fires for any MEMBER just as well** — `plan()` authors a move for everyone, so a squadmate holding a main action rolled the whole formation back, silently, from a row the gate still offered. `_can_group_move` therefore asks `_can_move` of every member; the clause lives at the Group Move caller rather than in `_can_move`, because **Move is a per-unit question and must not start reading squadmates** (`test_the_leader_keeps_its_own_move_when_a_squadmate_locks_a_main` is what pins that split). The rollback is unchanged and still the backstop for the doors that are not the menu — pinned at that layer by `test_group_move_is_refused_whole_when_a_MEMBER_holds_a_main_action`; its loop is now `cancel_squad_moves`, shared with the re-plan gesture #461 also added.
- **Right-click is a LIFO undo on the queue ([#228](https://github.com/Phaazoid/Godoiosis/issues/228), 2026-08-15), and the open mode wins.** One button carrying two meanings: it leaves whatever mode is open first, and only from a board at rest does it pop — so a player who opened Attack and changed their mind never loses an order they queued earlier (dev's call; the alternative ate one). The unit of undo is **one player GESTURE, not one array element**: a group move comes off whole, because a formation is one decision and a half-dissolved one is a plan the validator then has to refuse. That grouping is `BaseAction.batch_id`, stamped by `queue_action` — `SquadManager.batching` made durable, which is also what leaves the hold fillers unstamped, since they bypass the chokepoint and are nobody's order. **The pop authors no cancel semantics of its own**: `game._pop_last_gesture` routes every removal through the queue panel's `_on_queue_cancel_requested`, so the move-before-main cascade, the revalidate and the deactivation above are inherited rather than mirrored. One consequence worth stating, since it looks like a gap: the move→main half of that cascade is **unreachable** from a pop — `MoveAction.actor_can_perform` refuses a move to a unit holding a main, so the queue can never present a move newer than that unit's main, and LIFO always meets the main first. **MOVES gained a rung in front of the pop ([#417](https://github.com/Phaazoid/Godoiosis/issues/417) round 2, 2026-08-21, dev call):** when the newest gesture is ONE unit's own move, the press re-opens its planning instead of undoing it — *as if you hit Move again* — so the button cycles `move queued → planning → nothing`. The third rung needs no code, because re-planning spends the order on entry (#417); and the branch is scoped to a **lone** move, so a formation still pops whole — "as if you hit Move again" has no meaning for a row the menu hides once a move is queued. `game.begin_move_planning` is the one gesture both doors call, and `game.select_unit` is the extracted select write point the re-entry needs, since `_click_choosing_move` reads nothing but `selected_unit`.

## Validation rules (`validate_squad_plan`)

Run on every queue change; actions carry `is_valid` + error strings rather than being rejected:

- **V1.** Two units may not plan moves to the same destination.
- **V2.** A move may not target a cell occupied by a squadmate who isn't moving away.
- **V3.** Non-leader moves must land inside the leader's cohesion bubble measured from the leader's **projected** cell (the leader's own planned destination counts, not their current cell — range itself no longer derives from LDR, banner). `SquadCohesion.in_range` is the single copy of this test (I6 — path-based, per-member, board-fed since #151; the validator's old `cohesion_ok` delegator is deleted), and it is **strict for every move whatever authored it** — an individually ordered one, a Group Move placement, or the hold-position filler alike. A leader therefore cannot walk out of range of its own squadmates, by group move or alone.

  **Group Move splits into two outcomes around V3** (2026-08-04, after the rule was briefly relaxed and put back the same day):
  - **Case 1 — falls behind, stays in range.** The leader outruns a member, so it can't hold its formation offset, but it still lands inside the bubble. Legal. `MoveAction.is_trailing` marks it (set by `GroupMoveSolver` when the member ends *further* from the leader than it started) and `OverlayManager._arrow_modulate` draws its path arrow **green**.
  - **Case 2 — cannot reach the bubble at all.** Refused. `GroupMoveSolver.followable_destinations` answers this for the whole overlay at once, so `enter_group_move_mode` paints those destinations the **same red** a squadmate's own out-of-range tiles get, and clicking one behaves identically: nothing queues.

  The overlay and the refusal must agree, because the failure they replaced was a click that *looked* like it queued a ghost order — the tile was green, the plan was authored, V3 refused it, the rollback undid it, and the squad was left `active` behind a queue of hold rows with no cancel Xs and no Execute. Pinned by `tests/squad/test_squad_cohesion.gd`; story in [`docs/build-log.md`](../build-log.md).

## Reaction rules

*(Called "Counter-attack rules" until [#148](https://github.com/Phaazoid/Godoiosis/issues/148), 2026-08-07, when a second KIND of reaction landed. C1–C7 are unchanged by that; C8–C10 are the extension.)*

Reactions are **derived**: recomputed from the current plan whenever it changes, displayed in the queue under their own REACTION section, and instantiated only at execution.

- **C1.** When party X attacks party Y, every unit in Y gets the opportunity to counter **once per plan**. A "party" is the whole squad (a lone unit is a party of one).
- **C2.** A countering unit may target *any* unit in the attacking party that it can reach — not just the unit that attacked. (The sacrificial-frontliner rule: a long-range attacker exposes nearby squadmates to the response.)
- **C3.** Target choice is deterministic. Current policy: first valid target in attacking-party member order. **[OPEN — placeholder policy. Candidates: closest, lowest HP, leader-first. Lives in `choose_counter_target`; changing it touches nothing else. 2026-07-06: taunt/bodyguard **job abilities override** whatever the default is ([jobs.md](jobs.md) squad posture); the default itself stays a feel-test placeholder.]**
- **C4.** A defending party responds at most once per attacking squad's plan, triggered by the first *hostile* attack against it in queue order (C5).
- **C5.** Faction gate, **at BOTH ends** (`RulesService.can_target`, via `Team.is_enemy`): a reaction is **triggered** only by a hostile hit, and may only be **aimed** at the attacking party — friendly-fire victims never counter their own side.
  - **The trigger half went unenforced until [#767](https://github.com/Phaazoid/Godoiosis/issues/767) (2026-09-05), and C1's own verb is what it was missing** — *"when party X **attacks** party Y"*. The derivation walked every action in `plan.attacks`, and a heal is an ordinary `AttackAction` whose target is an **ally**, so queueing one made the healer's own squad the defending party and handed it a free reaction. A damaging squadmate was refused anyway by the aim half (nobody can `can_target` their own side), so the leak was invisible from that direction; a healing reaction turns inward and never asks who it is answering, so the healer simply healed twice. Reported from play, in the Prolog.
  - **The gate is FACTION-shaped, not heal-shaped** (dev ruling, 2026-09-05, choosing between exactly that pair): *"a squad should not be able to generate counter attacks by attacking itself… like being able to blow your own unit a tile to double their output."* So a heal aimed at an **enemy** still draws their reaction — a player-aimed heal on an enemy is authored canon (C8's own note), and being healed by an enemy is still being acted upon by one. It also closes the friendly-fire-splash route, which is C5's original sentence arriving at the trigger. Consequence worth knowing: a NEUTRAL or ALLY-faction target draws no reaction at all, `is_enemy` being narrower than "different faction" — theoretical today, since no content uses either.
  - **Overwatch already had this rule** (`PlanResolver._watch_triggered_by` gates on `Team.is_enemy`, *"neither does the watcher's own side"*), and Guard passes heals straight through `_guard_for` — the counter path was the only one of the three missing it. The gate reads the victim **after** Guard substitution, which is what makes it agree with [standing-reactions.md](standing-reactions.md)'s *the blocker's party counters, not the ward's*.
- **C6.** Weaponless units cannot counter. A unit's counter reach is its weapon pattern from its *projected* position, with free rotation (no facing persistence on the board — revisit if facing becomes a mechanic).
- **C7.** Bystander parties never counter: only the attacked party responds, and only against the attacking party. Reaction mechanics beyond that (overwatch, intercepts) would be separate named systems. **That system exists as of 2026-08-20: [standing-reactions.md](standing-reactions.md) (Guard + Overwatch), ratified with C1–C10 untouched — its listening grammar (*counters listen to authored attacks; watches listen to entries; Guards listen to hits on their ward*) is also why a derived overwatch shot draws no counter.**

### Reactive healing — BUILT 2026-08-07 ([#148](https://github.com/Phaazoid/Godoiosis/issues/148))

The 2026-07-31 capture ([jobs.md](jobs.md) → *Captured idea — reactive healing*) asked one question before anything could be built: *does a defending squad's healer EXTEND C1–C7, or is it one of the separate named systems C7 reserves?* **Answer: it extends them, and the extension is entirely in TARGETING.** C1, C4 and C7 come through untouched.

That is smaller than the ticket first assumed. C1 already gives *every unit in the defending party* a reaction, so a healer squadmate of the attacked unit was always eligible — no C7 override was needed and none was made. What actually stopped a healer reacting was C2/C5/C6: the candidate set, the faction gate and the reach test are all measured against the *attacking party*.

- **C8.** A reaction's **kind** is its source's `AttackData.heals` (read off `Unit.get_counter_attack()`, so a weapon answers with main and a rune with its live pick, #30/#72). A damaging source strikes the attacking party — C2/C3/C5 exactly as above. A **healing** source turns inward: it targets its own side and can **never** touch an enemy, at the target pick *or* as AoE splash. There is no fall-back — a healer with no valid heal target does not react, because a healing main cannot damage anything.
  - The splash half is a separate gate from the target pick, and it is the one that is easy to miss: an enemy inside any footprint is an ordinary victim, so a reaction heal expanding through the normal gather would top up the attacker even after picking the right ally. `RulesService.gather_attack_victims`/`is_attack_victim` take an **`allies_only` opt-in** (default false — the `path_hops(block_on_occupancy)` shape from #127) and the reaction expansion is its one caller. **A player-AIMED heal deliberately keeps its enemy splash** (dev, 2026-08-07): healing an enemy is a niche the player may want, and only the derived reaction is restricted.
- **C9.** A reaction heal's candidates are non-enemy units that are **not downed** and **below max HP**, reachable by the healing attack's own pattern from the healer's projected cell. Among those, the target is the **lowest current HP**, ties by board order (`_all_units()`, the same first-in-order tie-break C3 uses). Deterministic, never a prompt (Law #1; [jobs.md](jobs.md) chassis rule 3).
  - **"Below max HP" is a FILTER and "lowest HP" is the SORT — two rules, not one.** Collapsed into a single comparison, a unit at a full 19/19 outranks a hurt 20/23, which is exactly wrong (dev's own example).
  - **Downed allies are excluded outright, not deprioritised.** A heal moves HP but never lifts `lifecycle_state` (resolution-pipeline.md's 2026-07-30 amendment), so healing a body accomplishes nothing — and a downed unit clings at 1 HP, so it would win every lowest-HP comparison and eat the squad's whole reaction. Picking a body up at range is reserved for a future stronger transmutation.
  - **Every HP and lifecycle read comes off the THREADED HYPOTHETICAL** (R4/R7), via `PlanResolver.projected_hp`/`projected_lifecycle`. The derivation runs after the attacks have resolved, and their damage lives only in the hypo — read live, the healer picks whoever was hurt *before* the swing and filters out the squadmate who just took it. Projected positions are published to the board (`set_projected_knockback`); HP is not.
- **C10.** Healing reactions are emitted **after** the damaging ones and therefore resolve last within the counter phase (`PlanResolver.resolve_counters` walks the list in order), so a reaction heal already covers a counter that ally-splashed its own squad. **This is why no separate post-counter stage was built.** The stage `resolution-pipeline.md` defers is still owed to the *player-authored* twin — a stored order that defers past counters cannot live in `plan.counters`, which is derived-only (Law #2 / R5) — and it costs the same to build then as now.

One walk, one ledger: `SquadManager.calculate_reactions_for_squad` (ex-`calculate_counterattacks_for_squad`) derives both kinds in a single pass over the defending party, because C1 and C4 are bookkeeping a second sweep would have to keep its own drifting copy of (Law #4). Tests: `tests/squad/test_reaction_heal.gd` (15 cases, falsified against eight mutants incl. the full pre-#148 behaviour and the full pre-#767 one). That file also owns C5's trigger cases, for a reason worth knowing before moving them: **the trigger's only observable leak is heal-shaped**, because a damaging squadmate is refused by the aim half whatever the trigger was — so a healer is the only witness the suite can call, and the fixture lives here.

## Execution model

1. **Moves** — all squad moves execute in parallel (the squad repositions as one).
2. **Attacks** — sequentially, in queued order. Order matters by design (future elemental combos: wet *then* shock).
3. **Reactions** — sequentially, after the full attack chain, and never interrupting the combo. Damaging ones first, then healing ones (C10), which is what lets a reaction heal cover a counter's own ally-splash without a separate phase.
4. Reaction actions are computed **before** any phase executes (determinism: the plan decides, not mid-execution board state). Dead actors/targets cause individual actions to no-op safely; they never hang the phase (every `execute()` path must reach `finish_execution()`).

## AoE / volley semantics

- One AoE order resolves at queue time into one `AttackAction` per victim ("volley"), all sharing the `volley` array; the first is primary (plays the lunge), the rest are `is_secondary_hit`.
- Victims are gathered by **projected destination** over the pattern's affected cells: enemies always; non-enemies only when the weapon's `hits_allies` is true; the attacker itself only when the attack's `hits_self` is true ([#123](https://github.com/Phaazoid/Godoiosis/issues/123), 2026-08-06 — `RulesService.is_attack_victim` branches on `unit == attacker` and asks `hits_self` instead of refusing unconditionally; `hits_allies`/`can_target` are untouched, so a self-hitting attack can never leak into `SquadManager.choose_counter_target`). `Resources/TransmutationData/heal2.tres` authors both flags: `hits_self` so the caster can target their own cell (the geometry was already there — `min_range = 0` on its `ManhattanRangePattern` already made the caster's cell selectable), `hits_allies` for squadmates. (The original `Heal.tres` was deleted 2026-08-06 — every rune that had already carved it carries its own frozen copy per `RuneData`'s deep-copy `copy_for_grant()`, so nothing else referenced the catalog file.)
- Reactions key off each victim-action individually, so C1–C10 apply unchanged to AoE — including C8's ally-only splash, which is enforced at this same gather via `allies_only`, **and C5's trigger gate, which is asked of each victim-action on its own (#767)**: a blast catching an enemy and a squadmate draws a reaction from the enemy's party alone.

## Display model

The queue UI renders `ActionQueueDisplayEntry` lists built by `ActionQueueDisplayEntry.build_for(squad, plan)` (requested via `SquadManager.get_display_entries_for_squad`, which supplies the resolved plan) — never raw queues. Sections per action type, with derived reactions last under their own REACTION header (renamed from COUNTER by #148, since the section now holds heals too). Display rebuild happens on every plan change; the UI must tolerate freed units (actions cache display name/texture at init).
