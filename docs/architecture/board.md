# Architecture — Board, game.gd and selection

## game.gd

`game.gd` — input/game-state coordinator. **Reorganized 2026-07-26** into labelled sections (Lifecycle / Input / Turn flow / Modes / Queueing orders / The action-queue panel / Squads / Populating the board / Board visuals / Board queries), with three collaborators split out — each built in `_build_collaborators()` and holding a `game` back-ref, the `DevController`/`AIController` pattern: **`OrderExecutor`** (`actions/`, runs a squad's plan + the downed fallout), **`HoverPresenter`** (`board/`, mouse → cursor/overlays/queue-row highlight, incl. the `_process` hover detection and the two `hovered_*` signals), **`MainActionMenu`** (`ui/`, now the *whole* menu system — construction as well as gating/dispatch). Still the heaviest file; prefer moving domain logic out to the owning system when touching it.

**The current selection is STORED, not re-derived (#107): `game.selected_unit`** is set once, in `select_unit` (from `unit_at_pointer` on a board click, from the newest queued move when right-click re-opens its planning, #417, or by the F / Shift+F squad cycle, [#1038](https://github.com/Phaazoid/Godoiosis/issues/1038), `game.cycle_squad_member`) and read by all four mode click-handlers plus their three `HoverPresenter` twins. It replaced five hand-written `get_unit_at_cell(last_clicked_cell)` lookups that came in two contradictory precedences, one of which crashed on any unit selected via its shove-ghost. `last_clicked_cell` now means **only** "where the cursor sits in TILE_SELECTED" — a move path reconstructs from `unit.movement.cell`, which is what `compute_move_range` keyed `came_from` from. Never re-derive the selection from a cell; the cell and the resolver both drift.

**Anything reaching back through the untyped `game` ref must annotate its locals explicitly** — `game.gd` has no `class_name`, so every `game.*` call is Variant and `:=` cannot infer from it; and a bare array literal passed that way is NOT coerced to a typed parameter (it fails at *runtime* — this is why `clear_selection_icons()` exists instead of callers passing the literal).

## OverlayManager

`OverlayManager` — all board visuals (tile overlays, icons, path arrows, projected units, and since [#1247](https://github.com/Phaazoid/Godoiosis/issues/1247) a badge per queued attack row, derived by `StrikeMarks2D` off the plan the queue panel shows — `visual-clarity.md` → *Queued attacks wear the queue's icon*).

## The board/ folder: BoardGrid, BoardContext, rules, ZoneManager, HoverPresenter

`board/` — **`BoardGrid`** (the `Game.tscn` `Grid` node's script, and the ONE door a terrain write goes through since [#319](https://github.com/Phaazoid/Godoiosis/issues/319): `paint`/`erase`/`reset`, each marking a shared **`DirtyCells`** that `battle3d`'s authoring poll consumes so the 3D mirror reconciles only the cells that moved. **The ONE-CONSUMER rule is about the cell LIST, because `clear()` steals it — `DirtyCells.version` (#308) is a monotonic, non-consuming count beside it, for any number of readers.** It exists because a poll can draw THROUGH a store its own diff key cannot see: `OverlayMirror` reads `BoardHeights` for a fill's tilt and a flame's footing, so a rise painted onto a cell whose elevation did not change left its `Array[Vector3i]` identical and the quad kept the old tilt.

**A poll that draws through a second store gates on that store having changed, never on a copy of what it reads** — a copied key is a second spelling that goes stale the next time the render grows an input. It replaced a full-board diff that ran **every frame** in DEV_MODE — O(board) at ~6.5 µs/cell, i.e. a whole 60fps budget on Prolog *before* anyone painted; the fix took a brush drag on a 200×200 board from ~250 ms/frame to ~0.07 ms and made the cost flat in board size, which is why the resize SpinBox needs no cap. **Named doors, NOT overrides of `set_cell`/`erase_cell`/`clear`** — `native_method_override` is an error here, and an override would only intercept GDScript callers, i.e. a hole that looks covered.

**The bulk write got a FOURTH door in [#391](https://github.com/Phaazoid/Godoiosis/issues/391), `restore(data)`, and the declared exception is gone**: `tile_map_data` assigned wholesale used to be allowed because `ScenarioManager`'s board load emits `board_loaded` → `battle3d.rebuild()`, which full-syncs — an argument covering exactly one writer, and the authoring undo needed the same wholesale write. The door `mark_all`s, both bulk writers (scenario load, undo) go through it, and the law below scans for the assignment too. **It `clear()`s first, and that is the door's whole reason: assigning an EMPTY buffer to `tile_map_data` does nothing at all** (measured, 4.7.1 — the setter returns early rather than wiping), so restoring a board back to bare ground left every painted cell standing. Every pre-#391 caller happened to clear first, which is why the quirk was invisible until an undo asked for the empty board directly. The old poll caught every writer *for free* by re-reading everything; that guarantee is now `tests/law/test_board_writes_announce.gd`, which matches **grid-named receivers only** — its own first two runs proved `set_cell` is not unique to `TileMapLayer` (`BoardHeights` and `MovementComponent` have one) and that the board grid is not the only `TileMapLayer` (every overlay is). Two traps live in `docs/performance.md`: a **lowered floor still full-syncs** (every column reaches down to one shared floor, so moving it invalidates the board — `BoardHeights` caches the minimum so asking is O(1)), and the board rect **grows in place but shrinks by re-deriving**, since only a full pass knows the new edge — a mutant disabling that shrink left all 239 presentation cases green, which is why `test_painting_past_the_edge_grows_the_board_rect_and_erasing_shrinks_it_back` exists); overlays (`OverlayManager`/`OverlayIcon`), board rules (`RulesService`/`BoardContext` — **`BoardContext.is_walkable(cell)` is the ONE answer to "may a unit stand here?" (#109)**: it is the only reader that also knows dynamic tile *state*, so a FROZEN water tile is passable to movement, `GroupMoveSolver`, knockback, `game.spawn_unit`, the dev-mode cursor and the headless `play_session.terrain_at` alike — three of those used to re-read the `walkable` custom-data flag themselves and none could see state.

**`GridUtils.walkable_of(data)` ([#552](https://github.com/Phaazoid/Godoiosis/issues/552)) is a SPLIT of that answer, not a second one** — #109's rule and its `has_custom_data` guard live there now and `is_walkable` delegates its tile half to it, keeping the state short-circuit that needs a cell; it exists because the RENDER asks a NARROWER question than the rules do — `BoardMirror`'s water mask needs the tile TYPE's flag, and a FROZEN water cell is walkable while still being deep water to look at (the meshlib generator was the original caller; #552 slice 2b moved the read to the mask, per cell), so a water tile's rendered depth IS its walkability and the surface cannot drift from the ruleset. A tile whose tileset **doesn't declare the flag is NOT walkable** (decided in #109; the unguarded read it replaced raised two runtime errors per call, once per neighbour inside the move-range BFS).

**Occupancy is deliberately NOT folded in** — `is_walkable` never answers "is someone already standing here", so `spawn_unit` and `DevController.resolve_pending` each keep their own `get_unit_at_cell` test beside it. **The per-unit layer on top is `RulesService.can_traverse(cell, unit, board)` (#115)** — one home for "may THIS unit traverse this cell's terrain?", read by both `movement_cost` and `GroupMoveSolver._path_hops`, which used to decide separately so Waterwalk silently died whenever a unit moved with its squad. It adds Waterwalk and **excludes occupancy on purpose**: an enemy body blocks a move but is not terrain and moves every turn, so routing the cohesion field through `movement_cost` instead — the obvious-looking simplification — would let one enemy sever formations. `_path_hops` therefore takes a unit and the leash field is per-member; `docs/performance.md` records that this costs less than the profiler's own noise, and that the plan signature is unchanged.

**Occupancy is an OPT-IN on the hop walk since #127 (2026-08-06) — `path_hops(…, block_on_occupancy := false)`, and the default is the load-bearing half.** The rule above is about the *cohesion caller*, not the function: the AI's approach picker needs the opposite answer, since it is estimating the route a unit will really walk, so a standing enemy must be gone around. One question (hop distance under a traversal rule), so the rule is a parameter each caller states rather than a hand-copied second BFS. `GroupMoveSolver` never passes it and `test_an_enemy_body_does_not_sever_the_cohesion_field` calls the default form, so flipping the default goes red; **`AITactics.nearest_enemy` passes it too, but only by routing to each enemy's standable FIRING CELLS rather than its square** (`_approach_distances`) — routing to a square with occupancy on scores every enemy UNREACHABLE, since an active enemy blocks passage. Measuring to the square is what made target selection and the approach picker disagree about which enemy was closest; both now ask one shared helper, `_standable_attack_cells`.

**`AITactics._best_approach` passes it unconditionally**, covering BOTH approach callers (attack and Sentry's walk home) — it was briefly gated on the attack-specific retarget parameter, which welded two unrelated questions to one flag and left `closest_reachable_cell_to` unable to reach a fix it needs identically (an enemy holding a corridor stalls a sentry the same way); pinned by `test_walking_home_routes_around_a_body_holding_the_corridor`. The two occupancy questions are now named statics rather than inline clauses, because they have genuinely different answers: **`RulesService.blocks_passage(mover, occupant)`** (may I pass through — only a still-standing enemy stops you, #122's downed body is stepped over) vs **`is_standable_for(mover, occupant)`** (may I stop here — only a squadmate's cell is shareable). `movement_cost` and `compute_move_range`'s destination filter are their respective sole original homes; nothing re-derives either.

**The PATH a move walks is `RulesService.route_to` since [#920](https://github.com/Phaazoid/Godoiosis/issues/920)** -- the fewest hostile watches woken, then the cheapest, over exactly `compute_move_range`'s steps and MOV budget so the range never changes; a watch fires once, so it searches (cell, watches spent). Every production move asks it (arrow, click, Group Move, Play API, replay) and `tests/law/test_routes_come_from_route_to.gd` keeps `reconstruct_path` out of production code. **What a shove into a hazard does was [#116](https://github.com/Phaazoid/Godoiosis/issues/116)'s question and is fully answered as of #259 + #116 (2026-08-20 / 2026-08-26)**: a drop pays `FallRules` fall damage, a `Terrain.Kind.VOID` landing removes (KILLED + `ResolvedOutcome.removed`, both executors' `die()` doors).

**A TUMBLE that runs off into a hole removes too as of [#969](https://github.com/Phaazoid/Godoiosis/issues/969) (2026-09-15), and pays no fall for the way in** — the hole was the last of #259's conservative tumble stops still standing after the lip and water were both reversed, and it had the two halves of one shove disagreeing about what a hole does. **"Is this cell a HOLE" is `BoardContext.is_void_at(cell)` and nothing else since [#875](https://github.com/Phaazoid/Godoiosis/issues/875) (2026-09-09) — the authored kind, OR no ground inside `grid.get_used_rect()`.** Erased ground renders identically to a painted `hole` tile (`BoardMirror` clears the column for both, `BoardPicker` answers `NO_COLUMN` for both) and used to BRACE a shove like a wall; `PlanResolver` spelled the question by hand at three sites and all three were wrong the same way. The rect is the boundary because it is already what `movement_cost` and `compute_move_range` mean by *on the map* — **erasing a rim cell shrinks the board, erasing an interior one digs a hole** — and `terrain_kind_at` is deliberately NOT widened, its other readers (`Materia.sources_at`, `_resolve_cell_effect_at`, the tile card) asking what the AUTHOR wrote.

**The flight loop asks the hole BEFORE the uphill brace**, because a `hole` tile is FLAT and the brush may raise it, so a hole above the flight level used to read as high ground and stop the shove dead. Two surfaces read the rule and now agree with it: `play_session.terrain_at` reports `"void"` rather than `"offmap"`, and `board_view`'s glyph consults its ground table (`GROUND` since #46) before walkability — a hole is unwalkable, so the `#` branch had been drawing every chasm as MASONRY and the table's own `"void"` entry was unreachable from the day it was written. Blast radius measured before it shipped by `tools/audit_groundless.gd`: 66 groundless-inside-rect cells across the shipped scenarios, every one interior, none on the demo slate.

**The RULE moved to `GridUtils.is_void_at(grid, cell)` at [#876](https://github.com/Phaazoid/Godoiosis/issues/876), `BoardContext` delegating** -- the 3D mirror decides which cells get a lip and holds no BoardContext, which is `walkable_of`'s own split one question along. **That ticket DRESSES the absence**: every edge where a hole meets ground hangs a wall into the dark, nothing is drawn where two holes meet, and the shaft is FLOORED. **The wall hangs from `BoardSpace.board_underside`, never from the neighbour's surface** -- the first attempt did the latter and every ground block already emits all four of its own side faces (#559), so the wall duplicated the whole visible pit face and TORE against it; #259 was right that the neighbours' side faces ARE the pit walls, and only what lies below them was missing. Without the floor you look down the shaft and out of the world, and what you see is `sky_horizon_color`. `sync()` needs its own `used_rect` walk, since it iterates `get_used_cells()` and an erased hole has no tile to be listed by; `sync_cells` DILATES onto void neighbours, since a lip is built from facts about the cells around it.

**Winding is measured, not recalled** -- Godot's face normal is `(v0-v2).cross(v0-v1)`, and with `CULL_BACK` on a mis-wound quad VANISHES rather than looking wrong, and the shove is AIRBORNE — it flies over a void at its starting elevation, so only the LANDING asks these questions (`docs/design/verticality.md` → *Falls, shoves and tumbles*). **WATER CATCHES the shove (#116, 2026-08-26)** — the flight ENTERS the first cell the unit cannot stand on and stops IN it (deep water is simply the water tile with no `walkable` flag; ONE `Terrain.Kind`), and the water then takes whatever the blow and the fall left, so the ordinary ladder names the rung and a drowning IS a down that `RescueAction` can answer.

**`RulesService.drowns_in` is the one predicate and it is PER-UNIT, which REPEALS the cell-level exception this line used to declare** — that exception existed to keep water a wall for everyone, and a cell-level question would now drown a Waterwalker, who instead is shoved ONTO the water and stands there. One comparison, four right answers: deep drowns, Waterwalk stands, FROZEN catches (`can_traverse` reads tile state), shallow is ordinary ground at `move_cost` 2, the same as mud, and a FROZEN cell costs `Terrain.FROZEN_MOVE_COST` (1) whatever its tile authors ([#1223](https://github.com/Phaazoid/Godoiosis/issues/1223)) -- `BoardContext.move_cost_at` is `is_walkable`'s state-aware twin for cost, and the rule, the tile card and the Play API's `terrain_at` all read it.

**`RulesService.wets_in` is its SIBLING as of [#884](https://github.com/Phaazoid/Godoiosis/issues/884) (2026-09-10) and asks a DIFFERENT question — not whether the water is over your head, only whether you are in it — so shallow and deep soak IDENTICALLY and a drowning body comes up WET.** Waterwalk and FROZEN are the two exemptions (a CHILLED unit stays dry too, but that is [#1092](https://github.com/Phaazoid/Godoiosis/issues/1092)'s rule, asked by each caller with the pass's own states), and Waterwalk is asked of the ABILITY rather than through `can_traverse`, which answers for deep water and not for shallow (shallow being walkable to everyone).

**It reads the ground as it stands WHEN THE UNIT ARRIVES, which for a walk or a shove is the LIVE tile-state store**: cell effects apply after the whole attack phase (`OrderExecutor._apply_cell_effects`), so a lake THIS pass froze is still water when this pass's shove lands in it — `drowns_in` reads live for the same reason. The one caller asking AT the deposits' moment, `PlanResolver.settle_sinks` (#922), is handed the landed board, which is the same rule rather than an exception to it. Asked at the two places a unit comes to OCCUPY a water cell: `PlanResolver.resolve_move`'s per-cell walk (so wading soaks you, and the trigger is CROSSING rather than arriving) and a shove's LANDING — never the flight, which is airborne and passes over water the way it passes over a void. Both deposit through the resolver rather than at execution, which is what lets a SHOCK hit later in the SAME pass see it (E4).

**A rescue then HAULS the body onto a cell beside the rescuer, and the PLAYER picks which** (dev, 2026-08-26) — `RulesService.rescue_landings` is the candidate LIST, keyed on *can the body stand there* and never on WATER; the banks flash, picking the body commits nothing, and the click on a bank queues the order with that cell STAMPED on it (`RescueAction.haul_to`, CaptureAction's frozen-snapshot precedent). `resolve_plan` publishes THAT stamp so the board draws the chosen bank before Execute and `_haul_out` replays it — the stamp is the truth, the projection only its drawing. A re-plan that strands the stamp REDS the row rather than relocating a cell the player chose; a body with no legal bank is not a candidate at all; and a body on ordinary ground has one landing, its own, so it still queues in one step. Consequence: a body in deep water is the FIRST thing that legally occupies a cell nothing may stand on, so `game.spawn_unit` takes an `is_body` exception the scenario loader passes — without it a mid-battle save taken during a drowning came back one unit short.

**The floor can also LEAVE ([#922](https://github.com/Phaazoid/Godoiosis/issues/922), 2026-09-27): ice melting under a standing unit is the same drowning from the other side** — `PlanResolver.settle_sinks` asks *does the ground this pass's deposits leave drown you when the live ground did not*, names no state, and is asked when the deposits land (before counters are derived) and again at pass end; the resolver derives it, execution only plays it (terrain.md → *Water*)), `ZoneManager` (painted regions — **each carries a `Kind`** since #96: PATROL for Sentry (the layer itself is authoring-only, but since [#710](https://github.com/Phaazoid/Godoiosis/issues/710) ONE sentry's leash is revealed on demand -- hover a member, or hold T -- through the picked-zone highlight layer, `OverlayManager.reveal_leash`), CAPTURE/EXTRACTION for objectives, **DEPLOYMENT for where the player's force may start (#736)**. One mechanism instead of a parallel `Array[Vector2i]` per objective type — a capture point is a zone of size one. The enum is **append-only** (it serializes as an int), so save/load, authoring and persistence need no edit for a new kind — but the *drawing* costs ~10 places across both stacks, measured on #736 and now written down at `ZoneManager`'s own header rather than estimated there as "one registry line"; a kind needs its own TileMapLayer because colour is per-layer `modulate`. `redraw_zones(zones, hidden)` is the single draw path for all of them, and **`MissionController.hidden_zone_names()` is the ONE answer to what goes in that `hidden` list** (#736) — a claimed CAPTURE zone, plus every DEPLOYMENT zone once `_begin_turn` has fired, which is what makes a deployment area visible while authoring and gone the moment the battle starts. Before that it was answered twice (this node passed `_captured_zones`, `ScenarioManager`/`DevController` passed nothing), so painting a zone mid-battle re-lit a claimed capture point.

**Zones OVERLAP and a zone's kind locks at creation since 2026-08-12** — "the zone at this cell" stopped being a well-formed question, so the kind-sensitive read is `MissionController.capturable_zone_at(cell)` (menu gate + `CaptureAction`'s stamp both), brush erase is scoped to the picked zone, and `zones_changed` is the mutation signal the Tile Brush's zone picker rebuilds off — see `docs/design/missions.md` → *Zones overlap*), `CameraController`/`CursorController`, `HoverPresenter` (hover detection + one draw branch per `GameState`; read-only on game state apart from CHOOSING_MOVE's live plan preview, which IS the feature).
