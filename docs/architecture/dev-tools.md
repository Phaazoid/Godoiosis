## The dev-tools window and its pages

Dev tools: `Classes/dev/DevOverlay.gd` (+ per-tool scripts in `Classes/dev/`) — spawner, reflection-based weapon editor (`get_property_list` walker), pattern swapper (`ProjectSettings.get_global_class_list`), sprite catalog (folder scan). **A SCOPE TREE since [#382](https://github.com/Phaazoid/Godoiosis/issues/382) (2026-08-19): a left-hand `ToolTree` (Scenario / Project / Session) selects a leaf, and the old `DevTabs` TabContainer survives underneath with `tabs_visible = false`, purely as the page stack** — the load-bearing trick, because every behaviour keyed on the current tab (the zone-overlay rule, the brush disarm, the on-show refreshes) still hangs off `tab_changed` and the tree merely drives `current_tab`. `DevOverlay.LEAVES` is the one declaration (scope/label/page/tip per leaf), law-tested in `tests/dev/test_dev_tree.gd`: every leaf resolves, every page has exactly one leaf, every leaf has a tooltip — replacing the index-based `set_tab_tooltip` calls that had already rotted (tab 8 had none; 6/7 described pre-#373/#380 populations). `show_leaf(control)` is the one door to "show this tool" (the Unit Editor's click-a-unit jump rides it so the tree moves with the page); `current_tab_title()` reports "Scope / Leaf".

**A search box sits top right since [#1184](https://github.com/Phaazoid/Godoiosis/issues/1184)** (`DevSearch` indexes the BUILT window, `DevOverlay.reveal(control)` goes there), and **only the mouse changes the page**: the tree and every sub-tab bar take no keyboard focus — see `presentation-effects.md` beside #403. **The scenario's FILE OPS are a persistent header (`ScenarioHeader`, above the split, visible from every leaf)** — Load / Update / Save As / Delete + the authored-save checkbox + a `(modified)` marker meaning ANY change since load or save, authored or played (**dev ruling 2026-10-09, [#1182](https://github.com/Phaazoid/Godoiosis/issues/1182), reversing the old "unit movement deliberately never marks"**: Update would then write something the file does not hold). Its sources: the board stores' own `DirtyCells.version` counters (terrain, corner heights, tile states, gas), `ScenarioManager.play_version` for what play changes (bumped by its doors: a pass, a turn ending, Wait, a squad verb, a dock gear act, a pre-mission placing or loadout edit; the roster's own draw is NOT one, being what the file produces on every load), zones via `zones_changed`, and field edits via `mark_modified()` — **since the #259 rework the unit-shaped edits mark too**: the Unit Editor's Save and a dev spawn, which were the gap that hid the authored-save trap. An unsaved board never wears it, and a save that fails leaves it lit. `board_loaded` re-stamps, so an external load (Mission Select, F2) arrives clean. The old Scenario tab split at the AI seam: `ScenarioTool` is the Properties page (objectives, look preset, camera start), `SquadsAiTool` the occupants (faction AI toggles, squad archetype/zone rows), both refreshed by the header's `file_changed` through the window.

**Properties also carries `Check board` ([#390](https://github.com/Phaazoid/Godoiosis/issues/390)) — the one place to ask "is this board actually PLAYABLE?" before saving it.** `BoardLint` (`dev/`, static, `check(game, authored) -> Array[Dictionary]` of `{rule, severity, text}`) is the rule and the page is only its panel; the button is the one control here that does NOT `mark_modified()`, since it is a read. It BORROWS every rule it can (`objectives_missing_geometry`, `RulesService.spawn_block_reason`, `SquadManager.contact_breaks` — split out of `enforce_contact` for exactly this, so the warning and the sweep that will eject cannot disagree — and `LookKnobs.saved_presets`); the rules it OWNS are the ones nothing else asks: the `ai_factions` check described under `ai/` above, the deployment pair, and the dialog and tutorial-name checks. **`BoardLint.RULES` is the one statement of every finding's tier and wording ([#1432](https://github.com/Phaazoid/Godoiosis/issues/1432))**: `_add` files a finding at its rule's tier, and the Check board tooltip is built from the table (`ScenarioTool.check_tooltip`), because the hand-written tooltip had filed the AI-less ENEMY under BLOCKS and denied the dialog checks. The placement rule asks the loader's own questions: `spawn_block_reason` against the units placed before it, with the body exemption read off the entry the next save writes (`ScenarioManager.capture_entry(unit, authored).spawns_as_body()`), so `authored` is the header's Authored box, passed in by the button. Findings are two-tier — **BLOCKS** (unwinnable objective, a unit standing where spawn would refuse it) vs **DEGRADES** (an undeclared ENEMY, a squadmate out of cohesion, a look preset that no longer resolves) — because a flat list that buries "unwinnable" under "wrong lighting" is a list you skim; ordering lives in `check()`, not the panel.

**It reads the LIVE board, and for the placement check that is load-bearing:** `apply_scenario` DROPS a unit whose cell spawn refuses (`push_warning` only), so a board that has been through a load has already lost the evidence — that fault is reachable ONLY by painting terrain under a unit already standing there, and it is also why the leaderless-squad case is not a check of its own but the placement finding wearing its full cost (`apply_scenario`'s "saved without a leader → leave them as solos" branch has no other cause). The file-shaped half of that question is a CI case instead: `test_no_shipped_mission_loses_a_unit_on_load` compares the loaded roster against `valid_entries().size()`. The report persists across page switches (what it found is usually on another page) and carries a "snapshot" line; only `board_loaded` clears it — deliberately not the header's `file_changed`, which also fires on Update and Save As and would wipe the report at the moment you'd just run it. Session's leaves are `ExperimentsTool` (the surface `Experiments.gd` always documented and never had), `ReplayTool`, `CameraTool` (#705's live camera readout, beside the camera paragraph below) and, since [#690](https://github.com/Phaazoid/Godoiosis/issues/690), `DevInfoTool` — **the Info page, which is what the dev tools can tell you that a document cannot**. Two halves. The BINDINGS half is a pure projection of **`Classes/core/Controls.gd`**, the binding registry that REPLACED `docs/SHORTCUTS.md` (its dev-tools table at #690, the file entire at #691) (GlossaryScreen/Glossary's exact shape) — each entry naming the Input Map action it fires or declaring itself `HARDCODED`, which is the field #691's player rebinding is gated on and the reason the store is in `core/` rather than `dev/`.

**The registry is law-tested against the live Input Map in BOTH directions** (`tests/law/test_controls_coverage.gd`), which a markdown table never could: the reverse direction is what found `dev_spawn_unit`, an action declared in `project.godot` and consumed by nothing, and it is why an action renamed or deleted now reds instead of rotting. The MACHINE half is read at DISPLAY time off whatever already owns each fact — the globalized report folder from `BugReporter`, `Build.version()`, `Checkout.describe()`, `upload_configured()`, and since [#855](https://github.com/Phaazoid/Godoiosis/issues/855) the telemetry folder and its owed / sent / held counts from `TelemetryStore` — so it is a second RENDER, never a second source; `refresh_on_show()` re-reads it because the checkout changes under a running game.

**Copy-to-clipboard on the paths, never `OS.shell_open`**: Explorer stealing focus is the two-OS-window trap, and the next dev key would go nowhere. `battle3d._update_help` was checked as a fourth consumer and did NOT fit — it read four live predicates to pick between two spellings per segment, a live-state readout rather than a projection. **[#816](https://github.com/Phaazoid/Godoiosis/issues/816) deleted that line outright** (dev: the top bar's controls are *"in the way of things I want to see now"*, and every binding it named already had a home here), which took the per-frame edge-detection behind it with it; the checkout stamp and the DEV MODE badge stay, each its own label. **A `does` is a LABEL** since the same ticket and its second pass (#820) — the player entries ran to 450 characters, then to a sentence, and the dev's answer both times was shorter: *"nobody is going to read all of the current novel"*, then *"Left Click - Select / Right Click - Cancel / Tab - Menu Swap"*. Two or three words; WHY a binding is the way it is stays in `docs/design/` and is cited from there.

**A `when` is a SECTION NAME**, so equal ones are kept CONTIGUOUS in the list: the Settings pane prints one on the change and the run below belongs to it, which is what stopped three deploying rows each carrying the same sentence. That pane also now gives a context heading a size step, the warm title ink and a rule under it — font size alone read as one more row. Pinned by `tests/dev/test_dev_info_page.gd`, which exists because neither the leaf law nor the window-fit law can see an UNBUILT page: it resolves fine and fits perfectly. **Board authoring UNDOES since [#391](https://github.com/Phaazoid/Godoiosis/issues/391) — Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y, plus an Undo/Redo row on the Tile Brush.** **Every door shares ONE dev-mode gate since [#1432](https://github.com/Phaazoid/Godoiosis/issues/1432): `DevController.history_block_reason()`, asked INSIDE `undo_board`/`redo_board`** (the buttons used to skip the keys' gate, so an Undo click outside dev mode rewound a played round's fire and gas). The row greys while it refuses, with the reason as its tooltip; that half is POLLED in `TileBrushTool._process`, because `game_state` announces nothing. A step is a **stroke** (mouse-down to mouse-up, bracketed by `DevController`), never a cell, and there is **ONE stack** across all five paint modes (Gas joined at #508) plus Resize Map, Clear Tile States and Clear All Gas — because a step is a whole-board **snapshot** (`BoardSnapshot`, captured/restored by `ScenarioManager.capture_board`/`restore_board`, which `capture_scenario`/`apply_scenario` now route through as well), and a snapshot cannot be split per store anyway: erasing a tile prunes that cell's states AND its height.

**That is also why the recorder is NOT in `BoardGrid`, which is what the issue proposed** — since #340 one click writes the grid *and* `BoardHeights`, so a grid-shaped recorder puts a raised cell back flat. `BoardHistory` (dev/) is the linear stack — N steps cost N+1 snapshots, capped at 50, and `board_loaded` resets it because a history belongs to one board. Pinned by `tests/dev/test_board_undo.gd`. **`MoodsTool` is the Moods tab (#212, 2026-08-15) — the one live surface for the HD-2D stack's aesthetic values**, ~40 knobs over four sub-tabs since #373 took the markup half away. The knobs themselves STORE nothing: every entry names a property that already exists on the running `Battle3D` world — an `@export` on a presentation node, or a field of a sub_resource authored in `Battle3D.tscn` — and both are reached the same way, through `get_indexed`/`set_indexed`, which is why one table addresses both homes. Three things are load-bearing: **(1)** the host is PUSHED in by `battle3d._ready` (`DevOverlay.attach_3d_host`, which stores it as `DevOverlay.host_3d` and forwards a copy to this panel — **renamed and re-homed by #234**, when the Scenario tab became its second consumer and a tuning panel was quietly serving as the project's host registry), never looked up, so the game subtree gains no upward path to the 3D scene and a flat `Main.tscn` launch simply reports "no 3D host"; **(2)** a knob may only name a property that is authored and READ (see the tuning rule above); **(3)** "has this moved?" is an APPROXIMATE compare — engine properties store single-precision and a euler component round-trips through a basis, so an exact one reported the sun as changed immediately after a Reset restored it. Board-markup colours were a declared SECOND table here (`LAYER_KNOBS`) until #373 moved them to `GameKnobs.CLASS_KNOBS` with the rest of the markup; the reason they are a second table at all is unchanged — they address a value authored at CLASS level (an entry of `BoardOverlays.LAYERS`, or an `OverlayManager` static) rather than a node property. Which layers appear there is measured, not chosen: `set_layer_modulate` *replaces* a layer's albedo, so any layer `OverlayMirror` or `battle3d` already drives per frame (ATTACK, AIM, HOVER) would take a knob that silently reverts.

**A tuned look SAVES as of [#253](https://github.com/Phaazoid/Godoiosis/issues/253) part 1 (2026-08-15): a named `LookPreset` (`presentation/`, dumb data) under `Resources/LookPresets/`, on the ordinary dev-tab idiom** — Load / Save As / Update (load-gated *and* confirmed) / Delete, all riding `DevWidgets`. Four things are declared rather than obvious. **(a)** A preset stores `key → value` where the key is *derived* (`"<node>|<prop>"`), never the property path — `KNOBS` is the one answer to "which property is Sun energy", so a path in a preset file would be a second one, and a rename would mean editing every preset instead of one table row. **(b)** It captures **scene mood, not game settings** (dev, 2026-08-15): camera *framing* rides along; camera *handling*, all of board markup, the unit readout and the brush ghost do not. That was `PRESET_EXCLUDED`, a list, until **#373 made it structural by MOVING that whole population to `GameKnobs`** — a preset cannot reach a knob that is not in the table, so the list emptied and was deleted. The default is IN and now unconditional: every Look knob joins presets, which is why the question to ask of a new one is *may one board differ from another about this?* **(c)** Loading a preset is what **Reset** returns to: since #1376 Reset re-reads the FILE of the mood last loaded or saved here (see *Reset-to-saved* below), where it used to restore the values last applied, and a **Default** button is the one way back (it replaced an `(authored scene)` dropdown row in part 2 — once a mission carries a look, the scene stops being the truth, so two affordances were two names for one idea). **(d)** The DEFAULT is writable too since [#386](https://github.com/Phaazoid/Godoiosis/issues/386) — an *Update default* button beside Default, confirmed rather than load-gated (there is one default and it is always the target, so the mis-click to guard is not "the wrong file" but "not yet"), leaving the panel in the state pressing Default would because the file now holds what is on screen. It replaced **Copy Values**, which spelled the diff against `Battle3D.tscn` as paste-ready GDScript to hand-type back into the scene: the same act with a worse door, and a second answer to "make this the baseline". Its whole cluster went with it (`changed_values`/`_paste_split`/`_format`/`authored_of`/`target_of`), and the panel now says **mood** throughout while the files it writes stay `LookPreset`s — renaming the resource would drop the look from every saved mission, so the split is declared. Whole-table capture is deliberate (a preset cannot drift when the scene is re-tuned) and its twin cost is accepted: a preset does not mention a knob added later, so `apply_preset` **reports** both directions — knobs it predates (left at the authored value, named so they can be back-added via Update) and saved keys that no longer resolve.

**Part 3 shipped the starter set the same day — twelve presets under `Resources/LookPresets/`** (the four `look_dev.gd` moods — **whose source table [#393](https://github.com/Phaazoid/Godoiosis/issues/393) then DELETED, so the seed is not a fork: the look-dev scene resolves those four by NAME through `LookKnobs` now** — the un-tamed Forest Fire that got #212 filed, Dawn/Storm/Diorama, and the four `Opus` alchemical grades), authored *through* the capture path by a one-off generator that is deliberately **not** committed — the `.tres` files are the artifact and the panel is where they evolve, so a checked-in generator would be a second authority the moment one gets tuned and Updated. `tests/dev/test_look_presets.gd` is a content law over the shipped set (every preset names every in-scope knob; nothing out-of-scope leaks in), and its `_names()` non-empty assertion is **load-bearing, not decoration** — falsified by pointing the scan at an empty folder with the assertion removed, which passes all four cases over zero presets.

**PART 2 CLOSED #253 (2026-08-15): a board wears the look it names.** `ScenarioData.look_preset` holds a **NAME, never a `LookPreset` reference** — a dangling `ext_resource` can fail the whole scenario load rather than degrade, so "the preset was deleted → fall back to the default" is only implementable soft, and a Resource field risks EMBEDDING the preset on save (the #177 `unit_data` trap). `ScenarioManager.current_look_preset` is the one store (set in `apply_scenario` BEFORE its closing `board_loaded.emit()`, zeroed by `clear_board` so `spawn_sandbox` cannot inherit the last mission), the dev Scenario tab picks it, and `battle3d._apply_board_look` applies it — deliberately named *apply this preset*, never *the mission’s look*, because weather (#277) and battle-effect flashes (#278) are meant to drive the same seam and naming it after its first caller would fork a second applier. The knob table and the apply path therefore MOVED to **`Classes/presentation/LookKnobs.gd`** (static; `MoodsTool` is now purely the panel, and since #373 keeps no table at all), since shipping code cannot route through a dev tab. The fallback is **`res://Resources/DefaultLook.tres`, deliberately OUTSIDE the scanned folder** — invisible to the dropdown, untargetable by Delete, unshadowable by Save As, all structural rather than a filename check; it ships byte-identical to `Day` and is a *declared* duplication, since the two answer different questions and are meant to diverge. Pinned by `tests/flow/test_mission_look.gd`, whose load cases drive the real `apply_scenario → board_loaded → battle3d` path and assert on the live scene property (falsified by no-opping the handler — both ends were correct while nothing connected them is exactly #103).

**A board may also author WHERE THE CAMERA OPENS ([#234](https://github.com/Phaazoid/Godoiosis/issues/234), 2026-08-15) — the same store/writer shape, one field along**: `ScenarioData.camera_start` is a `CameraPose` (aim + yaw + distance), null = derive from the player's units, and *authored is authoritative, the derivation is the fallback* is declared at `battle3d.fit_camera`. Three things diverge from the look and are load-bearing. **(i) A REFERENCE, not a name** — the opposite of `look_preset` right above, because a `CameraPose` has no file and no life outside its board, so embedding it as a sub-resource is what should happen; *measured*, since #177 makes the worry reasonable: a load-then-Save-As re-embeds it as a fresh `[sub_resource]` rather than writing a cross-file `ext_resource`, so no defensive `duplicate()`.

**(ii) `frame(shot, bounds)` could not be the door** — it derives position and distance from a volume and deliberately never touches yaw, and free orbit makes yaw part of what a shot IS, so `CameraRig3D.pose()` is the authored twin, reusing `rebound()` verbatim for the bounds half; **yaw is set BEFORE the bounds are solved**, because `rebound()` fits through the camera's own basis and a ceiling solved at the old yaw is a fit for an orientation the shot is never seen at. **(iii) NOTHING VALIDATES a start** (dev call): a stale aim is clamped *silently* by the `pan_limit` clamp `_process` already runs, so there is no second answer to "where may the camera be" — re-capture is the fix. Authored via a Capture button on the Scenario tab; 3D only, declared on [#292](https://github.com/Phaazoid/Godoiosis/issues/292) because the flat view has no opening shot to diverge from. Pinned by `tests/presentation/test_camera_start.gd`.

## The Tiles tab

**The TILES tab (`Classes/dev/ObjectTool.gd` + `ObjectKnobs.gd`, [#272](https://github.com/Phaazoid/Godoiosis/issues/272) as the Objects tab, 2026-08-16; purely per-TYPE between [#380](https://github.com/Phaazoid/Godoiosis/issues/380) and [#902](https://github.com/Phaazoid/Godoiosis/issues/902)) is everything one TILE answers for, and since #902 it is THREE STORES read narrowest first — this tile (a TileSet column, *Save tile fields*), every tile of this ground (the ignition `.tres`, *Save ground rules*), game-wide (the `@export` declaration, *Save game-wide defaults*).** #902 is the dev's *"look values for objects on their individual pages, so that they are easier to find"* plus his #891 ask for a burnable tick and a turns dial; what moved for the seven globals is the PAGE, not the store — same `node:property` row, same `KnobSource`, same declaration — so #380's *two stores, declared* stands and only one of them changed which page draws it.

**The class and node names are deliberately unchanged** (`ObjectTool`/`ObjectKnobs`/`%Objects`): the leaf LABEL is what the dev reads, and a `class_name` rename is ~12 files of churn that would bury the change in review. The picker widened 25 props → 36 named tiles, because `grass_basic` and `grass_clover` are FLAT and half the grass in the game had no page while its ground's burn rules needed one; `object_tiles()` stays NARROW beside `authorable_tiles()` on purpose — it answers *which tiles stand something up*, which `BoardMirror`'s light coverage asks, and widening it in place would have left `test_board_mirror` picking a flat tile and passing **vacuously**. `fields_for` gained an explicit FLAT guard for the same class of reason: empty `shapes` meant *every object* while every object was non-FLAT, so re-reading it would hand `grass_basic` a Rules height, which `Reach` honours for any cell. Its globals half (prop geometry + the fire block) moved to the Game tab in #380, which also gave the four lamp defaults (`BoardMirror.prop_light_*`) their first rows anywhere — plus the setter-and-sweep the geometry globals already had (`_restyle_prop_lights`, walking `_props` ONLY so fire's own light never moves), without which a light knob is #264's born-dead slider. **PER-TYPE FIELDS** (`ObjectKnobs.FIELDS`) are TileSet custom-data columns on `Resources/TestTiles.tres`, **authored into the file rather than added at runtime** — a schema migration that runs once on one machine is a path no test executes again — with the table declaring which `PropShape`s each field applies to so a meaningless row cannot be drawn. A global is the DEFAULT and a tile may override it; `BoardMirror` is the only place that resolves the two — its light-override stash rides node meta (`LIGHT_OVERRIDE_META`, the `OVERRIDE_META` shape) because the sweeps have no grid to re-read a tile from.

**`INHERIT` is ZERO and that is forced, not chosen**: `TileData.has_custom_data` answers whether the LAYER exists, never whether this tile wrote a value, so an unauthored field reads its type's own default and the sentinel must BE that default — and a `Color` layer's default is OPAQUE BLACK, not transparent. `BoardMirror.LIT_PROPS` (a hardcoded `["Lantern"]` matched on display name) was **deleted** into the `prop_lit` column, the fact having always been content. Two traps it re-paid: `_reconcile_prop`'s diff key names only what the reconcile is HANDED (the cell's tile, and since #342 its corners), so a prop whose tile is unchanged is left standing and blind to the tile *gaining* a field (the #308 shape — `drop_props()` invalidates at the source rather than widening the key, and that is still right here for the reason #342 is the opposite case: a per-TYPE edit changes every cell of that type while no cell changes, so there is no per-cell fact to compare), and a global's setter that writes flat across standing nodes silently stomps an authored override, so every sweep re-derives through the same `_resolved()` the builder uses. Pinned by `tests/dev/test_object_fields.gd` + the light cases in `tests/presentation/test_board_mirror.gd`.

## The Game tab

**The Game tab (`Classes/dev/GameTool.gd` + `GameKnobs.gd`, [#373](https://github.com/Phaazoid/Godoiosis/issues/373), 2026-08-19) is where the game's own presentation constants live and are KEPT** — board markup and its colours, the unit readout, camera *handling*, the brush ghost. Every one of them was already excluded from presets; what it had no door to was PERSISTENCE, since the Moods tab's only *keep this* buttons write a `LookPreset` that deliberately omits them. The dev found it the ordinary way: *"these are game-wide settings I want permanently changed, but they are tied to different environmental things."* Since #380 it also holds world construction and the fire block (from the Objects tab), over seven sub-tabs (Mission joined for #101's clock threshold) — **though `GameKnobs.KNOBS` stopped being the game constants ENTIRE at [#902](https://github.com/Phaazoid/Godoiosis/issues/902), which moved seven world-construction rows to `ObjectKnobs.GLOBALS` so they sit on the tile that falls back to them. Same shape, same `KnobSource`, same declaration; only the page differs, and the laws that are about that SHAPE walk both tables (`_declaration_tables`) while the group / row-somewhere / Reset cases stay pointed at this panel alone** — the fire one widened to **Elemental** by [#420](https://github.com/Phaazoid/Godoiosis/issues/420), which also took `cover_scale` off World (#326 had already ruled it fire's kind of thing) and settled that **glow is two questions**: the `glow_*` bloom PASS is one Environment per board and therefore mission mood forever, while how hard a SOURCE burns is its own table's row — `flame_glow_color`/`flame_glow_energy`/`flame_light_color`, which had been hardcoded, so the only glow-shaped dial in the panel was the scene-wide wrong one. A knob written once at build needs a SWEEP (`_rebuild_fires()`) or it is #264's born-dead slider — which `flame_light_range` had actually shipped as.

**The build-time law ([#1373](https://github.com/Phaazoid/Godoiosis/issues/1373), 2026-10-21).** The live law (write, wait two frames, read the PROPERTY back) cannot see a row read only when something is BUILT: the property holds and nothing on screen hears of it. An audit and a windowed scan found thirteen such rows still shipping (the bracket's three, both camera limits and the Moods tab's fit margin, the brush ghost's alpha, the flame ground gap, the thin gas floor, the two lifts and the two billboard rows), plus the reach and tether cones' radii and the Glossary's cached Maim numbers. Two clauses in `tests/dev/test_build_time_knobs.gd` close it. Structurally, every node row in the declaration tables either carries a setter or is named in that suite's `READ_LIVE`, with HOW it is read. Behaviourally, one case per part stands the part up on the real board, writes the row through the panel's door, and requires the STANDING node to change. A number composed UPSTREAM of the node that owns it (a lift OverlayMirror bakes into a line, a cone radius that is a multiple of a beam width) reaches the screen through `BoardOverlays.geometry_version`. OverlayMirror and GasMirror gate on that version and drop their caches when it moves (#308's rule: gate on the store, never on a copy).

**TWO TABLES, because a game constant is authored two ways.** `KNOBS` names a node property (read/written through `LookKnobs.read/write` — only the table forks, the property access does not); **`CLASS_KNOBS` names a value authored at CLASS level** — an entry of `BoardOverlays.LAYERS` or a `static var` on `OverlayManager` — which has no node property to address, and no baseline until one is captured (they are readable with *no host at all*, so `_ready` captures too or all three statics read as moved the moment the panel is built). Both land in one edit list, so a marker's lift and a layer's colour, both authored in `BoardOverlays.gd`, are written in a single read-modify-write.

**`KnobSource` is the one writer** (extracted from `ObjectKnobs`; since #380 this tab is its one caller, but the split stands — the transform is testable without a table, and the next table that wants a Save gets this one rather than a copy): three shapes — an `@export` default, a `static var`, and one `"color"` entry inside a const `Layer -> spec` table — and **each returns `""` on a miss, never the source unchanged**, because the failure worth designing against is the save that silently writes nothing. An edit carries a `source` tag naming which table it came from, since the two tables share an index space and a bare row number would move the wrong baseline on a partial save. The LAYERS rewriter is deliberately fragile in a KNOWN way (one line per entry, `"color"` first): reformat that table and every colour save fails loudly, pinned by its own case. Also: **a colour save touches the entry's colour alone**, so the sort/kind relationships #231 pinned cannot be moved by tuning a colour.

**Every save that can overwrite asks first (#380, dev 2026-08-19: "anything that can overwrite settings should")** — every tool's Update (load-gated *and* confirmed, `DevWidgets.confirm_overwrite`), this tab's source save, the Objects tab's tileset save; Save As alone never confirms because `refuse_existing_file` makes it structurally unable to overwrite. **Its twin from the other end is the UNSAVED MARKER ([#389](https://github.com/Phaazoid/Godoiosis/issues/389)): a save button says whether there is anything to do (`Save *`) as well as asking before it does it.** `DevWidgets.mark_unsaved` is the one spelling, and it deliberately never DISABLES — Save As stays legitimate on a clean panel, and a greyed Save would bury the precise "Nothing has moved off what is saved" its handler already gives. Each panel answers `has_unsaved_changes()` its own way, which is why the three shipped together: Game holds value baselines; Moods keeps a flag and the FILE its Reset re-reads (a values baseline until #1376); Objects keeps a flag for its tile fields, because those edits go straight into the live TileSet, and a baseline only for its game-wide globals. The flag is TOUCHED-since-save, not a live compare — reading every knob resolves its node, so a derived answer would be dozens of `get_node` calls per drag tick — but **Game re-derives it from `changed_indices()` after a save rather than clearing blindly**, so a partial save stays marked. Pinned by `tests/dev/test_unsaved_markers.gd`, one suite over all three. Pinned by `tests/dev/test_game_knobs.gd` (the live no-placebo law, the panel wires, the save laws, the ask-first pair) + `test_knob_source.gd` (the transforms) + the per-button cases in `test_dev_tool_overwrite_guards.gd`.

## Reset-to-saved

**Every page that edits LIVE offers a Reset that puts it back to its FILE ON DISK ([#1376](https://github.com/Phaazoid/Godoiosis/issues/1376), 2026-10-21).** The dev's ask: *"There should be a reset button in any page where I'm editing visuals, which will reset it specifically to how it was before I last saved."* His ruling on the open question, the same day: Reset means **last saved, the file on disk, on every page, the Moods tab included; Default stays its own button.** He scoped it to the LIVE pages (an edit lands on the shared object before any save: Moods, Game, Tiles, Weather, Weights) and ruled one Reset per Save on the Tiles page, so putting back a burn clock never throws away a tile-light edit.

**One door, `DevWidgets.revert_to_saved(live, path)`, is `save_over` fed from the other end.** `load()` serves the cache, and on a live page the cached object IS the edit, so "saved" has to be read with `ResourceLoader.CACHE_MODE_IGNORE` (`DevWidgets.saved_copy`) and copied back onto the live object through the same `_adopt` a save writes through, so every holder sees the reset (#589: a path has one object). IGNORE and not IGNORE_DEEP, deliberately: dependencies come from the cache, so a shape or texture the file names stays the one object everything shares (pinned in `test_dev_tool_live_sync.gd`). **`DevWidgets.offer_reset(button, dirty)` greys a Reset while its page's marker is clear**, called beside every live page's `mark_unsaved` so the two cannot disagree. A Reset DOES disable, unlike the Save beside it: a clean page has nothing to put back, where a clean Save still has Save As's fork. The handlers stay ungated, since a clean press is a harmless no-op.

Per page:

- **Moods** names the mood FILE Reset re-reads (`_saved_path`) instead of holding a values snapshot: the mood last loaded or saved here, the default after Default or Update default, and with nothing applied through the panel, the mood the BOARD wears (`LookKnobs.resolve`, the answer battle3d applied at the board load). Before #1376 a fresh panel's Reset went to `Battle3D.tscn`'s raw values, which no board ever wears, and a look applied with no file behind it counted as "saved".
- **Game** and the Tiles page's **Reset defaults** were already right: their baselines are what the declarations held at attach, re-read after every landed save. They only gained the greying.
- **Tiles: Reset tile fields** is `ObjectKnobs.revert_fields`, COLUMN BY COLUMN rather than `revert_to_saved`. Adopting a TileSet whole would swap its atlas sources out from under every `TileMapLayer` drawing them, and the `FIELDS` columns at alternative 0 are all the page writes. **Reset ground rules** reverts each staged reaction onto the instance the running fire's `fuel_source` already holds. The Burnable tick is not undone: it already created or deleted its file.
- **Weather** mirrors its Save (#1370): every touched file, not only the one on show. `WeatherMirror` polls `look.fall` per frame, so a reverted fall re-switches the mirror with no extra wire.
- **Weights** reads only the field it edits (weight, or a sparse BLD that comes back absent) out of the file. Its old Reset restored a snapshot taken at first touch, which would have adopted another page's in-memory change as "saved".

**`tests/law/test_live_pages_offer_reset.gd`** scans `Classes/dev/`: a file calling `mark_unsaved` must call `offer_reset`, or be declared in `EDITS_A_COPY` (Rosters and Dialog timelines, whose marker sits on a form copy and whose Load re-reads the file). A declared page that stops wearing a marker goes red as stale. **Its stated limit is a live page with NO marker**: the Attack Editor's Weapon Families mode and its named effect looks edit the cached object (a named look's staged copy is a SHALLOW `duplicate()`, so its `overrides` Dictionary is still the library's) and wear no marker yet, so the scan cannot see them. That is the follow-up, not a pass.

## The dev/ folder and the content lints

`dev/` — dev-only tools (`DevOverlay` + per-tool scripts incl. `MoodsTool`/`GameTool`/`ObjectTool` and the `KnobSource` writer behind the latter two, `DevWidgets`, `Experiments`, and `LibraryField` — the one pick/name/fork/delete flow for a field holding a SHARED library resource, #900), plus `TestBoard`. **`AttackLint` (`weapons/`) is `BoardLint`'s sibling one domain over ([#473](https://github.com/Phaazoid/Godoiosis/issues/473)): *can this authored attack ever be fired?*, refused at the Attack Editor's save and swept in CI over every shipped attack. Same discipline — it BORROWS the rule, asking `Reach` rather than reading a pattern's numbers, so the bare-fists fallback comes along and a pattern class added later needs no edit. The rule is "selects at least one cell"; `min_range` above `max_range` is one way to break it, not the rule itself. **A SECOND rule landed with #485 — a `scaling_blend` that does not total `Stats.BLEND_TOTAL` — and it is the lint's first DEGRADES tier, which is what made the two tiers real at the CONSUMER as well as in the rule: the Attack Editor had treated every finding as fatal, and refusing there would have left the only tool that can repair such a file unable to write it.** **`WeaponTemplateLint` (`weapons/`) is the third of that family ([#486](https://github.com/Phaazoid/Godoiosis/issues/486)): *can this authored template become a weapon at all?*, refused at the Item Editor's Prototype-mode save and swept in CI over every shipped template. One BLOCKS rule — an unset `weapon_type`, which makes `WeaponInstance.make()` `push_error` and return NULL, so the file lists in every dropdown and produces nothing carryable — and two DEGRADES (no main attack, a space with capacity below 1). The missing-main tier is set by the OTHER surface rather than by taste: the Attack Editor's Weapon Families mode already saves a main-less family deliberately, and blocking here would give one rule two answers depending on which panel you were in. Scoped to faults the authoring door can produce: a template with NO spaces is a legal design (predetermined power, no customization), not a finding.** **`AttackLint` also carries a per-attack LOOK check since [#900](https://github.com/Phaazoid/Godoiosis/issues/900)** -- a slot holding another element's look, or a slot for an element the attack no longer carries; both DEGRADES, since the attack fires either way and a BLOCKS would refuse the one panel that can repair it. The per-FILE half (a key naming no live row, what a knob rename leaves behind) is `GameKnobs.stale_look_keys` and is swept per look rather than per attack, since a shared look would otherwise be counted once per wearer and an unworn one never at all. **`WeaponInstanceLint` (`weapons/`) is the FOURTH ([#837](https://github.com/Phaazoid/Godoiosis/issues/837), 2026-09-08): *is this weapon's fitting still legal?* — the instance question, split from the template one for the reason #486 split them everywhere else. Its one rule is `fit_block_reason` RE-ASKED for every fitted mod, which is what makes four faults cost one clause: a mod stranded past a space Remove deleted (and therefore UNREMOVABLE, since `space_holding` scans only the spaces the template still has), one over a capacity narrowed under it, one whose family stopped matching after a retype, and a hand-edited second main-replacer. It needs a PROBE — a `copy_for_grant` with that mod taken off — because `fit_block_reason` answers *"already fitted to this weapon"* for a mod that is on the weapon and counts its size in `used_capacity`; a COLLISION therefore names both its mods, which is the borrow being symmetric rather than a miscount. DEGRADES throughout, the Item Editor renders it under the weapon's form, `BoardLint` scopes it to the live board, and CI sweeps the two on-disk populations where each is already loaded.** (`TestBoard` is the hardcoded five-unit sandbox board, pre-scenario scaffolding: `game.spawn_sandbox()`, behind Mission Select's Sandbox row, is its one call site, and `game._ready` no longer spawns it.)

**Every dev Delete asks who uses the file BEFORE its confirm ([#1366](https://github.com/Phaazoid/Godoiosis/issues/1366)).** `DevWidgets.refuse_delete_in_use`, built on `ResourceCatalog.users_of`, refuses a file any `.tres` under `Resources/` or `Scenarios/` names by path, because the referrer would become a dangling `ext_resource` (#596). The Attack Editor and `LibraryField` asked from the start; the Character and Item pages went straight to the confirm, and the Dialog page asked a narrower scan of its own, until #1366. `tests/law/test_dev_deletes_ask_who_uses_the_file.gd` scans every `confirm_delete` door. Four pages are DECLARED exempt, because nothing names their files by path: Moods and Rosters are named by NAME, and nothing holds a scenario or an ignition reaction. A fifth, Tile Brush, deletes no file. The law reads the disk for that claim rather than trusting it: the day a scanned file names one of those pages' files by path, it goes red and names the page. Neither scan sees a `user://` save slot or an unsaved edit on the live board.
