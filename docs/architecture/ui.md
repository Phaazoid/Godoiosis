## ModalLock

**`ModalLock` (`ui/`) is the whole input lock. It freezes the GAME SUBTREE — `game.process_mode = PROCESS_MODE_DISABLED` — and must never go back to `get_tree().paused`.** `ModalLock.claim(self, game_node)` joins the `modal` group, sets `process_mode = ALWAYS` on the modal, and freezes Game — called from **`ModalCard._build_chrome`** and nowhere else, gated on that surface's `claims_modal_lock` (default `true`). **It pauses the DIALOG too since [#1034](https://github.com/Phaazoid/Godoiosis/issues/1034)** (dev ruling, replacing #687's *"not frozen by a card"*): the layout sits BESIDE `Game`, outside the subtree, and no card takes focus, so Enter/Space advanced the dialog behind the pause menu. `Dialogic.paused` is derived from the SAME group state, written before `_apply`'s `game_root` check so it lifts even for a card that outlives its Game — Dialogic is an autoload, and a stuck pause hangs every dialog after it, in the game or the next suite.

**An open action wheel is CLOSED rather than frozen at the two doors that can change the board under it** — Esc's `_open_pause_menu` (first, before it stashes `prior`, because the close clears the selection and so writes `game_state`) and `MissionController._close_deployment_menu` (every phase exit AND every board teardown, run before `clear_board` frees a unit) — through `MainActionMenu.close_ring()`; F3's card is a detour and leaves the wheel frozen underneath. Before [#143](https://github.com/Phaazoid/Godoiosis/issues/143) only `PauseMenu` claimed it, so the victory/defeat banner and the Crisis prompt left the board/camera unfrozen while up; all four cards now opt in and **`MissionSelectScreen` deliberately opts OUT** — it is not a modal, and a Game left DISABLED behind it would never run the mission picked next (pinned by `test_return_to_title_lands_on_the_menu_with_the_game_thawed`). Why a lock at all: **`CameraController._process` reads `Input.is_action_pressed("cam_*")` — bound to WASD — and a global `Input` poll does not travel through the scene tree**, so no focus, `mouse_filter` or `set_input_as_handled` can stop it (typing "was" into the report card panned the board, 2026-08-05). A predicate individual loops consult would have left `HoverPresenter._process`, and the next `_process` anyone writes, with the same bug.

**The tree-pause version SHIPPED BROKEN and bricked the game for one round — this is the trap.** A modal lives inside the SubViewport, so a click travels `root viewport → GameContainer (SubViewportContainer) → GameView (SubViewport) → card_layer → modal`, and **`GameContainer` only forwards input into the viewport while it can process**. `get_tree().paused` froze that link, so `PROCESS_MODE_ALWAYS` made the modal processable and it *still* could not be clicked: the pause menu drew, ate the board, and had no working way out. Probed both ways — identical on "game stopped", opposite on "click path alive". Any future full-screen UI inside this SubViewport inherits the same constraint.

**Group membership is the state; the lock is DERIVED from it** (`_apply` re-reads the group), which is what makes the pause-menu → card → pause-menu handoff gapless — no modal releases on the strength of its own departure while another is opening. It doubles as the re-entry brake: the relaxed Esc gate would otherwise stack a card on the pause menu, since MENU is itself a locked state.

**Anything under Game that must survive the freeze sets `process_mode = ALWAYS`**: the locking cards (`PauseMenu`/`MissionEndBanner`/`ReportPanel` — set for them by `ModalLock.claim`, which `ModalCard._build_chrome` calls; `CrisisPrompt` was one until #158 removed the prompt), and **`BugReporter` + `ReportUploader`** — load-bearing rather than tidy, because an upload is in flight *while the card is up*, `HTTPRequest` emits `request_completed` from its own internal process, and a freezable uploader never finishes: `submit()` awaits forever and the card sticks on "Sending..." with no button to press. `DevOverlay` needs nothing — it is a sibling of `GameContainer`, outside Game entirely.

**Dev controls are a LAYER ABOVE this lock ([#154](https://github.com/Phaazoid/Godoiosis/issues/154), 2026-08-07), and `DevController` is the in-Game exemption.** The lock's boundary was drawn before dev affordances were in scope, so every dev key sat under the freeze and **F3 did nothing while a menu was up** — found in play, right after #149. `DevController` now owns all three dev keys (F1 toggle overlay / F2 reset scenario / **Shift+F3 instant report**, plain F3 since [#1050](https://github.com/Phaazoid/Godoiosis/issues/1050)) and is `PROCESS_MODE_ALWAYS`, so they fire behind a card; the mechanism is that **a freeze stops callbacks, not method calls**, so an always-on node drives the frozen `ScenarioManager`/`BugReporter` fine. `game.gd._input` therefore keeps `ui_cancel` and the handful of player keys beside it — **a DEV key added back there dies silently whenever a modal is up**, which is the whole trap, and it is exactly the declared residual on the player's own F3: that one IS in `game.gd._input`, so it is inert under the pause menu, the mission-end banner, dialog, Settings and the Glossary, and live on the title screen and through the pre-mission phase (both set `claims_modal_lock = false`). The banner needs no key: it carries the report form itself since [#1052](https://github.com/Phaazoid/Godoiosis/issues/1052). Two deliberate exclusions: board manipulation (dev spawn, tile brush, DEV_MODE-gated) stays frozen, since editing what the card is covering is worth nothing -- the brush by living in `game.gd._unhandled_input`, and SPACE's spawn by asking `ModalLock.any_open` itself since [#1446](https://github.com/Phaazoid/Godoiosis/issues/1446) moved it into `DevController` so the dev window could reach it (F4 and F5 moved in with it and DO run behind a card: a view swap and a readout edit nothing); and all three dev keys are uniformly behind `DevTools.enabled()`, where previously only F2 was — so **the INSTANT report does not exist in the demo preset**, which omits the `devtools` feature, while the card-opening F3 ships to everyone. Pinned by `test_dev_controls_outlive_the_modal_lock` + `test_every_dev_key_reaches_its_target`. *(Corrected 2026-10-20: no test by that name ever existed. The per-key cases are `test_the_dev_overlay_hotkey_toggles_dev_mode` and `test_the_reset_hotkey_rebuilds_the_board` (`tests/ui/test_game_scene_smoke.gd`) and `test_the_report_hotkey_fires_behind_a_modal` (`tests/ui/test_report_flow.gd`).)*

Pinned by `test_a_modal_leaves_the_click_path_into_the_subviewport_alive`, which asserts the whole chain rather than the endpoint.

**Falsified: with the tree-pause version restored, every other case in that suite passes** — including the one asserting the game is frozen, since tree-pause does freeze it — and only this one goes red. That is the "test the wire" law in miniature: the original suite emitted `chosen`/`finished` directly and never exercised a modal button, so it could not have caught this.

## ModalCard

**`ModalCard` (`ui/`) is the one scaffold for every full-screen surface over the board** — `PauseMenu`, `MissionEndBanner`, `ReportPanel` and `MissionSelectScreen` all extend it (`CrisisPrompt` did too until #158 deleted it) (#143 + follow-up; it was `ChoiceModal` until `ReportPanel`, a *form* rather than a choice, moved onto it). These hand-built the same chrome five times, which is why ONE mistake — `set_anchors_preset` instead of `set_anchors_and_offsets_preset` — put three of them in the top-left corner at once (#132). **Styling is overridable FIELDS assigned in a subclass `_init()`, not call parameters**: `backdrop_color`, `margin_h`/`margin_v`, `content_separation`, `content_alignment`, `framed`, `title_font_size`/`title_color`, `button_size`, `card_z_index`, `claims_modal_lock`. Change the canon here and every surface changes; the four originals had drifted (margins 48/32 vs 32/24, separation 12/16/20, alpha 0.65/0.70/0.75) with no design reason.

**Chrome is overridable STEPS, not one growing parameter list** — `_apply_root`/`_build_backdrop`/`_build_branding`/`_build_frame`/`_build_content_box` — which is the only reason `MissionSelectScreen` fits at all: it is unframed (`framed = false` skips the panel+margin), opaquely backed, and adds its logo via `_build_branding` so the node lands in the right sibling order. **Its backdrop being fully opaque is load-bearing, not styling** — `MissionController.abandon_mission` leaves the abandoned board standing and relies on it to hide it (pinned by `test_mission_select_backdrop_is_fully_opaque`). All five take the **Game node**, never a parent, so a card cannot be built outside `card_layer` — every card's own CanvasLayer since [#1034](https://github.com/Phaazoid/Godoiosis/issues/1034), over the wheel and the dialog (see `UiLayers` below).

**ESC BELONGS TO THE CARD, and the base owns the mechanism while each subclass owns the POLICY (#418 follow-up, 2026-08-28)** -- `_input` here, an `_on_cancel() -> bool` virtual per surface, `true` meaning *I took the key*. It has nowhere else it could live: `game.gd._input` stands down on `ui_cancel` while anything is in the `modal` group, so **a card that does not answer SWALLOWS the key** -- which is how the settings page became a room with no door once its content outgrew the viewport, and PauseMenu and GlossaryScreen were silently in the same state. The three surfaces that had hand-written the handler (ReportPanel, SaveLoadScreen, ConfirmCard) collapsed into it with their policies verbatim, and the bool is what made that possible: ReportPanel SWALLOWS the key mid-send without acting, which a plain `dismiss_on_cancel` flag could not express. The default takes NOTHING -- `MissionEndBanner` and `MissionSelectScreen` keep it, because an ending is chosen rather than dismissed.

**A CARD WHOSE CONTENT CAN GROW MUST BOUND ITS OWN BODY**: the frame centres on a full-rect Control and has no ceiling, so an over-tall card simply hangs off both edges; `GlossaryScreen`/`MissionSelectScreen`/`SettingsScreen` each wrap their body in a `ScrollContainer`, and the settings page sizes its one from the viewport rather than a constant. **BOUNDING THE GROWING REGION IS NOT ENOUGH IF THE FIXED ROWS ALREADY OVERFLOW ([#723](https://github.com/Phaazoid/Godoiosis/issues/723), 2026-09-07)** — `MissionSelectScreen`'s mission list had its scroller from the start and still overflowed by 58px with no save on disk (832px wanted against 720 with one), because the scroller claimed a FIXED 420 and the eight fixed rows below it did the rest; *Send Feedback* and *Quit Game* sat off the bottom, which is why the title screen read as having no feedback door. It overrides `_build_frame` to a full-rect `MarginContainer` and lets the list EXPAND into what the fixed rows leave, so the only region that can scroll is the one that gives.

**This is never window-size dependent and that is the whole reason it had to be fixed**: `GameSurface` lays the UI out in a design space that is exactly 1280×720 for ANY 16:9 window, so a maximised 1440p monitor has the same 720px as the editor. Ask it as a property against the viewport's own height (`tests/ui/test_title_screen_fits_the_viewport.gd`), never a pixel count. Measuring that needs the **outermost CONTAINER**, never `self` -- a plain Control aggregates nothing, so `ModalCard.get_combined_minimum_size()` is `(0, 0)` however much is built under it. Pinned by `tests/ui/test_modal_card_scaffold.gd`, whose cancel cases were the FIRST `ui_cancel` coverage in the repo -- the three hand-written handlers had none.

## UiLayers

**`UiLayers` (`core/`) is the one declared UI stacking order, and it holds TWO AXES NAMED APART since [#1034](https://github.com/Phaazoid/Godoiosis/issues/1034)**: the `LAYER_*` constants are `CanvasLayer.layer` values (`LAYER_HUD 0` = `UILayer` → `LAYER_DIALOGUE 1` = Dialogic's layout → `LAYER_ACTION_MENU 20` = the wheel → `LAYER_CARDS 100` = `game.card_layer`, where every `ModalCard` mounts), and the rest are `z_index` values grouped under the layer they order WITHIN (`MISSION_STATUS 1` → `HOVER_PANEL 2` → `INVENTORY_POPUP 10` inside the HUD; `MENU_SCREEN 100` → `MODAL_CARD 200` → `DRAG_PREVIEW 300` inside the cards).

**A `z_index` never crosses a `CanvasLayer`, for the eye OR the mouse** — GUI picking sorts roots by layer first, and inside one layer by TREE order, not z (probed on 4.7.1). One unprefixed list is what shipped the bug: the cards read their 200 as a z inside layer 0 while the wheel read its 20 as a layer, so both the wheel and the dialog out-ranked the pause menu, and a click on it advanced the dialog. The order is FORCED, not chosen — the Prolog's `UNIT_SELECTED` line plays while the wheel is open, so the wheel must sit above the dialog; what moved was the cards. `tests/law/test_ui_layers_one_axis_each.gd` refuses a write that reads the wrong group. The table replaced four scattered magic numbers whose *relationship* lived only in prose. It had already gone wrong: the cards set no `z_index` at all while `HoverInfoPanelControl` authored `2` in its `.tscn`, so **the hover card drew on top of the pause menu, the victory banner and the Crisis prompt** — fixed by the table.

**This is the UI axis ONLY**; board sprite/overlay z (`Unit.BASE_SPRITE_INDEX`, `MoveAction.ARROW_BASE_Z_INDEX`, `OverlayManager.TERRAIN_Z_INDEX`, every `z_index` in `Game.tscn`) is a different axis and stays put — merging them would be Law #4 run in reverse.

## The ui/ folder

`ui/` — all player-facing HUD. Root = menus + prompts (`ActionMenuController` — the RADIAL widget since #467, one full-rect Control that is the backdrop AND the menu; `MainActionMenu` — the whole action-menu system: ids/display data/gating/dispatch AND the ring tree, pulled out of `game.gd` 2026-07-22 — `MissionEndBanner`, `MissionSelectScreen` — the boot screen, #96 slice 2 — `PauseMenu`, `GlossaryScreen` — the reference page, #135: a locking ModalCard opened from the pause-menu row and the title-screen button, a pure projection of core/'s `Glossary` — `SettingsScreen` — the options page, #350: the same shape and the same two doors, a pure projection of core/'s `PlayerSettings.DEFS`, and since [#691](https://github.com/Phaazoid/Godoiosis/issues/691) a SECOND pane beside it -- a read-only Controls list projected from `Controls.gd`'s player contexts, the same registry the dev Info tab reads. Both panes are built once and switched by `visible`, never rebuilt, so `_process` goes on reconciling the settings rows against the store while Controls is up. Rebinding is NOT there and is gated on promoting the hardcoded keycode checks to Input Map actions — `PreMissionScreen` + `PreMissionCard` -- the pre-mission menu, #740/#743: five regions over the paused board (the fifth, CONDITIONS, is #1324's), locking it through `game.menu_is_up()` rather than by eating clicks, and hidden rather than freed so Tab is a board preview, with `PreMissionBar` (#774) standing in the End Turn corner while it is away; `AuraRing` + `MapSpriteInk` (#930) -- a unit's elemental aura as a ring of five fixed sectors around its portrait, on the pre-mission card AND the inspect panel, which is #292's parity asked before rather than after.

**The first `_draw()` widget in `Classes/ui/`** (`presentation/UnitHealthBar.gd` is the only precedent anywhere). `rows()` is the whole model and `_draw` renders what it returns, so a headless case asserts the readout without a pixel; a tick has THREE states because affinity and aura are two fields, and one keyed on `aura >= 1` erases the maim-taxed alchemist `UnitInstance.gd:21` exists for. **FIVE since [#1019](https://github.com/Phaazoid/Godoiosis/issues/1019), and only while a DEMAND is shown**: `Row.wanted` is what a picked carving asks of this sector, HOLLOW is asked-for-and-not-held and HALOED is held past the recipe (uncapped `base_damage`, so surplus aura is damage rather than waste). Hollow is an OUTLINE and the off-recipe knock-back is DESATURATION, both for one reason -- `DIM_ALPHA`/`FAINT_ALPHA` already spend the alpha channel and a third value on it is indistinguishable at a 5px tick. The halo's spread is a RATIO OF THE MID RADIUS, never a px constant, or it fuses a sector into one arc at the smaller ring while reading correctly at the larger -- #930's own hover-border failure, and `tests/ui/test_aura_ring.gd` asserts a gap of at least one PIXEL rather than mere non-overlap, because the fuse ratio survived the weaker version. `rows(null, carving)` is legal and is the whole stash case: the demand with nothing paid against it. Its ink comes from the SURFACE (`QueueStyle` on the parchment-skinnable card, `ElementPalette` on the panel, which reads neither) -- one source would hand the panel's permanently dark ground the hues `_adapt` darkened for cream paper, #814 one surface along. `MapSpriteInk` is #560's ink-box scan hoisted out of `PreMissionScreen`'s pixel offset the day it got a second consumer at another size: **the measurement is the shared thing, not whichever surface solved it first**, and it answers FOUR questions now, one per way a surface uses the art: `window_offset` a 1:1 CROP (the 24px deployed-strip disc), `ink_fit_rect` a ZOOM (the card's ring, #990 -- fitting the 64px CELL into a 52px box drew the character at a third size, which is #937's law arriving at the surface its own sweep missed), `portrait` a TEXTURE for a slot that can only be handed one (the action-queue row, [#1082](https://github.com/Phaazoid/Godoiosis/issues/1082) -- the square around that sprite's OWN ink (`ink_of`, `BoardMirror.opaque_bounds` cached per texture), feet on its floor, which the slot stretches to fill, so the queue is the one surface where units do not share a scale (dev ruling, 2026-09-28); anything not sheet-sized passes through whole), and `ink_centre`/`ink_reach` the raw measurement the rest are built out of.

**The inspect panel's height budget is a law now** (`tests/ui/test_unit_info_panel_refresh.gd`): it is 300x720 and its body already wanted 648, so a 160px wheel in it overflowed by 92 and ran the bottom rows off the screen in silence -- #723's title-screen rule arriving at a surface that is not a `ModalCard`. -- `GearDropZone` + `GearRow` (#741) -- somewhere gear can LAND and a row that can also be picked up, wired with the judge and the act as CALLABLES so the drag never reaches for the screen; **its endpoint is a `holder: Object` since [#732](https://github.com/Phaazoid/Godoiosis/issues/732)** -- a `Unit`, a `WeaponInstance`, or null for the stash, since the field always meant "which END of a move is this" and could not say "fitted in this weapon" (Object rather than Variant, so `as Unit` degrades to null instead of throwing) -- `ModFittingCard` + `ShapePlate` (#732) -- the weapon detail card off a chip on any weapon row, and the read-only plate drawing one attack's aimable ring and footprint off `Reach` in the Attack Editor's own up-is-forward convention, inked with `OverlayManager`'s live aim colours so it follows the player's palette -- `RuneDetailCard` + `AttackChannelText` + `ItemDetail` ([#1019](https://github.com/Phaazoid/Godoiosis/issues/1019)) -- the rune's mirror of that card, a DISPLAY only (carving is ratified blind / workshop-only / irreversible, so a pre-mission surface offering it would contradict all three), with the element demand drawn on the `AuraRing` rather than in a widget of its own.

**`AttackChannelText` is #1017's enumeration EXTRACTED because a second card asked for it** -- the shipped carvings already differ across seven of those fields, so writing the list twice is how that ticket reopens; the composed values arrive as PARAMETERS (a weapon's fold through its mods, a carving's are its own, since a carving carries none), and what stays per-card is only what one kind of attack has -- readiness and the empowered form. **The battle ring reads ONE line of it since [#1083](https://github.com/Phaazoid/Godoiosis/issues/1083), `ally_line`** (dev: the ring stays succinct; the full list is the item card's, which [#1152](https://github.com/Phaazoid/Godoiosis/issues/1152) brings into battle) -- the one line that speaks both ways, and never on a one-cell attack (`weapons.md` -> *The ally line*).

**`ItemDetail` is the ONE fork for which card an item has**, which is why `PreMissionCard.fit_requested` became `detail_requested(item, owner)`: both chips ask the identical question, the screen is already the only thing that opens a card, and the fork was otherwise going to be spelled at four sites. **The battle inventory opens a card too since [#1152](https://github.com/Phaazoid/Godoiosis/issues/1152)** -- the dock's Inspect, for any unit you can inspect, READ-ONLY (`ItemDetail.open(..., read_only = true)`: no library and nothing wired), asked through `ItemDetail.has_card` (a card to READ, which a spaceless weapon has) rather than `chip_for` (the pre-mission FITTING chip, which it has not); `missions.md` -> *Fitting mods*. A rune's chip reads CAPACITY (`4/6`) where a weapon's reads spaces, and **a blank rune gets one** -- `0/1` is how a player learns a rune is blank without equipping it and reading the refusal off the gate -- where `ModFittingCard.chip_for` answers null for a weapon with no spaces.

**[#1022](https://github.com/Phaazoid/Godoiosis/issues/1022) (2026-09-18) then landed the dev's first playtest of it**, and four of its seven items were things the approved mockup carried and the build dropped: **the DEMAND ARC** (a stroke outside the band spanning the asked-for ticks -- ticks say what is PAID, the arc says what is OWED; its pad is taken ONLY while a demand is drawn, and taking it unconditionally reds #990's own case), **the cost bars' three STATES** (they shipped flat, which is most of why they said so little), **the row's subtext**, and **the LEGEND row** -- that last reversing #1019's own "the ring's tooltip explains itself" (dev: *"it will be useful for the player, too"*; the earlier call was not wrong about the tooltip, it was wrong about who finds one). Its one bug was `SIZE_EXPAND_FILL` on the name label, which ate the row and flung the bars to the far edge -- **and taking that flag off is what caused [#1024](https://github.com/Phaazoid/Godoiosis/issues/1024) an hour after it merged**: an `HBoxContainer` then handed the label the ONE PIXEL a `clip_text` Label declares as its minimum, so every carving name shipped as a sliver of its first glyph. It asks for its own measured text now, capped at half of `CARD_W`. The fix is #989's, which had been private to `PreMissionCard._chip` through four bugs in that family -- `UiText.fit_width(label, floor, ceiling)` is the measuring and **each caller keeps its own bounds**. Two things worth carrying: the case pinning *"the bars sit beside the name"* was made MORE TRUE by the name's loss (it measures the gap from the name's RIGHT edge, which at 1px is the separator's own 8px), so **pinning one of a tensioned pair is pinning neither**; and the sweep that would have caught it existed at three surfaces and could not travel -- `tests/support/label_fit.gd` is where it lives now, with its STRUCTURAL half (a clipped label in a row-laying container carrying neither `SIZE_EXPAND` nor a width) separate from its CONTENT half, because only the first is fixture-free and only HBox/HFlow are in the family. Full rule in `missions.md`.

**A ROW ALSO SAYS HOW COMFORTABLY IT CHANNELS** in three states off `TransmutationData.channel_state` -- the margin the ladder computes and threw away -- and **the CHIP finally reads as a button**: it was bare on both cards and took the engine's chrome, which is EXECUTE_BG's own diagnosis (*grey on a grey panel, and it simply disappeared*), so the chrome moved into ONE `ItemDetail.chip` builder with a warm-edged box the dev picked off four mocked candidates. **It also found a blind spot in `test_pre_mission_contrast`**: the walker read a Button's hover INK against its NORMAL box, judging a state that never exists -- unseen since #814 because no control on those menus had a differing hover box, and the chip is the first that inverts. -- `ItemText` ([#137](https://github.com/Phaazoid/Godoiosis/issues/137)) -- THE one answer to what a piece of gear says on hover, which three surfaces had answered three ways: name, then the kind's own GENERATED mechanical lines (`ArmorData.mechanical_text`, `RuneData.attack_detail`, `VialData.mechanical_text`, `WeaponModData.effect_text`, `WeaponInstance.status_text`), then authored flavour last. A NULL wielder is legal and is the stash's whole argument -- every term needing one drops out, which is also why the stash's own `requirement_text` special case is gone: `mechanical_text` already words that gate.

**The mechanical half is never authored into `description`**, which stays flavour and stays the dev's (#137's strip took my 19 lines out of the armour, vials and weapon families and left the abilities' terse readouts and his own prototype lines standing) -- `ReportPanel` — the player's report card, #131, and since #1052 only the chrome around `ReportForm`, the form itself, which the mission-end banner hosts too; the form is deliberately dumb, it collects a Kind and a note and is TOLD the outcome — `turn_banner`); `ui/queue/` = the action-queue panel (`SquadActionQueueControl`/`ActionQueueRow`/`ActionQueueDisplayEntry` — the latter is both the row view model AND, via `build_for(squad, plan)`, the panel's whole section layout); `ui/panels/` = the info/inspect surfaces (`info_panel`, `UnitInfoPanelControl`, `HoverInfoPanelControl`, `hover_info_grid_container`, `squad_info_panel`, `inventory_panel`, `portrait_panel`, `StateIcons`, `UnitStatesBar`, `TileInfoSections`).

**THE INFO CARD IS ASKED FOR BY A CLICK, NEVER BY HOVER, since [#1105](https://github.com/Phaazoid/Godoiosis/issues/1105)** (dev, 2026-09-27: *"Nothing on hover, at all"*). `HoverInfoPanelControl` keeps its old name (the hover setting that would have used it was dropped when #1105 closed) and shows ONE face at a time: the UNIT card while that unit's ring is up (`MainActionMenu.show_main_menu` shows it through `game.show_unit_card` and `_on_menu_cancelled` takes it down, so its life IS the ring's), or the TILE card -- a clicked empty tile's full readout (`game.show_tile_card`; the same tile again, or a click off the map, closes it), or, from the ring's Inspect (`game.inspect_unit`), the tile the unit stands on, parked right of the dock and FOLLOWING the unit, because the dock stays open through Execute.
