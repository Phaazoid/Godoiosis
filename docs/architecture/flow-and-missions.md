## TurnManager

`TurnManager` (`flow/`) — the faction turn cycle, **rebuilt from the board each hand-off** (refactored 2026-06-24). Tracks the **active faction by value** (the old two-sided `TurnPhase` enum is gone); `end_turn(present_factions)` recomputes the live order as `Team.all_factions()` (enum order) ∩ factions present, then advances past the active one. Handles **any number of teams**, and the cycle **builds itself from what's on the map** — a newly-spawned faction enrolls at the next hand-off, a wiped one drops out. **Single source of truth = the `Team.Faction` enum** (add a member → it's in the rotation). Trade-off: turn order follows enum-declaration order, which is **append-only** for save-compat, so a new faction acts *last* unless you migrate enum values; and presence *is* eligibility (a `NEUTRAL`/`OTHER` faction with units would take a turn — add an explicit opt-out if you ever want non-acting scenery). `game._on_turn_started(faction)` **auto-skips** a faction with no `is_active` units after ticking its downed clocks — guarded by `_board_has_active_units()` so an all-downed board can't infinite-loop; `start_faction_turn(faction)` replaced the old player/enemy split. Saved turn state = `ScenarioData.active_faction` (authoritative; the `turn_phase` field was removed), restored via `set_active_faction`. The headless Play API mirrors this exactly (`play_session.end_turn` derives present factions + runs the same guarded skip, and since [#898](https://github.com/Phaazoid/Godoiosis/issues/898) the same end-of-turn burn and turn-start ticks, through the static `TurnBoundary` both stacks call).

## ScenarioDirector

`ScenarioDirector` (`flow/`) — runs a scenario's authored script (#182): `DialogBeat`s (independent "when X, say Y" moments over Dialogic timelines) and `TutorialStep`s (a sequential lesson whose active step renders as the mission HUD's instruction row). Built in `_build_collaborators`, DevController pattern. **Dialogic 2 (vendored, `addons/dialogic/`, pure GDScript) owns HOW dialog displays; the director owns WHEN** — board state never enters Dialogic's variable store; triggers are the board's own signals (`turn_started`, `squad_created`, `squad_member_joined`, `unit_selected`) plus the #220 mission door.

**Content loads INERT and `begin_mission(path, armed)` arms it**: apply_scenario's spawn loop fires `squad_created` once per unit (the solo-squad invariant), so a loading board must never trip a beat — and `armed=false` is the watch-only/demo boot (#375: a lesson needs a student). Arming cannot be undone after the call: `Dialogic.start()` defers to the layout's ready, so `current_timeline` is a frame late — **gate on Dialogic's signals (`timeline_started`, `Dialogic.Text.text_finished`), never timers**. A resume disarms (fresh-start content); `clear_board` resets the director BEFORE `mission_controller` (mc.reset() is a HUD write point that reads `active_instruction()`).

**A SECOND door opened at [#882](https://github.com/Phaazoid/Godoiosis/issues/882) (2026-09-12) and it fires WITHOUT arming: `pre_mission_started()`, the BRIEFING** — a `PRE_MISSION_START` beat plays over the bare board before the loadout screen, because `MISSION_START` fires at the COMMIT and a line about what the map wants is then advice about a choice already made. It must not arm for the reason `deploy_roster` runs before `mission_started()` (the phase spawns and squads the roster, and an armed director answers every `squad_created`), and the new trigger is APPENDED to the enum because a beat serializes as its int. It answers whether anything will play, reading the PENDING QUEUE as well as `_dialog_active` — `end_timeline` is async, so a restart taken mid-dialog queues the briefing rather than starting it.

**`went_quiet` is the screen's wait**, emitted on the timeline end that EMPTIES the queue rather than on the first one; dialog turned off consumes the beats and answers false, so the screen opens at once instead of waiting for a signal that cannot come. One node runs beats AND steps on purpose — the order is pinned (step advances → HUD refreshes → `STEP_COMPLETED` payoff beats voice it) instead of racing between two listeners. **A THIRD door opened at [#982](https://github.com/Phaazoid/Godoiosis/issues/982) (2026-09-16), `preview(timeline)` — the dev-tools Play, which plays one timeline now and arms nothing.** It REFUSES rather than queues while anything is talking (a preview is wanted NOW, and a queued one plays after a beat nobody was watching for), sits OUTSIDE the `SHOW_DIALOG` gate (that check is `_fire`'s, for a player who turned dialog off) and never touches `_fired`, so previewing a beat's timeline does not spend that beat.

**Its `_dialog_active` latch is what stops a same-frame beat being SWALLOWED, and the obvious property is the wrong one**: `Dialogic.start()` defers to the layout's ready so `current_timeline` is a frame late, and without the latch the beat does not play over the preview — Dialogic absorbs the second start — it is marked fired with `_pending` left empty and is simply lost, which is only visible once the preview ENDS. Two versions of that case passed against the mutant before it was measured rather than reasoned at.

## Authoring a Dialogic timeline

**AUTHORING a Dialogic timeline is `Classes/dev/DialogicSource.gd` + the Dialog page's TIMELINES section ([#982](https://github.com/Phaazoid/Godoiosis/issues/982), 2026-09-16)** — the half Dialogic's editor owns and a running game cannot reach, so a briefing is written where the beat that plays it is. Canon: `docs/design/missions.md` → *Authoring a timeline*. **Registration is OURS because Dialogic's is editor-only** — `DialogicResourceUtil.set_directory` writes `project.godot` only under `Engine.is_editor_hint()` — so `register()` writes THREE stores in one call: the committed file (a surgical text rewrite of the `directories/<ext>_directory` block, `KnobSource`'s shape — never `ProjectSettings.save()`, which would rewrite the whole file, and never `ConfigFile`, which drops its comment header), the live `ProjectSettings` every picker reads, and the `Engine` meta Dialogic caches a directory in on first read. A writer touching fewer leaves the picker stale for the session, which is the mutant that pins it.

**Entries APPEND, never sort** — `plugin.gd._build()` runs `update()` on every editor Play against the editor's stale copy and appends, so matching that order keeps the file from churning AND makes a registration written while the editor was open self-heal. Registration is **not optional**: `test_every_dialog_file_on_disk_is_registered` reds CI on an unregistered `.dtl`, which is what rules out scanning the folder and leaves DialogTool's *never a second file scan* standing. Three rules the build paid for: **the beat holds the `load()`ed, path-bearing resource** (`events` is not an `@export`, so an in-memory timeline EMBEDS into the mission `.tres` and loads back silent — #177 one resource along; an edit updates the loaded object in place via `from_text` + `process`); **lines serialise through real `DialogicTextEvent.to_text()`, never `"%s: %s"`** (the parser's name group runs to the first unescaped colon, so narration holding one returns as a speaker, fabricates a nameless character and reds the law suite); and **`write()` mints the `.uid` sidecar**, which CI's sidecar guard FAILS without.

**Delete refuses while anything names the file** (an ext_resource by path — deleting a referenced timeline is a hard parse error, not a missing line) and **rename is deliberately absent**, repointing dependents being the editor's job. `referencing_files`/`delete` take a `scan_dir` so a case can exercise the refusal against its own referrer: the first version aimed a real delete at `causeway_intro.dtl` and DELETED IT the moment the guard was mutated out — **a case whose failure mode is destroying authored content is not a test.** A speaker is MINTED FROM THE CAST (`character_from_cast`, name and portrait off the `UnitData`, colour the one thing authored here), so a `.dch` is a derived artifact rather than a second character editor.

## Missions — the closed loop

**Missions — the closed loop (`flow/`, #96, all four slices built 2026-07-28; canon [`docs/design/missions.md`](docs/design/missions.md)):** the game can be **won and lost**, and it now BOOTS into `MissionSelectScreen` rather than a board (`TestBoard` retired as the boot path; `game.spawn_sandbox()` is its one remaining call site). Five parts, split on purpose. **`MissionRules`** (static, pure, `extends Object` — LethalityRules' shape) is the whole rule: `evaluate(board, contested, progress) -> ONGOING/VICTORY/DEFEAT`. **`MissionState`** (`RefCounted`, built over the board's `ZoneManager`, since #46) holds everything a pure predicate cannot — the ended-latch, the `contested` latch, captured-zone state, the round clock, the protected-unit latch, the objective and lose-condition composers — and is ONE object per mission that BOTH hosts own (the `TurnBoundary`/`PreMissionPhase` precedent), so the headless Play API scores a mission the way the game does. **`MissionController`** (a game collaborator, the DevController pattern) holds the game's one, delegates every rule to it under the names its readers already call (the authored lists FORWARD to the state's own arrays, so the Scenario tab's in-place appends land), and is what the game DOES about an ending (`GameState.MISSION_OVER`/`MENU` → `_board_locked_for_player`, the banner, the return path).

**`ScenarioData.objectives: Array[MissionRules.Objective]`** is what a mission REQUIRES (ROUT/CAPTURE/EXTRACT, composed by AND, edited in the dev Scenario tab); **`ScenarioData.zones`** is WHERE, via `ZoneManager.Kind`. **There is no `MissionData`** — a mission and its board are 1:1, so a wrapper resource is an extra hop, not a template/instance split (dev, reversing the original plan). Objectives are **declared explicitly, not inferred from painted zones**: rout has no geometry to paint, a mis-picked Zone Kind would otherwise silently rewrite the win condition, and geometry couldn't be authored ahead of its rule. Guard for the resulting second source of truth: a declared objective with no painted zone reads **PENDING, not NONE** (the map really is unwinnable — silently dropping it would convert a broken map into a different playable one), warned live in the Scenario tab and `push_error`'d by `set_objectives`. Doctrine, all load-bearing: **(1) an authored objective is the ONLY way to win** — routing a capture map wins nothing unless ROUT is ticked (lockout is a level-design problem, not a rule that hands out a consolation win); **(2) DEFEAT is checked first** — last player unit and last hostile falling in the same pass is a LOSS; **(3) `contested`** — "both sides were up at once", latched by the CALLER because the board can't tell *wiped out* from *never here* (`present_factions` drops an all-dead faction) and a LIVE read could never end a mission, which is what keeps **dev sandbox boards inert with no `dev_mode` flag**; **(4) extraction counts the DOWNED** — alive and inside the zone means they got out; what blocks it is a living unit OUTSIDE, and a downed one there needs a rescue; zero surviving players reads PENDING, not vacuous-MET (2026-08-12 — the missing twin of capture's zero-geometry guard; it ticked Extract on the HUD during load, and `apply_scenario` now re-pushes the HUD after the board is fully built). `check()` fires at the three points board state changes and settles — end of a resolution pass (`OrderExecutor.execute_orders`, *before* its squad-validity guard so a squad that wiped itself can't skip it), after the end-of-turn burn, and turn start *after* the downed clocks tick. Pass-end not turn-end: a friendly AoE can down your own last unit mid-pass. `AIController.take_faction_turn` guards on `is_over()`, and since [#714](https://github.com/Phaazoid/Godoiosis/issues/714) **takes no BoardContext at all — it re-derives one PER SQUAD** through `squad_manager.board_source`: it used to build one for the whole turn while `execute_orders` between squads spans frames, so a unit an earlier squad killed was genuinely FREED by the time a later squad planned and `_resolve_actions` called a method on it. `play_session._take_ai_turn` had always called `_board()` inside its own loop, which is why the headless API never reproduced it. Its other half: **`BoardContext`'s constructor excludes a unit whose death has RESOLVED**, asking the domain fact (`Unit.die()` sets lifecycle DEAD before it queue_frees) rather than `is_queued_for_deletion()`, and living in the constructor because three builders feed it.

**`MissionController.reset()` (from `ScenarioManager.clear_board`) is the first thing in the codebase to ever fire a mission-start event** — the [#87](https://github.com/Phaazoid/Godoiosis/issues/87) seam whose rule had never actually executed; keep the split when #87 lands (**loading a mid-battle save RESTORES, starting a mission RESETS**). NB `MissionRules.Progress` (NONE/PENDING/MET) and `MissionRules.Objective` (what's required) are different enums; `Progress` was called `Objective` in slice 1. Tested: `tests/flow/test_mission_rules.gd` (22) + `tests/ai/test_zone_manager.gd` (12) pin the rule and the geometry, and **`tests/flow/test_mission_controller.gd` (31, added 2026-07-29) pins the controller** — both latches, the objective composer's AND, capture state, extraction's downed-counting, declared-but-unpainted reading PENDING, and the MISSION_OVER board lock. It runs a real game scene (the #114 fixture) and is falsified against seven mutations, one per doctrine.

**LOSE CONDITIONS are their own list since [#101](https://github.com/Phaazoid/Godoiosis/issues/101) (2026-08-26), not negated objectives** (fork A, dev): `ScenarioData.lose_conditions: Array[MissionRules.LoseCondition]` + `round_limit`, composed by **ANY**, because the two are asked at different moments (an objective is checked for completion, a lose condition continuously) and a failure has to NAME a reason for the banner (`MissionRules.defeat_reason`, the one place that wording lives). `evaluate` takes `failure` exactly as it takes `progress` — the controller computes it, the rule stays pure — and **the order is load-bearing at both ends: the squad wipe is asked FIRST (so mutual destruction still reports SQUAD_LOST), and every VICTORY path is asked BEFORE an authored failure (finishing on the last allowed round is finishing in time)**. `MissionRules.AUTHORABLE` is a const rather than "every enum value", so the NONE sentinel and the always-on SQUAD_LOST floor are excluded by a visible decision — `MAIN_ACTION_NEVER`'s shape. The TURN CLOCK splits the way objectives do: **the count is battle-scoped (`MissionState`, saved with #87), the limit is authored (`ScenarioData.round_limit`, 0 = no limit and that sentinel IS the field's own default)**; the ONE increment point is `game._on_round_completed`, and since `TurnManager` emits `round_completed` before `turn_started` the next `check()` sees it, so **no new evaluation seam was added**. A declared `ROUND_LIMIT` with no limit is `objectives_missing_geometry`'s twin (`lose_conditions_missing_setup`, borrowed by the Scenario tab and `BoardLint`, never restated). The HUD row lives under its own FAIL IF header and **colours as it runs out** (fork C — no modal), thresholded by `MissionStatusPanel.URGENT_ROUNDS`/`URGENT_COLOR`, two `GameKnobs.CLASS_KNOBS` rows because `KNOBS` resolves against the Battle3D host and structurally cannot reach 2D UI.

**The trap it surfaced: `refresh_mission_status` gated the whole panel on `objectives.is_empty()`, so a board authoring a clock and no objectives hid its own countdown** — a HUD visibility gate must ask about everything the panel can draw. Pinned by `tests/flow/test_mission_lose_conditions.gd` (15, the clock driven through the real `end_turn` cycle), falsified against four mutants. **#101 CLOSED with the seam** and its unbuilt half split out rather than becoming an umbrella (dev, 2026-08-26): [**#571**](https://github.com/Phaazoid/Godoiosis/issues/571) defend a point (**BUILT 2026-09-11**) and [**#572**](https://github.com/Phaazoid/Godoiosis/issues/572) protect a unit.

**#571's own stated cost — "a captured zone has no OWNER" — was WRONG, and the correction is the reusable part:** it assumed a defended point is a capture point an enemy takes, where the dev's rule is **presence** (*"if any tile of a capture point is taken by the enemy, the player loses… if an enemy makes it that close, it has been destroyed"*). Nothing captures it, so no owner exists anywhere. It shipped as **`ZoneManager.Kind.DEFEND` + `LoseCondition.POINT_LOST`**, leaving `_captured_zones`, `ScenarioData.captured_zones`, `capturable_zone_at`, `capture_counts` and the #87 snapshot untouched — no persisted field changed shape. A fifth zone Kind cost one enum member and one overlay layer in both stacks (the #736 checklist) and **no authoring UI at all**, since the Tile Brush's dropdown is built off `Kind.values()`. Its AI half is **RUSHDOWN ONLY** (dev): a destination, not a builder — `CAPTURE` is still `NEVER` on every archetype, and `ai-tactics.md`'s standing prediction that this ticket would need "a real capture builder" was falsified. A DOWNED hostile on the cargo still loses it (arrival is the event).

**#572 shipped the same day and its stated cost was wrong the SAME WAY** — it claimed the gap was `ScenarioUnitEntry` having no stable identity field to name a protected unit with. A mission names nobody: the subject is marked WHERE THE SUBJECT LIVES (`ScenarioUnitEntry.must_survive`, authored per PLACEMENT), which is what every lose condition already does with its parameter — `ROUND_LIMIT` an int on the board, `POINT_LOST` a painted zone, this a flag on a unit. No id, no lookup, nothing to dangle; #501 asks *which person is this* and deserves its own answer. Death is a **LATCH** off `game._on_unit_died`, because `Unit.die()` queue_frees and *gone* is indistinguishable from *never placed*; battle-scoped and unsaved, since `check()` ends the mission in the pass the death resolved in. DEATH ONLY (a down is recoverable); *left behind* stays an EXTRACT objective not being MET. Two shape consequences: the setup guard needs `not protected_lost` or it reports a broken board at the instant the condition FIRED, and its SHOUT moved out of `set_lose_conditions` (which runs mid-load, before a unit exists) into `report_missing_setup()`, called where `apply_scenario` re-pushes the HUD — #134's write-point trap, EXTRACT's own fix. The flag rides `ScenarioUnitEntry.apply_placement` (both loaders' door since #46), OUTSIDE #177's fork, or a reference entry (which never calls `apply_unit_state`) would lose it silently and only for cast units.

**Ask what a rule IS before costing how to store it** — an issue's architecture section is written before the mechanic is stated, and rots first; two for two here. Fork F (authorable OR-composition) is deliberately UNFILED and recorded only in `missions.md`; the headless gap went to [#46](https://github.com/Phaazoid/Godoiosis/issues/46). **What a SHIPPED build lists is authored per board ([#860](https://github.com/Phaazoid/Godoiosis/issues/860), 2026-09-09):** `ScenarioData.in_demo`, ticked on the Scenario tab, default FALSE — *a board ships because someone ticked it*. Read only when `DevTools.enabled()` is false, which also now hides the `SCENARIOS & FIXTURES` section and the `Sandbox (Test Board)` row (both had shipped to every export).

**The filter is at the menu's call site, NEVER inside `get_missions()`** — CI sweeps that list to lint every shipped mission, and filtering at the source would stop linting exactly the boards nobody ticked.

## The flow/ folder

`flow/` — `TurnManager`, `ScenarioManager` + `ScenarioData`/`ScenarioUnitEntry`; `MissionRules` (the pure win/lose predicate) + `MissionState` (the latches and the rules over them, one per mission, owned by both hosts since #46) + `MissionController` (what the game does about an ending).
