Chronological build records, moved out of `CLAUDE.md` on 2026-07-24 so the project guide could go back to being a *guide*. At the time of the split these entries were **59% of CLAUDE.md**, which is loaded into context every session — one of them (weapons) was 28% of the file on its own, while the genuinely open debt it sat among totalled under 500 characters.

**What belongs here:** how a system came to be — what shipped when, what it replaced, what was migrated, which tests were added, what a build measured. Narrative and chronology.

**What belongs in `CLAUDE.md` instead:** anything that would cause a *mistake* if you didn't know it — invariants, "never do X", "this asymmetry is deliberate, don't reconcile it", and the current shape of the architecture. If a fact here is load-bearing for writing code today, it should also be stated (briefly) there; this file is the long version, not the only version.

**What belongs in [`performance.md`](performance.md) instead:** where frame time actually goes, how it was measured, and which optimisations must not be undone. That file is a standing reference rather than a chronology — measurements you'd want *before* touching a hot path, not a record of when they happened.

Entries are preserved **verbatim** from CLAUDE.md — including their original dates, test counts, and any "still stub" notes that were accurate when written. Treat a claim here as *true as of its date*, not necessarily true now; `CLAUDE.md` and the GitHub issues are authoritative for current state.

## Will, downed state, and limb loss — #33, #56, #59 (item 6), #60, #64

- **Will / downed / limb-loss (#33) — unblocked scaffold BUILT 2026-06-21 (uncommitted on `main`); the Will resource itself is still a stub.** In code now (all on the transient `Unit`): a `Unit.LifecycleState {ACTIVE, DOWNED, DEAD}` machine — downing happens at the `take_damage` seam (`_select_lethal_rung` → DOWN-at-1-HP vs overkill-dead, gated on the flat `OVERKILL_CEILING` constant, **not** spent Will); squad ejection on down (deferred to after the pass via `game._downed_pending`/`_process_downed_pending`); counter liveness (a unit downed mid-pass skips its resolved counter — `PlanResolver._counter_actor_live` + `ResolvedOutcome.skipped`); the **main-action rule** (attack/rescue mutually exclusive + must follow a move — `BaseAction.is_main_action`/`Unit.has_main_action_queued`); and a **manual `RescueAction`** (adjacent ally spends its main action → `Unit.revive()` to 1 HP, rescued unit spent for the turn); a **down/kill queue-icon preview** (Law #2 — `PlanResolver` predicts each hit's `ResolvedOutcome.lethality`; `AttackAction._lethality_icon()` swaps the sword for the Down/Ded icon, and **counters share that helper** as of 2026-06-24 so a lethal counter reads like a lethal attack instead of a plain counter); and a **downed countdown** (`Unit.downed_turns_remaining`, starts at 3) that ticks at the **owning faction's** phase start (`game._tick_downed_countdowns(faction)`, via `TurnManager`) and dies at 0 — equal grace on either team, the death half of the manual-rescue loop. Still design-only (`docs/design/will-and-death.md`): the Will resource + bar, the **text-popup** form of the down/maim/lethal preview, maiming, Crisis Mode. Forks: 1 resolved (Will persists on `UnitInstance`, #8); **provisional in-code calls** — per-unit Will (no pool), downed-attack = kill, maim deferred. **Design REFRAMED 2026-06-24 (grill — PROVISIONAL, not playtested / not co-dev-reviewed):** Will is now a **limb buffer, not a life buffer** — a sub-overkill fatal hit *always* downs (spending a flat Will cost `N`; **maim** if unaffordable, decided at down-time), and Will **never directly kills** (death = overkill / failed-rescue countdown / Crisis only). **Crisis** = a reactive, high-Will-gated **live interrupt** at a would-be-down → surge + Will→0 + no-safety-net (permadeath) for the rest of that battle. **Generation** = in-fight depletion-only + a **`RallyAction`** + deferred between-battle recovery (rest + a task-assignment metagame). - **Prosthetic re-link keyed on the INSTANCE, not the template — fixed 2026-07-30.** Reported as "a prosthetic leg doesn't survive a scenario save, but the arm does." Root cause was in `ScenarioUnitEntry`/`UnitEditorTool` alike: `LimbFitting.prosthetic_item` stored the shared `WeaponData` **template**, and both re-link paths searched the carried inventory for "the first item whose `template` matches." Two prosthetics built on the same family template (an arm and a leg — the exact case `test_same_family_template_can_back_an_arm_instance_and_a_leg_instance_at_once` has pinned as legal since #59) are indistinguishable to that search, so **both limbs re-linked to whichever carried copy came first** and the second slot's identity was never recorded. Fixed by typing the field as `WeaponInstance` and storing the carried instance itself, which turns all three lookups (`ScenarioUnitEntry` capture, its load-time re-link, and `UnitEditorTool._capture`) from a template-matching loop into a one-line `find()` — the fix made the code *shorter*. `is_installed_prosthetic` was the same bug in a second place (it took a template, so an installed arm made an uninstalled same-family leg un-Tossable) and now takes the instance; `limb_stat` reaches `built_in_stat` through `.template`, so the live-off-the-template contract is unchanged. **Latent since #83 (2026-07-22)** — unreachable until the item picker above gave `install_prosthetic` its first production caller. Tests: `test_two_prosthetics_sharing_one_template_stay_distinct_through_save_and_load` + `test_is_installed_prosthetic_distinguishes_same_template_different_instances`, plus `test_installed_prosthetic_survives_an_actual_disk_save_and_load` — the suite's **first scenario test to go through a real `ResourceSaver.save()`/`load()`**, since every other case here calls capture/apply back-to-back in memory.

- **Affinity + alkahest now round-trip a scenario save — fixed 2026-07-30.** `ScenarioUnitEntry` captured `aura` but never `affinity`/`is_alkahest_affine`, so a dev-editor affinity edit (which writes `UnitInstance.affinity`, not `UnitData.base_affinity`) was silently dropped on load — and because aura *is* restored wholesale, a loaded alchemist ended up holding a full pool with an empty affinity: an illegal pairing `initialize()` explicitly guards against, which trips the Rebecca-rule gate in `TransmutationData.can_channel` and makes **every carving on their rune silently unfireable**. The new `affinity_saved` bool is a **declared** sentinel, not a duplicate seam: an empty affinity is a legal saved value (Rebecca), so emptiness can't double as "unsaved" the way every other default in that block does, and without it a pre-existing save would apply `[]` over `initialize()`'s seeded `base_affinity`. Applied *before* aura (affinity is the gate aura's legality is judged against) and, per the armor precedent, the out-of-affinity filter is **not** re-run on load — a save is authoritative. Tests: `test_affinity_and_alkahest_round_trip`, `test_affinity_survives_so_a_loaded_alchemist_can_still_channel`, `test_a_unit_with_no_affinity_stays_rebecca_after_a_round_trip`.

- **The heal readout — `ResolvedOutcome.hp_before()`, 2026-07-30.** Reported as "the Heal Stone healed for 0." The heal itself was correct; the **queue row was lying** (Law #2). `ActionQueueRow._show_hp_delta` and `AttackAction.get_outcome_summary` each independently rebuilt "HP before this hit" as `target_hp_after + damage` — and a heal deliberately leaves `damage` at 0, so a real 4-point heal drew `14->14`. The heal feature only ever updated one of those two renderers, because the second one doesn't call the first (a pre-existing duplicate the feature walked into rather than created). Consolidated onto `ResolvedOutcome.hp_before()` (`target_hp_after + damage - heal_amount`; exactly one term is ever non-zero) rather than patching the arithmetic in two places again. CRISIS stays special-cased at both call sites — the target stands back up at a fixed revive HP, so no subtraction recovers its pre-hit number. Tests in `tests/law/test_healing.gd`.

## Weapons: parts, template/instance split, multi-attack, per-family mechanics — #59, #72, #73, #82, #84

- **Weapon parts core BUILT 2026-07-16 (#59, v2 build-spine, `docs/design/weapons.md`):** `WeaponModData` (typed effect fields — power delta, per-stat scaling nudge, added element, weight) fits into one of `WeaponData`'s three spaces (capacities 1/2/3; a prototype collapses to one size-1 space). Mid-build, a bigger realization landed: `WeaponData` (the family template) can't be both the shared, live-editable identity AND the thing a unit copies into its inventory — those are two different lifetimes. Resolved by splitting it the same way jobs split id-from-instance: `WeaponData` stopped extending `EquippableData` (now a pure template, `extends Item` directly, never duplicated), and a new `WeaponInstance` (`extends EquippableData`, what a unit actually carries) holds a direct `template` ref + its own mod spaces + the effective-weapon computation. `scaling_stat` (single enum) is retired in favor of `scaling_blend` (a `Dictionary[Stats.Stat, int]` % mix across STR/DEX/PER/CON — a real design pivot mid-session, not just a rename). Proficiency (`UnitInstance.weapon_proficiency`, per `WeaponData.WeaponType`, defaults to 3 = all spaces active) activates spaces 1..N; module weight now feeds `UnitInstance.get_weight()`'s gear term (threaded through `Unit._gear_weight()`, since `UnitInstance` has no visibility into equipped gear — the persistence-seam boundary holds). The 9 old-paradigm `WeaponVariants/` files (independent stat-tweaked copies — exactly the sync-breaking thing this split fixes) are deleted; the folder's new job is saved, NAMED, fitted `WeaponInstance` presets (the "get attached to your weapon" feature, kept deliberately). One real prototype exists (`TheJaw.tres`, Chainsword-family, `is_prototype = true`). ## Armor content pass — #89

- **Armor is real content as of [#89](https://github.com/Phaazoid/Godoiosis/issues/89) (2026-07-24), and it built three systems that had only been written down.** `ArmorData` grew `flat_def` (an un-scaled DEF term **amending** stats.md's ratified "multiplier with NO base" — a CON *gate* plus CON *scaling* double-dips one stat; the scaled half still zeroes at CON 0, so the rule is narrowed, not repealed), `stat_minimums`/`stat_maximums` (retiring the single `con_requirement`; a piece can demand a floor on one stat AND a ceiling on another), `stat_modifiers`, and `immune_elements`. **(1) The gear stage of the effective-stat chain finally exists** — `Effective stat = base → limb → job → gear` was documented since #56 with the last arrow unbuilt. Gear is derived LIVE on `Unit` from `worn_armor`, deliberately NOT written into `UnitInstance.stat_modifiers` (a stateful, unserialized add/subtract bag the Crisis surge owns — armor routed through it would restore `worn_armor` on load but silently lose its tax). It threads into derived readouts via `UnitInstance.get_mov(gear, dex_modifier)`, a second param in the same shape `gear` weight already used. **Wear gates read PRE-gear stats** (`can_equip` goes through `unit_instance`, not `Unit`) — otherwise a piece's own −DEX could unlock a DEX-*ceiling* piece and equip legality would depend on swap order. **(2) Elemental immunity** — ⚠ *the storage half of this was superseded by [#90](https://github.com/Phaazoid/Godoiosis/issues/90) (2026-07-29): `immune_elements` and `blocks_element()` no longer exist, and the Weave grants an ability instead. The resolver BEHAVIOUR described here is unchanged and still current — see the #90 section below.* Blocked elements are ERASED from an incoming hit in `PlanResolver` (via `Unit.is_immune_to`), so nothing keyed on them can fire; a weapon merely TAGGED with a blocked element still lands its physical swing, but a `TransmutationData` (damage that IS the element — it scales off aura, not the body) is turned aside entirely and **early-returns before lethality and knockback**, because a turned-aside attack is NOT a 0-damage hit: 0-damage hits still count as hits and still finish a downed unit, whereas a blocked bolt never arrived (dev call). It still consumes the attacker's action. Cell effects deliberately read UNFILTERED elements — armor insulates its wearer, not the ground. **(3) Armor rides the SAME inventory as weapons but fills a DIFFERENT slot** — since `ArmorData extends EquippableData`, every weapon-slot path had to learn to refuse it (`add_item` must not auto-equip armor, or it claims the empty weapon slot and shadows the real weapon acquired next; `equip_weapon_from_inventory` refuses it; `remove_item` clears `worn_armor` too, or a tossed vest keeps paying DEF). `Unit.wear_armor(index)` is the ONE chokepoint where armor gets worn, so the gate has exactly one home — the player surface enforces it, the dev tool deliberately BYPASSES it and labels the requirement instead. Four armors authored, each paying for DEF a different way (stat floor / stat ceiling / live tax / forgoing DEF for immunity). **Open:** armor has no weight (`_gear_weight()` reads only the weapon, so plate doesn't trip the heavy-load MOV step or the CON Weight term — the most obvious gap); the Play API has no wear/remove commands; armor acquisition is still dev-tool-only.

**#105 BUILT 2026-07-28, in three passes — and the first two were wrong, which is the useful part of this entry.**

Pass 1 was the design: one derivation, `Unit.projected_cell(unit, actions, require_valid, use_knockback)`, with `Unit.get_projected_destination()` and `SquadPlanValidator.projected_cell_for()` as the two call sites and `Unit.projected_unit_at(units, cell)` as the inverse that `BoardContext`/`SquadManager` both ask. The two axes turned out to be *constraints*, not sloppiness — the validator can't read `is_valid` (it runs inside the loop that computes it) and can't read knockback (derived by a resolve pass that reads validity) — and neither was written down anywhere. That undeclared constraint was arguably a bigger risk than the divergence itself.

Pass 2 fixed the bug the sweep *claimed* was already fixed. Making the reverse index able to see a shoved unit did nothing, because `resolve_plan` expanded **every** aim into a volley before resolving any of them, so all victim-gathering happened strictly before all shoves — a second aim at a landing cell found nobody. The sweep's probe had tested the index in isolation with a hand-set projection and never ran it inside `resolve_plan`. Fix: `PlanResolver.resolve_attack_group` split out so each aim is expanded, resolved, and its shoves published before the next is expanded.

Pass 3 fixed the preview that pass 2 broke. `game._preview_plan_effects` reconstructed a shove's start cell from `atk.target.movement.cell` — the *live* board cell, which never moves during preview. Correct for one shove; for the second in a chain it is two tiles from the landing cell, and both `_get_start_atlas`/`_get_arrowhead_atlas` `match` on unit cardinals and fall through to `PATH_ERROR`. The resolver already knew the answer and threw it away, so `ResolvedOutcome.knockback_from` now records it per hit — the same "pass the fact, don't look it up" remedy as #102, one layer over. `show_knockback_preview` also collapsed to **one ghost per target at its final cell** (it had been drawing a ghost per hit, leaving a copy of the unit on every waypoint) and normalizes direction through `GridUtils.cardinal_direction_i_between`, which also future-proofs a `knockback: 2` attack that would have hit `PATH_ERROR` on a *single* shove.

Also landed with #105: `game.clear_selection()` stopped destroying the knockback and terrain plan previews. Both are properties of the **queued plan**, not the selection — which is why planned-move arrows were never cleared there — and `_on_menu_cancelled` fires on every menu *pick*, so opening Attack wiped the shove ghost and restored the target's real sprite at its old cell for the whole targeting phase. That is what made the landing tile impossible to aim at in play.

Behaviour changes worth knowing: a unit shoved **out** of a later blast's footprint is now correctly missed by it; an attacker displaced by an earlier friendly shove fires from where it lands; chained shoves work. ## Dev-tool save/load verbs and staged unit editing — #99

**BUILT 2026-07-29.** #99 asked for the Scenario tab; the dev extended it to *every* tab with a save/load, so Scenario, Item Editor and Attack Editor now read identically: `[dropdown][Load][Update]` over `[name…][Save As]`, with **Update targeting the dropdown selection** (the thing you can see — `last_loaded_path` stays the F2 reset source and is deliberately not wired to it) and **Save As refusing an existing name** (dev call, reversing the issue's parked default), which is what keeps the two write verbs from overlapping. Shared presentation lives in four `DevWidgets` statics; the Attack Editor's FAMILY_MAINS mode disables Save As, since a family main is never created from scratch.

**One grammar, two implementations — a declared asymmetry, not drift.** A scenario dropdown entry *is* its path minus prefix and suffix, so `ScenarioManager.scenario_path(name)` (new, and the single formula all three call sites now share) rebuilds it exactly. An editor dropdown entry is the resource's own `display_name`/`item_name` — that is how every catalog keys its scan — and need not match the filename, so Update there writes to the entry's `resource_path` instead. Rebuilding a path from an editor name would silently miss any resource whose basename differs.

**Two pre-existing bugs surfaced by building it, both found by headless probe rather than by reading:**

- **`load()` serves the resource cache, so overwriting a `.tres` at runtime did not stick.** The file was written correctly, but every later `load()` returned the stale pre-edit object until restart. This already affected `ScenarioManager.save_scenario`: re-saving a loaded scenario made both Load **and the F2 reset** replay the pre-save board. `take_over_path()` is the only call that repairs the cache entry (`CACHE_MODE_IGNORE` forks a second object and leaves the cache stale for everyone else) and is a safe no-op when the resource already owns the path, so every save now routes through `DevWidgets.save_over()`. Editing a resource **in place** (FAMILY_MAINS mutates the live cached `main_attack`) was already correct. Sharp edge recorded in `CLAUDE.md`.
- **`OptionButton.add_item` auto-selects index 0**, so a dropdown rebuild finding no name match left the control pointing at whatever sorted first. Harmless while a dropdown only filters; not harmless once it names an overwrite target. Every rebuild `select(-1)`s before its match loop. This was a live defect in the issue's own proposed `refresh_dropdown`.

**Also in the same pass:** the Scenario tab's lower half moved into a `ScrollContainer` — it was the only tab without one, so its minimum height tracked the squad count and pushed the window past its own bounds until the tabs became unreachable; objectives moved above the squad list so the unbounded list sits last (they now build into their own `%ObjectiveList` rather than the tab root); and the tab shows which scenario is loaded, read off `last_loaded_path` rather than stored a second time. `DevOverlay._on_tab_changed` calls a new `refresh_on_show()`, which also fixes objective checkboxes going stale when a mission was loaded from the boot screen.

**Unit editor edits now stage behind Save** (dev-initiated, same session). Every control wrote straight through to the live unit, so nudging a spinbox and clicking away committed it. Edits go to a staging buffer; Save applies, Revert re-reads, switching units discards with a `push_warning` naming what was dropped, and re-selecting the *same* unit is a no-op so it cannot wipe staged work. **The buffer is hand-written field by field because there is no cheaper option: `UnitInstance` extends `Resource` but every editable field on it is a plain `var`, not `@export`, so `duplicate()` copies nothing but `data` and returns a blank.** (Probed, not assumed — this is also why `ScenarioUnitEntry.capture_unit_state` is hand-written.) Inventory is the easy half: a fixed-size `MAX_INVENTORY_SIZE` slot array, so a plain copy stages it, with equipped/worn held as **indices** into that copy — the same model `ScenarioUnitEntry` already uses. `_apply` writes back in dependency order (stats before HP because they move its ceiling; inventory and armor before HP because the clamp reads gear, #106; faction last so its repaint sees a finished unit) and still assigns equipment directly, bypassing the equip/wear gates, because dev tools staying omnipotent is the point. Delete/Move/Duplicate stay immediate — they are actions, not values — and MOV / Effective STR/DEX still read the live unit, labelled `(saved)`, because they derive through gear and effects the buffer deliberately does not model. Two fixes fell out: `Array.find(null)` returns the first **empty** slot rather than -1, so an unarmed unit used to come back "equipping" slot 0 (both index lookups now guard on null), and dropping armor into an empty slot no longer auto-equips it as a weapon.

Verified instead by a standalone `--script` probe (scripts parse, scene loads, all 24 signal connections resolve to real methods on their receiving script) plus in-game feel-testing by the dev. **#106 + #112 BUILT 2026-07-29, in one commit (`aa512ac`) because they are one seam.** #106 said max HP and LDR read the gear-less chain; #112 said temporary stat modifiers lived on the wrong side of the persistence boundary. They landed together because fixing either one alone re-opens the other — both are questions about *where a stage of the effective-stat chain lives*.

`UnitInstance.stat_modifiers` was a battle-scoped add/subtract bag parked on the **persistent** resource, purely because it was one stage of `get_effective_stat`'s chain. It was the persistence seam's last documented exception, and it had **already gone permanent once** by having its reset missed — the leak shape a hand-balanced +5/−5 pair invites. The seam's own test ("does it survive a mission?") always said temporary stats belong on `Unit`.

`StatEffect` replaces it, and the two design choices are the point. An effect is **RETIRED, never subtracted**, so forgetting to remove one leaves a stale effect rather than a corrupted number — the failure mode degrades instead of compounding. And it is authored as a template while a unit carries a **copy**, because `turns_remaining` is per-application state: two units drinking the same tonic must not share a countdown.

The chain is now stated once, and **where each stage lives is the whole finding**: `base → limb → jobs → temporary effects → gear`. Only the first three live on `UnitInstance`; `Unit.get_body_stat()` adds effects, `Unit.get_effective_stat()` adds gear. That is what made #106 the same bug — because the chain's top stages live on `Unit`, **every derivation off a stat must live on `Unit` too, or take the finished value as a parameter**. So `UnitInstance.get_max_hp(effective_con)` and `get_mov(effective_dex)` are now *passed* the value they used to re-derive without gear, `get_effective_ldr`/`get_effective_def` moved onto `Unit`, and `Unit.set_current_hp(value)` became the one door for writing HP (the clamp needs a ceiling `UnitInstance` cannot derive). Textbook law #4: the second answer existed because the first wasn't reachable from where the code was standing.

Everything that *follows* a stat change runs in `Unit._settle_stat_change`, in this order because each step feeds the next: enforce wear gates (stripping gear you no longer qualify for) → re-clamp HP → emit `stats_changed`. Stripping armour moves CON, which moves max HP. Wear gates read `get_body_stat`, i.e. **never gear**, which is what keeps the strip to a single pass with no cascade.

Decided forks, all live: wear gates **do** read temporary stats and a failed gate **force-unequips**; effects are **additive only** (no multipliers, no set-to); the Crisis surge is **3 turns** rather than an untracked flag. Sources *derived* from state that already exists — worn armour, and terrain if it ever moves an input stat — are deliberately **not** stored as effects; that would be a second seam for a fact the code already holds, and `get_effective_stat` reads them where they live. `stats_changed` is for **readouts only**: "may this be queued?" is a question about the *projected* stat and belongs to `SquadPlanValidator`, parked as [#113](https://github.com/Phaazoid/Godoiosis/issues/113) rather than answered twice — four questions, four mechanisms, and a signal answers repaint, never queue validity. Doctrine in `docs/design/stats.md` (*One chain, one layer*; *Temporary stats*); pinned by `tests/stats/test_stat_effects.gd` + `test_derived_stat_chain.gd`.

**#109 BUILT 2026-07-29 — the last `type/bug` finding from the sweep, and the probe corrected the issue twice.**

Four implementations of *can a unit stand on this cell?*, disagreeing on two axes. Re-verified before building (the #107 lesson): a throwaway suite copied each formula byte-for-byte onto a real `TestTiles.tres` board with a ground-truth column, and **deposited FROZEN through a real ICE map attack resolved by `PlanResolver` with the authored `TerrainReactionCatalog`** rather than hand-setting the state — the distinction that had made the original sweep's #105 probe wrong. Result: on a frozen water tile `BoardContext` answered `true` and `HoverPresenter`, `game.spawn_unit` and `play_session.terrain_at` all answered `false`, while ground truth (`RulesService.movement_cost`) answered `true`. Exactly as filed, and still live.

**Correction 1 — the missing-flag path throws, it is not a silent `false`.** The issue read `BoardContext`'s unguarded `get_custom_data` as "returns null → false". It actually raises *two* runtime errors per call (`TileSet has no layer with name: walkable`, then `Trying to return value of type "Nil" from a function whose return type is "bool"`), with `false` only the coercion byproduct afterwards. Since `is_walkable` runs per-neighbour inside `compute_move_range` and `GroupMoveSolver._path_hops`, on such a tileset that is a log flood at hover framerate, not a wrong answer. The guard is load-bearing. Still dormant only because every tile in `TestTiles.tres` declares the flag.

**Correction 2 — the missing-flag default is now a decision, not an accident: undeclared = NOT walkable.** It is what the authoritative reader already answered (so no board changed behaviour), it matches `play_session`, and refusing to path is the safer failure for what is really an authoring bug. `HoverPresenter`'s stated "undeclared = walkable" was the one retired.

**Ground truth confirmed rather than nominated.** `RulesService.movement_cost`, `GroupMoveSolver._path_hops` and `PlanResolver._resolve_knockback` all bottom out in `board.is_walkable` for the cell-level question, so `BoardContext` genuinely owns it. The fix is three deletions and a delegation: `HoverPresenter._is_walkable` deleted outright (one caller), `spawn_unit`'s inline block and `play_session.terrain_at`'s tile read both replaced by `is_walkable`, with **occupancy kept deliberately separate** — `is_walkable` answers "may a unit stand here", never "is someone already standing here".

**A fifth answer the issue never named:** `DevController.resolve_pending` (dev-mode "move unit") checked off-map and occupancy but **never asked about walkability at all**, so it dropped units onto open water while dev-*duplicate*, which routes through `spawn_unit`, refused the same cell. Two adjacent dev verbs, opposite answers. Folded in.

**A live divergence one layer up, filed as [#115](https://github.com/Phaazoid/Godoiosis/issues/115):** the *unit-level* question — "may **this** unit end up here?" — has two answers. `movement_cost` honours Waterwalk; `GroupMoveSolver` and `PlanResolver` call the bare cell predicate. Verified on a real board: a Waterwalking Scout's own move range crosses water while the formation solver treats it as a wall, so the ability silently stops working when the unit moves with its squad. Waterwalk is authored on the real `scout` job, so this needs no new content to reach. Kept out of #109 as a different question — and **built the same day**, see below.

Tests: `tests/play/test_play_session.gd` +1 (frozen water reads walkable to the headless view — the view and the rules agreeing is the Law #2 property the Play API exists to surface) and `tests/terrain/test_ice.gd` +1 (the missing-flag default, which was **red before the guard landed** — gdUnit4 reports the runtime error as a failure, so it is a genuine red→green pin). Full suite **712/712**. Two of the four sites sit in [#114](https://github.com/Phaazoid/Godoiosis/issues/114)'s blind zone (`game.gd` + `HoverPresenter` have no runner coverage), so this one was feel-tested in dev mode rather than trusted to green.

**Lesson recorded on the law itself:** four of the six findings live at a *layer boundary* — the second answer appears when the first isn't reachable from where you're standing (`UnitInstance.get_max_hp` can't see gear because gear lives a layer up, so it rebuilt locally). That is #102's "prefer passing over looking up" arrived at from the opposite direction, and the law now says so: **if you can't reach the existing answer from here, take it as a parameter — don't rebuild it.**

**#115 BUILT 2026-07-29 — the unit-level twin of #109, and the finding got narrower on inspection.**

Filed as "the Group Move solver treats water as a wall". Reading the solver showed something more precise and more embarrassing: **the member's own `reach` was already correct** — `compute_move_range` goes through `movement_cost`, which honours Waterwalk — and it was the **cohesion leash** that broke it. `GroupMoveSolver.plan` built one `_path_hops` field from the leader's destination using the bare cell predicate and shared it across every member; `_candidate_cells` then rejected any cell the field had no distance for. So a Scout's near-shore water cells were correctly offered by `reach` and then thrown away by the leash. The ability worked when the unit moved alone and stopped working the moment it moved with its squad — which is exactly the shape that makes a duplicate seam hard to notice from play.

The fix is the law's own remedy: **extract the shared question rather than let the second caller re-implement it.** `RulesService.can_traverse(cell, unit, board)` is now the one home for "may THIS unit traverse this cell's terrain?" — `movement_cost` became its first *caller* instead of its owner, and `_path_hops` takes a unit and asks it too.

**The near-miss worth recording: `_path_hops` must NOT use `movement_cost`.** That was the obvious consolidation and it is wrong — `movement_cost` also returns `CANNOT_WALK_TILE` for a cell occupied by an *enemy*, so routing a connectivity field through it would let a single enemy body sever the cohesion leash and change formations near any hostile. Occupancy blocks a move; it is not terrain, and it moves every turn. `can_traverse` therefore answers terrain only, and the split is pinned by a test rather than left to a comment. The general lesson: when you extract a shared question, check what *else* the fatter caller was folding in — the extra is usually the reason it was fat.

**Second change: the leash field is per member now**, since traversal differs per unit. Measured with `tools/profile_group_move.gd` on Castle Assault: `plan` came in at **5.6–7.0 ms across four runs** against a single-run 5.75 ms baseline — i.e. *inside the harness's own noise*, because the extra depth-bounded walks are trivial beside the ~1 ms `compute_move_range` sitting next to them in the same loop. **The plan signature was IDENTICAL on every run**, which is the claim that actually matters: Castle Assault has no Waterwalkers, so any signature change would have meant ordinary formations had moved. That also produced a new note in `docs/performance.md` — **one run is not a measurement**; this harness has a ~25% spread, so compare ranges.

**Knockback was deliberately NOT changed.** `PlanResolver._resolve_knockback` still asks the cell-level `is_walkable`, so a Waterwalker is not shoved onto water — being thrown isn't walking. That is now *declared* at the call site instead of being an accident, and it points at [#116](https://github.com/Phaazoid/Godoiosis/issues/116), filed the same day for the mechanic this was really blocked on: **shoving a unit off a height kills it outright** (airships, moving trains, cliffside cities), power-gated by map design and knockback distance rather than by any balance knob — which is a large part of why shove effects are costed the way they are. Shoving someone into plain **water** is explicitly *not* an instant kill, and what it should do instead is left open on purpose (nothing / a WET soaking / a movement penalty / just swim).

Tests: `tests/rules/test_movement_cost.gd` +2 (the `can_traverse` seam, and the occupancy split), `tests/ai/test_ai_control.gd` +2 (a water wall a Scout crosses and a plain unit doesn't; an enemy body that must not sever the field) plus the three existing `_path_hops` bound tests updated for the new signature. Full suite **716/716**.

**Sweep status.** Five of the six filed findings are built — #105, #106, #107, #108, #109 — and #112 (a later, separately-filed seam) shipped alongside #106. The sixth, [#110](https://github.com/Phaazoid/Godoiosis/issues/110) (the Play API mirror), is still open: it is *drift* rather than duplication, and #109 closed one of its symptoms (`terrain_at` now matching the rules) without touching the rest.

## An AI turn that never ended, and a signal nobody connected — #103, #117

**BUILT 2026-07-29.** Filed as a soft-lock: in `Castle Assault`, both player squads on AI/Rushdown and the enemy on AI/Hold, the game played itself into a permanent stuck state once the enemy leader was the last hostile standing — ghost movement projections and path arrows frozen on the map, the enemy AI swinging at a ghost and passing, the player side doing nothing and passing, forever.

**Two defects stacked, and the issue's own ordering was right: the second is the one that matters.**

*Defect 2 — the invalid-plan guard is a player affordance with no AI counterpart.* `OrderExecutor.execute_orders` flashes the invalid rows red and `return`s, above everything that ends a squad's turn. For a human that is exactly right: fix the plan, press Execute again. An AI squad has nobody to hand control back to. Measured on a minimised board, the refused pass left `has_acted` false, both orders still queued, `active_squad` still set, one ghost sprite and one path arrow drawn, the leader's real sprite hidden, and `get_projected_destination()` reporting `(5,0)` for a unit standing at `(1,0)` — which is precisely the cell the enemy AI was attacking. Three consecutive turns produced byte-identical state: nothing in the cycle mutates what produced the plan, so the loop is stable, not transient.

The fix is small because the cleanup already existed and only needed a name. `set_has_acted(squad, true)` empties the queue via `Squad._set_has_acted`, and each `action_cancelled` hop lands in `game._on_unit_action_cancelled`, which is what takes a move's ghost and arrow down. So the tail of `execute_orders` became `_end_squad_turn(squad)` — one definition of "this squad's turn is over" — and the AI branch of the guard routes through it. Keyed on `is_ai_faction`, i.e. the ENABLED toggle, not on `!= PLAYER`: a hotseat faction with AI off is a human and must keep its plan.

*Defect 1 — the AI can author a plan it cannot execute.* `GroupMoveSolver` places a member nowhere when no cell inside the leader's NEW cohesion range is free (`if candidates.is_empty(): continue`), and that member then keeps the hold-position order `setup_hold_move_actions` gave it, standing where it was. `SquadPlanValidator._check_leader_range` checks holds too, so the stranded member reads *"Squad leader range invalidates other movement"* and the **whole** plan is refused. The reported trigger is not incidental: with one hostile left, both squads converge on the same neighbourhood, and allied bodies are exactly what makes every in-range cell unavailable (allies don't block traversal, but `compute_move_range` drops their cells as destinations).

Fixed by `AITactics.queue_group_move_if_coherent` (**folded into `SquadManager.queue_group_move` on 2026-07-31 and deleted** — the queue-time gate made all-or-nothing the rule for every caller, not just the AI): commit the group move, and if the plan doesn't validate, cancel every member's move via `cancel_move_for_unit` — the player's own cancel seam — which restores the all-hold plan the squad started with. That is legal by construction (each member was already inside the leader's range, and a unit holding on its own cell cannot collide with itself), and main actions still queue from where each unit stands. **Give up the advance, not the turn.** Both moving archetypes call it; the deliberate non-fix was gating every candidate cell in `best_attack_destination` on coherence, which runs the whole formation solver ~40 times per squad per turn and belongs in a measured pass.

**The dev's follow-up question was better than the fix.** *Why does the AI use group move at all — isn't that a player convenience?* Measured answer: it is not the cause. One individual leader move, no group move anywhere, produces the identical refusal, because the invalid order is the hold filler a `game.gd` signal handler inserts regardless of who authored the move, and the binding rule is cohesion, which applies to any plan from any author. Deleting group move would remove the AI's *only* cohesion solver and fix nothing. But the design instinct holds, and the path is cheap: `compute_move_range` already leashes a non-leader to the leader's projected destination, so queueing the leader first makes each member's own range cohesion-clamped, and per-unit destinations need no new solver — only a decision about each archetype's movement taste. Parked on **[#117](https://github.com/Phaazoid/Godoiosis/issues/117)**, a new *evergreen* AI catch-up tracker opened on the premise that the AI is permanently behind the feature set: every system we add creates AI work that lands after the system ships.

**And then the real find.** The dev also reported units walking onto their own downed bodies. Root cause was not an occupancy rule: **`Unit.went_downed` was never connected in the game.** `OrderExecutor.on_unit_downed` is written to receive it and fill `_downed_pending`; the only `went_downed.connect` in the repo was `play/play_session.gd`'s. So the headless API ejected downed units and the game never did — for thirteen months of build notes claiming otherwise. `_downed_pending` was never written, making **both** consumers dead code: `_process_downed_pending` (no ejection, so a downed unit stayed a squad member, so its tile stayed a legal destination — `compute_move_range` only excludes *non*-squadmate cells, since squads rotate through each other on purpose) and `_offer_pending_crisis` (**the Crisis prompt could never fire**). Two further measured consequences: a downed **leader** kept the squad, because `check_reassign_leader` only runs via ejection — so every member's move range stayed leashed to a corpse's tile. One line in `game.spawn_unit`, beside the `unit_died` connection it should always have had.

The lesson is the reusable part, and it is not "test more": **a feature can be fully built, correct at both ends, and separately tested at both ends, and still never run because nobody tested the wire.** What let it hide for so long is a Law #4 shape nobody had named — the Play API keeps its own connection for the same seam, so the behaviour was demonstrably present in one implementation while absent in the other.

**Tests, both on the real game scene, both falsified case-by-case before the fixes landed.** `tests/ai/test_ai_turn_terminates.gd` (5) pins the terminal state as one block — `has_acted`, empty queue, zero ghosts, zero arrows, visible sprites, projected cell equals actual cell — because #103 was every one of those leaking together, plus two cases guarding the human affordance the fix could easily have eaten (player-controlled and hotseat-enemy squads must both keep a refused plan), plus a three-turn loop, because *stability* was the bug's signature and one turn cannot see it. `tests/squad/test_downed_ejection.gd` (4) pins the wire itself and the observable rule, deliberately not membership. Full suite **803/803, 0 orphans, 49.3s**.

Two things learned about the runner while doing it, now in `tests/README.md`: **the first failure in a suite file silently skips every later case in it** (measured exactly — a three-case throwaway suite reports `Executed test cases : (1/1)` when case 1 fails and `(3/3)` when it passes; discovery finds all of them, so it is the runner), which means a new suite has to be falsified one case at a time; and **plan-validity tests need the real scene**, because `board_builder` boards never grow the hold filler that decides validity.

## A save becomes a mid-battle snapshot — #87

**BUILT 2026-07-30.** Filed during #84 in-game testing when a Kinetic Mace lost its banked charge across a save/load; on inspection the charge was one symptom of the whole battle-scoped layer being absent from saves.

**The decision the issue already carried, and why weapon-state-only was refused.** Scenario save/load round-tripped only the persistent `UnitInstance` side (#83). That is correct for a **mission boundary** — you re-arm each mission — and wrong for a **save = pause/resume**, which is a different axis the persistence seam had never separated. Fixing charge alone would have produced a lopsided snapshot: charge kept, but downed units standing up and fires going out. So the whole layer moves together: per-weapon battle state, element states, lifecycle + the downed clock, the three Crisis flags, `rally_count`, live `StatEffect`s with their countdowns — plus two the issue's sketch had not named and the same argument demands, `Squad.has_acted` (reload after a mid-turn save and every spent squad gets a second turn) and `MissionController`'s captured zones + `contested` latch (reload mid-mission and every objective you already paid for is silently un-taken).

**The mechanism is what keeps the seam intact.** Nothing became `@export` where it lives. Weapon readiness/charge/rev/ammo are still plain vars on `WeaponInstance` subclasses, so `make()`/`copy_equippable()` re-arm every weapon and a mission boundary still resets for free; lifecycle, states, Crisis and rally are still plain vars on the transient `Unit`. The snapshot captures them **explicitly**, exactly the way limb fittings have always been captured rather than serialized. That is also the answer to the split `MissionController.reset()`'s header had been promising since #96 (*"loading a save RESTORES, starting a mission RESETS"*): it is **not a flag on the load**. A scenario file *is* its board, so a load restores what the file recorded and an authored mission recorded nothing; the reset half stays real for the roster → board path (#70) that does not exist yet, where units arrive carrying no battle state by construction.

**`WeaponInstance.capture_battle_state()`/`apply_battle_state()`** is a third family-agnostic virtual pair beside the readiness and status ones, base returning `{}`. A **Dictionary**, not one int, even though all four families track exactly one number today — #108's lesson is that a seam which cannot say what content needs grows a second one, and the first family wanting two counters would have been that seam. Keys are family-private strings rather than a shared enum: they name one class's fields, not a game vocabulary. States are keyed **by inventory index**, the same identity rule the prosthetic re-link had just learned the hard way — a unit can carry two Carbines and they must track independently.

**Two structural rules, each with a falsified test.**

*A restore replays the RESULT, never the EVENT.* `Unit.restore_lifecycle`/`restore_stat_effects` exist because the normal entry points carry consequences the save already recorded: `_go_downed()` emits `went_downed` (ejecting the unit from a squad the loader has not rebuilt yet) and spends Will a second time, so a unit could reload maimed for a down it already paid for; `apply_stat_effect()` calls `instantiate()`, which reseeds `turns_remaining` from `duration`, handing a one-turn-left Crisis surge back with all three. `StatEffect.turns_remaining` became `@export` for this and only this — `instantiate()` still reseeds it, so an authored template cannot leak a stale countdown.

*Effects settle before gear and before HP.* Settling enforces the wear gates, so restoring effects after the armour lets a saved debuff strip gear the save says is worn — the same *a save is authoritative* rule `worn_armor_index` follows; and a `+CON` effect moves the max HP the saved `current_hp` was measured against. Reintroducing that ordering bug failed the new case **and** an existing #89 one (`test_load_does_not_re_run_the_wear_gate`), which is the independent confirmation the constraint was real rather than invented.

**One refactor fell out of testing, and it was overdue.** `ScenarioManager.capture_scenario`/`apply_scenario` were split out of `save_scenario`/`load_scenario` — the shape `play/board_builder.gd` has had all along — because a whole board could otherwise only be round-tripped through the disk, and writing a test `.tres` into `Scenarios/` would be picked up by Mission Select and by #9's folder-scan suite. `load_scenario` is now `load()` + `apply_scenario` + the path bookkeeping.

**A comment that claimed a mechanism the code does not have.** The first draft justified applying `has_acted` after the squad rebuild with *"can_join_squad refuses a squad that has already acted"*. It does — but the loader joins through `join_squad`, which is deliberately ungated, so the ordering is a forward guard rather than a live constraint. Corrected in both loaders and in the test's own comment. Worth recording: a justification that sounds like Law #4 is not evidence of it.

**Tests.** `tests/flow/test_battle_state_snapshot.gd` (22) pins one entry — per-family weapon round trips, two of a family staying independent, a real `ResourceSaver`/`load` pass for the nested typed Dictionary, element states, the downed clock and sprite, Crisis/rally, effect countdowns and expiry, both ordering halves, and the pre-#87 additive-default contract. `tests/flow/test_scenario_round_trip.gd` (10) pins a whole board through `capture_scenario`/`apply_scenario` on the real game scene, because `has_acted` and the mission latches have no per-unit entry to live on. Six mutants were reintroduced one at a time and every one was caught (countdown reseed, `_go_downed` on restore, rev refresh, `has_acted` skipped, effects-after-gear, weapon state applied by first match instead of index). Suite **783/783** across every area except `tests/ai`, which was independently broken at the time by an untyped in-flight change (`RulesService.path_hops` does not exist yet).
