# Iosis — Project Guide

Tactical RPG (Fire Emblem-influenced), Godot 4.7, GDScript. Solo hobbyist developer.

## Collaboration contract (read first)

**Claude implements; the dev reviews.** Contract changed **2026-08-05**, replacing the hand-typed-walkthrough model that ran from project start. Claude edits every file directly — `Classes/`, `Scenes/` and `game.gd` included. The dev is practicing an agentic workflow for a role that requires it; **he will say so explicitly if he ever switches back**, so until those words are said, this is the contract. He is still here to learn: explain the *why*, not just the *what*.

**Plan before touching ANY file — tightened 2026-08-06, no size exception.** The trigger used to be blast radius (feature / invasive change / bugfix); it no longer is. The dev's words, after `Stats.Stat.COH` vs. a bespoke field (#142) got decided and coded before he ever saw the fork stated: *"I'd like to see a plan from you about what code changes you are going to make... before you edit something, no matter how minor."* Every file — `Classes/`, `Scenes/`, `game.gd`, `docs/`, `tests/`, scaffolding, all of it — gets a plan first, him included on things he'd otherwise never be asked about (a `.gitignore` fix made and only narrated afterward, same session, is the shape to avoid). Reading/searching to build the plan needs no announcement — only `Edit`/`Write`/anything that mutates a tracked file does.

**Depth scales with the change; the plan step itself never gets skipped.** Hitting more than one of — a new capability, more than one valid approach, an architectural choice, more than a couple of files, unclear scope — means **formal Plan Mode** (`EnterPlanMode`/`ExitPlanMode`): explore, write the plan, nothing gets edited until he approves it. That is a lock, not a promise. A genuinely fork-free edit (an obvious typo, a one-liner he already dictated verbatim) still gets stated before it happens — one line, then wait a beat — but doesn't need the formal mode-switch.

**A plan that stops working gets RE-PLANNED, not patched around and narrated after.** Discovering mid-implementation that the approach is wrong, or silently switching to a different one, means STOP before finishing the edit — lay out the revised plan and wait, exactly like the first one. Explaining a pivot in the wrap-up is the failure this replaces, not a lighter version of compliance.

**What a plan must contain** (the full version — a fork-free one-liner just needs the one-line statement of intent above):

- **The question** the change answers, and **what already answers it**, naming what was actually grepped. *Grep the question, not the name* (Law #4).
- **Every caller/reader of anything being changed, counted from the code.** Relaxing a predicate for one caller without checking its other three is exactly how the Group Move hole shipped (2026-08-04).
- **Files touched** and what each change is.
- **How it will be verified** — decided before building, not after.
- **The riskiest assumption**: what would make this plan wrong.

**Review surface = the plan + the diff.** A summary of a change is not evidence of the change. Keep the unit of work to **one reviewable diff**; never chain several tasks' worth of edits before he has seen any of them. Commit points are review points.

**Report verification honestly** — what ran, what passed, and what was *not* checked. **The suite is not the gate:** 6 of 7 cases passed against the build that bricked the pause menu (#131), and 955 green cases sat on top of a `clear_board` that had stopped clearing the board (#132). Anything touching UI, input, or ordering needs the game actually launched. **Falsification — reintroducing a bug to prove its regression test goes red — answers whether the TEST has teeth, not whether the fix works;** that second question is his, by playing. So falsify only where the test could plausibly be blind: **ordering/timing**, a **missing wire**, an assertion leaning on a Godot quirk (freed refs, `visible`, orphan counts, queue state), or a test that reaches its precondition by *setting state directly* rather than driving the real path. Skip it when the assertion sits one hop from the change. Run the **one suite file**, never the tree.

**Retired with the old contract (2026-08-05).** These existed *solely* because a human retyped Claude's output, and that whole failure class is now gone — do not re-derive them from this file's git history: the whole-function code-block law (#128/#132), file+function prose anchoring, one-heading-one-file (#141), and "verify by reading the real file after a walkthrough — transcription drift is the top failure mode." Likewise the standing exceptions that carved narrow write permission out of the old rule (2026-06-12 scaffolding, 2026-07-16 header comments / `.tscn` / comments, 2026-08-05 bug-reporting) are **absorbed, not revoked** — everything they permitted is now simply permitted.

**Still live, unchanged by the switch:**

- **Content is disposable; cleanliness is not.** `.tscn` scenes and saved `Scenarios/*.tres` are placeholder — fix them to match the code rather than carrying a legacy-compat branch for their sake.
- **File header comments.** Any `Classes/`/`Scenes/`/`game.gd` file touched that lacks a top-of-file description comment (what the file/class IS and its place in the architecture) gets one added.
- **Terse comments in source.** Rationale goes in chat, `docs/`, and issue text — never walkthrough prose in a `.gd` file.
- **A dirty working tree is a ticket defect at BOTH ends (dev rule, 2026-08-26).** His words: *"no issue is acceptable if it causes the workspace to be continuously dirty… and no issue is complete if it can still leave the tree dirty."* Two gates, at opposite ends of a ticket. **Acceptance:** refuse a design whose ordinary operation — running the game, opening the editor, a routine tool pass — produces tracked modifications; say so before building rather than shipping it. **Completion:** green tests and a clean `git status` at commit time are NOT the test; the question is whether anything he normally does re-dirties it afterwards. A permanently-modified file trains him to ignore `git status`, and a real uncommitted change then hides in the noise — it also destroys the staleness tell for whose work a tree is holding. **How:** for any file the project writes back (a `.tres`, a generated artifact, a settings file), ask what the real writer emits when it saves and make the committed bytes BE that — round-trip through that writer and diff, never hand-author a serialized format and reason that it is equivalent. There is already ONE answer to putting uids back after a save that drops them, `DevWidgets.restore_uids` ([#481](https://github.com/Phaazoid/Godoiosis/issues/481)) — it handles the `[gd_resource` header line as well as the `ext_resource` ones; do not write a second. The two cases, and note that in BOTH the code was correct and the only symptom was a `git status` line: **acceptance = [#540](https://github.com/Phaazoid/Godoiosis/issues/540)** — `lookdev_meshlib.tres` embedded the ground atlas as an `Image` sub-resource, and `ImageTexture::set_image()` keeps **no reference** to the Image it is handed, so the parsed sub-resource id was gone the moment the file was read and the next editor save minted a fresh one; fixed by moving the atlas to a PNG on disk, since only an `ext_resource` survives a save. That ticket is also a standing warning about naming a cause you have not measured — the *generator* was the obvious suspect and was measured **innocent** (`gen_lookdev_assets.gd --meshlib` is byte-stable over a clean tree), and the missing `uid=` attributes were a separate, already-closed matter. **Completion = [#111](https://github.com/Phaazoid/Godoiosis/issues/111)** — `display_name` hand-inserted into `MainAttacks/*.tres` at a position Godot does not use (a `WeaponAttackData` field serializes *before* the inherited `AttackData` ones), so the first editor save handed him a modified `ChainSword.tres` he never edited; fixed in #546, proven by the committed file becoming byte-identical to his editor's own output. Two traps found there: a headless `ResourceSaver.save()` **strips every `uid=`** where the editor preserves them, and it **materializes a defaulted property** — `WeaponData.mod_spaces` defaults to `SPACE_CAPACITIES.duplicate()`, so a headless round-trip writes `[1, 2, 3]` out and pins that family to today's value instead of following the constant.
- **Aesthetic tuning values get a knob, not a guess (dev rule, 2026-08-12).** When a shader/lighting/post/animation value is a matter of taste, don't burn rounds picking numbers — expose it and hand it to the dev: *"I can find the values that work, and we can save a lot of time."* **The surface exists as of #212 (2026-08-15): the dev-tools window's Moods tab (`Classes/dev/MoodsTool.gd`)**, so the usual answer is one line in a knob table, not a new panel. **Since #272/#373/#380 there are THREE tabs and the fork is "who may disagree about this value": one board vs another → a Look knob (it joins presets, and since #373 every Look knob does — the table is scene mood entire); nobody, ever → a `GameKnobs` row (board markup, the unit readout, camera handling, world construction, fire — the game constants, entire since #380), written back into the declaration that authors it; one tile TYPE vs another → an `ObjectKnobs.FIELDS` row (a TileSet custom-data column). Putting a game-wide value in Look is the mistake that shape exists to prevent — see `docs/design/presentation-effects.md` → *Where a presentation value is authored*.** A knob there may only name a property that is **authored and READ** — anything the game writes back per frame gives a slider that moves and silently reverts, which is the one failure that makes a tuning panel worthless, and `tests/dev/test_moods_tool.gd` pins it by writing, waiting two frames and reading back. An `@export` or an inspector-reachable resource is still right for a value the dev tunes in the editor rather than in play.

## GitHub issue workflow (Claude ↔ human handoff)

Open work lives in [GitHub Issues](https://github.com/Phaazoid/Godoiosis/issues).

**Whose turn it is is DERIVED FROM THE THREAD, never labelled (dev ruling, 2026-08-25).** The last thing said on an issue is the answer: if the newest comment leads with `🤖 Claude says:`, Claude spoke last and it is waiting on the dev; otherwise it is Claude's. An issue with no comments is judged by its **body** the same way. Run **`/agent-queue`** to walk everything that is Claude's turn (`priority/P1-soon` first) and advance each one step.

- **When it's Claude's turn:** post a plan (for a feature or a core-gameplay change), or just do the work and post a writeup (small bugfix, `tests/`, `docs/`). **Standing exception to the 2026-08-06 plan-first tightening above, pending the dev's confirmation:** a queue run is unattended, and the value of a plan is his input before Claude commits to an approach — that doesn't apply when he isn't there to answer. Until he says otherwise, small `tests/`/`docs/` work in the queue keeps going straight to a diff + writeup rather than a posted-plan-and-wait.
- **Handing back is just commenting.** There is nothing to set afterwards; the comment *is* the hand-off. The dev replying — including "this needs rework" — hands it back to Claude by the same rule.

**This makes the comment convention load-bearing rather than decorative.** Every comment Claude posts under the user's account **leads with `🤖 Claude says:`** and **ends with** `— Claude (<model>) · <date>` (name the model actually running, e.g. Fable 5 / Opus 5 — the signature is provenance), authored via the Write tool → `gh issue comment --body-file` (never an inline non-ASCII arg — Windows PowerShell 5.1 mojibakes it before upload; see the encoding note in `tests/README.md`). **Drop the lead-in and the queue will hand that issue back to Claude forever.**

> **Why the labels went (2026-08-25).** `agent/claude` / `agent/human` were invented for the pre-2026-08-05 contract, where *"Claude owns the next step"* meant *"Claude drafts a walkthrough the dev types in"* — a distinction that stopped existing the day Claude began writing the code. Measured at retirement: **80 `agent/human` to 5 `agent/claude`** across 90 open issues, i.e. a field that was 89% one value — and **wrong 24 times out of 85.** Five issues Claude had already answered still read as its turn, and **nineteen the dev had replied to were still marked as waiting on him, so `/agent-queue` could not see them at all.** The thread already held the answer; the label was a hand-maintained copy that drifted — Law #4, one question one answer, on the tracker instead of in the code. The old assignments are archived in the retirement PR if they are ever wanted.

**Every merge bumps the version — each build must be distinguishable (dev rule 2026-08-11; the MECHANISM moved to merge time 2026-08-14).** The one store is `project.godot`'s `application/config/version` (`Build.version()` is the one reader, #134). Semver-shaped: a **feature** bumps the middle digit (`0.1.0` → `0.2.0`), a **bugfix or docs-only** change bumps the last (`0.2.0` → `0.2.1`; docs ruled equivalent to a bugfix 2026-08-12, PR #206).

**Do NOT bump it in a PR's diff.** `.github/workflows/version-bump.yml` does it on main after a merge, reading the merged PR's **labels** for the semver call (`type/feature` → middle digit, anything else → last). The old rule put the bump inside each PR, and the cost turned out to be structural rather than occasional: **any two PRs branched off one base edit the same line, so every concurrent pair conflicts on `project.godot`** — four collisions in one day (2026-08-14) before the dev called it. Consequence to remember: the label is now load-bearing, so a feature PR that ships unlabelled silently gets a patch bump; and the version on your branch is always *behind* main by design — never "fix" it by hand.

**LEAVE THE WORKING TREE ON THE BRANCH HE HAS TO TEST, and say which branch that is (dev rule, 2026-08-14).** His words: *"I don't like having to merge to see the changes you made. That makes it so I have to merge before testing things."* Merging is what a review EARNS; it must never be the way he obtains the code to review. So the last act of any PR that needs his eyes is to check that branch out and say plainly *"you are on `<branch>` — launch it."* Corollaries, each of which has already cost something:

- **Never move his working tree silently.** His Godot session is open on `C:\Iosis\Godoiosis` and renders whatever is checked out. Switching to a branch off main without saying so is what produced the false bug report *"the camera doesn't follow enemies anymore"* — he was playing a build that predated the camera work. **Since #295 the running build says which checkout it came from** — `branch @ shortsha` under the Battle3D help line, and a `Checkout:` line in every `report.md` — so a wrong build is a glance rather than a diagnostic round trip. `Checkout.describe()` (`Classes/core/Checkout.gd`) is the one reader, dev-only, and it answers a *different* question from `Build.version()`: a branch's version is deliberately behind main, so it names a release and can never identify a working tree. The rule above is unchanged by it — a readout catches the mistake, it does not prevent it.
- **ONLY switch his tree when it is on `main` — HARD RULE (dev, 2026-08-25).** His words: *"you're only allowed to switch my work tree if I'm on main. Otherwise, it means I'm looking at another agent's session, and don't want to be moved."* `main` is the idle state and the only one that is safe to take. **Any other branch means someone else's work is checked out and being looked at**, and the rest of this section does not authorize moving it — check `git branch --show-current` BEFORE `git switch`, and if it is not `main`, leave it and say which branch your work is on so he can check it out himself. This bit on 2026-08-25: #497 followed the leave-him-on-the-branch rule below and moved him off `fix/427-corner-cap-zfight`, which he had switched to mid-session. Nothing was lost — the switch was clean and his work was pushed — but he was looking at it. **ONE CARVE-OUT (dev, 2026-08-28): a branch YOU put him on, that you are about to work on, may be taken back to `main` first — his proposal, on being shown the bind.** The hard rule's reason is *another agent's session is checked out*, and that does not apply to a branch this session owns and handed him. It exists because **git refuses a second worktree on a branch already checked out**, so him sitting on your branch is exactly what forces you into his tree — which the worktree convention forbids; #418's settings-lock fix was done in his tree for want of this. **THE TELL IS OWNERSHIP, NOT THE BRANCH NAME**: if you did not put him there this session, nothing changes — leave it and say which branch your work is on. Two preconditions, both required: `git status --short` must be **CLEAN** (dirt may be his own content edits, so stop and ask rather than carry it across), and the move is **announced**, never silent. Put him back on the branch at hand-off as usual. Practical companion: keep ONE long-lived agent worktree and `git switch` inside it, so Godot's cold import (~1 min, `.godot/` being gitignored) is paid once rather than per ticket.
- **Never leave him on `main` or an unrelated branch after doing work.** That is the state that forces a merge-to-test — *subject to the hard rule above, which outranks it: an occupied tree stays put.*
- **Prefer ONE open PR at a time** when the work needs feel-checks, so "the branch you're on" is unambiguous. Four concurrent PRs is also what produced the `project.godot` collisions.
- Getting back: `git switch main && git pull`. Testing a different open PR: `gh pr checkout <n>`.

**DELETE A BRANCH WHEN ITS PR MERGES — remote AND local (dev rule, 2026-08-14).** GitHub auto-deletes the head branch on merge here, so the copy that actually rots is the **local** one: `git switch main && git pull && git branch -d <branch>` is the last step of landing work, not a chore for later. Left alone it compounds — the first sweep deleted **101** stale branches (93 local, 96 remote, overlapping), leaving exactly `main` on both sides.

**Sweep discipline, because a branch cleanup is the one tidy-up that can destroy work.** Delete with `git branch -d` / `git push origin --delete` only what is **merged into main**; `-d`'s refusal to drop an unmerged branch IS the safety net, so never reach for `-D` just to get past it. For anything git calls unmerged, check the CONTENT before deciding: `git diff main...<branch> --name-only` coming back **empty** means the branch introduces nothing main lacks. **Unmerged by SHA is not unlanded by content** — all five survivors of the first sweep were either content-identical to main or strictly *behind* it, including one that looked exactly like lost design canon (*"Record three dev rulings"*) whose every line had already landed via a different commit. Check, then delete; do not bulk-force and do not leave them forever out of caution.

**Canon-sweep discipline before calling a doc update done (added 2026-07-16, after a full-corpus staleness sweep found 9/22 `docs/design/` files drifted):** a "canon swept" claim means a grep-verified pass over the *whole* `docs/design/` tree (+ this file) for the issue's own number and any renamed/removed code symbol or term it touched — not just an edit to the one file that's obviously the topic's home. Staleness hides in three places a narrow, feature-specific edit misses: (1) a status banner elsewhere in the *same* file that a detail-section-only edit didn't reach; (2) a sibling file stating the same fact from a different angle (weapons.md and elemental-system.md both independently described issue #7 as open after it closed); (3) a "living list" tracker (`docs/design/grill-queue.md`) that can go stale from a *different* ticket's work than the one closing. For multi-session issues, sweep against the issue's *final* state at close — re-read its own comment history, not just what the current session built.

**Embedded-content sweep when a diff adds fields to EMBEDDED content (dev rule, 2026-08-20, from #258's fireball):** `.tres` files omit properties at their default value, so every committed resource that EMBEDS a copy of a content type — snapshot scenarios under `Scenarios/` and `tests/fixtures/` above all — silently predates any field added later and loads the default, however the canonical file was authored. That is how the Fireball lob shipped flat: the snapshot's embedded carving predated `arc_clearance`/`up_tolerance`, so the authored arc never reached the board the dev tested on, while every test stayed green against the canonical resource. So a diff that adds an authored field to an embeddable content type (`AttackData`, `WeaponData`, anything a scenario snapshot copies) must, in the SAME diff: (1) sweep the committed `.tres` fixtures that embed that type and re-author the ones whose defaults are now wrong, and (2) say in the PR which fixtures were swept — or state explicitly that nothing embeds the type, so the dev knows the staleness class was checked rather than missed. His words: *"if something like this fireball issue ever happens in the future, I'd like it called out, so that I know not to rely on stale tests."* A field whose default is correct for old content needs no rewrite — but the sweep statement is still owed.

**The mirror — a DELETED or RENAMED content file sweeps its `ext_resource` REFERRERS in the SAME diff (#596, 2026-08-27):** the rule above is a field *added* to embedded content; this is the same law pointed the other way, and it bites harder because **the tree that authors the rename is the one place structurally unable to see it.** `356a2e7` renamed `WeaponMods/Super Scope.tres` → `Line Sniper.tres` and `WeaponVariants/brrr.tres` → (gone) without touching the four files still naming the old paths, so `Noemie.tres` stopped loading, `Scenarios/missions/Level_1.tres` went with it, and five cases reddened across four suites two steps from the cause — while the editor stayed happy, since it holds the old resource in memory and the deleted file may still sit untracked beside it. **A green local run is not evidence here; it is the one environment that cannot detect the fault.** So: grep the repo for the OLD basename before committing any content deletion or rename, and repoint every referrer in the same diff. `tests/law/test_resource_uid_references.gd` grades this automatically since #596 — it now holds BOTH halves of *a reference that resolves to nothing*, the `uid=` half (#240) and the `path=` half (#596), and one failure names referrer and target together. **Which file a referrer should point at afterwards is a CONTENT call, not a code one:** the rename pairing makes a guess look obvious, and a wrong guess is silent — `Super Scoper.tres` reads like `brrr.tres`'s heir and is actually `Super Gun.tres`'s, so it would have re-armed three boards with a mod they never carried. Ask.

**...and content that lost one loads DEGRADED rather than refusing ([#608](https://github.com/Phaazoid/Godoiosis/issues/608), 2026-08-27).** The rule above makes a dangling reference loud; this makes it survivable. **The dev tools live INSIDE the running game**, so content that refuses to load takes the Unit and Item Editors down with it — the only surfaces that could repair it. His words: *"I can't go in and author the fix myself in dev mode."* **Measured before designing, and it decides the mechanism: a dangling `ext_resource` is a hard PARSE error** — `load()` returns null for the WHOLE file and then for everything referencing it, so there is no "let that property come back null" to reach for and the text must be repaired *before* Godot parses it. That fact is pinned by `tests/core/test_content_repair.gd`'s first case, so if Godot ever starts returning a partial resource the mechanism gets revisited instead of quietly rotting. `ContentRepair.load_tolerant` is the ONE answer: strip the dangling reference, load the repaired text, `take_over_path` back to the real file (without which every dev tool writes its edits into `user://__repaired/` and the real content is never fixed). **The CHAIN is the hard half and was #596's actual shape** — `Level_1` → `Noemie` → a weapon that was gone, where the middle file EXISTS so the top file's own references all look fine while it still will not load; children are repaired first, each claiming its real path, which caches it so the parent's retry resolves from memory. **A repaired child must be HELD across that retry** — it is refcounted, and dropping the reference frees it *and* its cache entry, a false negative that reads exactly like the feature not working. It **refuses rather than guesses** twice: a missing SCRIPT is a code fault, not content, and a file broken some other way gets no repaired copy. Wired at `ScenarioManager.load_scenario` and `ResourceCatalog` (the catalogs every editor reads) — ordinary runtime `load()` stays strict. **The save refusal is what stops the repair BECOMING the loss:** `DevWidgets.save_over` rejects a degraded resource while the gap is still open, naming the missing file, and lifts the moment the property is filled — which is how a repair is meant to end, with the dev replacing the reference rather than anything quietly dropping it. `BoardLint` reports it as DEGRADES.

**Staleness marker (added 2026-07-16):** every living design doc (all of `docs/design/` except the three deliberately-frozen historical records — the coherence audit, the co-dev agenda, the wiki triage ledger) carries a `**Canon checked through #NN (date).**` line in its opening banner. When a sweep re-verifies a doc, bump its marker to the current highest issue number + that day's date. A marker sitting far behind the current issue count is the at-a-glance signal a doc is due for a re-check — don't let it go stale by forgetting the bump once you've actually re-verified the doc.

## Design laws (non-negotiable)

1. **No randomness in gameplay.** No hit/miss rolls, no crit chance, nothing. Combat is fully deterministic. (Old design docs mentioning crits predate this law.)
2. **The action queue never lies.** Planned actions must preview exactly what execution does. Queue/cancel/requeue must be idempotent. Derived actions (counter-attacks) are *computed* from the plan, never stored as player orders. **Absolute as of 2026-08-09 (dev + co-dev, out of #124/#155):** the BREAK doctrine (resolution-pipeline R9, 2026-07-05) that sanctioned divergence classes is REPEALED before anything of it was built — plans do not break, execution never re-enters the resolver, and a mechanism that would diverge is redesigned until the resolver can predict it (Crisis → an equipped ability, [#158](https://github.com/Phaazoid/Godoiosis/issues/158)) or doesn't ship. See [`docs/design/resolution-pipeline.md`](docs/design/resolution-pipeline.md)'s repeal record.
3. **Future AI uses the player's API.** AI issues orders exclusively through `SquadManager.queue_action` — no side channels. This protects law #2 forever.
4. **One question, one answer — never build a second seam for a fact the code already holds.** (Added 2026-07-28 after #102; elevated to a law because it has already bitten five times.) Before adding a field, flag, predicate, method, or *content convention*, find what already answers the question it would answer, and either extend that or explicitly retire it. **Grep the question, not the name** — the duplicate almost never shares a token with the original, which is exactly why it slips through (`requires_readiness` vs `knockback > 0`). **Suspect anything with an honest local motive**: the second seam always looks like it solves a different problem, and that motive is the disguise. **Prefer passing over looking up** — and its sharper form, learned from the #104 sweep: *if you can't reach the existing answer from where you're standing, take it as a parameter; don't rebuild it locally.* Four of that sweep's six findings sat at a layer boundary, where the second answer appeared precisely because the first wasn't in scope (`UnitInstance.get_max_hp()` can't see gear, so it re-derived CON without it — fixed in #106, it now takes `effective_con` as a parameter). A looked-up fact can silently diverge from a passed one; a parameter makes divergence unrepresentable (`Reach.get_affected_cells_from(…, attack)`, `WeaponInstance.base_damage(wielder, attack)`). This applies to authored content as much as to code — the content layer is where it's easiest to do accidentally, because it doesn't feel like architecture. If a second representation is genuinely warranted, **declare it out loud**: name both sides and state which is authoritative (the `objectives` vs painted `zones` guard under *Missions* is the model). The undeclared second source is the hazard; a declared one is a design. Why it's a law and not a sharp edge: these fail *late*, once both answers have callers, and the divergence can go **load-bearing** — #102's stale pick was the only reason secondary AoE resolved correctly, so the obvious cleanup would have broken more than it fixed. Prior instances, all now resolved: `LethalityRules.predict()` (preview and execution were two hand-synced ladders), `MENU_ORDER` vs `ACTION_DATA` order, `KineticMaceWeaponInstance`'s `knockback > 0` (#108 — fixed by adding `builds_readiness`, the missing third state that had made the shortcut tempting; **note the fix was to close the expressive gap, not just delete the duplicate** — a seam that can't say what content needs will grow another one), and the three-way `dead` split the persistence seam now guards with "don't add a fourth". A duplicate also propagates into FIXTURES: #108's `knockback`-means-spender assumption had been copied into four test files, none of which the production fix touched. **And a duplicate is rarely just wrong — it is often wrong in a way nobody measured**: #109's four walkability readers disagreed as filed, but the probe also found the "silent false" in the authoritative one was actually two runtime errors per call, and turned up a *fifth* site (`DevController.resolve_pending`) that didn't ask the question at all. Enumerate by re-deriving from the code, never from the issue's own table.

## Architecture map

- `game.gd` — input/game-state coordinator. **Reorganized 2026-07-26** into labelled sections (Lifecycle / Input / Turn flow / Modes / Queueing orders / The action-queue panel / Squads / Populating the board / Board visuals / Board queries), with three collaborators split out — each built in `_build_collaborators()` and holding a `game` back-ref, the `DevController`/`AIController` pattern: **`OrderExecutor`** (`actions/`, runs a squad's plan + the downed fallout), **`HoverPresenter`** (`board/`, mouse → cursor/overlays/hover card/queue-row highlight, incl. the `_process` hover detection and the two `hovered_*` signals), **`MainActionMenu`** (`ui/`, now the *whole* menu system — construction as well as gating/dispatch). Still the heaviest file; prefer moving domain logic out to the owning system when touching it. **The current selection is STORED, not re-derived (#107): `game.selected_unit`** is set once, in `select_unit` (from `unit_at_pointer` on a board click, or from the newest queued move when right-click re-opens its planning, #417) and read by all four mode click-handlers plus their three `HoverPresenter` twins. It replaced five hand-written `get_unit_at_cell(last_clicked_cell)` lookups that came in two contradictory precedences, one of which crashed on any unit selected via its shove-ghost. `last_clicked_cell` now means **only** "where the cursor sits in TILE_SELECTED" — a move path reconstructs from `unit.movement.cell`, which is what `compute_move_range` keyed `came_from` from. Never re-derive the selection from a cell; the cell and the resolver both drift. **Anything reaching back through the untyped `game` ref must annotate its locals explicitly** — `game.gd` has no `class_name`, so every `game.*` call is Variant and `:=` cannot infer from it; and a bare array literal passed that way is NOT coerced to a typed parameter (it fails at *runtime* — this is why `clear_selection_icons()` exists instead of callers passing the literal).
- `SquadManager` — **the only owner of squad lifecycle**: create/destroy/join/leave. Member removal funnels through `Squad._erase_member()` (the sole `members.erase` caller, mirroring `_add_member`); its callers are `_detach_from_current_squad()` (single-unit) and `disband_squad()` (bulk). Also home of order queueing (the Law #3 `queue_action` chokepoint), activation state, plan resolution, and counter-attack resolution. **Slimmed 770 → 516 lines 2026-07-26**: it had become the second dumping ground after game.gd — two of its sections were literally labelled *"migrated from game.gd (#22)"* — so three tenants moved out to **`SquadPlanValidator`** (plan-context validity, stamped onto each action), **`GroupMoveSolver`** (the pure formation solver; `queue_group_move` is the committing half), and **`ActionQueueDisplayEntry.build_for()`** (queue-panel layout, now beside the view model). All three are fully static — they read a plan and return a result, touching no squad state. **Queueing is STRICT and validity is one-way (2026-07-31): you cannot AUTHOR an invalid order, but a queued one can BECOME invalid.** `queue_action`'s third gate runs `validate_squad_plan_preview` and reads **the candidate's own `is_valid`, never `validate`'s return value** (that is whole-plan validity — one already-broken row would refuse everything queued after it). A break caused by a LATER re-plan leaves the order queued **in red, not deleted** — and for an *attack* that is the whole answer: a move is never refused for breaking a queued aim (dev fork, 2026-08-02, fork ii), the aim falls into invalid instead, because a planned heal does not lock its ally in place. The gate has a **second half** since then, `_candidate_aim_connects` — the whiff question, which only a candidate may ever be asked (see `SquadPlanValidator` below) — **and a third since #124 (2026-08-09), `_candidate_rescue_target_ok`**: a candidate rescue may target a unit that is down OR one the squad's last resolve predicts will be down by the side channel. That resolve is stored (`_last_resolved_plan`, read via `resolved_plan_for(squad)`; `ResolvedPlan.hypo` now survives the pass for exactly this) and is the right witness for a candidate the same way published knockback is — it covers the already-queued prefix, kept fresh by the synchronous queue→repaint→resolve chain, so a headless caller queueing twice with no resolve between hits the same known coupling aims do. The lifecycle rule itself is ONE seam, `RulesService.is_rescueable(target, plan)` — menu candidate list, this gate clause, and the validator's plan-armed `_revalidate_rescue_targets` (outside the fixed-point loop beside the attack whiff clause; adjacency stays inside) all call it; plan-less callers (the AI builder) keep the live `is_downed` rule. (An interim clause excluding Crisis-eligible player allies lived here for the hours the live prompt outlasted #124; #158 deleted both — a Crisis-armed ally now predicts CRISIS and falls out of candidacy through the ordinary DOWNED filter.) A same-pass revive is still ejected and SPENT — `OrderExecutor._process_downed_pending` marks the fresh solo squad, because at `RescueAction.execute` time the solo squad doesn't exist yet — and execute's `is_downed()` guard firing is now a `push_error` (post-#155, a wrong lethality prediction is a bug, never a fizzle). This collapsed three hand-synced answers to "may this be ordered" (menu gate, click handlers, AI builders); `_click_choosing_move`'s private leader-range copy went with it. The hypothetical list displaces via **`Squad.displaces()`**, the same predicate `_queue_action` uses. **Batched orders skip the gate** — a formation is one decision, judged whole by `queue_group_move`. Refusals are silent (dev call). Rationale, forks and the three traps (leaf ordering, rollback scope, the knockback/resolve dependency): [`docs/build-log.md`](docs/build-log.md). **Order batching (`SquadManager.batching`, 2026-07-26):** Group Move queues N orders as ONE player action, so the expensive squad-level repaint runs once at the end rather than per order (a 5-member click went 232 ms → 65 ms). Every order still passes `queue_action`'s gates (Law #3), and `action_queued` still fires per order so cheap per-UNIT listeners don't miss anyone. **It is safe only while a batch stays synchronous** — if one ever spans a frame, the queue panel goes stale and Law #2 breaks. Invariants + measurements: [`docs/performance.md`](docs/performance.md).
- `Squad` — member list + `action_queue` (player-authored orders only). Enforces one order per action-type per unit (volley siblings exempt — see `_is_volley_sibling`).
- **Persistence seam (locked, #8):** transient `Unit` node holds battle-scoped state that resets each mission (element states, projected position, lifecycle ACTIVE/DOWNED/DEAD); persistent `UnitInstance` resource holds identity that survives missions (HP, fixed stats, limb loss, proficiency, **Will**, and `permadead`). **`permadead` (added 2026-07-27) is declared but deliberately UNWIRED** — nothing sets or reads it until there are missions and a persistent roster, at which point `Unit.die()` is the setter and roster assembly the reader. It is the *third* distinct "dead" on this seam and the only non-battle-scoped one: `UnitInstance.is_dead()` is `current_hp <= 0`, `Unit.is_dead()` is "went down the permanent path this mission", `permadead` is "never fields again". Don't add a fourth, and don't rename any of them to plain `dead`. New per-unit state picks its side by one test — *does it survive a mission?* No third store. **The seam now has NO exceptions** — the one that used to be documented here, `UnitInstance.stat_modifiers`, was **deleted by #112 (2026-07-28)**. It was a battle-scoped add/subtract bag (the Crisis surge) parked on the persistent instance purely because it was a stage of `get_effective_stat`'s chain, and it had already gone permanent once by having its reset missed. Temporary stats are now `StatEffect`s on the transient `Unit`, which is where the seam's own test ("does it survive a mission?") always said they belonged. **The effective-stat chain is base → limb → jobs → temporary effects → gear**, and only its first three stages live on `UnitInstance`: `Unit.get_body_stat()` adds effects, `Unit.get_effective_stat()` adds gear. **Because the chain's top stages live on `Unit`, every DERIVATION off a stat must live on `Unit` too, or take the finished value as a parameter** (#106: `UnitInstance.get_max_hp(effective_con)` and `get_mov(effective_dex)` are passed it; `get_effective_ldr`/`get_effective_def` sit on `Unit`; `Unit.set_current_hp(value)` is the one door for writing HP, since the clamp needs a ceiling `UnitInstance` can't derive). **Everything that follows a stat change runs in `Unit._settle_stat_change`** — enforce wear gates (stripping gear you no longer qualify for) → re-clamp HP → emit `stats_changed` — in that order, because stripping armour moves CON which moves max HP. Wear gates read `get_body_stat`, i.e. **never gear** — and the gate step's second clause since #157 (2026-08-10), the equipped rune's channel gate (`EquippableData.can_equip`, aura+affinity), also never reads gear — which is what keeps the strip to a single pass with no cascade. **The gear stage grew a SECOND source in [#74](https://github.com/Phaazoid/Godoiosis/issues/74) (2026-08-23)** — a fitted `WeaponModData`'s `stat_modifiers`, summed over `Unit._mod_sources()` alongside `worn_armor` — so the "no gate reads gear" property is now what keeps *two* clauses non-cascading rather than one, and is pinned rather than merely written down (`tests/weapons/test_weapon_mod_grants.gd`). `stats_changed` is for READOUTS only; "may this be queued?" is a question about the *projected* stat and belongs to `SquadPlanValidator` ([#113](https://github.com/Phaazoid/Godoiosis/issues/113)). Doctrine + the save/load bug #106 caused: [`docs/design/stats.md`](docs/design/stats.md) → *One chain, one layer* and *Temporary stats*. Pinned by `tests/stats/test_stat_effects.gd` + `test_derived_stat_chain.gd`. (Cross-mission save/load is the future campaign layer; boundary is locked now so features land on the right side. See `docs/design/resolution-pipeline.md` → "The persistence seam".) **Scenario save/load round-trips the whole `UnitInstance` side since #83 (2026-07-22):** `ScenarioUnitEntry.capture_unit_state`/`apply_unit_state` own the unit-state snapshot (stats, current HP/Will, full inventory via `copy_equippable` + `equipped_index` — the old standalone `equipped_weapon` copy is retired — `worn_armor_index` (#89 — armor is carried in the SAME inventory as weapons but fills a DIFFERENT slot, so it saves as an index exactly like `equipped_index`, never as a second copy beside the carried one; **load assigns directly and never re-runs the wear gate** — a save is authoritative, and re-gating would strip armor off a unit whose stats drifted after saving), limb states with prosthetic re-link-**by carried instance**, not by template — two prosthetics built on one shared family template are different items and matching by template links both slots to whichever copy is found first (the TorvArm/TorvLeg bug, latent since #83 and unreachable until `install_prosthetic` got its first production caller) — proficiency, aura, **affinity** (`affinity_saved` is a DECLARED sentinel: an empty affinity is a legal saved value, the Rebecca rule, so emptiness cannot double as "unsaved" the way every other default in that block does; without it, aura was restored while affinity was not, leaving a loaded alchemist with a full pool, an empty affinity, and every carving silently unfireable), jobs), applied AFTER `initialize()`'s reset on load; `ScenarioManager` and the Play API's `board_builder` both call the same pair. **The entry has TWO declared kinds since [#177](https://github.com/Phaazoid/Godoiosis/issues/177) (2026-08-10), forked per unit by `ScenarioUnitEntry.state_saved`** (default `true` = the snapshot every pre-#177 save is; the `affinity_saved` pattern widened to the whole block): an **authored** save (`capture_scenario(name, authored = true)`, the Scenario tab checkbox) writes a **cast** unit — spawned from a standalone character file under `Resources/Units/`, provenance carried by `Unit.unit_data_source`, which `UnitFactory` stamps only for a `::`-free real `resource_path` — as a **reference** (`entry.unit_data` = the file itself, `state_saved = false`, nothing captured, and the loader must NOT call `apply_unit_state`; both loaders gate on it). Every load re-reads the character as authored then — *references for the cast; snapshots return with mission-to-mission carryover* (dev, 2026-08-10). **A DEV EDIT breaks the reference (dev-ratified 2026-08-20):** transient `Unit.dev_edited` (set by the Unit Editor's Save, and by a cast spawn placed on a non-file faction) makes the authored capture snapshot that unit instead — a re-reference would silently discard the edit, which is how inventory/team edits to the verticality fixture could never be saved; sticky across loads, since the snapshot entry respawns without `unit_data_source`. `BugReporter` and every other caller keep the default full snapshot. `UnitData` grew the **starting-kit block** (`starting_jobs`/`starting_inventory`/equip+wear picks/`starting_proficiency`/`starting_prosthetics`), seeded by `Unit._seed_starting_kit()` right after `initialize()` through the gated equip doors (refusals `push_warning` — bad authoring surfaces at spawn); `apply_unit_state` **clears the seeded kit before restoring** so a snapshot stays authoritative instead of doubling inventory. The loader passes `entry.unit_data` to `spawn_unit` UN-duplicated (the factory copies; the old outer `duplicate(true)` severed provenance so a load-then-resave silently embedded). Pinned by `tests/flow/test_cast_references.gd` + `tests/unit/test_starting_kit.gd`, falsified against all three of those bugs.
- **A save is a true MID-BATTLE SNAPSHOT since [#87](https://github.com/Phaazoid/Godoiosis/issues/87) (2026-07-30) — this REVERSES, for the save-resume axis only, the "battle-scoped `Unit` state deliberately stays out" line that used to end the paragraph above.** That line was right for a *mission boundary* and wrong for *pause/resume*: a different axis the seam had never separated. Weapon-state-only was explicitly rejected as a lopsided snapshot (mace charge kept, but downed units standing up and fires going out). Now round-tripping alongside the instance side: per-carried-weapon battle state (spring readiness, carbine magazine, mace charge, chainsword rev — **keyed by inventory index**, because a unit can carry two of a family and they must track independently, the same identity rule the prosthetic re-link learned), `element_states`, `lifecycle_state` + the downed clock, the two Crisis flags (`in_crisis` + `crisis_surge_pending` — `crisis_offered_pending` died with the offer, #158), `rally_count`, live `StatEffect`s **with their remaining countdowns**, `Squad.has_acted` (saved on the leader's `ScenarioUnitEntry`, applied after the squad rebuild), and `MissionController`'s captured zones, `contested` latch and `rounds_elapsed` clock (#101) (on `ScenarioData` — `outcome` is deliberately NOT saved, since it is derived from those plus the board and the next `check()` re-reaches it). **The seam is unweakened, and that is the whole mechanism:** nothing became `@export` where it lives — weapon state is still plain vars on `WeaponInstance` subclasses so `make()`/`copy_equippable()` re-arm every weapon, and lifecycle/states/Crisis/rally are still plain vars on the transient `Unit`. The snapshot captures them EXPLICITLY, exactly the way limb fittings have always been captured rather than serialized, so a mission boundary still resets for free. `WeaponInstance.capture_battle_state()`/`apply_battle_state()` are the family-agnostic seam (base returns `{}`); a **Dictionary** rather than one int even though every family tracks exactly one number today, because #108's lesson is that a seam which can't say what content needs grows a second one. Two structural rules, each pinned by a test falsified against its own bug: **(1) a restore replays the RESULT, never the EVENT** — `Unit.restore_lifecycle`/`restore_stat_effects` exist because `_go_downed()` would emit `went_downed` (ejecting the unit from a squad the loader hasn't rebuilt) and re-spend Will, and `apply_stat_effect()` would reseed a countdown from its `duration`; **(2) effects settle BEFORE gear and BEFORE HP** in `apply_unit_state` — settling enforces the wear gates, so a restored debuff applied after the armour strips gear the save says is worn, and a `+CON` effect moves the max HP the saved `current_hp` was measured against. `ScenarioManager.capture_scenario`/`apply_scenario` were split out of `save_scenario`/`load_scenario` (the shape `play/board_builder.gd` already had) so a whole board round-trips in memory — writing a test `.tres` into `Scenarios/` would be picked up by Mission Select and by #9's folder scan. **The mission-start RESET half stays real for the path that doesn't exist yet** (the roster → board flow — its character-file half landed as #177; the mission-boundary concept still missing is [#70](https://github.com/Phaazoid/Godoiosis/issues/70)'s debt): units arriving off a persistent roster carry no battle state by construction. Still deliberately out: the queued action plan (player intent, re-authorable, and serializing `BaseAction` graphs with live `Unit` refs is its own feature), `active_attack` (an aiming cursor), and projected-knockback cells (re-derived each resolve pass). **The snapshot has PLAYER doors since [#144](https://github.com/Phaazoid/Godoiosis/issues/144) (2026-08-11)**: three `SaveGame` slots under `user://saves/` (never `Scenarios/` — folder scan + #9 + read-only-when-packed), Save/Load on the pause menu, Load Game on the title, `MissionController.resume_from_slot` aiming `last_loaded_path` at the ORIGIN mission so Restart/F2 reload the mission not the slot. The rule it forced: **`reset_faction_actions` fires from the turn HANDOFF (`game._on_turn_started`), never from `start_faction_turn`** — a menu arrival trusts the file, or every resume hands acted squads their actions back. Canon: `docs/design/missions.md` → *Player save slots*.
- **Actions are a small in-code registry, not a framework** (`BaseAction` → `MoveAction`, `AttackAction` (→ `CounterAttackAction`), `RescueAction` (#33), `RallyAction`, `IntimidateAction` (#61), `ReloadAction`/`RevAction`/`BurrowAction` (the weapon-signature verbs, #73/#84), `GuardAction` (#414 — the bodyguard verb; substitution itself is entirely PlanResolver's, this order only arms the ward), `OverwatchAction` (#413 — the standing-watch verb; the trigger and the shot are entirely PlanResolver's, this order only arms the watch), `CaptureAction` (#96 — stamps its cell, zone name and the MissionController at queue time, so the resolver reads a frozen snapshot and a re-planned move can't quietly capture elsewhere); action-registry refactor 2026-07-20/21): the `ActionType` enum plus two declared `const` lists on `BaseAction` ARE the registry. `MAIN_ACTION_TYPES` (ATTACK/RESCUE/RALLY/INTIMIDATE/RELOAD/REV/BURROW/CAPTURE/**GUARD**/**OVERWATCH**) drives `is_main_action()` — mutually exclusive, one per unit per turn, must come *after* any move (locking one removes the move option). `SIDE_CHANNEL_ORDER` (RESCUE/RALLY/INTIMIDATE/RELOAD/REV/BURROW/CAPTURE/**OVERWATCH**/**GUARD** — the two standing reactions are LAST on purpose and in that order: a Guard or a watch armed this pass must arm after every hit it was resolved against has played back — stored orders that bypass `PlanResolver`) is iterated by THREE places at once: `OrderExecutor.execute_orders`'s phase loop, `ActionQueueDisplayEntry.build_for`'s queue-panel sections (header = the enum's own key string), and the headless Play API's `_describe_plan`/`execute()` — a new type registered there gets a phase, a queue section, and Play support for free, with no per-type mirror to add. Per-action **queueing requirements** live on the action itself via the `actor_can_perform()` virtual (move-before-main on `MoveAction`, verb locks on `AttackAction`/`RescueAction`, the Will-room check on `RallyAction`, the ability gate on `IntimidateAction`) — `SquadManager.queue_action` calls it once as the sole Law #3 chokepoint instead of a per-type match arm. `game.gd`'s `GameState.PICKING_TARGET` is the one generic "pick one of these highlighted CELLS" flow. **`enter_cell_pick_mode(cells, on_pick, mark, flash)` is the mode and `enter_target_pick_mode(candidates, on_pick)` is a declared SPECIALIZATION over it (#116)** — the click guard was always cell-shaped underneath (`target_pick_cells.has(cell)`), and what makes the unit flavour a flavour is the two lines in the wrapper: map the clicked cell back through `unit_at_pointer`, and refuse when nothing is there. Keeping that refusal in the wrapper is what lets a CELL pick accept an EMPTY cell, which a rescue haul's bank is by definition. Rescue, intimidate, squad-up and join-squad ride the unit form (candidates from a predicate query, `on_pick` closes over the acting unit); the rescue TILE pick is the cell form's first caller and the only one that passes `flash`. **A pick may CHAIN another (rescue: body, then the tile to haul it onto), and `_pick_generation` is what makes that survivable** — `_click_picking_target` used to call `exit_current_mode()` unconditionally after its callback, which would tear down a chained pick the instant it opened, with both halves correct in isolation (#103's shape). A `game_state` compare cannot see it: a chained pick leaves the state identical. **Both halves of it read PROJECTED cells (#126 follow-up, 2026-08-08)**: `_unit_cells` marks the overlay with `get_projected_destination()`, and `_click_picking_target` resolves with `unit_at_pointer`, not the raw live `get_unit_at_cell` — it was the last click handler that never got the #107 treatment. Until then a rescue aimed at a shoved body's landing cell **hit nothing at all**: the overlay marked the cell the body was leaving, so the click failed `target_pick_cells.has(cell)` and fell through to `exit_current_mode()` silently, while clicking the vacated cell reached `queue_rescue` and was refused by the (correctly projected) validator, also silently. The two no-plan callers are unaffected either way — `can_squad_up`/`can_join_squad` require an empty queue on both sides, so projected == live for them. **The generalizable half: fixing "where is this unit?" at the rule layer is not finished until the PICK layer agrees** — #126 fixed the candidate query and the validator, both suites went green, and the feature did not work, because no test fired a menu pick. `tests/ui/test_target_pick_projection.gd` drives populate → press → click → assert-on-the-queue for exactly that reason; it deliberately does NOT extend to `CHOOSING_MOVE`/`CHOOSING_GROUP_MOVE` (live path-preview IS the feature) or `ATTACK_TARGETING` (directional aiming, not a unit pick) — those stay bespoke on purpose. **Menu system lives in `MainActionMenu` (`Classes/ui/MainActionMenu.gd`), pulled out of `game.gd` 2026-07-22 and completed 2026-07-26** — it holds a `game` back-ref (same pattern as `DevController`/`AIController`: instantiated and `.game = self`'d in `game._ready()`) for everything it reads or dispatches into. It now owns menu **construction** too, so `game.gd` holds no menu knowledge at all: `show_main_menu` is the one door and `build_tree(unit)` is what it hands the widget -- **the WHOLE ring tree, built once at open (#467)**, because a hovered category is ghosted before it is opened and a preview that re-queried could disagree with what commits. **Rows are built by one builder as of #166 (2026-08-10), `_entry(name, blocked_reason, detail)` — a menu can only grey what it can explain, so the REASON a row is dead belongs to the data layer, never here**: `EquippableData.attack_block_reason(wielder, attack)` is answered per kind (a weapon reports readiness in its family's own `status_text()` words, a rune reports aura via `TransmutationData.channel_block_reason`), and `Unit.is_attack_fireable` is **derived** from it so a greyed row and a refused order can never disagree. The menu's one hardcoded reason string is gone. Which options are listed-and-greyed rather than hidden is still per-menu POLICY, and only the Transmutation submenu changed: `RuneData.choice_attacks` became the catalogue (every inscription) to match `WeaponInstance.secondary_attacks`, while `selectable_attacks` stays channel-filtered as the "what can actually fire" list the AI and `has_any_fireable_attack` consume — a declared split, commented at the source. The Weapon Action self-verbs stay hidden-when-unavailable because `can_reload()` still conflates "can't reload at all" with "already full". Menu order is still just `ACTION_DATA`'s declaration order — now the CLOCKWISE order **within** a category, which is what preserves a stable sequence in a ring that compacts. `ACTION_DATA` also carries each verb's `group` (Move / the KIT slice / Action / Squad / Inspect) and `expands` (the ids that are only category headers, contributing their children instead of a row of their own); a verb naming a group the ring has no slice for is a row nobody could reach, which `tests/law/test_glossary_coverage.gd` refuses. **A category whose ONE child is its own verb COLLAPSES to a terminal slice** — Move holding nothing but Move — and that same rule is the whole of "Inspect is top level": a group of one, holding the verb of its name. Deliberately not "collapse whenever there is one child", because a lone Squad Up names something the word Squad does not. **Three verbs LEFT the ring in #467 round 2** and their ids went with them: Execute Orders and Cancel Actions (the queue panel's Execute button and its per-row X, plus right-click's LIFO undo) and End Turn (the corner button, which is permanently on screen precisely because that row is gone). The unit's menu is what the UNIT does; the turn is the HUD's business. **The KIT slice is labelled after what is EQUIPPED** -- "Weapon" or "Rune", never "Attack", because it holds Reload and Burrow and carvings, none of which are attacks (#467 round 3); `MainActionMenu.category_display(group, unit)` is the one answer to what a slice is called, and it is public because three suites had spelled the old label themselves and all three reddened when it moved. **There is no generic Attack row either** — the ring lists every attack by ITS OWN NAME, which needed the MAIN attack listing too, since `WeaponInstance.secondary_attacks()` excludes it and deleting the row alone would have left a plain sword unable to attack at all; a rune's default attack IS one of its carvings, hence the name-dedupe when a group is filled. New-action checklist: the class (with its `actor_can_perform()` override) → one line each in `MAIN_ACTION_TYPES`/`SIDE_CHANNEL_ORDER` → **the player surface** → **its AI stance** in `AIArchetype`'s `MAIN_ACTION_PRIORITY`/`MAIN_ACTION_NEVER` (the law test fails until it lands in exactly one, per archetype) → a `SquadPlanValidator` clause only if the action has plan-context (adjacency/occupancy) rules, mirroring `_revalidate_rescues`/`_revalidate_intimidates`/`_revalidate_captures`. **Queueing a no-argument verb goes through `game.queue_simple_action(unit, type)`** (2026-07-28): `queue_rally`/`queue_reload`/`queue_rev`/`queue_burrow` were four byte-identical copies and are now one path with a `_make_simple_action` factory — a `match`, not a class dictionary, because class references aren't const-foldable and a dict lookup loses static typing. Verbs taking a real argument (rescue/intimidate take a unit, capture takes a cell) deliberately stay separate; forcing them through one signature just moves the branching into a parameter bag. **The player surface forks by kind since the 2026-07-24 Weapon Action refactor:** a *general* verb (rescue/rally/…) still takes a top-level `MainActionMenu` slot — menu-id const + `ACTION_DATA` entry + gate clause in `populate()` + dispatch arm in `_dispatch()` (which `on_pressed` wraps, so the #471 camera return cannot be skipped by an arm's early return); a *weapon-specific* one (Rev/Reload/Burrow, Overwatch since #413, and any future family signature) instead adds a branch in `MainActionMenu._weapon_children`, and an inert `can_<verb>()` default on `EquippableData` (overridden on the family's `WeaponInstance` subclass), a thin `can_<verb>_weapon()` delegator on `Unit`, and one `or can_<verb>_weapon()` in `Unit.has_weapon_actions()` — since #467 it lands one ring out, inside the KIT slice (labelled Weapon or Rune), no matter how many signatures exist. Either way the queued `ActionType` is unchanged, so registry/resolver/queue/AI wiring is identical. Trade-off: turn order follows enum-declaration order, which is **append-only** for save-compat, so a new faction acts *last* unless you migrate enum values; and presence *is* eligibility (a `NEUTRAL`/`OTHER` faction with units would take a turn — add an explicit opt-out if you ever want non-acting scenery). `game._on_turn_started(faction)` **auto-skips** a faction with no `is_active` units after ticking its downed clocks — guarded by `_board_has_active_units()` so an all-downed board can't infinite-loop; `start_faction_turn(faction)` replaced the old player/enemy split. Saved turn state = `ScenarioData.active_faction` (authoritative; the `turn_phase` field was removed), restored via `set_active_faction`. - **Missions — the closed loop (`flow/`, #96, all four slices built 2026-07-28; canon [`docs/design/missions.md`](docs/design/missions.md)):** the game can be **won and lost**, and it now BOOTS into `MissionSelectScreen` rather than a board (`TestBoard` retired as the boot path; `game.spawn_sandbox()` is its one remaining call site). Four parts, split on purpose. **`MissionRules`** (static, pure, `extends Object` — LethalityRules' shape) is the whole rule: `evaluate(board, contested, progress) -> ONGOING/VICTORY/DEFEAT`. **`MissionController`** (a game collaborator, the DevController pattern) holds everything a pure predicate cannot — the ended-latch, the `contested` latch, captured-zone state, the objective composer, and what the game DOES about an ending (`GameState.MISSION_OVER`/`MENU` → `_board_locked_for_player`, the banner, the return path). **`ScenarioData.objectives: Array[MissionRules.Objective]`** is what a mission REQUIRES (ROUT/CAPTURE/EXTRACT, composed by AND, edited in the dev Scenario tab); **`ScenarioData.zones`** is WHERE, via `ZoneManager.Kind`. **There is no `MissionData`** — a mission and its board are 1:1, so a wrapper resource is an extra hop, not a template/instance split (dev, reversing the original plan). Objectives are **declared explicitly, not inferred from painted zones**: rout has no geometry to paint, a mis-picked Zone Kind would otherwise silently rewrite the win condition, and geometry couldn't be authored ahead of its rule. Guard for the resulting second source of truth: a declared objective with no painted zone reads **PENDING, not NONE** (the map really is unwinnable — silently dropping it would convert a broken map into a different playable one), warned live in the Scenario tab and `push_error`'d by `set_objectives`. Doctrine, all load-bearing: **(1) an authored objective is the ONLY way to win** — routing a capture map wins nothing unless ROUT is ticked (lockout is a level-design problem, not a rule that hands out a consolation win); **(2) DEFEAT is checked first** — last player unit and last hostile falling in the same pass is a LOSS; **(3) `contested`** — "both sides were up at once", latched by the CALLER because the board can't tell *wiped out* from *never here* (`present_factions` drops an all-dead faction) and a LIVE read could never end a mission, which is what keeps **dev sandbox boards inert with no `dev_mode` flag**; **(4) extraction counts the DOWNED** — alive and inside the zone means they got out; what blocks it is a living unit OUTSIDE, and a downed one there needs a rescue; zero surviving players reads PENDING, not vacuous-MET (2026-08-12 — the missing twin of capture's zero-geometry guard; it ticked Extract on the HUD during load, and `apply_scenario` now re-pushes the HUD after the board is fully built). `check()` fires at the three points board state changes and settles — end of a resolution pass (`OrderExecutor.execute_orders`, *before* its squad-validity guard so a squad that wiped itself can't skip it), after the end-of-turn burn, and turn start *after* the downed clocks tick. Pass-end not turn-end: a friendly AoE can down your own last unit mid-pass. `AIController.take_faction_turn` guards on `is_over()`. **`MissionController.reset()` (from `ScenarioManager.clear_board`) is the first thing in the codebase to ever fire a mission-start event** — the [#87](https://github.com/Phaazoid/Godoiosis/issues/87) seam whose rule had never actually executed; keep the split when #87 lands (**loading a mid-battle save RESTORES, starting a mission RESETS**). One seam, two forms that cannot drift (`in_range` decides, `cells`/`field` draw — a bounded `path_hops` from the leader's cell): the validator, the solver, the squad-up gates, `compute_move_range`'s clamp, the three overlay draws and the ejection sweep all route through it, which is what made the metric swap a one-function edit — eleven sites used to hand-roll the Manhattan compare. Per-member (a Waterwalker's bubble crosses water; flyers later), occupancy-blind always (an enemy body never severs a squad — the pin test calls `path_hops`' default form). **The board it walks arrives via `SquadManager.board_source`, a Callable returning a FRESH `BoardContext` per query** — terrain state changes mid-battle (FROZEN melts), so caching a board would validate against a world that no longer exists; game/play/test fixtures each wire their own source once at bootstrap, and `SquadPlanValidator.validate` takes the board as an explicit parameter. **`SquadManager.enforce_contact()` is #151's backstop**: movement can no longer author a split (the validator refuses it), but a shove or melting ice still can — an out-of-contact member ejects to a solo squad at the two settle points (end of `execute_orders`, turn start after ticks), mirroring downed ejection, equally un-previewed; also the self-heal path for pre-#151 saves. COH default went 3 → 4 with the swap (path ≥ Manhattan, so the old number was a strictly tighter leash). **It was briefly relaxed to let an outrun member trail, and put back the same day**: the relaxation reached every squadmate move, not just group-move placements, and a member could then be individually ordered *and executed* far outside its leader's range (12 of 40 tiles the red INVALIDMOVE overlay was painting had started accepting orders). **The generalizable lesson — a rule read by more than one surface must be justified at every surface, not at the one that motivated the change.** Group Move now splits into two visible cases: **Case 1**, the member falls behind but stays in range — legal, and `GroupMoveSolver` sets `MoveAction.is_trailing` (it ends *further* from the leader than it started) so `OverlayManager._arrow_modulate` draws its arrow GREEN; **Case 2**, the member cannot reach the range at all — refused, and `GroupMoveSolver.followable_destinations` marks those destinations so `enter_group_move_mode` paints them the same red a squadmate's own out-of-range tiles get, clicking one doing nothing exactly as there. That sweep is one `compute_move_range` per member plus a dilation, NOT a `plan()` per destination — the real solver is 4–6 ms a cell, i.e. 176 ms to filter a 44-cell range, and the sweep costs the SAME for 1 destination as for 38 (it is per-squad work). **Placement is most-constrained-first, and that is load-bearing, not a tidy-up**: assignment is first-come-first-served with no backtracking, so a member with two options must pick before one with twelve — member order silently dropped **6 of 16** green destinations for one Castle Assault squad, i.e. a third of that squad's range clicked and did nothing, on a 952/952 green suite. `_candidate_cells` therefore has no `taken` filter (options for every member are computed before any placement, because knowing who is constrained requires it), and moves are **emitted in member order** so queue rows don't reshuffle. `followable_destinations` also requires *distinct reachable cells ≥ member count* — the genuinely impossible case (a one-wide corridor collapsing the squad onto one tile), which no ordering can fix; it is necessary rather than sufficient and wrongly refused nothing on either authored board. Three consequences to know: `RulesService.compute_move_range` filters occupancy BEFORE cohesion, because `reachable + squad_unreachable` became the standable footprint that sweep unions; the leash-as-PREFERENCE retry `_candidate_cells` used to carry (drop the leash when it leaves nothing) is **deleted as of #151** — with cohesion itself path-based, the solver's `leader_field` IS `SquadCohesion.field`, the same field the validator refuses against, so the two can no longer disagree and a member with no candidate genuinely cannot follow; and `queue_group_move`'s rollback calls `revert_if_only_hold`, since a refused batch that leaves a hold-only queue used to strand the squad `active` behind a panel with no X and no Execute — the reported symptom, *"a ghost order that did nothing"*. Residual: the sweep cannot see two members contending for one bubble cell (`taken`), so a green tile can still be refused, rarely, and now reverts cleanly. Story + the measured 40-of-44 reproduction: [`docs/build-log.md`](docs/build-log.md) → *Group Move's two cases*. ## Sharp edges (each of these has already bitten once)

- **Missions talk now (#182) — a test fixture that boots one through `begin_mission` must hang up.** Dialogic's layout lands on the TREE ROOT, outside every suite fixture: it eats synthesized clicks (the #370 CI red — "the press never armed the drag"), survives `_scene.free()`, and bleeds into later suites through the persistent autoload. `DialogFixtures.end_all_dialog(self)` (`tests/support/`) is the one teardown dance (end, await `timeline_ended`, two frames); a suite that synthesizes clicks also calls `scenario_director.disarm()` in `before_test`.

- **Grant/copy an equippable via `copy_equippable()`, never a bare `duplicate(true)`** (revised #59 — this used to say the opposite). `RuneData` still wants a full deep copy (its base implementation), but `WeaponInstance` overrides it to keep `template` a SHARED reference while each of its own `spaces` copies shallowly — a generic `duplicate(true)` would deep-copy the template too and silently fork a weapon off its family.
- **NEVER run the full test suite locally. CI owns it (dev rule, 2026-08-15).** `.github/workflows/tests.yml` runs the whole tree on every push and every PR against `main`, carrying the *same* two guards as `run_tests.ps1` (#93's verdict parsing and #146's zero-cases check) — measured at **127s on GitHub's machine, in parallel, costing the dev nothing**, against ~230s of his laptop that he sits through. The full tree's job has always been *"don't merge a regression"*, and CI is already that gate; a local full run duplicates it exactly and buys nothing. **Locally: area folders only** (`run_tests.ps1 rules`, `presentation`, …), and a bare `run_tests.ps1` now defaults to the `fast` tier rather than the whole tree so the expensive thing takes deliberate typing. If something cross-cutting needs checking before pushing, run the narrowest area that loads the surface you touched — a change that breaks `game.gd` parsing shows up in `ai`/`flow`/`ui`, not in `rules`. **This rule is unconditional on purpose.** It replaces a conditional one ("one full run, after his feel-check") that got misapplied three times, twice on #254 and once on #257 — and the #257 miss happened because the rule was *paraphrased into an approved plan* with the timing inverted, which gave the paraphrase more authority than the rule. Cite this line; do not restate it.
- **NEVER pin AUTHORED CONTENT in a test (dev rule, 2026-08-15; full rule + the seams to use = `tests/README.md` #9, *the content razor*).** A test may **load** a real mission to exercise a real path; it may not **assert** anything about what that mission contains — not a cell coordinate, an elevation, a cell *count*, a footprint size, or a roster size. Sibling of #8's tuning razor, for the other thing the dev edits without touching code: *"authored content shouldn't be pinned, and level geometry, not to mention contents, units, objectives, all of it is authored."* **`b057f6e` "quick level update" painted eight tiles onto `Level_1` and reddened a case about the board-swap funnel** — a content commit breaking a test about input wiring. Measured while fixing it (PR #290): three raised cells added to Prolog took `tests/presentation` from **165 executed / 1 failure to 116 / 7**, four suites reddening at their first content-dependent case — and since a failure aborts the rest of its own suite, three painted tiles cost **49 test cases**. Derive every expectation from the seam under test (`BoardPicker.column_tops_from` = the footprint, `BoardSpace.surface_point` = where a sprite sits, **`BoardSpace.surface_transform` = how flat markup LIES on a cell, tilt included (#281)**, `board_heights.elevation_at` = an overlay's level, `game.get_move_range` = where a unit may be ordered), and make a content precondition a non-vacuity **message**, never a threshold. `tests/presentation/` is the DECLARED exception to `tests/README.md` #4's "never load a `.tres`": it loads real missions on purpose, because the wire bugs it hunts (#103, #222) only appear on the real load path. Two hazards that exist only on a non-flat board, both found by falsification rather than reasoning: a taller column **shadows** the cell behind it so a click lands on the blocker (ask the real picker, not a UI-overlap check), and a unit on a terrace with no ramp off it **genuinely cannot move** (find one that can, don't assume the first).
- **gdUnit4's `Total execution time` line is not wall clock** — it read `1min 55s` for a 573-case run right after a cache clear, then `12s` for the identical run warm. It is not a usable number in either direction; trust `run_tests.ps1`'s own stopwatched `Elapsed` line instead. **Measured on `Elapsed`: full run 153–157s** (eleven consecutive runs 2026-07-26, 605 cases; independently 158s at 610 cases on 2026-07-27), **`fast` 42s** (156 cases), **51s for three areas together** (2026-07-27). The same suite passes **Linux CI in a 34s total job** while the case count only grew 573 → 610, so it is a Windows/environment factor, not suite size — **cause unconfirmed** (antivirus scanning the repo tree and `.godot` cache state are the untested suspects). The old "~20s full / ~7s fast / ~3-5s per area" figures came from trusting gdUnit4's warm number; all corrected 2026-07-27. Practical consequence: **no tier is a fast inner loop right now** — pick the narrowest area you can. That is a data point for the `.godot`-cache suspect, **not** a correction: **this entry stands as written**, because the slow behaviour has recurred repeatedly and the fast state has not been shown to last. A colour row is `DevWidgets.add_color` — a live swatch plus four **0-255** slider/SpinBox pairs (one scale for both controls, or typing a number and dragging the handle disagree), and editing one channel replaces only that component so the untouched three keep their authored float precision instead of being re-derived through 8-bit and reading as changed. Pinned by a law in `tests/dev/test_moods_tool.gd` that walks the built panel for ColorPicker descendants.
- **AN INSTANCE OVERRIDE IN A PARENT SCENE SHADOWS THE VALUE EVERYONE EDITS, silently and forever ([#403](https://github.com/Phaazoid/Godoiosis/issues/403), 2026-08-21).** `Scenes/Main.tscn` instances `DevOverlay.tscn` and carried `size = Vector2i(900, 720)` on that instance, so [#382](https://github.com/Phaazoid/Godoiosis/issues/382)'s widening of the declared size (900x360 → 1160x520), made in the very commit that added the tool tree, **never reached a running build** — the dev-tools window stayed 900 wide while the file said otherwise, which is why the dev's own suggested fix ("open a little wider") had already been applied and changed nothing. Nothing is wrong at either end: the declaration is right, an override is a legal edit, and the only symptom is that editing the declaration does nothing. **The general shape is Law #4 in a `.tscn`: an instance override is a second answer that WINS, and it is invisible from the file it overrides** — so a value with a scene default is worth asking *which* file the running game reads. The cheap general form of the guard is `tests/dev/test_dev_window_fit.gd`'s seam law, which instantiates the overlay by BOTH paths and requires them to agree. Its sibling law measures each page's widest ROW against the width the window leaves it, and deliberately **not** the page's ScrollContainer — the knob panels scroll horizontally since #403, so that container's minimum is near zero by design and an assertion pointed there could never fire. Two measured facts from the same ticket, each the opposite of the obvious guess: an `HSplitContainer` does **not** squeeze its first child to fit its second (the tree was never displaced; the overflow goes off the RIGHT edge), and **`clampi(v, lo, hi)` answers with the bound it tests LAST** — so with `hi < lo`, `show_beside`'s position clamp returned a NEGATIVE x and parked a too-wide window off the left of the screen, taking the tree with it. `DevOverlay.clamp_to_screen` is static and pure so a screen this machine does not have can still be asked about.
- **A KEYBINDING LIVES IN ONE OS WINDOW AND IS DEAD IN THE OTHER — the project has two (dev rule, 2026-08-16, after this bit for the fifth time).** `embed_subwindows` is off, so the game and `DevOverlay` are two real OS windows, and a key event reaches only the **focused** one. Every dev key was handled in `DevController._input`, which lives in the game subtree — so F1/F2/F3 **and** Z/C did nothing whenever the dev-tools window had focus, which is exactly where authoring leaves you: pick a tile from the palette, press Z to turn the ramp rise, and nothing happens until you click the game window back. The dev found it in play, again: *"this is maybe the 5th time this issue has bit us."* **The fix is a FORWARD, never a second handler** — `DevController.handle_dev_key(event)` is the one public entry and `DevOverlay._input` calls it, so two windows are two input SOURCES for one set of bindings; it is idempotent by construction because only one window has focus, so exactly one caller fires per event. **Cost of forwarding, and it is not optional:** a focused `LineEdit`/`TextEdit` in the dev window has to be excluded first, or typing a scenario name toggles the overlay and resets the board (a `SpinBox` edits through a `LineEdit`, so that covers the level and map-size fields too). The generalizable shape: **"which window is this handler in?" is a question every binding in a multi-window project must answer, and nothing in the code says it out loud** — a handler compiles, runs, and is simply never reached. Pinned by `test_the_rise_keys_work_from_the_dev_tools_window_too` (drives `DevOverlay._input`, so the forward is asserted rather than assumed) plus its typing-guard twin. **Its sibling rule: a dev PAGE owns its own input (dev, 2026-08-23).** `DevOverlay.showing(page)` is the one answer to which page is up -- a FUNCTION, because Spawn and Character Editor share the Unit Authoring container, so either shows only when that container is the current top-level tab AND the current authoring one. `DevController.brush_armed()` / `spawn_armed()` combine it with the game state, and BOTH halves are load-bearing: Spawn is the overlay's BOOT page, so the page test alone made SPACE spawn during ordinary play. Both SPACE handlers (game.gd's and battle3d's) plus the 3D help line read the one predicate -- a readout that names a key must ask the same question the gate does, and it must join the help line's DIFF KEY too or the label goes stale (#308's shape).
- **A tooltip on a code-built row must be set on EVERY control in it, not the row** (#212, 2026-08-15). A slider and a SpinBox have `mouse_filter` STOP, so Godot asks *them* for the tooltip and never walks up to the row's label — set it on the row alone and hovering the handle you are dragging shows nothing, which is exactly when the text is wanted. `DevWidgets.apply_tooltip` walks and sets all of them. Related: a tooltip is a plain `Label` with no autowrap, so long text runs off the screen — `DevWidgets.wrap_tooltip` wraps in code rather than by hand-typed newlines, so the width cannot drift the next time the wording is edited. And the tooltip PANEL is opaque by project theme (#384): the engine default draws it at half-alpha black, unreadable over other text, so `Resources/UiTheme.tres` (wired as `gui/theme/custom`) overrides exactly `TooltipPanel/panel` -- that resource is the ONE seam for game-wide control chrome, so a future global style override is a line in it, not a per-control hunt. **The REFLECTIVE editor had no tooltips at all until [#473](https://github.com/Phaazoid/Godoiosis/issues/473) (2026-08-22)** — `apply_tooltip`/`wrap_tooltip` existed and `build_resource_editor` simply never called them, so every field in the Attack and Item editors drew bare and `Max Range`/`Min Range` were two adjacent lookalike spinboxes with nothing to tell them apart (the dev typed into the wrong one and silently emptied the Carbine's reach). Text lives in an overridable **static `property_tips()`** beside the `@export` it describes, each class merging its parent's. **A function rather than a const table, and not by preference: GDScript refuses to let a subclass declare a member its parent already has**, so a `const PROPERTY_TIPS` on `AttackData` makes one on `WeaponAttackData` a *parse error* — a data table meant to be extended down an inheritance chain cannot be a const. The object row is tipped BEFORE its nested block is built, since `apply_tooltip` recurses and the other order paints the parent's text over every field inside.
- UI rule: **scene for static, code for dynamic.** Fixed controls live in `.tscn`; data-shaped UI (editor fields, stat rows) is generated.

- `Unit.has_squad()` means "has squad*mates*" (members > 1). Every unit always belongs to exactly one managed squad, even solo.
- **A `Packed*Array` IS A VALUE TYPE, AND THE ASSERTION YOU WOULD CATCH IT WITH CANNOT SEE IT (2026-08-28, #629 — bit twice in one session).** `Array` and `Dictionary` are reference types; `PackedStringArray`/`PackedInt32Array` are **values**. So `(store["errors"] as PackedStringArray).append(x)` appends to a **copy** and the store never changes — silently, with no error and no warning. It cost a generator that read every duration correctly and reported none of them, and then, after the same trap was fixed once, an error channel that recorded nothing. **The second half is what makes it dangerous: `assert_array()` on a Packed*Array reached through a Dictionary reports it EMPTY whatever it holds**, so `is_empty()` on one passes *vacuously and can never fail* — which is exactly the assertion anyone writes to check the channel. That is how a case that deliberately corrupts input went GREEN against code that was correctly refusing it. **Use `Array[String]` for anything a Dictionary hands out for appending** (the reference semantics are the point, not the typing), and **assert on `.size()` of a TYPED local**, never `assert_array()` on the Variant chain. Indexing that chain (`store["errors"][0]`) fails at runtime too, for the same reason `game.*` reads need explicit locals.
- **`Sprite3D.offset`'s TWO AXES DO NOT SHARE A SIGN, `flip_h` MOVES NO GEOMETRY, AND THE PROBE YOU WOULD CHECK THAT WITH ANSWERS ZERO (2026-08-28, #634).** The origin sits at column `w/2 - offset.x` from the texture's left but row `h/2 + offset.y` from its top — guess one sign from the other and the art lands mirrored about its own pivot. `flip_h` leaves the QUAD exactly where it is and mirrors only the UVs, so any horizontal offset correction must invert with it by hand; an engine that mirrored the quad instead would make that line double-negate. **And the trap that nearly hid both: `get_aabb()` on a Sprite3D returns `(0,0,0)` until the node is IN THE TREE** — headless included, which is where you would probe it. A first pass compared flip on to flip off, got zero from each, and reported "unchanged" as if that were the answer. **A probe that returns the same value for both branches of a fork has answered neither** — print the raw numbers and check they are not all zero before reading a verdict off them.
- **THE MIDPOINT OF TWO ADJACENT CELL CENTRES SITS EXACTLY ON THEIR SHARED BOUNDARY, AND `floori` RESOLVES A BOUNDARY TO THE `+` SIDE — so a symmetric-looking operation is DIRECTION-DEPENDENT (2026-08-29, #602 round 2).** `map_to_local(a).lerp(map_to_local(b), 0.5)` for adjacent `a`,`b` is not "between two cells", it is *on the line*, and `floori(v / TILE_SIZE)` then names cell `b` for a step north/east and cell `a` for one south/west. `MovementComponent` parked a falling body there and `UnitMirror` asked which cell it was over: the sprite popped back to the LAUNCH surface for a shove north or west and behaved correctly for one south or east — wrong half the time, invisible the other half, and it survived a suite that only ever shoved one way. **Never resolve a cell from a point you deliberately placed on a cell edge**; either finish the step into the destination (what #602 did) or carry the cell you already know — `MovementComponent.cell` is assigned to the destination before the legs run. The general form: a *tie* in a floor/round is a decision, and an operation that lands on ties by construction has made it for you.
- **A VERSION-GATED POLL MEANS A CONTINUOUS ANIMATION MUST ANNOUNCE ITSELF ON DISCRETE EVENTS, NEVER PER FRAME (2026-08-28, #521 slice B).** `OverlayMirror` rebuilds every standing prop, flame and marker whenever `BoardSpace.staging_version` moves — that gate is what makes a tear-out re-seat what stands on it (#308's shape). So an animation that moves those cells CONTINUOUSLY cannot bump the version to be drawn: it would rebuild the whole board every frame. The answer is to find the discrete events inside the motion — a tile LANDING, not a tile moving — and bump only there, letting the thing fly undressed in between. **Generalizable: when a new animation crosses a diff-keyed store, the question is not "how do I invalidate" but "what are the discrete moments inside this motion".**
- **A CHANNEL POLLED BELOW A GATE NEEDS A DOOR ON EVERY PATH THAT ENDS THE GATE — AND THE OBVIOUS DOOR CAN EARLY-RETURN (2026-08-29, #602).** The cliff follow publishes its depth inside `battle3d._mirror_camera`'s playback-locked block, and closes it on `CameraRig3D.restore_view` — correct for an ordinary pass. A BOARD SWAP releases the same lock and never reaches it: `frame()` calls `drop_stashed_view()` first, so `restore_view` early-returns on `_view_borrowed`, and with nothing left polling, the rig sat under the *new* board for ever. Two doors for two meanings — a release CLIMBS out (the player was watching), a swap CUTS (the pit does not exist any more). **Enumerate the paths that clear the gate, not the ones that clear the channel**; and note the guard door was not silent-broken but *conditional*, which no grep for the reset call would have shown. Found by `SharedBoard`'s leak fingerprint, which reds when the reset door cannot reach something — a diff it cannot undo IS a channel with no door.
- **A LATCH MAKES EVERY CHOICE BEHIND IT UNOBSERVABLE — so a case claiming to pin one of those choices is vacuous, and only a mutant will say so (2026-08-29, #602 round 3; TWO survived in a row).** The tear-out solves the diorama's camera height ONCE and holds it. Two design decisions sit behind that latch — reading the ground under each unit rather than their stand height, and the latch itself — and the comment claimed each was what kept a fall from being counted twice. Deleting the latch: **green**, because the height is read off the ground and a falling body's ground does not move. Swapping the ground read for a stand-height read: **also green**, because the latch settles the height before anything is falling, so at the only moment either is evaluated the two agree exactly. **The generalizable form: ask what STATE EXISTS at the instant the latched value is computed — anything that only differs later is invisible to every test, however carefully the case is written.** Both survivors were fixed the same way: name the property the latch really has (a body THROWN onto lower ground must not walk the shot down after it), test that, and say in the comment that the other choice is kept for what it MEANS rather than for a behaviour it protects. **Do not delete an unobservable-but-correct choice to make the mutants tidy** — declare it.
- **ONE SPELLING CAN STILL BE TWO BASES (2026-08-29, #602 round 4).** Round 2 anchored the void death's brick burst by re-deriving the camera's stop from the body's own fall through the SAME function the shot read (`Pacing.followed_fall`) — one spelling, per #472's law, so it could not drift. It was wrong anyway: the shot hangs off the STAGE's height and the body off the VOID's lip, so a shared formula fed from two different bases put the cubes five units under the frame on any fight staged above a pit, while agreeing with itself perfectly — and being base-relative, NO slider setting could close it, which is what the dev's fruitless tuning session was. Sharing the arithmetic is necessary, not sufficient: **check what each reader measures FROM, and when the bases can differ, pass the composed FACT (a callable answering "where is the frame's bottom") rather than the recipe.** Its two companions from the same round: a knob whose store is re-pushed per frame is only tunable at the store (`HealthBlockDebris.lifetime` is overwritten from `block_lifetime` every frame — the born-dead-slider guard read from the other side), and a repealed ruling's arithmetic may stand on a reason the ruling never named (the dolly floor's contribution-cap survived the wheel carve-out it was written for; deleting them together went red inside the round).
- **A POST-PHASE ASSERTION IS WORTHLESS WHEN A LATER PHASE TIDIES UP REGARDLESS (2026-08-28, #521 slice B — found by a mutant, after the identical trap had just been fixed one case over).** A case asserting "nothing is left in the air after the pass" passed with the code that guaranteed it DELETED, because the exit's `clear_staging()` puts the board down either way. The property actually at risk was one phase earlier — the board the ENTRY hands the fight. **Ask which phase owns the property, and drive that phase alone**; slice A already wrote this down as "test the decision, not the aftermath" and it still cost two cases in one session.
- Godot ternary exists (`x if cond else y`); typed dictionaries (`Dictionary[String, int]`) are used throughout — keep chains typed end-to-end.
- **Retyping a persisted `@export` field from String to an enum is a *data* migration, not just a code change.** Godot silently *drops* type-mismatched values when loading a `.tres` (a saved `Dictionary[String, int]` won't populate a `Dictionary[Stats.Stat, int]` — it loads empty) and *strips* them on the next resave. Everything below is unchanged, it is just mounted one level deeper, at `/root/Battle3D/Main`. **Consequence already paid once: `game.gd` resolved the dev overlay by the ABSOLUTE path `/root/Main/DevOverlay`, which silently returned null under the new mount and made F1 dead in the 3D build. It is relative now (`../../../DevOverlay`) — do not put an absolute `/root/...` path anywhere in the game subtree.**): `Main` (Node) → `GameContainer` (SubViewportContainer, Stretch on, texture_filter Nearest) → `GameView` (SubViewport, embed ON) → `Game` (game.tscn instance); `DevOverlay` (a `Window`, embed ON) is a sibling of `GameContainer` under `Main`. Project `embed_subwindows` = **OFF** → `DevOverlay` is a real OS window (second-monitor capable); `GameView` embeds so the game's own popups (action menu) stay in-game. Cross-boundary refs: `game.gd` → `get_node("/root/Main/DevOverlay")`; `dev_overlay.gd` → `get_node("../GameContainer/GameView/Game")` (+ `…/Game/ScenarioManager`). Gotchas this created — all already handled, **do not undo**: (1) SubViewports default to LINEAR filtering; `game._ready` sets the viewport default to Nearest via `RenderingServer.viewport_set_default_canvas_item_texture_filter(get_viewport().get_viewport_rid(), RenderingServer.CANVAS_ITEM_TEXTURE_FILTER_NEAREST)` — per-node `texture_filter` only patches part of the tree (the chain breaks at any `CanvasLayer` / non-CanvasItem ancestor). (2) Embedded popups don't auto-dismiss on outside-click (input is forwarded through the container), which is why the action menu has been Control-based since #26 and must not go back to a `Popup`. (3) Stretch mode = `disabled`; UI is real pixels — no hardcoded pixel positions (use viewport-relative; the hover panel's old `BOTTOM_LEFT_POS=410` broke on a viewport-height change). (4) Any new subwindow UI (PopupMenu/dialogs) inherits these quirks — prefer Control-based menus.
