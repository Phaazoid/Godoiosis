# Iosis — Project Guide

Tactical RPG (Fire Emblem-influenced), Godot 4.6, GDScript. Solo hobbyist developer.

## Collaboration contract (read first)

- **The user types all gameplay code themselves** (`Classes/`, `Scenes/`, `game.gd`). Guide with complete code blocks and file/line anchors; never edit those files directly unless explicitly asked. The user is here to learn — explain the *why*, not just the *what*.
- **Deliver every change as a typed code block.** Prose-described steps ("then update the click handler to...") reliably fail to get implemented. If the user must type it, write it out fully.
- Claude MAY directly create/edit: `CLAUDE.md`, `docs/`, `tests/`, `play/` (the headless Play API — confirmed 2026-07-16 as already Claude's domain, not user-typed gameplay code), GitHub issue text, and other non-gameplay scaffolding (standing exception granted 2026-06-12).
- **Standing exception (2026-07-16):** when a walkthrough touches a `Classes/`/`Scenes/`/`game.gd` file that has no top-of-file description comment (what the file/class IS and its place in the architecture), Claude adds that comment directly instead of asking the user to type it. Everything else in the file stays hand-typed. Start-of-session sweep target: any file touched by the issue in progress.
- **Standing exception (2026-07-16): `.tscn` scenes and saved scenarios.** If a code change breaks an existing `.tscn` file or a saved scenario `.tres` (`Scenarios/*.tres`), Claude has full permission to edit it directly to keep it working — current scene/scenario content is disposable placeholder, and a clean codebase (no legacy-compat branches carried for their sake) matters more than preserving them untouched. Doesn't extend to gameplay `.gd` code in `Classes/`/`game.gd`, which stays hand-typed regardless.
- **Standing exception (2026-07-16): comments in `Classes/`/`game.gd`.** Claude may edit comments directly (stale references, renamed symbols, drifted explanations) even in files whose code stays hand-typed — comments aren't code. Actual logic in these files is still the user's to type.
- After walkthroughs land, *verify by reading the actual files* before debugging from theory — transcription drift is the most common failure mode.

## GitHub issue workflow (Claude ↔ human handoff)

Open work lives in [GitHub Issues](https://github.com/Phaazoid/Godoiosis/issues). Two **mutually exclusive** assignment labels say whose turn it is (exactly one per open issue):

- **`agent/claude`** — Claude owns the next step: draft/revise a fix walkthrough, or (for `tests/` & `docs/`) just do the work directly.
- **`agent/human`** — a human owns the next step: type a posted walkthrough, make a design decision, or test. Flip an issue back to `agent/claude` (with a reply) when a fix needs rework.

Run **`/agent-queue`** to have Claude scan the `agent/claude` issues and advance each one, then hand back. Every comment Claude posts under the user's account **leads with `🤖 Claude says:`** and **ends with** `— Claude (<model>) · <date>` (name the model actually running, e.g. Fable 5 / Opus 4.8 — the signature is provenance), authored via the Write tool → `gh issue comment --body-file` (never an inline non-ASCII arg — Windows PowerShell 5.1 mojibakes it before upload; see the encoding note in `tests/README.md`). After acting, Claude flips the label to `agent/human`.

**Canon-sweep discipline before calling a doc update done (added 2026-07-16, after a full-corpus staleness sweep found 9/22 `docs/design/` files drifted):** a "canon swept" claim means a grep-verified pass over the *whole* `docs/design/` tree (+ this file) for the issue's own number and any renamed/removed code symbol or term it touched — not just an edit to the one file that's obviously the topic's home. Staleness hides in three places a narrow, feature-specific edit misses: (1) a status banner elsewhere in the *same* file that a detail-section-only edit didn't reach; (2) a sibling file stating the same fact from a different angle (weapons.md and elemental-system.md both independently described issue #7 as open after it closed); (3) a "living list" tracker (`docs/design/grill-queue.md`) that can go stale from a *different* ticket's work than the one closing. For multi-session issues, sweep against the issue's *final* state at close — re-read its own comment history, not just what the current session built.

**Staleness marker (added 2026-07-16):** every living design doc (all of `docs/design/` except the three deliberately-frozen historical records — the coherence audit, the co-dev agenda, the wiki triage ledger) carries a `**Canon checked through #NN (date).**` line in its opening banner. When a sweep re-verifies a doc, bump its marker to the current highest issue number + that day's date. A marker sitting far behind the current issue count is the at-a-glance signal a doc is due for a re-check — don't let it go stale by forgetting the bump once you've actually re-verified the doc.

## Design laws (non-negotiable)

1. **No randomness in gameplay.** No hit/miss rolls, no crit chance, nothing. Combat is fully deterministic. (Old design docs mentioning crits predate this law.)
2. **The action queue never lies.** Planned actions must preview exactly what execution does. Queue/cancel/requeue must be idempotent. Derived actions (counter-attacks) are *computed* from the plan, never stored as player orders.
3. **Future AI uses the player's API.** AI issues orders exclusively through `SquadManager.queue_action` — no side channels. This protects law #2 forever.
4. **One question, one answer — never build a second seam for a fact the code already holds.** (Added 2026-07-28 after #102; elevated to a law because it has already bitten five times.) Before adding a field, flag, predicate, method, or *content convention*, find what already answers the question it would answer, and either extend that or explicitly retire it. **Grep the question, not the name** — the duplicate almost never shares a token with the original, which is exactly why it slips through (`requires_readiness` vs `knockback > 0`). **Suspect anything with an honest local motive**: the second seam always looks like it solves a different problem, and that motive is the disguise. **Prefer passing over looking up** — a looked-up fact can silently diverge from a passed one; a parameter makes divergence unrepresentable (`Reach.get_affected_cells_from(…, attack)`, `WeaponInstance.base_damage(wielder, attack)`). This applies to authored content as much as to code — the content layer is where it's easiest to do accidentally, because it doesn't feel like architecture. If a second representation is genuinely warranted, **declare it out loud**: name both sides and state which is authoritative (the `objectives` vs painted `zones` guard under *Missions* is the model). The undeclared second source is the hazard; a declared one is a design. Why it's a law and not a sharp edge: these fail *late*, once both answers have callers, and the divergence can go **load-bearing** — #102's stale pick was the only reason secondary AoE resolved correctly, so the obvious cleanup would have broken more than it fixed. Prior instances: `LethalityRules.predict()` (preview and execution were two hand-synced ladders), `MENU_ORDER` vs `ACTION_DATA` order, `KineticMaceWeaponInstance`'s `knockback > 0`, and the three-way `dead` split the persistence seam now guards with "don't add a fourth".

## Architecture map

- `game.gd` — input/game-state coordinator. **Reorganized 2026-07-26** into labelled sections (Lifecycle / Input / Turn flow / Modes / Queueing orders / The action-queue panel / Squads / Populating the board / Board visuals / Board queries), with three collaborators split out — each built in `_build_collaborators()` and holding a `game` back-ref, the `DevController`/`AIController` pattern: **`OrderExecutor`** (`actions/`, runs a squad's plan + the Crisis/downed fallout), **`HoverPresenter`** (`board/`, mouse → cursor/overlays/hover card/queue-row highlight, incl. the `_process` hover detection and the two `hovered_*` signals), **`MainActionMenu`** (`ui/`, now the *whole* menu system — construction as well as gating/dispatch). Still the heaviest file; prefer moving domain logic out to the owning system when touching it. **Anything reaching back through the untyped `game` ref must annotate its locals explicitly** — `game.gd` has no `class_name`, so every `game.*` call is Variant and `:=` cannot infer from it; and a bare array literal passed that way is NOT coerced to a typed parameter (it fails at *runtime* — this is why `clear_selection_icons()` exists instead of callers passing the literal).
- `SquadManager` — **the only owner of squad lifecycle**: create/destroy/join/leave. Member removal funnels through `Squad._erase_member()` (the sole `members.erase` caller, mirroring `_add_member`); its callers are `_detach_from_current_squad()` (single-unit) and `disband_squad()` (bulk). Also home of order queueing (the Law #3 `queue_action` chokepoint), activation state, plan resolution, and counter-attack resolution. **Slimmed 770 → 516 lines 2026-07-26**: it had become the second dumping ground after game.gd — two of its sections were literally labelled *"migrated from game.gd (#22)"* — so three tenants moved out to **`SquadPlanValidator`** (plan-context validity, stamped onto each action), **`GroupMoveSolver`** (the pure formation solver; `queue_group_move` is the committing half), and **`ActionQueueDisplayEntry.build_for()`** (queue-panel layout, now beside the view model). All three are fully static — they read a plan and return a result, touching no squad state. **Order batching (`SquadManager.batching`, 2026-07-26):** Group Move queues N orders as ONE player action, so the expensive squad-level repaint runs once at the end rather than per order (a 5-member click went 232 ms → 65 ms). Every order still passes `queue_action`'s gates (Law #3), and `action_queued` still fires per order so cheap per-UNIT listeners don't miss anyone. **It is safe only while a batch stays synchronous** — if one ever spans a frame, the queue panel goes stale and Law #2 breaks. Invariants + measurements: [`docs/performance.md`](docs/performance.md).
- `Squad` — member list + `action_queue` (player-authored orders only). Enforces one order per action-type per unit (volley siblings exempt — see `_is_volley_sibling`).
- **Persistence seam (locked, #8):** transient `Unit` node holds battle-scoped state that resets each mission (element states, projected position, lifecycle ACTIVE/DOWNED/DEAD); persistent `UnitInstance` resource holds identity that survives missions (HP, fixed stats, limb loss, proficiency, **Will**, and `permadead`). **`permadead` (added 2026-07-27) is declared but deliberately UNWIRED** — nothing sets or reads it until there are missions and a persistent roster, at which point `Unit.die()` is the setter and roster assembly the reader. It is the *third* distinct "dead" on this seam and the only non-battle-scoped one: `UnitInstance.is_dead()` is `current_hp <= 0`, `Unit.is_dead()` is "went down the permanent path this mission", `permadead` is "never fields again". Don't add a fourth, and don't rename any of them to plain `dead`. New per-unit state picks its side by one test — *does it survive a mission?* No third store. **The one documented exception is `UnitInstance.stat_modifiers`** — a battle-scoped add/subtract bag (the Crisis surge) that has to sit on the persistent instance because it's a stage of `get_effective_stat`'s chain (base → limb → jobs → **stat_modifiers** → gear). It is therefore cleared by `initialize()` alongside HP/Will, and is deliberately NOT captured by `ScenarioUnitEntry`. Write it only through `UnitInstance.add_stat_modifier(stat, delta)` (added 2026-07-27) — the bag's one mutator, so every write sits beside the `initialize()` that clears it; `Unit`'s Crisis surge used to read-modify-write the dictionary directly, the single place `Unit` reached into `UnitInstance`'s internals rather than asking it something. Before 2026-07-26 that reset was missing, so a surge still applied when a battle ended would have become permanent the moment instances start surviving missions; pinned by `tests/stats/test_gear_stat_modifiers.gd`. (Cross-mission save/load is the future campaign layer; boundary is locked now so features land on the right side. See `docs/design/resolution-pipeline.md` → "The persistence seam".) **Scenario save/load round-trips the whole `UnitInstance` side since #83 (2026-07-22):** `ScenarioUnitEntry.capture_unit_state`/`apply_unit_state` own the unit-state snapshot (stats, current HP/Will, full inventory via `copy_equippable` + `equipped_index` — the old standalone `equipped_weapon` copy is retired — `worn_armor_index` (#89 — armor is carried in the SAME inventory as weapons but fills a DIFFERENT slot, so it saves as an index exactly like `equipped_index`, never as a second copy beside the carried one; **load assigns directly and never re-runs the wear gate** — a save is authoritative, and re-gating would strip armor off a unit whose stats drifted after saving), limb states with prosthetic re-link-by-index, proficiency, aura, jobs), applied AFTER `initialize()`'s reset on load; `ScenarioManager` and the Play API's `board_builder` both call the same pair. Battle-scoped `Unit` state (element states, lifecycle, weapon readiness) deliberately stays out.
- **Actions are a small in-code registry, not a framework** (`BaseAction` → `MoveAction`, `AttackAction` (→ `CounterAttackAction`), `RescueAction` (#33), `RallyAction`, `IntimidateAction` (#61), `ReloadAction`/`RevAction`/`BurrowAction` (the weapon-signature verbs, #73/#84), `CaptureAction` (#96 — stamps its cell, zone name and the MissionController at queue time, so the resolver reads a frozen snapshot and a re-planned move can't quietly capture elsewhere); action-registry refactor 2026-07-20/21): the `ActionType` enum plus two declared `const` lists on `BaseAction` ARE the registry. `MAIN_ACTION_TYPES` (ATTACK/RESCUE/RALLY/INTIMIDATE/RELOAD/REV/BURROW/**CAPTURE**) drives `is_main_action()` — mutually exclusive, one per unit per turn, must come *after* any move (locking one removes the move option). `SIDE_CHANNEL_ORDER` (RESCUE/RALLY/INTIMIDATE/RELOAD/REV/BURROW/**CAPTURE** — stored orders that bypass `PlanResolver`) is iterated by THREE places at once: `OrderExecutor.execute_orders`'s phase loop, `ActionQueueDisplayEntry.build_for`'s queue-panel sections (header = the enum's own key string), and the headless Play API's `_describe_plan`/`execute()` — a new type registered there gets a phase, a queue section, and Play support for free, with no per-type mirror to add. Per-action **queueing requirements** live on the action itself via the `actor_can_perform()` virtual (move-before-main on `MoveAction`, verb locks on `AttackAction`/`RescueAction`, the Will-room check on `RallyAction`, the ability gate on `IntimidateAction`) — `SquadManager.queue_action` calls it once as the sole Law #3 chokepoint instead of a per-type match arm. `game.gd`'s `GameState.PICKING_TARGET` + `enter_target_pick_mode(candidates, on_pick: Callable)` is the one generic "pick a highlighted unit" flow — rescue, intimidate, squad-up, and join-squad all ride it (candidates from a predicate query, `on_pick` closes over the acting unit); it deliberately does NOT extend to `CHOOSING_MOVE`/`CHOOSING_GROUP_MOVE` (live path-preview IS the feature) or `ATTACK_TARGETING` (directional aiming, not a unit pick) — those stay bespoke on purpose. **Menu system lives in `MainActionMenu` (`Classes/ui/MainActionMenu.gd`), pulled out of `game.gd` 2026-07-22 and completed 2026-07-26** — it holds a `game` back-ref (same pattern as `DevController`/`AIController`: instantiated and `.game = self`'d in `game._ready()`) for everything it reads or dispatches into. It now owns menu **construction** too (`show_main_menu`/`show_attack_menu`/`show_weapon_action_menu`, plus `begin_attack`), so `game.gd` holds no menu knowledge at all: three near-identical copies of the `ActionMenuController` boilerplate collapsed into `_open_menu()`, and two copies of the fireable-or-disabled row into `_attack_entry()`. Menu print order is just its `ACTION_DATA`'s declaration order (no separate `MENU_ORDER` list to keep in sync — an entry left out of `ACTION_DATA` can't silently vanish from the menu because there's nowhere else for it to be declared). New-action checklist: the class (with its `actor_can_perform()` override) → one line each in `MAIN_ACTION_TYPES`/`SIDE_CHANNEL_ORDER` → **the player surface** → **its AI stance** in `AIArchetype`'s `MAIN_ACTION_PRIORITY`/`MAIN_ACTION_NEVER` (the law test fails until it lands in exactly one, per archetype) → a `SquadPlanValidator` clause only if the action has plan-context (adjacency/occupancy) rules, mirroring `_revalidate_rescues`/`_revalidate_intimidates`/`_revalidate_captures`. **Queueing a no-argument verb goes through `game.queue_simple_action(unit, type)`** (2026-07-28): `queue_rally`/`queue_reload`/`queue_rev`/`queue_burrow` were four byte-identical copies and are now one path with a `_make_simple_action` factory — a `match`, not a class dictionary, because class references aren't const-foldable and a dict lookup loses static typing. Verbs taking a real argument (rescue/intimidate take a unit, capture takes a cell) deliberately stay separate; forcing them through one signature just moves the branching into a parameter bag. **The player surface forks by kind since the 2026-07-24 Weapon Action refactor:** a *general* verb (rescue/rally/…) still takes a top-level `MainActionMenu` slot — menu-id const + `ACTION_DATA` entry + gate clause in `populate()` + dispatch arm in `on_pressed()`; a *weapon-specific* one (Rev/Reload/Burrow, and any future family signature) instead adds a branch in `MainActionMenu.show_weapon_action_menu` + its `_pick_weapon_action` match, and an inert `can_<verb>()` default on `EquippableData` (overridden on the family's `WeaponInstance` subclass), a thin `can_<verb>_weapon()` delegator on `Unit`, and one `or can_<verb>_weapon()` in `Unit.has_weapon_actions()` — the top-level menu shows only the single "Weapon Action" entry no matter how many signatures exist. Either way the queued `ActionType` is unchanged, so registry/resolver/queue/AI wiring is identical. Registry completeness is pinned by `tests/law/test_action_registry.gd` (every `ActionType` must land in exactly one of the fixed pipeline or `SIDE_CHANNEL_ORDER`) and `tests/squad/test_action_queue_display.gd` (queue sections follow registry order regardless of queue insertion order). AoE = a **volley**: one `AttackAction` per victim, all sharing a `volley` array; secondaries set `is_secondary_hit` and skip the lunge animation.
- `Reach` (`weapons/`, **static**) — weapon-aware attack geometry: `get_attack_cells_from` (facing-specific), `get_all_attack_cells_from` (union over 4 facings, for overlays), `get_affected_cells_from` (AoE), `is_directional_attack()` (does this attack's pattern aim by facing?). **Every one of them TAKES the `AttackData` it is reasoning about (#102, 2026-07-28)** — they used to look it up themselves via `Unit.get_fired_attack()`, i.e. the live `active_attack` pick, while the queued order carried its own frozen `AttackAction.fired_attack` stamp; geometry answered from one source and damage from the other, and a leftover pick re-shaped stored blasts and granted counter reach the counter couldn't fire with. Each caller now names its source: **aiming/preview** → `unit.get_fired_attack()`, **a stored order** → `action.fired_attack`, **a counter** → `unit.get_counter_attack()`. Law #4 in practice — passing beats looking up. Null attack (or one with no pattern) = adjacency fallback (Manhattan 1 selectable, the aimed cell alone affected) — load-bearing in the tests, where a pattern-less weapon is how they get trivial geometry. **Was `CombatComponent`, a Node on every Unit, until 2026-07-26.** It held no state: every method opened by fetching its owner back, `apply_damage` was a pass-through to `Unit.take_damage`, and `can_attack(attacker, target)` took the attacker as a parameter despite being an instance method on it (now `RulesService.can_target`). Its lone `@export can_counter` was **never authored on any unit**, so SquadManager's gate on it was permanently open and shadowed the real, authored `AttackData.can_counter` — the gate is gone and `Unit.attack_source_can_counter()` is the single check.
- **Targeting modes (#25):** patterns are **directional** (`AttackPattern.is_directional()` true — forward line/wide: the player points a cardinal direction and the whole spread fires; the pointed cell need not be a spread member) or **point** (false — Manhattan / no weapon: the hovered cell itself must be in range). ATTACK_TARGETING branches on `Reach.is_directional_attack(attack)` for both hover-preview (`HoverPresenter._hover_attack_targeting`) and click (`game._click_attack_targeting`) — both hoist `attacker.get_fired_attack()` into a local first, since aiming is the one context where the live pick genuinely IS the question; the red overlay still shows the full 4-facing reach (`get_all_attack_cells_from`). ForwardWide `width` is **odd-only** (`@export_enum`); `ManhattanRangePattern` supports a no-float blended Manhattan/Chebyshev range (`max_and_a_half` bevels in the diagonal corners of the max ring → `GridUtils.cells_within_blended_range`). The attacker's chosen facing is now explicit — the intended seam for a future **backstrike** (facing-vs-facing damage).
- **Weapons are template + instance, and the attack is its own content (#59 then #72, mirrors the jobs id-reference pattern + the rune/carving system):** `AttackData` (`extends Resource`) is the shared skeleton anything a unit can fire carries — `display_name`, `power`, `attack_pattern`, `can_counter`, `hits_allies`, `targets` — with damage math deliberately OFF the base (carvings scale off aura, weapon attacks off the wielding weapon's blend + mods). `WeaponAttackData extends AttackData` adds only `elemental_damage_type`; `TransmutationData` (the rune carving) is its sibling subclass. `WeaponData` is the shared family TEMPLATE (family base like `ChainSword.tres`, or a named prototype) — `main_attack: WeaponAttackData` (the one REQUIRED attack, a curated resource the family points at — never a bare array slot — used by default aim and ALWAYS by counters) + `extra_attacks: Array[WeaponAttackData]` (no count cap; mod spaces gate access), plus `scaling_blend` (a `Dictionary[Stats.Stat, int]` % blend across STR/DEX/PER/CON), `weapon_type`, `is_prototype`, and the `weight` it inherits from `Item` (was its own `base_weight` until 2026-07-27). It is NOT equippable (extends `Item`, not `EquippableData`) and is never duplicated — a unit that owns a template edits it live for every weapon built on it, main attack included. `WeaponInstance` (extends `EquippableData`, what a unit actually carries) holds a direct `template: WeaponData` ref plus its own `space_1`/`space_2`/`space_3` (fitted `WeaponModData`, the only true per-weapon state) and computes the effective view (`base_damage`/`get_elements`/`hits_map`, all taking an optional `attack: WeaponAttackData` override that defaults to main when null) from template + active modules. **Never `duplicate(true)` a `WeaponInstance`** — that deep-copies the shared template and severs the sync; use `copy_equippable()` (the `EquippableData` virtual every equippable overrides as needed — `WeaponInstance`'s keeps `template` shared and copies spaces shallowly, the default falls back to `duplicate(true)` for `RuneData`). In battle, `Unit.get_fired_attack()` (live pick else first-channelable-carving/main) answers **"what would this unit fire if it declared right now"** — read at AIM time only (the targeting overlay, the hover preview, and `AttackAction.declare()`'s stamp). It is deliberately NOT what reach and ally-splash read: since #102 those take the `AttackData` as a parameter, so a stored order's geometry comes off its own stamp and a counter's off `get_counter_attack()`. `active_attack` is therefore a pure **aiming cursor**, cleared when targeting ends (`game._clear_aiming_pick`, from `exit_current_mode` while the state is still ATTACK_TARGETING) — a reset that was only safe to add *after* the parameterization, because until then the stale pick was the one thing making secondary AoE resolve correctly. `Unit.get_counter_attack()` is a deliberate exception — weapons always counter with main, ignoring any live pick (a rune counters with whatever it fires; overwatch-style alt-attack countering is future scope, #73) — and since #84 that main must also be FIREABLE (`Unit.attack_source_can_counter()` checks readiness), so an empty Carbine magazine or a sprung Springspear stops countering, and a counter that does land spends whatever its main consumes — and the chosen `AttackData` is stamped onto `AttackAction.fired_attack` at declare time so the resolver reads a frozen snapshot, never re-derives (Law #2). `AttackPattern` resources stay pure **geometry** (selectable cells vs affected cells), unaffected by any of this split; terrain/LoS filtering belongs at the resolution layer when it arrives (planned weapon flag: `arcs_over_obstacles`). **Per-attack readiness BUILT 2026-07-22 (#73):** `WeaponAttackData.requires_readiness`/`consumes_readiness` (both default `false`) author a wind-up/recovery economy; the actual readiness STATE lives on `WeaponInstance` itself, not `Unit` (a unit can carry more than one of the same weapon — they must track independently) and not the shared template (battle-scoped). `WeaponInstance.make()` dispatches on `weapon_type` to build the right concrete subclass — every family has one (`SpringspearWeaponInstance` plus six pure pass-throughs added by [#82](https://github.com/Phaazoid/Godoiosis/issues/82), 2026-07-22), and the base class declares the readiness surface as no-op virtuals (`is_attack_fireable`/`consume_readiness_for`), so families with no signature mechanic yet pay nothing — **and as of 2026-07-27 the argument-free self-ability verbs (`can_reload`/`reload`/`reload_label`, `can_rev`/`rev`/`tick_rev`, `can_burrow`) sit one level higher still, on `EquippableData`**, so `Unit` delegates to whatever is equipped without casting. Only the two `WeaponAttackData`-taking methods stayed on `WeaponInstance`: widening their parameter to `AttackData` for the base would break every family override's signature. **The bool generalizes to a counter without touching the seam** — `CarbineWeaponInstance.shots_remaining` (#84) reads the same two authored flags as a magazine, and `KineticMaceWeaponInstance.charge` reads them backwards as a bank. `Unit` only holds thin delegators reading whatever's equipped. An unmapped `weapon_type` is a loud failure (`push_error` + `null` return from `make()`), never a silent fallback. See [`docs/build-log.md`](docs/build-log.md) → *Weapons* for #82's full build note.
- Execution order: moves (parallel) → attacks (sequential — combo order matters for future elemental) → counters (sequential) → rescues (sequential). Units downed mid-pass are queued and ejected from their squads **after** the whole pass (`OrderExecutor._process_downed_pending`), never mid-`execute` (restructuring squads mid-resolution was buggy).
- `TurnManager` (`flow/`) — the faction turn cycle, **rebuilt from the board each hand-off** (refactored 2026-06-24). Tracks the **active faction by value** (the old two-sided `TurnPhase` enum is gone); `end_turn(present_factions)` recomputes the live order as `Team.all_factions()` (enum order) ∩ factions present, then advances past the active one. Handles **any number of teams**, and the cycle **builds itself from what's on the map** — a newly-spawned faction enrolls at the next hand-off, a wiped one drops out. **Single source of truth = the `Team.Faction` enum** (add a member → it's in the rotation). Trade-off: turn order follows enum-declaration order, which is **append-only** for save-compat, so a new faction acts *last* unless you migrate enum values; and presence *is* eligibility (a `NEUTRAL`/`OTHER` faction with units would take a turn — add an explicit opt-out if you ever want non-acting scenery). `game._on_turn_started(faction)` **auto-skips** a faction with no `is_active` units after ticking its downed clocks — guarded by `_board_has_active_units()` so an all-downed board can't infinite-loop; `start_faction_turn(faction)` replaced the old player/enemy split. Saved turn state = `ScenarioData.active_faction` (authoritative; the `turn_phase` field was removed), restored via `set_active_faction`. The headless Play API mirrors this exactly (`play_session.end_turn` derives present factions + runs the same guarded skip).
- **Missions — the closed loop (`flow/`, #96, all four slices built 2026-07-28; canon [`docs/design/missions.md`](docs/design/missions.md)):** the game can be **won and lost**, and it now BOOTS into `MissionSelectScreen` rather than a board (`TestBoard` retired as the boot path; `game.spawn_sandbox()` is its one remaining call site). Four parts, split on purpose. **`MissionRules`** (static, pure, `extends Object` — LethalityRules' shape) is the whole rule: `evaluate(board, contested, progress) -> ONGOING/VICTORY/DEFEAT`. **`MissionController`** (a game collaborator, the DevController pattern) holds everything a pure predicate cannot — the ended-latch, the `contested` latch, captured-zone state, the objective composer, and what the game DOES about an ending (`GameState.MISSION_OVER`/`MENU` → `_board_locked_for_player`, the banner, the return path). **`ScenarioData.objectives: Array[MissionRules.Objective]`** is what a mission REQUIRES (ROUT/CAPTURE/EXTRACT, composed by AND, edited in the dev Scenario tab); **`ScenarioData.zones`** is WHERE, via `ZoneManager.Kind`. **There is no `MissionData`** — a mission and its board are 1:1, so a wrapper resource is an extra hop, not a template/instance split (dev, reversing the original plan). Objectives are **declared explicitly, not inferred from painted zones**: rout has no geometry to paint, a mis-picked Zone Kind would otherwise silently rewrite the win condition, and geometry couldn't be authored ahead of its rule. Guard for the resulting second source of truth: a declared objective with no painted zone reads **PENDING, not NONE** (the map really is unwinnable — silently dropping it would convert a broken map into a different playable one), warned live in the Scenario tab and `push_error`'d by `set_objectives`. Doctrine, all load-bearing: **(1) an authored objective is the ONLY way to win** — routing a capture map wins nothing unless ROUT is ticked (lockout is a level-design problem, not a rule that hands out a consolation win); **(2) DEFEAT is checked first** — last player unit and last hostile falling in the same pass is a LOSS; **(3) `contested`** — "both sides were up at once", latched by the CALLER because the board can't tell *wiped out* from *never here* (`present_factions` drops an all-dead faction) and a LIVE read could never end a mission, which is what keeps **dev sandbox boards inert with no `dev_mode` flag**; **(4) extraction counts the DOWNED** — alive and inside the zone means they got out; what blocks it is a living unit OUTSIDE, and a downed one there needs a rescue. `check()` fires at the three points board state changes and settles — end of a resolution pass (`OrderExecutor.execute_orders`, *before* its squad-validity guard so a squad that wiped itself can't skip it), after the end-of-turn burn, and turn start *after* the downed clocks tick. Pass-end not turn-end: a friendly AoE can down your own last unit mid-pass. `AIController.take_faction_turn` guards on `is_over()`. **`MissionController.reset()` (from `ScenarioManager.clear_board`) is the first thing in the codebase to ever fire a mission-start event** — the [#87](https://github.com/Phaazoid/Godoiosis/issues/87) seam whose rule had never actually executed; keep the split when #87 lands (**loading a mid-battle save RESTORES, starting a mission RESETS**). NB `MissionRules.Progress` (NONE/PENDING/MET) and `MissionRules.Objective` (what's required) are different enums; `Progress` was called `Objective` in slice 1. Tested: `tests/flow/test_mission_rules.gd` (22) + `tests/ai/test_zone_manager.gd` (12) pin the rule and the geometry; **`MissionController` itself is not covered** (needs the game scene, which segfaults in the runner). Lose conditions beyond the last unit falling, and authorable OR-composition, are [#101](https://github.com/Phaazoid/Godoiosis/issues/101).

## Sharp edges (each of these has already bitten once)

- **Grant/copy an equippable via `copy_equippable()`, never a bare `duplicate(true)`** (revised #59 — this used to say the opposite). `RuneData` still wants a full deep copy (its base implementation), but `WeaponInstance` overrides it to keep `template` a SHARED reference while its own `space_1/2/3` copy shallowly — a generic `duplicate(true)` would deep-copy the template too and silently fork a weapon off its family.
- **gdUnit4's `Total execution time` line is not wall clock** — it read `1min 55s` for a 573-case run right after a cache clear, then `12s` for the identical run warm. It is not a usable number in either direction; trust `run_tests.ps1`'s own stopwatched `Elapsed` line instead. **Measured on `Elapsed`: full run 153–157s** (eleven consecutive runs 2026-07-26, 605 cases; independently 158s at 610 cases on 2026-07-27), **`fast` 42s** (156 cases), **51s for three areas together** (2026-07-27). That is **~0.26s/case across every tier** — a flat per-case cost, not a startup overhead you can amortize, and ~7x the "~0.035s/case warm" this note used to claim. The same suite passes **Linux CI in a 34s total job** while the case count only grew 573 → 610, so it is a Windows/environment factor, not suite size — **cause unconfirmed** (antivirus scanning the repo tree and `.godot` cache state are the untested suspects). The old "~20s full / ~7s fast / ~3-5s per area" figures came from trusting gdUnit4's warm number; all corrected 2026-07-27. Practical consequence: **no tier is a fast inner loop right now** — pick the narrowest area you can. Re-measure before ever acting on "the tests are getting slow". **Observation, same day (2026-07-27, Unit.gd review session): three consecutive full runs came in at 19.5s / 19.9s / 20.9s at 610–612 cases — ~8x faster than the measurements above, on the same machine, hours apart.** The session had just run `godot --headless --import` (needed to register a new `class_name`), and the speed persisted across later runs that did not re-import. That is a data point for the `.godot`-cache suspect, **not** a correction: **this entry stands as written**, because the slow behaviour has recurred repeatedly and the fast state has not been shown to last. If you find yourself waiting 2.5 minutes again, an import pass is worth trying before anything else.
- `.tres` files omit properties at default values — an "empty-looking" resource may just be unsaved-at-defaults.
- UI rule: **scene for static, code for dynamic.** Fixed controls live in `.tscn`; data-shaped UI (editor fields, stat rows) is generated.
- Plain `Panel`s report 0×0 minimum size for absolutely-positioned children inside containers.
- `Unit.has_squad()` means "has squad*mates*" (members > 1). Every unit always belongs to exactly one managed squad, even solo.
- Godot ternary exists (`x if cond else y`); typed dictionaries (`Dictionary[String, int]`) are used throughout — keep chains typed end-to-end.
- **Retyping a persisted `@export` field from String to an enum is a *data* migration, not just a code change.** Godot silently *drops* type-mismatched values when loading a `.tres` (a saved `Dictionary[String, int]` won't populate a `Dictionary[Stats.Stat, int]` — it loads empty) and *strips* them on the next resave. After retyping such a field (stat-dict keys, `weapon_type`, `scaling_stat`), rewrite every saved `.tres` to the enum form — enums serialize as plain ints (`base_stats = Dictionary[int, int]({0: 20, …})`, `weapon_type = 1`). Bit 2026-06-19 (#7 fallout): every unit loaded with 0 stats → LDR 0 → nobody could move; the only intact copy of the string data was git HEAD, since the migration commit never touched the `.tres`. Migrate from HEAD, not the working tree (Godot may have already stripped it).
- **Dev tools = separate OS window; the game is wrapped in a SubViewport (June 2026 refactor).** Scene tree (`Main.tscn` is the main scene): `Main` (Node) → `GameContainer` (SubViewportContainer, Stretch on, texture_filter Nearest) → `GameView` (SubViewport, embed ON) → `Game` (game.tscn instance); `DevOverlay` (a `Window`, embed ON) is a sibling of `GameContainer` under `Main`. Project `embed_subwindows` = **OFF** → `DevOverlay` is a real OS window (second-monitor capable); `GameView` embeds so the game's own popups (action menu) stay in-game. Cross-boundary refs: `game.gd` → `get_node("/root/Main/DevOverlay")`; `dev_overlay.gd` → `get_node("../GameContainer/GameView/Game")` (+ `…/Game/ScenarioManager`). Gotchas this created — all already handled, **do not undo**: (1) SubViewports default to LINEAR filtering; `game._ready` sets the viewport default to Nearest via `RenderingServer.viewport_set_default_canvas_item_texture_filter(get_viewport().get_viewport_rid(), RenderingServer.CANVAS_ITEM_TEXTURE_FILTER_NEAREST)` — per-node `texture_filter` only patches part of the tree (the chain breaks at any `CanvasLayer` / non-CanvasItem ancestor). (2) Embedded popups don't auto-dismiss on outside-click (input is forwarded through the container); `ActionMenuController._input` closes them manually. (3) Stretch mode = `disabled`; UI is real pixels — no hardcoded pixel positions (use viewport-relative; the hover panel's old `BOTTOM_LEFT_POS=410` broke on a viewport-height change). (4) Any new subwindow UI (PopupMenu/dialogs) inherits these quirks — prefer Control-based menus.

- **The AI can't use most signature mechanics.** Rev and Burrow sit in `AIArchetype.MAIN_ACTION_NEVER` with no scored builder, and mace charge→Blowback has no scoring. Each omission was individually reasonable; the aggregate is that the enemy plays a progressively smaller subset of the game than the player, which degrades playtest signal. **The Carbine (#84) is the counter-example worth copying:** it needed zero AI work because it rode an existing declared verb (`RELOAD`, already in every archetype's `MAIN_ACTION_PRIORITY`) plus the `is_attack_fireable` filter the chooser already applies — the AI reloads a dry carbine on day one. A signature that needs new AI wiring is a signature that invented its own surface.
- AoE victim lists don't re-resolve when moves are re-planned after queuing — belongs in `validate_squad_plan`.
- Volley cancel propagation needed if per-row queue cancel UI ever arrives (`volley` array already linked).
- `ForwardLinePattern` vs `ForwardWidePattern(width=1)`: **decided NOT to consolidate ([#20](https://github.com/Phaazoid/Godoiosis/issues/20))** — kept as distinct concepts (forward-line reach vs sideways cleave) that may diverge as patterns grow.

### Tooling / tests

- **[#80](https://github.com/Phaazoid/Godoiosis/issues/80) residue — narrower than it used to be** (hand-typed `Classes/dev/` territory). `UnitEditorTool._entry_matches()` compares `item.template == entry`, and a scenario-embedded weapon's template is inline and scenario-local, so it can never match a catalog entry. What's left is only that you **can't re-select** such a weapon in the inventory dropdown. You *can* see it: `_add_inventory_section` renders a `holds: <name>` label whenever no entry matches, so the old "(empty)"-for-a-weapon-you-hold symptom is **fixed** (landed in `9dffc3a`; this entry claimed otherwise until 2026-07-27). Granting a NEW weapon has always worked. Low severity — accepted-as-is unless a scenario-local weapon ever needs re-picking.
- **[#93](https://github.com/Phaazoid/Godoiosis/issues/93): `tests/flow/test_scenario_load_integrity.gd` segfaults on shutdown when run alone** (`0xC0000005`) — all 7 cases pass first, and the full run masks it, so `run_tests.ps1 flow` reports failure on a clean pass. A latent crash in the scenario-load path, which is where [#87](https://github.com/Phaazoid/Godoiosis/issues/87) is headed next.
- **Armor acquisition is dev-tool-only**, same as weapon mods and prosthetics. The Play API also has no wear/remove commands, so headless coverage of the equip surface rides on unit-level tests.
- **The Play API sees rout and defeat only (#96).** `play_session.mission_outcome()` calls the same `MissionRules.evaluate`, but with no `MissionController` out there it always passes `Progress.NONE` — so an authored CAPTURE/EXTRACT objective is invisible headlessly and every board evaluates as a rout map. There is also no `capture` command (the action itself would execute fine — `SIDE_CHANNEL_ORDER` gives it a phase for free). Closing it means teaching the headless board about zones + captured-zone state.
- **`MissionController` has no test coverage.** The pure halves are well pinned (`tests/flow/test_mission_rules.gd`, `tests/ai/test_zone_manager.gd`); the latches, the objective composer, the banner and the six `check()` call sites are not, because they need the game scene, which segfaults inside the runner. In-game feel-testing is currently the only coverage.
- **No mission-status UI (#96).** Nothing on screen says what a mission's objectives are or how far along they are — you find out by winning. It is the prerequisite [#101](https://github.com/Phaazoid/Godoiosis/issues/101) names (a turn clock forces a persistent surface), and the reason the queue still doesn't preview a win.
