# Iosis — Project Guide

Tactical RPG (Fire Emblem-influenced), Godot 4.6, GDScript. Solo hobbyist developer.

## Collaboration contract (read first)

- **The user types all gameplay code themselves** (`Classes/`, `Scenes/`, `game.gd`). Guide with complete code blocks and file/line anchors; never edit those files directly unless explicitly asked. The user is here to learn — explain the *why*, not just the *what*.
- **Deliver every change as a typed code block.** Prose-described steps ("then update the click handler to...") reliably fail to get implemented. If the user must type it, write it out fully. **A partial block inside a loop or `match` arm is the same failure in miniature** (#128, 2026-08-02): "replace its `squad_note` block with…" read as *replace the loop body*, and the `out +=` line that did the actual work went with it — the section rendered empty, costing a full round trip to find. When patching *inside* an enclosing structure, post the **whole enclosing block** (the entire `for`, the entire function) and say what it replaces, top and bottom. Never describe a sub-block in prose and expect the boundary to be inferred. **The unit is the WHOLE FUNCTION, always — never a subset of one, and never a boundary stated in prose** (2026-08-04, #132, the second self-inflicted break in one session). Posting `clear_board()`'s first eleven lines with "the `for unit in units_root...` loop after it is unchanged — leave it in place" deleted that loop: **scenario loads stopped clearing the board at all**, and the full 955-case suite stayed green because nothing asserted that `clear_board` actually clears. The reasoning that produced it — *"this line isn't inside a nested block, so a partial function is safe"* — is the trap; nesting is irrelevant, a partial function is never safe. If a function is too long to repost, that is a signal to split the function, not the block.
- **Anchor a block by file + function name, in the prose *outside* it — never as a comment line inside the block, and never by line number** (dev, 2026-07-29). Anything inside the fence gets typed into the file verbatim, so a `# line 196, _click_idle` marker lands in the source as a stray comment. Line numbers are also stale on arrival: several edits to one file shift every anchor below the first one, so they can be wrong before the walkthrough is even posted. Function names survive. **One heading, one file — never group two files under a shared heading** (2026-08-04, #141): a section headed ``ArmorCatalog.gd / WeaponModCatalog.gd`` with two code blocks under it put *both* blocks in the first file, so one file gained a stray function referencing a const it doesn't own and the other was never updated at all. Two parse errors, and the walkthrough looked fine. The blast radius is the same as the partial-block failure above and the fix is the same shape: every block gets its own heading naming exactly one file.
- Claude MAY directly create/edit: `CLAUDE.md`, `docs/`, `tests/`, `play/` (the headless Play API — confirmed 2026-07-16 as already Claude's domain, not user-typed gameplay code), GitHub issue text, and other non-gameplay scaffolding (standing exception granted 2026-06-12).
- **Standing exception (2026-07-16):** when a walkthrough touches a `Classes/`/`Scenes/`/`game.gd` file that has no top-of-file description comment (what the file/class IS and its place in the architecture), Claude adds that comment directly instead of asking the user to type it. Everything else in the file stays hand-typed. Start-of-session sweep target: any file touched by the issue in progress.
- **Standing exception (2026-07-16): `.tscn` scenes and saved scenarios.** If a code change breaks an existing `.tscn` file or a saved scenario `.tres` (`Scenarios/*.tres`), Claude has full permission to edit it directly to keep it working — current scene/scenario content is disposable placeholder, and a clean codebase (no legacy-compat branches carried for their sake) matters more than preserving them untouched. Doesn't extend to gameplay `.gd` code in `Classes/`/`game.gd`, which stays hand-typed regardless.
- **Standing exception (2026-07-16): comments in `Classes/`/`game.gd`.** Claude may edit comments directly (stale references, renamed symbols, drifted explanations) even in files whose code stays hand-typed — comments aren't code. Actual logic in these files is still the user's to type.
- After walkthroughs land, *verify by reading the actual files* before debugging from theory — transcription drift is the most common failure mode.

## GitHub issue workflow (Claude ↔ human handoff)

Open work lives in [GitHub Issues](https://github.com/Phaazoid/Godoiosis/issues). Two **mutually exclusive** assignment labels say whose turn it is (exactly one per open issue):

- **`agent/claude`** — Claude owns the next step: draft/revise a fix walkthrough, or (for `tests/` & `docs/`) just do the work directly.
- **`agent/human`** — a human owns the next step: type a posted walkthrough, make a design decision, or test. Flip an issue back to `agent/claude` (with a reply) when a fix needs rework.

Run **`/agent-queue`** to have Claude scan the `agent/claude` issues and advance each one, then hand back. Every comment Claude posts under the user's account **leads with `🤖 Claude says:`** and **ends with** `— Claude (<model>) · <date>` (name the model actually running, e.g. Fable 5 / Opus 4.8 — the signature is provenance), authored via the Write tool → `gh issue comment --body-file` (never an inline non-ASCII arg — Windows PowerShell 5.1 mojibakes it before upload; see the encoding note in `tests/README.md`). After acting, Claude flips the label to `agent/human`.

**Canon-sweep discipline before calling a doc update done (added 2026-07-16, after a full-corpus staleness sweep found 9/22 `docs/design/` files drifted):** a "canon swept" claim means a grep-verified pass over the *whole* `docs/design/` tree (+ this file) for the issue's own number and any renamed/removed code symbol or term it touched — not just an edit to the one file that's obviously the topic's home. Staleness hides in three places a narrow, feature-specific edit misses: (1) a status banner elsewhere in the *same* file that a detail-section-only edit didn't reach; (2) a sibling file stating the same fact from a different angle (weapons.md and elemental-system.md both independently described issue #7 as open after it closed); (3) a "living list" tracker (`docs/design/grill-queue.md`) that can go stale from a *different* ticket's work than the one closing. For multi-session issues, sweep against the issue's *final* state at close — re-read its own comment history, not just what the current session built.

**Staleness marker (added 2026-07-16):** every living design doc (all of `docs/design/` except the three deliberately-frozen historical records — the coherence audit, the co-dev agenda, the wiki triage ledger) carries a `**Canon checked through #NN (date).**` line in its opening banner. When a sweep re-verifies a doc, bump its marker to the current highest issue number + that day's date. A marker sitting far behind the current issue count is the at-a-glance signal a doc is due for a re-check — don't let it go stale by forgetting the bump once you've actually re-verified the doc.

## Design laws (non-negotiable)

1. **No randomness in gameplay.** No hit/miss rolls, no crit chance, nothing. Combat is fully deterministic. (Old design docs mentioning crits predate this law.)
2. **The action queue never lies.** Planned actions must preview exactly what execution does. Queue/cancel/requeue must be idempotent. Derived actions (counter-attacks) are *computed* from the plan, never stored as player orders.
3. **Future AI uses the player's API.** AI issues orders exclusively through `SquadManager.queue_action` — no side channels. This protects law #2 forever.
4. **One question, one answer — never build a second seam for a fact the code already holds.** (Added 2026-07-28 after #102; elevated to a law because it has already bitten five times.) Before adding a field, flag, predicate, method, or *content convention*, find what already answers the question it would answer, and either extend that or explicitly retire it. **Grep the question, not the name** — the duplicate almost never shares a token with the original, which is exactly why it slips through (`requires_readiness` vs `knockback > 0`). **Suspect anything with an honest local motive**: the second seam always looks like it solves a different problem, and that motive is the disguise. **Prefer passing over looking up** — and its sharper form, learned from the #104 sweep: *if you can't reach the existing answer from where you're standing, take it as a parameter; don't rebuild it locally.* Four of that sweep's six findings sat at a layer boundary, where the second answer appeared precisely because the first wasn't in scope (`UnitInstance.get_max_hp()` can't see gear, so it re-derived CON without it — fixed in #106, it now takes `effective_con` as a parameter). A looked-up fact can silently diverge from a passed one; a parameter makes divergence unrepresentable (`Reach.get_affected_cells_from(…, attack)`, `WeaponInstance.base_damage(wielder, attack)`). This applies to authored content as much as to code — the content layer is where it's easiest to do accidentally, because it doesn't feel like architecture. If a second representation is genuinely warranted, **declare it out loud**: name both sides and state which is authoritative (the `objectives` vs painted `zones` guard under *Missions* is the model). The undeclared second source is the hazard; a declared one is a design. Why it's a law and not a sharp edge: these fail *late*, once both answers have callers, and the divergence can go **load-bearing** — #102's stale pick was the only reason secondary AoE resolved correctly, so the obvious cleanup would have broken more than it fixed. Prior instances, all now resolved: `LethalityRules.predict()` (preview and execution were two hand-synced ladders), `MENU_ORDER` vs `ACTION_DATA` order, `KineticMaceWeaponInstance`'s `knockback > 0` (#108 — fixed by adding `builds_readiness`, the missing third state that had made the shortcut tempting; **note the fix was to close the expressive gap, not just delete the duplicate** — a seam that can't say what content needs will grow another one), and the three-way `dead` split the persistence seam now guards with "don't add a fourth". A duplicate also propagates into FIXTURES: #108's `knockback`-means-spender assumption had been copied into four test files, none of which the production fix touched. **And a duplicate is rarely just wrong — it is often wrong in a way nobody measured**: #109's four walkability readers disagreed as filed, but the probe also found the "silent false" in the authoritative one was actually two runtime errors per call, and turned up a *fifth* site (`DevController.resolve_pending`) that didn't ask the question at all. Enumerate by re-deriving from the code, never from the issue's own table.

## Architecture map

- `game.gd` — input/game-state coordinator. **Reorganized 2026-07-26** into labelled sections (Lifecycle / Input / Turn flow / Modes / Queueing orders / The action-queue panel / Squads / Populating the board / Board visuals / Board queries), with three collaborators split out — each built in `_build_collaborators()` and holding a `game` back-ref, the `DevController`/`AIController` pattern: **`OrderExecutor`** (`actions/`, runs a squad's plan + the Crisis/downed fallout), **`HoverPresenter`** (`board/`, mouse → cursor/overlays/hover card/queue-row highlight, incl. the `_process` hover detection and the two `hovered_*` signals), **`MainActionMenu`** (`ui/`, now the *whole* menu system — construction as well as gating/dispatch). Still the heaviest file; prefer moving domain logic out to the owning system when touching it. **The current selection is STORED, not re-derived (#107): `game.selected_unit`** is set once in `_click_idle` (from `unit_at_pointer`) and read by all four mode click-handlers plus their three `HoverPresenter` twins. It replaced five hand-written `get_unit_at_cell(last_clicked_cell)` lookups that came in two contradictory precedences, one of which crashed on any unit selected via its shove-ghost. `last_clicked_cell` now means **only** "where the cursor sits in TILE_SELECTED" — a move path reconstructs from `unit.movement.cell`, which is what `compute_move_range` keyed `came_from` from. Never re-derive the selection from a cell; the cell and the resolver both drift. **Anything reaching back through the untyped `game` ref must annotate its locals explicitly** — `game.gd` has no `class_name`, so every `game.*` call is Variant and `:=` cannot infer from it; and a bare array literal passed that way is NOT coerced to a typed parameter (it fails at *runtime* — this is why `clear_selection_icons()` exists instead of callers passing the literal).
- `SquadManager` — **the only owner of squad lifecycle**: create/destroy/join/leave. Member removal funnels through `Squad._erase_member()` (the sole `members.erase` caller, mirroring `_add_member`); its callers are `_detach_from_current_squad()` (single-unit) and `disband_squad()` (bulk). Also home of order queueing (the Law #3 `queue_action` chokepoint), activation state, plan resolution, and counter-attack resolution. **Slimmed 770 → 516 lines 2026-07-26**: it had become the second dumping ground after game.gd — two of its sections were literally labelled *"migrated from game.gd (#22)"* — so three tenants moved out to **`SquadPlanValidator`** (plan-context validity, stamped onto each action), **`GroupMoveSolver`** (the pure formation solver; `queue_group_move` is the committing half), and **`ActionQueueDisplayEntry.build_for()`** (queue-panel layout, now beside the view model). All three are fully static — they read a plan and return a result, touching no squad state. **Queueing is STRICT and validity is one-way (2026-07-31): you cannot AUTHOR an invalid order, but a queued one can BECOME invalid.** `queue_action`'s third gate runs `validate_squad_plan_preview` and reads **the candidate's own `is_valid`, never `validate`'s return value** (that is whole-plan validity — one already-broken row would refuse everything queued after it). A break caused by a LATER re-plan leaves the order queued **in red, not deleted** — and for an *attack* that is the whole answer: a move is never refused for breaking a queued aim (dev fork, 2026-08-02, fork ii), the aim falls into invalid instead, because a planned heal does not lock its ally in place. The gate has a **second half** since then, `_candidate_aim_connects` — the whiff question, which only a candidate may ever be asked (see `SquadPlanValidator` below). This collapsed three hand-synced answers to "may this be ordered" (menu gate, click handlers, AI builders); `_click_choosing_move`'s private leader-range copy went with it. The hypothetical list displaces via **`Squad.displaces()`**, the same predicate `_queue_action` uses. **Batched orders skip the gate** — a formation is one decision, judged whole by `queue_group_move`. Refusals are silent (dev call). Rationale, forks and the three traps (leaf ordering, rollback scope, the knockback/resolve dependency): [`docs/build-log.md`](docs/build-log.md). **Order batching (`SquadManager.batching`, 2026-07-26):** Group Move queues N orders as ONE player action, so the expensive squad-level repaint runs once at the end rather than per order (a 5-member click went 232 ms → 65 ms). Every order still passes `queue_action`'s gates (Law #3), and `action_queued` still fires per order so cheap per-UNIT listeners don't miss anyone. **It is safe only while a batch stays synchronous** — if one ever spans a frame, the queue panel goes stale and Law #2 breaks. Invariants + measurements: [`docs/performance.md`](docs/performance.md).
- `Squad` — member list + `action_queue` (player-authored orders only). Enforces one order per action-type per unit (volley siblings exempt — see `_is_volley_sibling`).
- **Persistence seam (locked, #8):** transient `Unit` node holds battle-scoped state that resets each mission (element states, projected position, lifecycle ACTIVE/DOWNED/DEAD); persistent `UnitInstance` resource holds identity that survives missions (HP, fixed stats, limb loss, proficiency, **Will**, and `permadead`). **`permadead` (added 2026-07-27) is declared but deliberately UNWIRED** — nothing sets or reads it until there are missions and a persistent roster, at which point `Unit.die()` is the setter and roster assembly the reader. It is the *third* distinct "dead" on this seam and the only non-battle-scoped one: `UnitInstance.is_dead()` is `current_hp <= 0`, `Unit.is_dead()` is "went down the permanent path this mission", `permadead` is "never fields again". Don't add a fourth, and don't rename any of them to plain `dead`. New per-unit state picks its side by one test — *does it survive a mission?* No third store. **The seam now has NO exceptions** — the one that used to be documented here, `UnitInstance.stat_modifiers`, was **deleted by #112 (2026-07-28)**. It was a battle-scoped add/subtract bag (the Crisis surge) parked on the persistent instance purely because it was a stage of `get_effective_stat`'s chain, and it had already gone permanent once by having its reset missed. Temporary stats are now `StatEffect`s on the transient `Unit`, which is where the seam's own test ("does it survive a mission?") always said they belonged. **The effective-stat chain is base → limb → jobs → temporary effects → gear**, and only its first three stages live on `UnitInstance`: `Unit.get_body_stat()` adds effects, `Unit.get_effective_stat()` adds gear. **Because the chain's top stages live on `Unit`, every DERIVATION off a stat must live on `Unit` too, or take the finished value as a parameter** (#106: `UnitInstance.get_max_hp(effective_con)` and `get_mov(effective_dex)` are passed it; `get_effective_ldr`/`get_effective_def` sit on `Unit`; `Unit.set_current_hp(value)` is the one door for writing HP, since the clamp needs a ceiling `UnitInstance` can't derive). **Everything that follows a stat change runs in `Unit._settle_stat_change`** — enforce wear gates (stripping gear you no longer qualify for) → re-clamp HP → emit `stats_changed` — in that order, because stripping armour moves CON which moves max HP. Wear gates read `get_body_stat`, i.e. **never gear**, which is what keeps the strip to a single pass with no cascade. `stats_changed` is for READOUTS only; "may this be queued?" is a question about the *projected* stat and belongs to `SquadPlanValidator` ([#113](https://github.com/Phaazoid/Godoiosis/issues/113)). Doctrine + the save/load bug #106 caused: [`docs/design/stats.md`](docs/design/stats.md) → *One chain, one layer* and *Temporary stats*. Pinned by `tests/stats/test_stat_effects.gd` + `test_derived_stat_chain.gd`. (Cross-mission save/load is the future campaign layer; boundary is locked now so features land on the right side. See `docs/design/resolution-pipeline.md` → "The persistence seam".) **Scenario save/load round-trips the whole `UnitInstance` side since #83 (2026-07-22):** `ScenarioUnitEntry.capture_unit_state`/`apply_unit_state` own the unit-state snapshot (stats, current HP/Will, full inventory via `copy_equippable` + `equipped_index` — the old standalone `equipped_weapon` copy is retired — `worn_armor_index` (#89 — armor is carried in the SAME inventory as weapons but fills a DIFFERENT slot, so it saves as an index exactly like `equipped_index`, never as a second copy beside the carried one; **load assigns directly and never re-runs the wear gate** — a save is authoritative, and re-gating would strip armor off a unit whose stats drifted after saving), limb states with prosthetic re-link-**by carried instance**, not by template — two prosthetics built on one shared family template are different items and matching by template links both slots to whichever copy is found first (the TorvArm/TorvLeg bug, latent since #83 and unreachable until `install_prosthetic` got its first production caller) — proficiency, aura, **affinity** (`affinity_saved` is a DECLARED sentinel: an empty affinity is a legal saved value, the Rebecca rule, so emptiness cannot double as "unsaved" the way every other default in that block does; without it, aura was restored while affinity was not, leaving a loaded alchemist with a full pool, an empty affinity, and every carving silently unfireable), jobs), applied AFTER `initialize()`'s reset on load; `ScenarioManager` and the Play API's `board_builder` both call the same pair.
- **A save is a true MID-BATTLE SNAPSHOT since [#87](https://github.com/Phaazoid/Godoiosis/issues/87) (2026-07-30) — this REVERSES, for the save-resume axis only, the "battle-scoped `Unit` state deliberately stays out" line that used to end the paragraph above.** That line was right for a *mission boundary* and wrong for *pause/resume*: a different axis the seam had never separated. Weapon-state-only was explicitly rejected as a lopsided snapshot (mace charge kept, but downed units standing up and fires going out). Now round-tripping alongside the instance side: per-carried-weapon battle state (spring readiness, carbine magazine, mace charge, chainsword rev — **keyed by inventory index**, because a unit can carry two of a family and they must track independently, the same identity rule the prosthetic re-link learned), `element_states`, `lifecycle_state` + the downed clock, the three Crisis flags, `rally_count`, live `StatEffect`s **with their remaining countdowns**, `Squad.has_acted` (saved on the leader's `ScenarioUnitEntry`, applied after the squad rebuild), and `MissionController`'s captured zones + `contested` latch (on `ScenarioData` — `outcome` is deliberately NOT saved, since it is derived from those two plus the board and the next `check()` re-reaches it). **The seam is unweakened, and that is the whole mechanism:** nothing became `@export` where it lives — weapon state is still plain vars on `WeaponInstance` subclasses so `make()`/`copy_equippable()` re-arm every weapon, and lifecycle/states/Crisis/rally are still plain vars on the transient `Unit`. The snapshot captures them EXPLICITLY, exactly the way limb fittings have always been captured rather than serialized, so a mission boundary still resets for free. `WeaponInstance.capture_battle_state()`/`apply_battle_state()` are the family-agnostic seam (base returns `{}`); a **Dictionary** rather than one int even though every family tracks exactly one number today, because #108's lesson is that a seam which can't say what content needs grows a second one. Two structural rules, each pinned by a test falsified against its own bug: **(1) a restore replays the RESULT, never the EVENT** — `Unit.restore_lifecycle`/`restore_stat_effects` exist because `_go_downed()` would emit `went_downed` (ejecting the unit from a squad the loader hasn't rebuilt) and re-spend Will, and `apply_stat_effect()` would reseed a countdown from its `duration`; **(2) effects settle BEFORE gear and BEFORE HP** in `apply_unit_state` — settling enforces the wear gates, so a restored debuff applied after the armour strips gear the save says is worn, and a `+CON` effect moves the max HP the saved `current_hp` was measured against. `ScenarioManager.capture_scenario`/`apply_scenario` were split out of `save_scenario`/`load_scenario` (the shape `play/board_builder.gd` already had) so a whole board round-trips in memory — writing a test `.tres` into `Scenarios/` would be picked up by Mission Select and by #9's folder scan. **The mission-start RESET half stays real for the path that doesn't exist yet** (#70's roster → board): units arriving off a persistent roster carry no battle state by construction. Still deliberately out: the queued action plan (player intent, re-authorable, and serializing `BaseAction` graphs with live `Unit` refs is its own feature), `active_attack` (an aiming cursor), and projected-knockback cells (re-derived each resolve pass).
- **Actions are a small in-code registry, not a framework** (`BaseAction` → `MoveAction`, `AttackAction` (→ `CounterAttackAction`), `RescueAction` (#33), `RallyAction`, `IntimidateAction` (#61), `ReloadAction`/`RevAction`/`BurrowAction` (the weapon-signature verbs, #73/#84), `CaptureAction` (#96 — stamps its cell, zone name and the MissionController at queue time, so the resolver reads a frozen snapshot and a re-planned move can't quietly capture elsewhere); action-registry refactor 2026-07-20/21): the `ActionType` enum plus two declared `const` lists on `BaseAction` ARE the registry. `MAIN_ACTION_TYPES` (ATTACK/RESCUE/RALLY/INTIMIDATE/RELOAD/REV/BURROW/**CAPTURE**) drives `is_main_action()` — mutually exclusive, one per unit per turn, must come *after* any move (locking one removes the move option). `SIDE_CHANNEL_ORDER` (RESCUE/RALLY/INTIMIDATE/RELOAD/REV/BURROW/**CAPTURE** — stored orders that bypass `PlanResolver`) is iterated by THREE places at once: `OrderExecutor.execute_orders`'s phase loop, `ActionQueueDisplayEntry.build_for`'s queue-panel sections (header = the enum's own key string), and the headless Play API's `_describe_plan`/`execute()` — a new type registered there gets a phase, a queue section, and Play support for free, with no per-type mirror to add. Per-action **queueing requirements** live on the action itself via the `actor_can_perform()` virtual (move-before-main on `MoveAction`, verb locks on `AttackAction`/`RescueAction`, the Will-room check on `RallyAction`, the ability gate on `IntimidateAction`) — `SquadManager.queue_action` calls it once as the sole Law #3 chokepoint instead of a per-type match arm. `game.gd`'s `GameState.PICKING_TARGET` + `enter_target_pick_mode(candidates, on_pick: Callable)` is the one generic "pick a highlighted unit" flow — rescue, intimidate, squad-up, and join-squad all ride it (candidates from a predicate query, `on_pick` closes over the acting unit); it deliberately does NOT extend to `CHOOSING_MOVE`/`CHOOSING_GROUP_MOVE` (live path-preview IS the feature) or `ATTACK_TARGETING` (directional aiming, not a unit pick) — those stay bespoke on purpose. **Menu system lives in `MainActionMenu` (`Classes/ui/MainActionMenu.gd`), pulled out of `game.gd` 2026-07-22 and completed 2026-07-26** — it holds a `game` back-ref (same pattern as `DevController`/`AIController`: instantiated and `.game = self`'d in `game._ready()`) for everything it reads or dispatches into. It now owns menu **construction** too (`show_main_menu`/`show_attack_menu`/`show_weapon_action_menu`, plus `begin_attack`), so `game.gd` holds no menu knowledge at all: three near-identical copies of the `ActionMenuController` boilerplate collapsed into `_open_menu()`, and two copies of the fireable-or-disabled row into `_attack_entry()`. Menu print order is just its `ACTION_DATA`'s declaration order (no separate `MENU_ORDER` list to keep in sync — an entry left out of `ACTION_DATA` can't silently vanish from the menu because there's nowhere else for it to be declared). New-action checklist: the class (with its `actor_can_perform()` override) → one line each in `MAIN_ACTION_TYPES`/`SIDE_CHANNEL_ORDER` → **the player surface** → **its AI stance** in `AIArchetype`'s `MAIN_ACTION_PRIORITY`/`MAIN_ACTION_NEVER` (the law test fails until it lands in exactly one, per archetype) → a `SquadPlanValidator` clause only if the action has plan-context (adjacency/occupancy) rules, mirroring `_revalidate_rescues`/`_revalidate_intimidates`/`_revalidate_captures`. **Queueing a no-argument verb goes through `game.queue_simple_action(unit, type)`** (2026-07-28): `queue_rally`/`queue_reload`/`queue_rev`/`queue_burrow` were four byte-identical copies and are now one path with a `_make_simple_action` factory — a `match`, not a class dictionary, because class references aren't const-foldable and a dict lookup loses static typing. Verbs taking a real argument (rescue/intimidate take a unit, capture takes a cell) deliberately stay separate; forcing them through one signature just moves the branching into a parameter bag. **The player surface forks by kind since the 2026-07-24 Weapon Action refactor:** a *general* verb (rescue/rally/…) still takes a top-level `MainActionMenu` slot — menu-id const + `ACTION_DATA` entry + gate clause in `populate()` + dispatch arm in `on_pressed()`; a *weapon-specific* one (Rev/Reload/Burrow, and any future family signature) instead adds a branch in `MainActionMenu.show_weapon_action_menu` + its `_pick_weapon_action` match, and an inert `can_<verb>()` default on `EquippableData` (overridden on the family's `WeaponInstance` subclass), a thin `can_<verb>_weapon()` delegator on `Unit`, and one `or can_<verb>_weapon()` in `Unit.has_weapon_actions()` — the top-level menu shows only the single "Weapon Action" entry no matter how many signatures exist. Either way the queued `ActionType` is unchanged, so registry/resolver/queue/AI wiring is identical. Registry completeness is pinned by `tests/law/test_action_registry.gd` (every `ActionType` must land in exactly one of the fixed pipeline or `SIDE_CHANNEL_ORDER`) and `tests/squad/test_action_queue_display.gd` (queue sections follow registry order regardless of queue insertion order). AoE = a **volley**: one `AttackAction` per victim, all sharing a `volley` array; secondaries set `is_secondary_hit` and skip the lunge animation.
- `Reach` (`weapons/`, **static**) — weapon-aware attack geometry: `get_attack_cells_from` (facing-specific), `get_all_attack_cells_from` (union over 4 facings, for overlays), `get_affected_cells_from` (AoE), `is_directional_attack()` (does this attack's pattern aim by facing?). **Every one of them TAKES the `AttackData` it is reasoning about (#102, 2026-07-28)** — they used to look it up themselves via `Unit.get_fired_attack()`, i.e. the live `active_attack` pick, while the queued order carried its own frozen `AttackAction.fired_attack` stamp; geometry answered from one source and damage from the other, and a leftover pick re-shaped stored blasts and granted counter reach the counter couldn't fire with. - **Targeting modes (#25):** patterns are **directional** (`AttackPattern.is_directional()` true — forward line/wide: the player points a cardinal direction and the whole spread fires; the pointed cell need not be a spread member) or **point** (false — Manhattan / no weapon: the hovered cell itself must be in range). - **Weapons are template + instance, and the attack is its own content (#59 then #72, mirrors the jobs id-reference pattern + the rune/carving system):** `AttackData` (`extends Resource`) is the shared skeleton anything a unit can fire carries — `display_name`, `power`, `attack_pattern`, `can_counter`, `hits_allies`, `targets`, **`heals`** (BUILT 2026-07-30: an attack is EITHER damage OR a heal, never both — the heal reinterprets the same base-damage number as HP restored, capped at max HP, short-circuiting `PlanResolver._resolve_one` before DEF/elemental/lethality/knockback ever run, since none of those are questions a heal raises; see [`docs/design/resolution-pipeline.md`](docs/design/resolution-pipeline.md)'s 2026-07-30 amendment) — with damage math deliberately OFF the base (carvings scale off aura, weapon attacks off the wielding weapon's blend + mods). `WeaponAttackData extends AttackData` adds only `elemental_damage_type`; `TransmutationData` (the rune carving) is its sibling subclass. `WeaponData` is the shared family TEMPLATE (family base like `ChainSword.tres`, or a named prototype) — `main_attack: WeaponAttackData` (the one REQUIRED attack, a curated resource the family points at — never a bare array slot — used by default aim and ALWAYS by counters) + `extra_attacks: Array[WeaponAttackData]` (no count cap; mod spaces gate access), plus `scaling_blend` (a `Dictionary[Stats.Stat, int]` % blend across STR/DEX/PER/CON), `weapon_type`, `is_prototype`, and the `weight` it inherits from `Item` (was its own `base_weight` until 2026-07-27). It is NOT equippable (extends `Item`, not `EquippableData`) and is never duplicated — a unit that owns a template edits it live for every weapon built on it, main attack included. `WeaponInstance` (extends `EquippableData`, what a unit actually carries) holds a direct `template: WeaponData` ref plus its own `space_1`/`space_2`/`space_3` (fitted `WeaponModData`, the only true per-weapon state) and computes the effective view (`base_damage`/`get_elements`/`hits_map`, all taking an optional `attack: WeaponAttackData` override that defaults to main when null) from template + active modules. **Never `duplicate(true)` a `WeaponInstance`** — that deep-copies the shared template and severs the sync; use `copy_equippable()` (the `EquippableData` virtual every equippable overrides as needed — `WeaponInstance`'s keeps `template` shared and copies spaces shallowly, the default falls back to `duplicate(true)` for `RuneData`). In battle, `Unit.get_fired_attack()` (live pick else first-channelable-carving/main) answers **"what would this unit fire if it declared right now"** — read at AIM time only (the targeting overlay, the hover preview, and `AttackAction.declare()`'s stamp). It is deliberately NOT what reach and ally-splash read: since #102 those take the `AttackData` as a parameter, so a stored order's geometry comes off its own stamp and a counter's off `get_counter_attack()`. `active_attack` is therefore a pure **aiming cursor**, cleared when targeting ends (`game._clear_aiming_pick`, from `exit_current_mode` while the state is still ATTACK_TARGETING) — a reset that was only safe to add *after* the parameterization, because until then the stale pick was the one thing making secondary AoE resolve correctly. `Unit.get_counter_attack()` is a deliberate exception — weapons always counter with main, ignoring any live pick (a rune counters with whatever it fires; overwatch-style alt-attack countering is future scope, #73) — and since #84 that main must also be FIREABLE (`Unit.attack_source_can_counter()` checks readiness), so an empty Carbine magazine or a sprung Springspear stops countering, and a counter that does land spends whatever its main consumes — and the chosen `AttackData` is stamped onto `AttackAction.fired_attack` at declare time so the resolver reads a frozen snapshot, never re-derives (Law #2). `AttackPattern` resources stay pure **geometry** (selectable cells vs affected cells), unaffected by any of this split; terrain/LoS filtering belongs at the resolution layer when it arrives (planned weapon flag: `arcs_over_obstacles`). **Per-attack readiness BUILT 2026-07-22 (#73), completed by a third flag 2026-07-28 (#108):** `WeaponAttackData.requires_readiness`/`consumes_readiness`/**`builds_readiness`** (all default `false`) author a wind-up/recovery economy — gated / spends / banks; the actual readiness STATE lives on `WeaponInstance` itself, not `Unit` (a unit can carry more than one of the same weapon — they must track independently) and not the shared template (battle-scoped). `WeaponInstance.make()` dispatches on `weapon_type` to build the right concrete subclass — every family has one (`SpringspearWeaponInstance` plus six pure pass-throughs added by [#82](https://github.com/Phaazoid/Godoiosis/issues/82), 2026-07-22), and the base class declares the readiness surface as no-op virtuals (`is_attack_fireable`/`consume_readiness_for`), so families with no signature mechanic yet pay nothing — **and as of 2026-07-27 the argument-free self-ability verbs (`can_reload`/`reload`/`reload_label`, `can_rev`/`rev`/`tick_rev`, `can_burrow`) sit one level higher still, on `EquippableData`**, so `Unit` delegates to whatever is equipped without casting. Only the two `WeaponAttackData`-taking methods stayed on `WeaponInstance`: widening their parameter to `AttackData` for the base would break every family override's signature. **The bool generalizes to a counter without touching the seam** — `CarbineWeaponInstance.shots_remaining` (#84) reads the authored flags as a magazine, and `KineticMaceWeaponInstance.charge` reads them as a bank. The mace only became true of that in #108: it had inferred its charge-spender from `knockback > 0`, a private predicate for a fact these flags already carried, which made authoring a readiness flag on that family silently inert and would have rewired the economy the moment any second mace attack gained knockback. `builds_readiness` is the state whose absence caused the shortcut — the seam could say "needs one and spends one" but not "banks one". Doctrine, now authored on Smash rather than emergent: **a counter banks charge** (it stamps main, main builds; the swing is what stores the energy). `Unit` only holds thin delegators reading whatever's equipped. An unmapped `weapon_type` is a loud failure (`push_error` + `null` return from `make()`), never a silent fallback. **That battle state now SAVES without becoming persistent (#87, 2026-07-30):** `capture_battle_state()`/`apply_battle_state()` are a third family-agnostic virtual pair beside the readiness and status ones (base returns `{}`), and the fields themselves stay non-`@export` — so `make()`/`copy_equippable()` still re-arm every weapon, and only an explicit scenario snapshot puts a magazine or a rev timer back. See the persistence-seam bullet above. See [`docs/build-log.md`](docs/build-log.md) → *Weapons* for #82's full build note.
- Execution order: moves (parallel) → attacks (sequential — combo order matters for future elemental) → counters (sequential) → rescues (sequential). Pinned by `tests/squad/test_downed_ejection.gd`. - `TurnManager` (`flow/`) — the faction turn cycle, **rebuilt from the board each hand-off** (refactored 2026-06-24). Tracks the **active faction by value** (the old two-sided `TurnPhase` enum is gone); `end_turn(present_factions)` recomputes the live order as `Team.all_factions()` (enum order) ∩ factions present, then advances past the active one. Handles **any number of teams**, and the cycle **builds itself from what's on the map** — a newly-spawned faction enrolls at the next hand-off, a wiped one drops out. **Single source of truth = the `Team.Faction` enum** (add a member → it's in the rotation). Trade-off: turn order follows enum-declaration order, which is **append-only** for save-compat, so a new faction acts *last* unless you migrate enum values; and presence *is* eligibility (a `NEUTRAL`/`OTHER` faction with units would take a turn — add an explicit opt-out if you ever want non-acting scenery). `game._on_turn_started(faction)` **auto-skips** a faction with no `is_active` units after ticking its downed clocks — guarded by `_board_has_active_units()` so an all-downed board can't infinite-loop; `start_faction_turn(faction)` replaced the old player/enemy split. Saved turn state = `ScenarioData.active_faction` (authoritative; the `turn_phase` field was removed), restored via `set_active_faction`. The headless Play API mirrors this exactly (`play_session.end_turn` derives present factions + runs the same guarded skip).
- **Missions — the closed loop (`flow/`, #96, all four slices built 2026-07-28; canon [`docs/design/missions.md`](docs/design/missions.md)):** the game can be **won and lost**, and it now BOOTS into `MissionSelectScreen` rather than a board (`TestBoard` retired as the boot path; `game.spawn_sandbox()` is its one remaining call site). Four parts, split on purpose. **`MissionRules`** (static, pure, `extends Object` — LethalityRules' shape) is the whole rule: `evaluate(board, contested, progress) -> ONGOING/VICTORY/DEFEAT`. **`MissionController`** (a game collaborator, the DevController pattern) holds everything a pure predicate cannot — the ended-latch, the `contested` latch, captured-zone state, the objective composer, and what the game DOES about an ending (`GameState.MISSION_OVER`/`MENU` → `_board_locked_for_player`, the banner, the return path). **`ScenarioData.objectives: Array[MissionRules.Objective]`** is what a mission REQUIRES (ROUT/CAPTURE/EXTRACT, composed by AND, edited in the dev Scenario tab); **`ScenarioData.zones`** is WHERE, via `ZoneManager.Kind`. **There is no `MissionData`** — a mission and its board are 1:1, so a wrapper resource is an extra hop, not a template/instance split (dev, reversing the original plan). Objectives are **declared explicitly, not inferred from painted zones**: rout has no geometry to paint, a mis-picked Zone Kind would otherwise silently rewrite the win condition, and geometry couldn't be authored ahead of its rule. Guard for the resulting second source of truth: a declared objective with no painted zone reads **PENDING, not NONE** (the map really is unwinnable — silently dropping it would convert a broken map into a different playable one), warned live in the Scenario tab and `push_error`'d by `set_objectives`. Doctrine, all load-bearing: **(1) an authored objective is the ONLY way to win** — routing a capture map wins nothing unless ROUT is ticked (lockout is a level-design problem, not a rule that hands out a consolation win); **(2) DEFEAT is checked first** — last player unit and last hostile falling in the same pass is a LOSS; **(3) `contested`** — "both sides were up at once", latched by the CALLER because the board can't tell *wiped out* from *never here* (`present_factions` drops an all-dead faction) and a LIVE read could never end a mission, which is what keeps **dev sandbox boards inert with no `dev_mode` flag**; **(4) extraction counts the DOWNED** — alive and inside the zone means they got out; what blocks it is a living unit OUTSIDE, and a downed one there needs a rescue. `check()` fires at the three points board state changes and settles — end of a resolution pass (`OrderExecutor.execute_orders`, *before* its squad-validity guard so a squad that wiped itself can't skip it), after the end-of-turn burn, and turn start *after* the downed clocks tick. Pass-end not turn-end: a friendly AoE can down your own last unit mid-pass. `AIController.take_faction_turn` guards on `is_over()`. **`MissionController.reset()` (from `ScenarioManager.clear_board`) is the first thing in the codebase to ever fire a mission-start event** — the [#87](https://github.com/Phaazoid/Godoiosis/issues/87) seam whose rule had never actually executed; keep the split when #87 lands (**loading a mid-battle save RESTORES, starting a mission RESETS**). NB `MissionRules.Progress` (NONE/PENDING/MET) and `MissionRules.Objective` (what's required) are different enums; `Progress` was called `Objective` in slice 1. Tested: `tests/flow/test_mission_rules.gd` (22) + `tests/ai/test_zone_manager.gd` (12) pin the rule and the geometry, and **`tests/flow/test_mission_controller.gd` (31, added 2026-07-29) pins the controller** — both latches, the objective composer's AND, capture state, extraction's downed-counting, declared-but-unpainted reading PENDING, and the MISSION_OVER board lock. It runs a real game scene (the #114 fixture) and is falsified against seven mutations, one per doctrine. Lose conditions beyond the last unit falling, and authorable OR-composition, are [#101](https://github.com/Phaazoid/Godoiosis/issues/101).
- **Archetype AI (`ai/`, #29, built 2026-07-01):** `AIController` (child of Game) runs AI-controlled factions — per squad: fixed-duration camera `pan_to` the leader → archetype plans → the same `OrderExecutor.execute_orders` the player's Execute button calls. Orders go through `SquadManager.queue_action`/`queue_group_move` ONLY (Law #3). **An AI squad's turn must ALWAYS terminate (#103, 2026-07-29):** `execute_orders`' invalid-plan guard is a *player affordance* — flash the bad rows, leave the plan queued, hand control back — and its early `return` sits above everything that ends a turn. An AI squad refused there has nobody to hand control back to, so it left the board dressed for a plan that never ran (ghosts, path arrows, `get_projected_destination()` pointing at an unreached cell — which is what enemy AI then swung at) with `has_acted` false and `active_squad` still set; nothing in the cycle mutated the state that produced the plan, so the identical plan was refused **every turn, forever**. Its scope must be **every MOVE in the queue, not just the batch's own**: a member the solver could place nowhere has no move in the batch, it keeps the hold order it already had, and that is the order cohesion refuses. Root cause of the illegal plan: `GroupMoveSolver` places a member nowhere when no cell inside the leader's NEW cohesion range is free, and it then keeps the hold-position order `setup_hold_move_actions` gave it — which `SquadPlanValidator._check_leader_range` refuses. **That root cause is UNCHANGED, but the player no longer meets it (2026-08-04 — see the cohesion rule under `squads/` below).** `GroupMoveSolver.followable_destinations` paints such destinations red before the click, so a human is refused at the overlay; the AI does not read that overlay, authors the refusal anyway, and everything in this paragraph still describes its path exactly. **That is NOT a group-move bug** — a single individual leader move produces the identical refusal (measured), because the filler is inserted by a `game.gd` signal handler regardless of who authored the move. Per-unit AI movement is [#117](https://github.com/Phaazoid/Godoiosis/issues/117), the evergreen AI catch-up tracker. ## Sharp edges (each of these has already bitten once)

- **Grant/copy an equippable via `copy_equippable()`, never a bare `duplicate(true)`** (revised #59 — this used to say the opposite). `RuneData` still wants a full deep copy (its base implementation), but `WeaponInstance` overrides it to keep `template` a SHARED reference while its own `space_1/2/3` copy shallowly — a generic `duplicate(true)` would deep-copy the template too and silently fork a weapon off its family.
- **gdUnit4's `Total execution time` line is not wall clock** — it read `1min 55s` for a 573-case run right after a cache clear, then `12s` for the identical run warm. It is not a usable number in either direction; trust `run_tests.ps1`'s own stopwatched `Elapsed` line instead. **Measured on `Elapsed`: full run 153–157s** (eleven consecutive runs 2026-07-26, 605 cases; independently 158s at 610 cases on 2026-07-27), **`fast` 42s** (156 cases), **51s for three areas together** (2026-07-27). That is **~0.26s/case across every tier** — a flat per-case cost, not a startup overhead you can amortize, and ~7x the "~0.035s/case warm" this note used to claim. The same suite passes **Linux CI in a 34s total job** while the case count only grew 573 → 610, so it is a Windows/environment factor, not suite size — **cause unconfirmed** (antivirus scanning the repo tree and `.godot` cache state are the untested suspects). The old "~20s full / ~7s fast / ~3-5s per area" figures came from trusting gdUnit4's warm number; all corrected 2026-07-27. Practical consequence: **no tier is a fast inner loop right now** — pick the narrowest area you can. Re-measure before ever acting on "the tests are getting slow". **Observation, same day (2026-07-27, Unit.gd review session): three consecutive full runs came in at 19.5s / 19.9s / 20.9s at 610–612 cases — ~8x faster than the measurements above, on the same machine, hours apart.** The session had just run `godot --headless --import` (needed to register a new `class_name`), and the speed persisted across later runs that did not re-import. That is a data point for the `.godot`-cache suspect, **not** a correction: **this entry stands as written**, because the slow behaviour has recurred repeatedly and the fast state has not been shown to last. If you find yourself waiting 2.5 minutes again, an import pass is worth trying before anything else. **Third data point (2026-07-29, #103): 49.3s at 803 cases = 0.061s/case, again after an `--import` pass earlier in the session** (run to generate a new test file's `.uid`). Note the direction: the case count grew 610 → 803 while wall clock fell 155s → 49s, which is more evidence that suite size is not the variable. Two of two fast runs followed an import; the hypothesis is holding but still uncontrolled — nobody has yet run the same suite slow-then-import-then-fast in one sitting, which is the measurement that would settle it. **Fourth data point (2026-08-02, #128): 53.9s at 937 cases = 0.058s/case, again after two `--import` passes earlier in the session** (run to check for script errors and to verify a UID fix). Three of three fast runs have now followed an import, and the per-case cost has sat within 0.058–0.061 across the last two while the suite grew 803 → 937. Still uncontrolled in the same way — nobody has deliberately reproduced the SLOW state to import out of it — but the import-first advice above has yet to be contradicted.
- **`game.clear_selection()` runs on every menu PICK, not just on cancel** — `ActionMenuController` emits `cancelled` *before* `action_selected`, so `MainActionMenu._on_menu_cancelled` fires it on the way **into** whatever mode you just chose. Anything that must survive into a mode therefore cannot be cleared there: `exit_current_mode()` is the mode-ending path, and that is why `last_clicked_cell` (and, since #107, `selected_unit`) are nulled there instead. **Bitten twice** — #105 (clearing the knockback/terrain previews there wiped the shove ghost the instant you opened Attack, making its landing tile unaimable) and #107 (clearing `selected_unit` there crashed Move/Group Move and silently no-op'd Attack). **Both are now pinned by `tests/ui/test_game_scene_smoke.gd` (#114, 2026-07-29)** — the claim that the game scene segfaults inside gdUnit4 was **false**, and that layer is ordinary-suite testable; see `tests/README.md` → *Testing the game scene*. The one trap to respect when adding cases there: a test that sets `game.game_state` directly instead of firing a real menu pick **cannot see either bug**, because `clear_selection()` only runs on the `cancelled`-before-`action_selected` ordering.
- `.tres` files omit properties at default values — an "empty-looking" resource may just be unsaved-at-defaults.
- **`load()` serves the resource CACHE, so overwriting a `.tres` at runtime needs `take_over_path(path)` first** (measured 2026-07-29, #99). Save a *fresh or duplicated* resource over a path that has been `load()`ed this session and the file on disk is written correctly — but every later `load()` of that path keeps handing back the **stale pre-edit object**, so the tool shows old content until a restart. `CACHE_MODE_IGNORE` reads the new file but forks a second object and leaves the cache stale for everyone else; `take_over_path` is the only call that repairs the entry, and it is a **safe no-op when the resource already owns the path** (verified), so it can go on every save site unconditionally. The rule: *whoever writes a path must claim it.* This silently affected `ScenarioManager.save_scenario` (re-saving a loaded scenario made Load **and the F2 reset** replay the pre-save board) and both dev editors; all three now route through it. Editing a resource **in place** — the Attack Editor's FAMILY_MAINS mode, which mutates the live cached `main_attack` — was already correct, because the object being saved *is* the cache entry.
- **`DirAccess.get_files()` on `res://` returns PACKED names in an exported build, not source names** (found by the first export, 2026-08-04, #130 → [#141](https://github.com/Phaazoid/Godoiosis/issues/141)). A text resource comes back as `Foo.tres.remap` and an imported asset as `Mage.png.import` — the source `.png` is never in the pack at all, only `.godot/imported/*.ctex`. So **every scan that filters on a source extension matches nothing once exported**, and eleven of them do: the ten `.tres` catalogs (weapons, armor, jobs, runes, transmutations, elemental + terrain reactions, mods, attacks, scenarios) and `SpawnTool._build_sprite_catalog`'s `.png`. The symptom is not a crash, it is an **empty game** — Mission Select lists nothing and every catalog is silently empty; `SpawnTool` is the only one that turns it into a visible error (`keys()[-1]` off its empty dropdown). **The suite is structurally blind to this** — it runs in the editor context, where every scan is correct, so nothing here is caught by a green run. **FIXED 2026-08-04 by `Classes/core/ResourceDir.gd`**, the one answer to "which resource files of this extension live in this folder?": it strips the packed suffix, de-duplicates (the editor holds *both* `Mage.png` and `Mage.png.import`) and sorts, so discovery is deterministic in every context. All eleven scans call it; **never re-derive a folder listing beside it.** `project.godot` briefly carried `export/convert_text_resources_to_binary=false` as a stopgap — that is **reverted, deliberately**: with the strip in place the default (binary, `.remap`) is both faster and the *harder* path, and leaving it off meant the `.remap` branch never executed in any real build, i.e. coverage that only looked like coverage. Note `project.godot` cannot carry an explanatory comment — Godot rewrites the file and strips them — which is why this note lives here. What the suite CAN pin is the normalization itself: `tests/core/test_resource_dir.gd` uses the real `.png`/`.png.import` pairing (54 of each) and is falsified against its own bug — a no-de-dup mutant returns 108.
- **`OptionButton.add_item` auto-selects the first entry** (`selected` goes -1 → 0 on the first add; `clear()` resets to -1). So a dropdown rebuild that re-selects by name **must `select(-1)` before its match loop**, or a name that no longer exists leaves the control silently pointing at whatever sorts first. Load-bearing wherever a dropdown selection is a write target rather than a filter — the dev tabs' Update button overwrites the file the dropdown names (#99).
- **A code-built full-screen Control needs `set_anchors_and_offsets_preset`, never `set_anchors_preset`** (measured 2026-08-04, #132). Anchors alone leave a freshly-`new()`ed Control added under the `ui_layer` CanvasLayer at **0x0**, so its dim never covers anything and its `CenterContainer` centres on the origin — the modal renders in the top-left corner. Measured: `PauseMenu`, `MissionEndBanner` and `CrisisPrompt` were all root=(0,0) with their panel at (0,0), against a 1152x640 viewport; `MissionSelectScreen` was the only one correct. It is **not** limited to Controls built during `_ready()` before the SubViewport has a size, which is what that file's own SIZING note claimed until this was measured. `ActionMenuController._backdrop` still uses the anchors-only form **on purpose for now**: it is therefore inert, and making it full-size would newly start eating clicks, which is a behaviour change needing its own look. Related: three of those modals are copy-paste siblings (dim + CenterContainer + PanelContainer), which is exactly how one sizing mistake reached three files — a shared modal scaffold is the standing follow-up.
- UI rule: **scene for static, code for dynamic.** Fixed controls live in `.tscn`; data-shaped UI (editor fields, stat rows) is generated.
- Plain `Panel`s report 0×0 minimum size for absolutely-positioned children inside containers.
- `Unit.has_squad()` means "has squad*mates*" (members > 1). Every unit always belongs to exactly one managed squad, even solo.
- Godot ternary exists (`x if cond else y`); typed dictionaries (`Dictionary[String, int]`) are used throughout — keep chains typed end-to-end.
- **Retyping a persisted `@export` field from String to an enum is a *data* migration, not just a code change.** Godot silently *drops* type-mismatched values when loading a `.tres` (a saved `Dictionary[String, int]` won't populate a `Dictionary[Stats.Stat, int]` — it loads empty) and *strips* them on the next resave. After retyping such a field (stat-dict keys, `weapon_type`, `scaling_stat`), rewrite every saved `.tres` to the enum form — enums serialize as plain ints (`base_stats = Dictionary[int, int]({0: 20, …})`, `weapon_type = 1`). Bit 2026-06-19 (#7 fallout): every unit loaded with 0 stats → LDR 0 → nobody could move; the only intact copy of the string data was git HEAD, since the migration commit never touched the `.tres`. Migrate from HEAD, not the working tree (Godot may have already stripped it).
- **Dev tools = separate OS window; the game is wrapped in a SubViewport (June 2026 refactor).** Scene tree (`Main.tscn` is the main scene): `Main` (Node) → `GameContainer` (SubViewportContainer, Stretch on, texture_filter Nearest) → `GameView` (SubViewport, embed ON) → `Game` (game.tscn instance); `DevOverlay` (a `Window`, embed ON) is a sibling of `GameContainer` under `Main`. Cross-boundary refs: `game.gd` → `get_node("/root/Main/DevOverlay")`; `dev_overlay.gd` → `get_node("../GameContainer/GameView/Game")` (+ `…/Game/ScenarioManager`). Gotchas this created — all already handled, **do not undo**: (1) SubViewports default to LINEAR filtering; `game._ready` sets the viewport default to Nearest via `RenderingServer.viewport_set_default_canvas_item_texture_filter(get_viewport().get_viewport_rid(), RenderingServer.CANVAS_ITEM_TEXTURE_FILTER_NEAREST)` — per-node `texture_filter` only patches part of the tree (the chain breaks at any `CanvasLayer` / non-CanvasItem ancestor). (2) Embedded popups don't auto-dismiss on outside-click (input is forwarded through the container); `ActionMenuController._input` closes them manually. (3) Stretch mode = `disabled`; UI is real pixels — no hardcoded pixel positions (use viewport-relative; the hover panel's old `BOTTOM_LEFT_POS=410` broke on a viewport-height change). (4) Any new subwindow UI (PopupMenu/dialogs) inherits these quirks — prefer Control-based menus.

### Gameplay / model

- **Weight is tracked but feeds no rule, on purpose.** `weight` lives on `Item` (so anything inventory-able can carry mass) and `Unit.get_weight()` sums the whole inventory, but nothing reads the result — the Weight×MOV step was **unwired** 2026-07-27 rather than tuned. Two things were corrected at once that day: CON was removed from the calculation (it was drift — Weight is gear-only, and STR-as-*capacity* is the named candidate if it ever gets teeth), and the old `_gear_weight()` summing only the equipped weapon became a full inventory sweep, which is what finally gave armor mass. Live options are **wire it to something** or **cut it entirely**; both are open (dev, 2026-07-27) — with one concrete proposal on the board since 2026-07-29, [#120](https://github.com/Phaazoid/Godoiosis/issues/120) (shove resistance: push tiers + weight-modified knockback distance, interlocked with #116's ledge kill). Doctrine + the retraction record: [`docs/design/stats.md`](docs/design/stats.md). Nothing is authored yet — every `weight` is still 0, so the readout reads 0 until content lands.
- **Transmutation strain is computed but never charged.** `forced_points`/`strain_cost` correctly gate `can_channel`'s leeway budget, but the resolver-stage affordability check + HP payment is deliberately deferred so the access rules could be playtested alone — [#76](https://github.com/Phaazoid/Godoiosis/issues/76) (audit A7).
- **Intimidate's preview is accurate but shallow** — it shows the Will drain correctly, but doesn't thread into `PlanResolver`'s same-pass maim-cliff prediction the way a queued attack does (#61, flagged at build time, not a regression).
- **Counter-gating on the two-handed verb lock** is deferred to the two-handed weapon content pass. Nothing is observably wrong today because no weapon carries the flag yet.
- **The which-limb maim rotation is VERY subject to change** (dev, 2026-07-15) — a story-layer "main humor" selector is on the table. Any replacement must stay deterministic + previewable (Law #1). Tracked with the aura-tax tiebreak as [#77](https://github.com/Phaazoid/Godoiosis/issues/77).

- **The AI can't use most signature mechanics** — and as of 2026-07-29 this whole class of debt has a standing home, [#117](https://github.com/Phaazoid/Godoiosis/issues/117) (*evergreen*), on the premise that the AI is permanently behind the feature set: every system we add creates AI work that lands after the system ships. ### Tooling / tests

- **[#80](https://github.com/Phaazoid/Godoiosis/issues/80) residue — narrower than it used to be** (hand-typed `Classes/dev/` territory). `UnitEditorTool._entry_matches()` compares `item.template == entry`, and a scenario-embedded weapon's template is inline and scenario-local, so it can never match a catalog entry. What's left is only that you **can't re-select** such a weapon in the inventory dropdown. You *can* see it: `_add_inventory_section` renders a `holds: <name>` label whenever no entry matches, so the old "(empty)"-for-a-weapon-you-hold symptom is **fixed** (landed in `9dffc3a`; this entry claimed otherwise until 2026-07-27). Granting a NEW weapon has always worked. Low severity — accepted-as-is unless a scenario-local weapon ever needs re-picking.
- **[#93](https://github.com/Phaazoid/Godoiosis/issues/93): the engine can segfault on SHUTDOWN after a clean pass** (`0xC0000005`). Root-caused 2026-07-29: **a gdUnit4 teardown bug, not ours and not in the scenario-load path** — the same work under a plain `--script` probe exits 0, it still reproduces on gdUnit4 v6.2.0 stable, and the minimal repro is a four-line suite that loads nothing (`var item: EquippableData = null` + `item is WeaponInstance`, which does not even have to execute). What leaks is gdUnit4's own script graph; zero Iosis scripts leak. **No test result is ever affected**, and `run_tests.ps1` now reports gdUnit4's own verdict instead of the process exit code, so it no longer lies in either direction — a run that dies *before* reporting still fails loudly. Full write-up + the exit-code table: `tests/README.md`.
- **Armor acquisition is dev-tool-only**, same as weapon mods and prosthetics. The Play API also has no wear/remove commands, so headless coverage of the equip surface rides on unit-level tests.
- **The Play API sees rout and defeat only (#96).** `play_session.mission_outcome()` calls the same `MissionRules.evaluate`, but with no `MissionController` out there it always passes `Progress.NONE` — so an authored CAPTURE/EXTRACT objective is invisible headlessly and every board evaluates as a rout map. There is also no `capture` command (the action itself would execute fine — `SIDE_CHANNEL_ORDER` gives it a phase for free). Closing it means teaching the headless board about zones + captured-zone state.
- **No mission-status UI (#96).** Nothing on screen says what a mission's objectives are or how far along they are — you find out by winning. It is the prerequisite [#101](https://github.com/Phaazoid/Godoiosis/issues/101) names (a turn clock forces a persistent surface), and the reason the queue still doesn't preview a win.
