# Iosis — Project Guide

Tactical RPG (Fire Emblem-influenced), Godot 4.7, GDScript. Solo hobbyist developer.

## How this file works (read first)

This file holds the **rules** and **short pointers**. The long versions:

- [`docs/workflow.md`](docs/workflow.md): the contract, GitHub workflow, branches/versions and content rules in full.
- [`docs/architecture/`](docs/architecture/README.md): one file per domain, the long version of every *Architecture map* and *Code layout* entry (reasons, measurements, bugs, rejected designs).
- [`docs/sharp-edges.md`](docs/sharp-edges.md): the story behind every sharp edge.
- [`docs/build-log.md`](docs/build-log.md): pure chronology.

A pointer reads `→ docs/architecture/ui.md → *ModalLock*`: file, then section heading.

- **Before editing code in an area, read its section in `docs/architecture/`.** The entry here names the rules you must not break; the section says why, and what was tried and failed.
- **Keep this file small.** A new rule goes here in **three lines or fewer**, with a pointer; its story, measurement or ruling history goes into the long-form file.
- The long-form files are true **as of the dates they state**; this file and the code are authoritative. When a long version disagrees with an entry here, the long version is stale: fix it, don't follow it.

## Collaboration contract (read first)

**Claude implements; the dev reviews.** Contract changed **2026-08-05**, replacing the hand-typed-walkthrough model that ran from project start. Claude edits every file directly — `Classes/`, `Scenes/` and `game.gd` included. The dev is practicing an agentic workflow for a role that requires it; **he will say so explicitly if he ever switches back**, so until those words are said, this is the contract. He is still here to learn: explain the *why*, not just the *what*.

**Plan before touching ANY file — tightened 2026-08-06, no size exception.** The trigger used to be blast radius (feature / invasive change / bugfix); it no longer is. The dev's words, after `Stats.Stat.COH` vs. a bespoke field (#142) got decided and coded before he ever saw the fork stated: *"I'd like to see a plan from you about what code changes you are going to make... before you edit something, no matter how minor."* Every file — `Classes/`, `Scenes/`, `game.gd`, `docs/`, `tests/`, scaffolding, all of it — gets a plan first, him included on things he'd otherwise never be asked about (a `.gitignore` fix made and only narrated afterward, same session, is the shape to avoid). Reading/searching to build the plan needs no announcement — only `Edit`/`Write`/anything that mutates a tracked file does.

**Depth scales with the change; the plan step itself never gets skipped.** Hitting more than one of — a new capability, more than one valid approach, an architectural choice, more than a couple of files, unclear scope — means **formal Plan Mode** (`EnterPlanMode`/`ExitPlanMode`): explore, write the plan, nothing gets edited until he approves it. That is a lock, not a promise. A genuinely fork-free edit (an obvious typo, a one-liner he already dictated verbatim) still gets stated before it happens — one line, then wait a beat — but doesn't need the formal mode-switch.

**A plan that stops working gets RE-PLANNED, not patched around and narrated after.** Discovering mid-implementation that the approach is wrong, or silently switching to a different one, means STOP before finishing the edit — lay out the revised plan and wait, exactly like the first one. Explaining a pivot in the wrap-up is the failure this replaces, not a lighter version of compliance.

**What a plan must contain** (the full version — a fork-free one-liner just needs the one-line statement of intent above):

- **The question** the change answers, and **what already answers it**, naming what was actually grepped. *Grep the question, not the name* (Law #4).
- **Every caller/reader of anything being changed, counted from the code.** Relaxing a predicate for one caller without checking its other three is exactly how the Group Move hole shipped (2026-08-04).
- **Files touched** and what each change is.
- **How it will be verified** — decided before building, not after.
- **The riskiest assumption**: what would make this plan wrong.

**Review surface = the plan + the diff.** A summary of a change is not evidence of the change. Keep the unit of work to **one reviewable diff**; never chain several tasks' worth of edits before he has seen any of them. Commit points are review points.

**Report verification honestly** — what ran, what passed, and what was *not* checked. **The suite is not the gate:** 6 of 7 cases passed against the build that bricked the pause menu (#131), and 955 green cases sat on top of a `clear_board` that had stopped clearing the board (#132). Anything touching UI, input, or ordering needs the game actually launched. **Falsification — reintroducing a bug to prove its regression test goes red — answers whether the TEST has teeth, not whether the fix works;** that second question is his, by playing. So falsify only where the test could plausibly be blind: **ordering/timing**, a **missing wire**, an assertion leaning on a Godot quirk (freed refs, `visible`, orphan counts, queue state), or a test that reaches its precondition by *setting state directly* rather than driving the real path. Skip it when the assertion sits one hop from the change. Run the **one suite file**, never the tree.

**Retired with the old contract (2026-08-05)** — do not re-derive them from this file's git history: the whole-function code-block law, file+function prose anchoring, one-heading-one-file, and "verify by reading the real file after a walkthrough". The old narrow write exceptions are **absorbed, not revoked**. → `docs/workflow.md` → *Retired with the old contract*

**Still live, unchanged by the switch:**

- **Content is disposable; cleanliness is not.** `.tscn` scenes and saved `Scenarios/*.tres` are placeholder — fix them to match the code rather than carrying a legacy-compat branch for their sake.
- **File header comments.** Any `Classes/`/`Scenes/`/`game.gd` file touched that lacks a top-of-file description comment (what the file/class IS and its place in the architecture) gets one added.
- **Terse comments in source.** Rationale goes in chat, `docs/`, and issue text — never walkthrough prose in a `.gd` file.
- **A dirty working tree is a ticket defect at BOTH ends (dev rule, 2026-08-26).** His words: *"no issue is acceptable if it causes the workspace to be continuously dirty… and no issue is complete if it can still leave the tree dirty."* **Acceptance:** refuse a design whose ordinary operation (running the game, opening the editor, a routine tool pass) produces tracked modifications, and say so before building it. **Completion:** a clean `git status` at commit time is NOT the test; ask whether anything he normally does re-dirties it. **How:** make the committed bytes BE what the real writer emits: round-trip through that writer and diff, never hand-author a serialized format. Putting uids back after a save has ONE answer, `DevWidgets.restore_uids` (#481). Traps: a headless `ResourceSaver.save()` strips every `uid=`; only an `ext_resource` survives an editor save (an embedded `Image` sub-resource re-mints its id, #540); and **an `@export` whose default is a CALL has no default any saver can see** (a collection default must be one the parser can FOLD, #1185). → `docs/workflow.md` → *A dirty working tree is a ticket defect at both ends*
- **Aesthetic tuning values get a knob, not a guess (dev rule, 2026-08-12).** When a shader/lighting/post/animation value is a matter of taste, expose it and hand it to the dev: *"I can find the values that work, and we can save a lot of time."* The usual answer is one row in an existing knob table, not a new panel. The dev-tools window has three knob tabs (Moods, Game, Tiles), plus the Weather page and two homes outside the window. The fork is **who may disagree about this value**:
  - **one board vs another:** a **Look** knob (`LookKnobs`). Every Look knob joins presets.
  - **nobody, ever:** a **`GameKnobs`** row, written back into the declaration that authors it. `GameKnobs` is dev-only: shipping code never reads it.
  - **one tile vs another:** an **`ObjectKnobs.FIELDS`** row (a TileSet custom-data column); the Tiles page also draws the globals those rows fall back to (#902).
  - **one weather vs another:** its `WeatherLook`/`WeatherRules` file, on the Weather page (#1260).
  - **one authored attack vs another,** for an effect that attack plays: a shared **`EffectLook`** (#900), partial, falling through to the `GameKnobs` row. Only an effect's LOOK goes here, never its RULE, and an effect that outlives its attack (a burning tile) belongs to the ground.
  - **anyone (the player):** a **`PlayerSettings`** row (#394). *By degree*, a `PlayerSettings.Scale` multiplier over the dev's value, so no slider is ever inert. *On the same axis*, the value moves to `PlayerSettings`. *Between authored sets*, a palette (only a ROLE colour needs re-authoring per palette, #685).

  Never put a game-wide value in Look. **A knob may only name a property that is authored and READ**: anything the game writes back per frame gives a slider that silently reverts (`tests/dev/test_moods_tool.gd`). An `@export` is still right for a value tuned in the editor rather than in play. → `docs/workflow.md` → *Aesthetic tuning values get a knob, not a guess*; `docs/design/presentation-effects.md` → *Where a presentation value is authored*

## GitHub issue workflow (Claude ↔ human handoff)

Open work lives in [GitHub Issues](https://github.com/Phaazoid/Godoiosis/issues).

**Whose turn it is is DERIVED FROM THE THREAD, never labelled (dev ruling, 2026-08-25).** The last thing said on an issue is the answer: if the newest comment leads with `🤖 Claude says:`, Claude spoke last and it is waiting on the dev; otherwise it is Claude's. An issue with no comments is judged by its **body** the same way. Run **`/agent-queue`** to walk everything that is Claude's turn (highest priority label first) and advance each one step. The `agent/*` labels this replaced drifted from the thread; do not bring a hand-maintained turn field back (→ `docs/build-log.md` → *Why the agent/\* labels went*).

**CLAIM AN ISSUE BY ASSIGNING IT BEFORE STARTING WORK (dev rule, 2026-09-06).** His words: *"when we start working on an issue/series of issues, we use the assignees feature in github to mark it… now that codev is starting to more actively use the github, we don't want to accidentally overlap work."* `c3potheds` (codev) works this tracker too. So `gh issue edit <n> --add-assignee @me` before advancing an issue. **An issue already assigned to someone else is theirs**: leave it, take another, and say which ones you skipped. Two dev rulings, both 2026-09-06:

1. **An assignment means "this side OWNS this thread"**, not "hands on it right now": held through plan → build → review → merge, left on the closed issue, released only when we walk away (re-scoped, deferred, blocked).
2. **Claim only what is ACTUALLY being worked.** An umbrella is claimed when the whole arc is in flight, never as a reservation over children you are not building yet.

**Assignment is NOT turn.** Turn is derived from the thread; assignment is claimed; an issue assigned to us while waiting on the dev is the normal mid-arc state. An issue assigned to us **and** someone else is not ours either (`/agent-queue` drops it). An unassigned issue is **not** proof codev is not on it, and `gh` is authed as **Phaazoid**, so the line this draws is *this side vs codev*, never *Claude vs the dev*. → `docs/workflow.md` → *Claim an issue…*, *Assignment is not turn*

**The slash commands** live as files in `.claude/commands/` (the filename IS the command name; anything typed after it scopes the run). They are typed into the Claude Code chat, not into the game (#690).

| Command | What it does |
|---------|--------------|
| `/agent-queue` | Advance every open issue whose **last word was the dev's**, highest priority first: post a plan, fix and write it up, or flag a decision. The comment IS the hand-back. `/agent-queue 23 25` works only those. |
| `/scratchpad-sweep` | File each **Inbox** idea in `docs/SCRATCHPAD.md` into a design doc / a proposed issue / the defer pile, log where it went, and leave the Inbox empty. `/scratchpad-sweep weapons` sweeps one area. |

- **When it's Claude's turn:** post a plan (for a feature or a core-gameplay change), or just do the work and post a writeup (small bugfix, `tests/`, `docs/`). **Standing exception to the 2026-08-06 plan-first tightening, pending the dev's confirmation:** a queue run is unattended, so small `tests/`/`docs/` work in the queue goes straight to a diff + writeup rather than a posted-plan-and-wait.
- **Handing back is just commenting.** The comment *is* the hand-off. The dev replying — including "this needs rework" — hands it back to Claude by the same rule.

**This makes the comment convention load-bearing rather than decorative.** Every comment Claude posts under the user's account **leads with `🤖 Claude says:`** and **ends with** `— Claude (<model>) · <date>` (name the model actually running — the signature is provenance), authored via the Write tool → `gh issue comment --body-file` (never an inline non-ASCII arg: Windows PowerShell 5.1 mojibakes it before upload). **Drop the lead-in and the queue will hand that issue back to Claude forever.**

**Every PR body carries a `## How to check this` section (dev rule, 2026-09-02):** what to do, what you should see, what a failure looks like, and what the tests already cover. His words: *"a question I've been asking you a lot lately is 'What can I do to test this'… it's fine if the answer is just 'this is a docs-only change, nothing to see', but I'd still like an easy place to see and know."* The fourth line is load-bearing: it states **the suite's blind spots** out loud.

## Branches, PRs and versions

**Every merge bumps the version — each build must be distinguishable (dev rule 2026-08-11; the mechanism moved to merge time 2026-08-14).** The one store is `project.godot`'s `application/config/version` (`Build.version()` is the one reader, #134). A **feature** bumps the middle digit (`0.1.0` → `0.2.0`); a **bugfix or docs-only** change bumps the last (docs ruled equivalent to a bugfix 2026-08-12, PR #206).

**Do NOT bump it in a PR's diff.** `.github/workflows/version-bump.yml` does it on main after a merge, reading the merged PR's **labels** (`type/feature` → middle digit, anything else → last). So the label is load-bearing (a feature PR shipped unlabelled silently gets a patch bump), and a branch's version is always *behind* main by design; never "fix" it by hand. (Bumping in-PR made every concurrent pair of PRs conflict on `project.godot`.)

**A build that goes OUT is made by `tools/archive-build.ps1`** (#1027, #1060), never exported by hand. It refuses a dirty tree, exports the one `Windows Desktop` preset, zips it, **pushes it to itch with `butler`**, **tags `v<version>` at the commit it was built from**, and last **announces the version into the intake Worker's `release` row**. **That order is load-bearing:** each prefix fails safe. `-NoUpload` skips itch and the announce; `-NoPush` skips only pushing the git tag. It **refuses a version `CHANGELOG.md` has no `## v<version>` heading for** (#1075): that ledger SHIPS (the one non-resource in `include_filter`) and feeds the what's-new card through `ReleaseNotes`. An entry arrives by an unlabelled RELEASE PR, merged last, headed with the version main will be at once it merges, whose player lines are the dev's prose (procedure at the top of `CHANGELOG.md`). → `docs/workflow.md` → *Every merge bumps the version*

**LEAVE THE WORKING TREE ON THE BRANCH HE HAS TO TEST, and say which branch that is (dev rule, 2026-08-14).** His words: *"I don't like having to merge to see the changes you made. That makes it so I have to merge before testing things."* Merging is what a review EARNS; it must never be the way he obtains the code to review. So the last act of any PR that needs his eyes is to check that branch out and say plainly *"you are on `<branch>` — launch it."* Corollaries:

- **Never move his working tree silently.** His Godot session is open on `C:\Iosis\Godoiosis` and renders whatever is checked out. The running build names its checkout (`Checkout.describe()`, #295 — dev-only, and never `Build.version()`, which is behind main on any branch). That catches a wrong build; it does not prevent one.
- **ONLY switch his tree when it is on `main` — HARD RULE (dev, 2026-08-25).** His words: *"you're only allowed to switch my work tree if I'm on main. Otherwise, it means I'm looking at another agent's session, and don't want to be moved."* Check `git branch --show-current` BEFORE `git switch`; if it is not `main`, leave it and say which branch your work is on. **ONE CARVE-OUT (dev, 2026-08-28):** a branch YOU put him on this session, and are about to work on, may be taken back to `main` first (git refuses a second worktree on a checked-out branch). **The tell is ownership, not the branch name.** Both preconditions are required: `git status --short` is **CLEAN** (dirt may be his own edits: stop and ask), and the move is **announced**. Put him back on the branch at hand-off. Keep ONE long-lived agent worktree and `git switch` inside it.
- **Never leave him on `main` or an unrelated branch after doing work.** That forces a merge-to-test — *subject to the hard rule above, which outranks it: an occupied tree stays put.*
- **Prefer ONE open PR at a time** when the work needs feel-checks, so "the branch you're on" is unambiguous.
- Getting back: `git switch main && git pull`. Testing a different open PR: `gh pr checkout <n>`.

→ `docs/workflow.md` → *Leave the working tree…*, *Only switch his tree when it is on main*

**DELETE A BRANCH WHEN ITS PR MERGES — remote AND local (dev rule, 2026-08-14).** GitHub auto-deletes the head branch, so the copy that rots is the **local** one: `git switch main && git pull && git branch -d <branch>` is the last step of landing work. **Sweep discipline:** delete with `git branch -d` / `git push origin --delete` only what is **merged into main**; never reach for `-D` past `-d`'s refusal. For anything unmerged, check the CONTENT: `git diff main...<branch> --name-only` coming back empty means nothing main lacks. **Unmerged by SHA is not unlanded by content.** → `docs/workflow.md` → *Branch sweep discipline*

## Content and docs discipline

- **Canon-sweep discipline.** "Canon swept" means a grep-verified pass over the *whole* `docs/design/` tree (plus this file and its long-form docs) for the issue's number and every renamed or removed symbol or term it touched. Staleness hides in a status banner elsewhere in the same file, in a sibling file stating the same fact, and in a "living list" tracker (`docs/design/grill-queue.md`). Sweep a multi-session issue against its *final* state. → `docs/workflow.md` → *Canon-sweep discipline*
- **Staleness marker.** Every living design doc (all of `docs/design/` except the three frozen historical records: the coherence audit, the co-dev agenda, the wiki triage ledger) carries a `**Canon checked through #NN (date).**` line in its opening banner. When a sweep re-verifies a doc, bump the marker to the current highest issue number and that day's date.
- **Embedded-content sweep (dev rule, 2026-08-20, from #258's fireball).** `.tres` files omit default values, so every committed resource that EMBEDS a content type silently loads the default of any field added later (snapshot scenarios under `Scenarios/`, fixtures included, above all). A diff adding an authored field to an embeddable type (`AttackData`, `WeaponData`, anything a snapshot copies) must, in the SAME diff, (1) sweep the committed `.tres` files that embed it and re-author those whose defaults are now wrong, and (2) say in the PR which were swept, or that nothing embeds the type. The statement is owed even when no file needed rewriting. His words: *"if something like this fireball issue ever happens in the future, I'd like it called out, so that I know not to rely on stale tests."* → `docs/workflow.md` → *Embedded-content sweep*
- **A DELETED or RENAMED content file sweeps its `ext_resource` REFERRERS in the SAME diff (#596).** Grep for the OLD basename and repoint every referrer. **A green local run is not evidence**: the editor holds the old resource in memory. `tests/law/test_resource_uid_references.gd` grades both halves (`uid=`, #240; `path=`, #596). **Which file a referrer should point at afterwards is a CONTENT call: ask.** → `docs/workflow.md` → *A deleted or renamed content file sweeps its referrers*
- **Content that lost a reference loads DEGRADED rather than refusing (#608).** The dev tools live inside the game; his words: *"I can't go in and author the fix myself in dev mode."* A dangling `ext_resource` is a hard PARSE error, so **`ContentRepair.load_tolerant` is the ONE answer**: it strips the dangling reference, loads the repaired text and `take_over_path`s back to the real file, children first, HOLDING each repaired child across the parent's retry. It refuses a missing SCRIPT (a code fault). It is wired at `ScenarioManager.load_scenario` (and its headless twin `BoardBuilder.load_scenario`, #1365), `ResourceCatalog`, `RosterCatalog.resolve`, `SubstanceCatalog` and `ReplayRun.load_run`; ordinary runtime `load()` stays strict. For the diagnosis only, ask `ContentRepair.missing_references(path)`, which reports what a file *references* and cannot load. `DevWidgets.save_over` refuses to save a degraded resource while the gap is open. → `docs/workflow.md` → *Content that lost a reference loads degraded*

## Design laws (non-negotiable)

1. **No randomness in gameplay.** No hit/miss rolls, no crit chance, nothing. Combat is fully deterministic. (Old design docs mentioning crits predate this law.)
2. **The action queue never lies.** Planned actions must preview exactly what execution does. Queue/cancel/requeue must be idempotent. Derived actions (counter-attacks) are *computed* from the plan, never stored as player orders. **Absolute as of 2026-08-09 (dev + co-dev, out of #124/#155):** the BREAK doctrine (resolution-pipeline R9, 2026-07-05) that sanctioned divergence classes is REPEALED before anything of it was built — plans do not break, execution never re-enters the resolver, and a mechanism that would diverge is redesigned until the resolver can predict it (Crisis → an equipped ability, [#158](https://github.com/Phaazoid/Godoiosis/issues/158)) or doesn't ship. See [`docs/design/resolution-pipeline.md`](docs/design/resolution-pipeline.md)'s repeal record.
3. **Future AI uses the player's API.** AI issues orders exclusively through `SquadManager.queue_action` — no side channels. This protects law #2 forever.
4. **One question, one answer — never build a second seam for a fact the code already holds.** (Added 2026-07-28 after #102; elevated to a law because it has already bitten five times.) Before adding a field, flag, predicate, method, or *content convention*, find what already answers the question it would answer, and either extend that or explicitly retire it. **Grep the question, not the name** — the duplicate almost never shares a token with the original, which is exactly why it slips through (`requires_readiness` vs `knockback > 0`). **Suspect anything with an honest local motive**: the second seam always looks like it solves a different problem, and that motive is the disguise. **Prefer passing over looking up** — and its sharper form, learned from the #104 sweep: *if you can't reach the existing answer from where you're standing, take it as a parameter; don't rebuild it locally.* A looked-up fact can silently diverge from a passed one; a parameter makes divergence unrepresentable (`Reach.get_affected_cells_from(…, attack)`, `WeaponInstance.base_damage(wielder, attack)`). This applies to authored content as much as to code — the content layer is where it's easiest to do accidentally, because it doesn't feel like architecture. If a second representation is genuinely warranted, **declare it out loud**: name both sides and state which is authoritative (the `objectives` vs painted `zones` guard under *Missions* is the model). The undeclared second source is the hazard; a declared one is a design. Why it's a law and not a sharp edge: these fail *late*, once both answers have callers, and the divergence can go **load-bearing** — #102's stale pick was the only reason secondary AoE resolved correctly, so the obvious cleanup would have broken more than it fixed. When fixing one, **close the expressive gap, not just delete the duplicate** (#108): a seam that can't say what content needs will grow another one. A duplicate also propagates into FIXTURES. Enumerate by re-deriving from the code, never from the issue's own table. → `docs/build-log.md` → *Law #4 as it was written, with its past instances*

## Architecture map

- `SquadManager` (`squads/`) — **the only owner of squad lifecycle** (create/destroy/join/leave), and home of order queueing (the Law #3 chokepoint, `try_queue_action`, with `queue_action` its bool wrapper), activation state, plan resolution and counter resolution. Member removal funnels through `Squad._erase_member()`, the sole `members.erase` caller (#367). **Queueing is STRICT and validity is one-way:** you cannot AUTHOR an invalid order, but a queued one can BECOME invalid and stays queued **in red**, never deleted. The gate reads **the candidate's own `is_valid`, never `validate`'s return value** (whole-plan validity). Its fizzle, whiff and rescue halves are CANDIDATE-only questions: a stored aim's whiff comes from the resolved plan, never from `aim_finds_a_target`. The rescue lifecycle rule is ONE seam, `RulesService.is_rescueable(target, plan)`. **Batched orders skip the gate** (`queue_group_move` judges a formation whole), and `SquadManager.batching` is safe only while a batch stays synchronous. → `docs/architecture/squads.md` → *SquadManager*
- `game.gd` — input/game-state coordinator, in labelled sections. Its collaborators are built in `_build_collaborators()` and hold a `game` back-ref. Prefer moving domain logic out to the owning system. **The selection is STORED, not re-derived: `game.selected_unit`** is assigned only in `select_unit` (#107) and nulled only by `exit_current_mode` and `_on_unit_died` (never by `clear_selection`). Never re-derive it from a cell. **`game.gd` has no `class_name`, so everything reached through the untyped `game` ref is Variant: annotate locals explicitly** (`:=` cannot infer). A bare array literal passed that way is NOT coerced to a typed parameter and fails at runtime, which is why `clear_selection_icons()` exists. → `docs/architecture/board.md` → *game.gd*
- `Squad` — member list + `action_queue` (player-authored orders only). **`Squad.displaces()` is the one displacement rule** (one order per action type and one MAIN action per unit; volley siblings exempt); hypothetical lists reuse it.
- **Persistence seam (locked, #8):** the transient `Unit` holds battle-scoped state that resets each mission; the persistent `UnitInstance` holds what survives missions. New per-unit state picks its side by one test, *does it survive a mission?* There is no third store and no exception (temporary stats are `StatEffect`s on `Unit`, #112). **There are three distinct "dead"s** (`UnitInstance.is_dead()`, `Unit.is_dead()`, the unwired `permadead`): don't add a fourth or rename any to plain `dead`. **The effective-stat chain is base → limb → jobs → temporary effects → gear**, and only the first three stages live on `UnitInstance`, so **every derivation off a stat lives on `Unit` or takes the finished value as a parameter** (#106). `Unit.set_current_hp` is the one HP door. `Unit._settle_stat_change` runs wear gates → HP re-clamp → `stats_changed`, in that order. **Wear gates read `get_body_stat`, never gear**, so the strip stays single-pass. `stats_changed` is for readouts only. → `docs/architecture/units-and-saves.md` → *The persistence seam*; `docs/design/stats.md` → *One chain, one layer*
- **Scenario save/load round-trips the whole `UnitInstance` side** through `ScenarioUnitEntry.capture_unit_state`/`apply_unit_state`. **Both loaders (`ScenarioManager`, the Play API's `board_builder`) share every load step through `ScenarioUnitEntry`'s doors**; a new step goes there, never into one host. **Load assigns gear directly and never re-runs the wear gate**: a save is authoritative. A prosthetic re-links **by carried instance, never by template**. An entry is a **reference** or a **snapshot**, forked by `state_saved` (#177): an authored save references a cast unit's file and the loader must NOT call `apply_unit_state` on it, unless `Unit.dev_edited` made it a snapshot. So **a per-placement field (e.g. `must_survive`) rides `ScenarioUnitEntry.apply_placement`**, never `apply_unit_state`, or reference entries drop it. An authored save skips `drawn_from_roster` units. The loader passes `entry.unit_data` UN-duplicated. → `docs/architecture/units-and-saves.md` → *The persistence seam*
- **A save is a true MID-BATTLE SNAPSHOT (#87).** Battle state is captured EXPLICITLY (per-weapon state keyed by inventory index via `WeaponInstance.capture_battle_state()`, lifecycle, effects with their countdowns, `Squad.has_acted`, the mission's latches); nothing became `@export`, so a mission boundary still resets for free. **A restore replays the RESULT, never the EVENT** (`Unit.restore_lifecycle`/`restore_stat_effects`). **Effects settle BEFORE gear and BEFORE HP** in `apply_unit_state`. ## Sharp edges (each of these has already bitten once)

Each entry's story → `docs/sharp-edges.md`, under the same name, unless the entry points elsewhere.

- **Missions talk now (#182) — a test fixture that boots one through `begin_mission` must hang up.** End with `DialogFixtures.end_all_dialog(self)`, and call `scenario_director.disarm()` in `before_test` when the suite synthesizes clicks.
- **Grant/copy a carried item via `copy_for_grant()`, never a bare `duplicate(true)`.** A `WeaponInstance` keeps its `template` SHARED, while a deep copy forks the family. A `WeaponData` answers with an INSTANCE, or NULL for an unmapped type, so every granting door guards null (`Unit.add_item(null)` reports success).
- **NEVER run the full test suite locally. CI owns it (dev rule, 2026-08-15).** `.github/workflows/tests.yml` runs the whole tree on every push to `main` and every PR against it (a docs-only change skips the run; `CHANGELOG.md` counts as code), with the same guards as `run_tests.ps1`. **Locally: area folders only** (`run_tests.ps1 rules`, `presentation`, …); a bare `run_tests.ps1` defaults to the `fast` tier. For something cross-cutting, run the narrowest area that loads the surface you touched. A job queued past six minutes is GitHub's outage (`tools/ci-failover/`). **This rule is unconditional on purpose:** the conditional version was misapplied three times, once because it was *paraphrased into an approved plan* with the timing inverted. Cite this line; do not restate it.
- **NEVER pin AUTHORED CONTENT in a test (dev rule, 2026-08-15; the content razor, `tests/README.md` #9).** His words: *"authored content shouldn't be pinned, and level geometry, not to mention contents, units, objectives, all of it is authored."* A test may LOAD a real mission but never ASSERT what it contains. Derive every expectation from the seam under test (e.g. `BoardSpace.surface_point`, `game.get_move_range`), and make a content precondition a non-vacuity MESSAGE, never a threshold. On a non-flat board, click through the real picker (a tall column shadows the cell behind it) and search for a unit that can move.
- **gdUnit4's `Total execution time` line is not wall clock.** Trust `run_tests.ps1`'s own `Elapsed` line. If a run is slow, try an `--import` pass first; the cause is unconfirmed.
- **`game.clear_selection()` runs on every TERMINAL menu pick, not just on cancel** (`cancelled` fires BEFORE `action_selected`), so nothing that must survive INTO a mode can be cleared there; `exit_current_mode()` is the mode-ending path. Test through a real menu pick: setting `game_state` directly hides this. **A stored selection must be RELEASED whenever its unit is freed (#149)** (`_on_unit_died` nulls it, and must not call `exit_current_mode`, which would unlock the board mid-AI-turn). A freed reference compares `== null` as TRUE, so only a TYPED read catches it, and a regression test must do the typed read.
- **`get_tree().paused` breaks every click in this project, because the game lives in a SubViewport.** Freeze `game.process_mode = PROCESS_MODE_DISABLED` instead (`ModalLock`).
- **A HUD SURFACE MUST CATCH ITS OWN CLICKS, or the click lands on the board (#929).** A box (or an ancestor up to its full-rect host) is `MOUSE_FILTER_STOP`; the full-rect host stays `IGNORE`; `PASS` falls through exactly like `IGNORE`. `tests/law/test_hud_catches_its_clicks.gd` walks every CanvasLayer and cannot see a surface its fixture never builds.
- **gdUnit4's `await_millis` HANGS THE WHOLE RUN if the tree is paused.** Count frames on `process_frame` instead. A failing case also aborts the rest of its suite.
- **`await RenderingServer.frame_post_draw` never resumes in a headless run.** Code awaiting it needs a `DisplayServer.get_name() == "headless"` escape (`BugReporter.capture_frame`).
- **A bare `[]` literal passed to a typed `Array[T]` parameter through an untyped (Variant) call fails at RUNTIME, not parse time.** Use a typed local (`OverlayManager.clear_target_pulse`) or a no-argument wrapper on the typed side (`game.clear_selection_icons()`). → `docs/architecture/board.md` → *game.gd*
- **A TERRAIN HEIGHT NUMBER IS HALF A LEVEL (#427).** `Terrain.UNITS_PER_LEVEL` is 2, and `BoardSpace.top_row_of` is the one height-to-row conversion. The store is FOUR CORNER HEIGHTS per cell, and **`Terrain.height_at_uv` is the one surface**; the meshlib generator restates its diagonal rule and `tests/law/test_cap_mesh_matches_the_surface.gd` pins the two together. The rules ask the shared EDGE (`Terrain.edge_of_corners`). Flat markup on a corner cell is folded (`BoardOverlays._surface_mesh`), never tilted. **A cap draws nothing in its own floor plane**, so the block beneath it is load-bearing; fix coplanarity by geometry, never by an epsilon.
- **A BURIED FACE IS STILL A DRAWN FACE, AND BACK-FACE CULLING IS LOAD-BEARING (#559).** A ground block's TOP face keeps its full extent, its sides start `BoardSpace.SIDE_RIM` below the surface, and `_mat()` is `CULL_BACK`, so an exposed cap opening shows the sky.
- `.tres` files omit properties at default values — an "empty-looking" resource may just be unsaved-at-defaults.
- **`load()` serves the resource CACHE.** A runtime save must do all three: **write through to the object that owns the path** (#589; that object is what every holder still references), **claim the path** (`take_over_path`), and **preserve its uids** (#481). `DevWidgets.save_over` does all three; a new save route must not do fewer. An ext_resource uid follows the `path=`, never the line's `id=` (#996).
- **`DirAccess.get_files()` on `res://` returns PACKED names in an exported build** (`Foo.tres.remap`, `Mage.png.import`). **Every folder scan goes through `ResourceDir`**; never re-derive a listing beside it. Only `tests/export/test_export_smoke.gd` (a real pack, launched from OUTSIDE the project dir, or `res://` silently mounts the source tree) can see this class. Ask `ResourceLoader.exists`, never `FileAccess.file_exists`, about a packed resource. When a new ADDON lands, decide whether the running game needs it (`exclude_filter`).
- **A headless `--import` used to EMPTY Dialogic's registries in `project.godot`; the fix is a LOCAL PATCH to the VENDORED addon** (#447, two clauses in `DialogicResourceUtil`, each useless alone; re-fixing it in the prune predicate segfaults the cold import). **A Dialogic upgrade will silently drop this patch**; CI's *Guard committed project settings* step is the canary. A law must read the committed file through `ConfigFile`, never the live registry the process keeps repairing.
- **A LEGACY `device` ON AN INPUT BINDING IS REWRITTEN AT EVERY LOAD.** 4.7 migrates key 0 → 16 and mouse 0 → 32, and `device` gates matching. Normalize by round-tripping through `ProjectSettings.save()`, never by hand.
- **`OptionButton.add_item` auto-selects the first entry**, so a rebuild that re-selects by name **must `select(-1)` before its match loop**. This is load-bearing wherever a dropdown names a write target.
- **A code-built full-screen Control needs `set_anchors_and_offsets_preset`, never `set_anchors_preset`.** Anchors alone leave it at 0x0.
- **NEVER put a `ColorPicker` or `ColorPickerButton` in the dev-tools window**: it froze the window solid. Use `DevWidgets.add_color`.
- **AN INSTANCE OVERRIDE IN A PARENT SCENE SHADOWS THE VALUE EVERYONE EDITS (#403).** A value with a scene default: ask *which* file the running game reads. `clampi(v, lo, hi)` answers with the bound it tests LAST when `hi < lo`.
- **A TYPED ARRAY'S ELEMENT ARRIVES AS A TYPE ID, NOT A CLASS NAME** (`hint_string` is `"6:"` for `Array[Vector2i]`). A new `match` arm in a UI builder needs a case that FINDS its control.
- **A KEYBINDING LIVES IN ONE OS WINDOW AND IS DEAD IN THE OTHER — the project has two** (the two-OS-window trap). The dev-tools window FORWARDS to `DevController.handle_dev_key(event)`, the one entry, skipping a focused `LineEdit`/`TextEdit`; never write a second handler. **A dev PAGE owns its own input**: gate on `DevOverlay.showing(page)` plus the game state (`DevController.brush_armed()`).
- **A tooltip on a code-built row must be set on EVERY control in it, not the row** (`DevWidgets.apply_tooltip`). A plain `Label` is `MOUSE_FILTER_IGNORE`, so its tooltip is dead unless set to `STOP`; `Control.get_tooltip(point)` cannot see either failure. A reflective editor reads field text from static `property_tips()` and layout from `property_sections()` (functions merged down the chain, never consts); a new `@export` needs a section home.
- UI rule: **scene for static, code for dynamic.** Fixed controls live in `.tscn`; data-shaped UI (editor fields, stat rows) is generated.
- **A plain `Panel` lays out nothing.** It reports 0×0 for children inside containers, so give a plate with children a `PanelContainer` and keep `Panel.new()` for childless rectangles.
- **AN `HFlowContainer`'S MINIMUM WIDTH IS ITS WIDEST CHILD, AND A `Panel` IMPOSES NO CEILING.** Assert against a reference the `.tscn` ANCHORS: a budget that grows with what it measures is no budget.
- **A `clip_text` LABEL DECLARES A MINIMUM WIDTH OF ONE**, so in an HBox or HFlow it draws as a sliver unless it carries `SIZE_EXPAND` or `UiText.fit_width(label, floor, ceiling)`, with the bounds kept at the caller.
- **A surface that rebuilds itself from its own child's signal must DEFER the rebuild**, or it frees the emitting node. Act on a click's RELEASE, never its PRESS, or dragging is impossible. Type-check drag data; `data as Dictionary` is a hard cast that throws. → `docs/architecture/pre-mission.md` → *The pre-mission phase*
- `Unit.has_squad()` means "has squad*mates*" (members > 1). Every unit always belongs to exactly one managed squad, even solo.
- **A `Packed*Array` IS A VALUE TYPE.** Appending to one reached through a Dictionary changes a copy. Use `Array[String]` for anything handed out for appending, and assert on `.size()` of a TYPED local, because `assert_array()` on the Variant chain reads it empty.
- **`get_theme_stylebox()` ANSWERS FOR A CONTROL THAT OVERRIDES NOTHING.** Ask `has_theme_stylebox_override(name)` when the point is that the control brings its own.
- **`Sprite3D.offset`'s TWO AXES DO NOT SHARE A SIGN, AND `flip_h` MOVES NO GEOMETRY.**
- **`set_process(false)` IN `_init` DOES NOT SURVIVE ENTERING THE TREE**, so `_process` ticks once anyway. `_process` hands `texture` back only if it BORROWED it, and a pooled ghost writes through `show_still()`. Ask `VisualInstance3D.get_base()` whether it is drawn.
- **THE MIDPOINT OF TWO ADJACENT CELL CENTRES SITS EXACTLY ON THEIR BOUNDARY**, and `floori` resolves a tie to the `+` side. Never resolve a cell from a point placed on a cell edge.
- **A VERSION-GATED POLL MEANS A CONTINUOUS ANIMATION ANNOUNCES ITSELF ON DISCRETE EVENTS, NEVER PER FRAME.** Rebuilding and PLACING are different prices: between the events, re-read placement without bumping the version (`BoardMirror.reseat_cell`, #893).
- **A CHANNEL POLLED BELOW A GATE NEEDS A DOOR ON EVERY PATH THAT ENDS THE GATE**, and the obvious door can early-return. Enumerate the paths that clear the gate, not the ones that clear the channel.
- **A LATCH MAKES EVERY CHOICE BEHIND IT UNOBSERVABLE.** Ask what state exists at the instant the latched value is computed. Test the property the latch really has, and declare (don't delete) a choice that is correct but unobservable.
- **ONE SPELLING CAN STILL BE TWO BASES.** A shared formula fed from two different bases agrees with itself and is still wrong. When the bases can differ, pass the composed FACT, not the recipe.
- **A POST-PHASE ASSERTION IS WORTHLESS WHEN A LATER PHASE TIDIES UP REGARDLESS.** Drive the phase that owns the property, alone.
- Godot ternary exists (`x if cond else y`); typed dictionaries (`Dictionary[String, int]`) are used throughout — keep chains typed end-to-end.
- **Retyping a persisted `@export` field from String to an enum is a *data* migration, not just a code change.** Godot silently drops type-mismatched values on load and strips them on resave. Migrate every saved `.tres` from git HEAD. This is the retyping trap.
- **Dev tools = separate OS window; the game is wrapped in a SubViewport.** `Battle3D.tscn` is the main scene and hosts `Main.tscn` at `/root/Battle3D/Main`: **never put an absolute `/root/...` path anywhere in the game subtree.** `Main` → `GameContainer` → `GameView` (SubViewport) → `Game`; `DevOverlay` is a sibling `Window`, a real OS window because project `embed_subwindows` is OFF, while `GameView` embeds. Gotchas, already handled, **do not undo**:
  1. SubViewports default to LINEAR filtering; `game._ready` sets the viewport default to Nearest.
  2. Embedded popups don't dismiss on outside-click, which is why the action menu is Control-based and a settings choice row is never an `OptionButton`.
  3. The UI lays out in a fixed 1280x720 design space stretched to the window (`GameSurface`). An authored pixel is a design unit; `get_viewport_rect()` inside the game is the design space, while `GameView.size` is physical. A Control's screen position is `get_final_transform() * get_global_transform_with_canvas()`, never `get_screen_transform()`. Never hardcode pixel POSITIONS.
  4. Any new subwindow UI inherits these quirks, so prefer Control-based menus.
